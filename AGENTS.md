# Project guidance

This is a pre-release, internal-only Bun and Turborepo workspace. Libraries are private source packages; applications own their executable toolchains. Do not add publishing, CI/CD, deployment infrastructure, or Git-hook installation. The tooling that transforms this workspace's source into the public mirror repositories used to be the one exception. It now lives in the separate private repository `stevekinney/corvidae-mirror`, which reads a corvidae checkout and writes nothing here, so no path in this workspace is exempt: publishing, CI/CD, deployment infrastructure, and Git-hook installation are prohibited everywhere in it, workflow files included. One application-owned hosting file is not infrastructure in this sense: `applications/playground/vercel.json` gives the existing Vercel project that serves cinder.website its install and build commands, response headers, and redirects, which project settings cannot express. Its `ignoreCommand` is covered the same way: `applications/playground/scripts/ignore-build.sh`, with the `ignore-build.ts` and `environment-configuration.ts` beside it, decides only whether that project builds a given commit, so that the hour-long export runs only when the deployed site could change. None of it adds a workflow, and the Vercel project's Git integration builds it.

## Workflow

- Inspect the existing workspace and nearby conventions before changing code.
- Plan non-trivial work, implement one complete testable capability at a time, and add a regression test for every defect.
- Use current official Bun, TypeScript, Turborepo, and dependency documentation for unfamiliar APIs or configuration.
- Run the relevant focused command or `bun run check` while working and `bun run validate` before finishing. Treat warnings, console errors, and failed checks as defects.
- Treat file length as review guidance, including in imported tests. Enforce classic cyclomatic complexity of at most 100 in implementation and tests, or 300 under `scripts/`. Keep executable repository tooling in its owning workspace’s `scripts/` directory; required tool configuration and application entrypoints retain their documented locations. Require a concrete ownership, duplication, or correctness benefit before restructuring code. Keep correctness, types, tests, and builds enforced. Prefer platform and Bun primitives over new abstractions or dependencies.
- Do not add compatibility, migration, shim, adapter, or re-export layers while the template is pre-release unless the requirement explicitly demands one.

## Review guidelines

This software is pre-1.0 and still being prototyped, so the goal is to move fast on stable infrastructure: spend review effort where a mistake is expensive to undo, and keep everything else simple. These rules apply to human reviewers, review bots, and the agents answering them. `.github/copilot-instructions.md` carries the short form for Copilot.

- Sort by reversibility. A _two-way door_ is internal code or a private source package that a later change can cheaply alter; prefer the simple version and do not harden it against hypotheticals. A _one-way door_ is a persisted format or schema, a wire protocol, an exported surface the mirrors publish; review those closely and ask whether the design paints the project into a corner.
- Find root causes. Ask what class of defect a finding is and grep for its siblings. Fix the class once, with a regression test, lint rule, or type constraint, or decline the finding as a one-off. Do not patch instances one at a time. A finding earns this treatment only if it would plausibly recur or sits on a one-way door.
- Block on correctness. Defects in correctness, data loss, concurrency, state transitions, boundary validation, or a one-way door block a merge. Style, naming, contrived edge cases, and speculative hardening of internal code do not.
- Take one fix pass. After the first round of fixes, a new review comment gets action only if it is a regression the fixes introduced or a serious defect on a one-way door. Anything else is advisory: reply with a one-line reason and resolve the thread.
- Stop patching a repeating class. If a later round surfaces another instance of an earlier round's class, the causal model was wrong. Reassess the shared cause instead of adding another patch.
- Prefer a guard to a comment. When the same class of finding recurs across pull requests, the repository is missing a guard. Add the lint rule, type constraint, or test.
- Gate on local checks. A pull request merges when `bun run validate` passes at the head that contains current `origin/main` and no review thread names a serious defect. Do not wait for bots to go quiet.

## Workspace and dependencies

- `applications/*` contains deployable applications; `components/*` contains browser component libraries; `packages/*` contains other shared libraries; `testing/*` contains verification tooling (the shared test helpers and the agent evaluator), which libraries and components may name only in `devDependencies`, never in `dependencies` or `peerDependencies` (applications, which nothing depends on, are exempt); `internal/*` contains repository configuration; `scripts/browser-fixtures` is a private workspace that only declares the workspaces the root browser fixtures import. Every workspace is named `@lostgradient/*`, except `armorer` and `conversationalist`, which carry their unscoped npm names. Repository scripts read these directories from `scripts/workspace-directories.ts` rather than spelling their own list, and `scripts/workspace-contract.test.ts` keeps that list equal to the root `workspaces` field and enforces the `testing/*` rule.
- Internal dependencies always use `workspace:*`. Shared external tool versions belong in the root Bun `catalog`; add runtime dependencies to the workspace that imports them.
- Component source uses the shared browser TypeScript configuration and root browser lint policy. Keep Bun and Node APIs in tests or scripts. Run both the browser source check and the inclusive tooling/test check.
- The `@lostgradient/typescript` configuration package under `internal/typescript` exports only `library.json` and `browser.json`; `base.json` is private composition.
- Shared source libraries export TypeScript source directly. Consumers compile it at runtime, so do not add a build step to a just-in-time package without a packaging need. Type-checking is the one exception: a TypeScript library that another package type-checks against has a `tsconfig.source.json` (composite, declarations only, into the ignored `.types/`), its `types` script builds it with `tsc -b`, and each consumer's `tsconfig.json` lists it under `references`, so the consumer reads those declarations instead of type-checking the library's source again. A consumer with references type-checks with `tsc -b tsconfig.json`, which rebuilds stale declarations first. Svelte packages still read source, because `svelte-check` does not substitute declarations.
- Use Bun commands only. `bun.lock` is authoritative, and dependency changes must update it with `bun install`.
- Keep `typescript` explicit at the root. Do not rely on a transitive or peer dependency to supply `tsc`.

## Release intent

- Per-change publishing is paused, and this workspace carries no `.changeset/` directory. Release intent for a batch backport is written in `stevekinney/corvidae-mirror`, next to the tooling that carries it to the mirrors, when the backport is made.
- The published versions the playground displays live in `applications/playground/published-versions.json`, and `scripts/published-exports.json` is the snapshot of each public package's `exports` map that Weft's documentation check and Markdown's import-graph test resolve against. The tooling that used to record both no longer writes here, so update them by hand after a backport, along with `applications/playground/src/cinder-published-bases.json` when Cinder's version changes.
- Corvidae never publishes.

## Turborepo

- Only applications have `build` tasks. Cache their declared application outputs. Lint, test, and development tasks consume library source directly and must not depend on upstream library builds; `typecheck` depends only on its dependencies' `types` tasks, whose declarations it reads.
- Declare an environment variable in `turbo.json` only when it changes that task's result. Add task outputs whenever a task writes reusable artifacts; keep watchers and mutation tasks uncached.
- Use `--filter` for focused work, for example `bunx turbo run test --filter=@lostgradient/operative`, or `bun run check` to lint, type-check, and test only the workspaces a change can affect (Turborepo's `--affected`, against the default branch, plus the root lint). It skips root type-checking, coverage, the build, and formatting, so run `bun run validate` for the complete graph.
- The heavy root stages—`lint`, `typecheck`, `test`, `coverage`, and `build`—run through `scripts/run-exclusively.ts`, which holds one lock in the Git common directory that every worktree on the host shares. Concurrent `bun run validate` runs queue stage by stage instead of oversubscribing the machine, which otherwise times out unrelated tests at random. A waiting stage prints which process holds the lock, and a lock whose holder died is reclaimed. Focused `bunx turbo run … --filter` commands bypass the lock on purpose, so keep them focused. `scripts/workspace-contract.test.ts` keeps each stage behind the lock.
- The wrapper also gives each stage two Turborepo defaults, unless the environment already sets them. `TURBO_CACHE_DIR` points at one cache in the Git common directory, so a task any worktree has run replays in every other one. `TURBO_CONCURRENCY` is one task per 16 GiB of memory, because a single type-check peaks near 5 GB. A stage that passes `--concurrency` keeps its own value, as the serial test stages do.
- `bun run validate` runs each test suite once. A workspace whose `test:coverage` runs its fast suite through `scripts/bun-test-junit.ts`, with coverage flags only, writes its JUnit report there, and validate's `test` stage filters that workspace out; the duration report runs after `coverage` so it reads those reports. `scripts/workspace-contract.test.ts` derives the filter list from the manifests. A workspace whose coverage run differs from its `test` (Weft's sharded run with a longer timeout, chat's parallel run, terminal's run without isolation) keeps both.
- Every turbo task runs the uncached root `//#preflight` task (`bun install --frozen-lockfile`) first, by way of `transit`, so a `package.json` edit without a matching `bun install` fails every turbo command rather than running against a stale tree. Turbo hashes `bun.lock` but never `node_modules`, so a drifted install would otherwise cache a result under a key describing a toolchain it was not built with. A package-specific `<package>#<task>` entry replaces the generic task definition instead of merging with it, so any new override must restate `"dependsOn": ["transit"]`; `scripts/task-cache.test.ts` enforces that every cacheable task still reaches the preflight.
- Keep cache keys scoped to what a task can observe, so a change reruns only the packages it can affect. Because every task depends on `//#preflight`, its inputs are only `bun.lock` and the `package.json` manifests. The root package depends on no workspace except `@lostgradient/typescript`: turbo folds the files of every workspace the root depends on into the global hash, which would invalidate every cached task whenever one of them changed. Give root tooling that needs a workspace its own workspace, as `scripts/browser-fixtures` does. `globalDependencies` names individual configuration files, never directory globs; a package task that runs a root script lists that script in its own `inputs`. `scripts/task-cache.test.ts` enforces all three.

## Worktrees and agents

- Treat each worktree as an isolated checkout. From a fresh worktree, run `bun install --frozen-lockfile` before development or validation.
- Claude Code uses `claude --worktree <name>`; Codex uses its managed Worktree mode with a local-environment setup command of `bun install --frozen-lockfile`. Use native Git worktree behavior rather than custom creation hooks.
- Never copy `.env`, credentials, `node_modules`, caches, generated artifacts, or other ignored local state between worktrees. Do not add `.worktreeinclude` unless a specific non-secret ignored file is required.
- Preserve unrelated worktrees and their branches. Remove only a clean worktree created by the current task after its branch is merged or retired.

## Dev Container

`.devcontainer/` is a local development environment in which `bun run validate` passes from a fresh checkout with nothing on the host but Docker. It is not CI: nothing builds, runs, or publishes it automatically. Its image is Debian 13 (`oven/bun`) with the workspace's pinned Bun, PostgreSQL 17's `initdb` and `pg_ctl` on `PATH`, Node.js 24 and its `npm` (Weft's native SQLite suite runs under a real Node), node-gyp's compiler toolchain (two native dependencies build from source on linux/arm64), Playwright's Chromium and headless shell in the `bun` user's default Playwright cache (Turborepo's strict environment mode would drop a `PLAYWRIGHT_BROWSERS_PATH`) with their system libraries, and Git; it copies nothing from the checkout, so `.env`, credentials, and caches never enter it, and it has no `.dockerignore` because its build context is `.devcontainer/` alone. `scripts/dev-container.test.ts` keeps its Bun tag equal to `packageManager` and its Playwright version equal to the `playwright-core` that `bun.lock` resolves.

- Open any checkout or worktree with "Reopen in Container" (or `devcontainer up --workspace-folder .`). The checkout is mounted at its host path; `initializeCommand` links `.devcontainer/.git-common-dir` (ignored) to the host's Git common directory, the container mounts it, and `scripts/dev-container.ts` makes a linked worktree's absolute `gitdir:` resolve. The root `node_modules` and Turborepo's cache live in per-container volumes, so the host's darwin packages and cached task results never meet the container's Linux ones. With the isolated linker, the per-workspace `node_modules` links the container's install rewrites point into the root store, so run `bun install --frozen-lockfile` on the host again before using the same checkout there; a dedicated worktree for container work avoids the round trip.
- The container works as the `bun` user, because `initdb` refuses to run as root, and runs Docker's init as PID 1 (`"init": true`, or `docker run --init`): without it the zombies of killed processes are never reaped, and `scripts/run-exclusively.test.ts` sees their process groups as still alive.
- The image sets `TURBO_CONCURRENCY=1`. Measured in the image, Weft's type-check peaks near 3.5 GB and its type-contract check near 4.4 GB, so with Docker Desktop's default 8 GB virtual machine even two parallel tasks can be killed for memory (exit 137). Give Docker more memory before raising it.
- To validate a committed branch without an editor, clone it inside the image rather than mounting the host checkout: `docker build -t corvidae-dev .devcontainer`, `git bundle create /tmp/corvidae.bundle HEAD`, then `docker run --rm --init -v /tmp/corvidae.bundle:/tmp/corvidae.bundle:ro corvidae-dev sh -c 'git clone -q /tmp/corvidae.bundle ~/corvidae && cd ~/corvidae && bun install --frozen-lockfile && bun run validate'`.

What the container enables, suite by suite:

- Live PostgreSQL (`packages/weft/src/storage/postgres.test.ts`) and live Neon driver (`neon-live.test.ts`, through `neon-proxy.test-support.ts` to the same disposable cluster): enabled. They need only `initdb` and `pg_ctl`, and they are what keeps `@lostgradient/weft#test:coverage` above its floor for `neon.ts`, `postgres.ts`, and their two test-support modules. The cluster is `initdb --no-locale -E UTF8`, so no system locale is needed; the C collation the key-value schema depends on is pinned in its DDL. PostgreSQL 17 is Debian 13's server major and the release the host-side fix used.
- A real Neon endpoint: not provisioned. The live Neon suite tests the real driver's wire protocol against the local cluster, and a hosted database would need credentials the container must not carry.
- Playwright's browser-fixture suite (`test:browser-fixtures`, part of `bun run test`): enabled, and required. It launches Chromium's headless shell, so `validate` fails without a browser.
- Weft's real-browser smoke tests (`WEFT_BROWSER_SMOKE=1`: WebExtensionStorage, IndexedDB, HttpClient, Service Worker): runnable, still opt-in. The image carries full Chromium as well as the headless shell because WebExtensionStorage loads an unpacked extension, and all four suites pass in it with `bun run --filter=@lostgradient/weft test:browser`. They stay outside `validate` here exactly as on the host.
- The full Playwright suite (`bun run test:browser`): not enabled. Its Firefox and WebKit keyboard projects need `npx playwright install --with-deps firefox webkit` (as root), and in this linux/arm64 image some Chromium cases fail (observed in a partial run, which included the `markdown-editor-template-placeholders` assertions and a few accessibility and scrolling checks; no complete run's counts are recorded), so treat its results there as advisory. It is outside `validate` on every machine.
- The Agent Skills reference validator (`AGENT_SKILLS_REFERENCE_VALIDATOR`): not installed. It is opt-in and fetches a pinned Python tool with `uvx`.
- Cinder's Svelte coverage floor is recorded as measured on linux/x64. On Apple silicon the container runs linux/arm64, so `check-coverage-ratchet.ts` prints its platform notice there just as it does on macOS; the floor still applies and passes (measured in the container: Svelte functions 83.25% against 75.00%, lines 35.58% against 19.90%). Weft's coverage gate keys its two host-dependent allowances the same way: `memory-footprint.ts`'s macOS-only FFI path is excused off macOS, and `workflow-event-feed.ts` line 398 only on linux/x64, where Bun misses it.

## Commands

```bash
bun install --frozen-lockfile
bun run dev
bun run check
bun run build
bun run lint
bun run typecheck
bun run test
bun run test:slow
bun run report:test-durations
bun run check:test-durations
bun run format:check
bun run test:self
bun run validate
bun run audit
bun run --filter=@lostgradient/weft test:benchmarks
bun run --filter=@lostgradient/markdown test:benchmarks
bun run --filter=@lostgradient/cinder test:benchmarks
bun run --filter=@lostgradient/ventriloquist test:benchmarks
```

Run local quality commands explicitly. This repository has no Git hooks or automated release pipeline.

`bun run audit` runs `bun audit --audit-level=high` through `scripts/check-audit-exceptions.ts`. An advisory may be tolerated only by an entry in `scripts/audit-exceptions.ts`, which needs an owner decision, a tracking issue, a review-by date, and the exact dependency chains that may reach the package; the guard fails on a stale, expired, or widened exception. Never add a bare `--ignore`.

The `test:benchmarks` commands are the workspace-scoped entries in that list, because each belongs to a single package and `bun run --filter` is how the root invokes one workspace's script. `bun run test` excludes what they run: a suite that asserts a wall-clock or memory target measures the machine as much as the code, and on a host running several agents at once those measurements swing far enough that they cannot gate validation. They record numbers on demand instead. Their targets are unchanged. A root lint guard, `scripts/check-wall-clock-assertions.ts`, fails the build when a `*.test.ts` outside `scripts/benchmarks/` asserts an upper bound on a duration or a rate it can derive from a timing reading.

Correctness assertions never move with them. Weft keeps its benchmark directory's unit tests in the default suite, and Markdown's pathological-document and diff-identity checks stayed behind in `src/` when its timing assertions left. Each package excludes its benchmarks in the way its layout allows: Weft path-ignores the `.test.ts` benchmark files under `scripts/benchmarks/` in its `test` script and also keeps `*.bench.ts` files there, run by explicit `test:benchmarks` entries; Markdown, Cinder and Ventriloquist name theirs `*.bench.ts` under `scripts/benchmarks/`, which Bun's default discovery skips on its own. The rule is the same everywhere: a target that depends on host load belongs outside the gate, and the correctness it was bundled with belongs inside it.

A test that does seconds of real work (spawning processes, bundling, git, ts-morph, instrumented loops) is a different class: its assertion is correctness, so it stays in the gate, but it sits near Bun's 5-second per-test limit and host contention pushes it over (COR-1499). Such a test either becomes fast by removing redundant work, or moves to a `*.slow.test.ts` file. A workspace's `test` ignores those files (`--path-ignore-patterns='**/*.slow.test.ts'`, or the playground runner's own lane split) and its `test:slow` runs only them. `bun run validate` runs `bun run test:slow` with `--concurrency=1` after the fast phase, so nothing leaves the gate and no timeout is raised. A workspace that holds `*.slow.test.ts` files must define both scripts, and `scripts/check-test-durations.ts` fails `bun run validate` otherwise.

Each workspace's fast `test` runs through `scripts/bun-test-junit.ts` (the playground through `scripts/run-tests.ts`), which writes JUnit XML to `test-output/junit/`. A per-test time budget depends on host load, which AGENTS.md keeps out of the gate, so it is enforced on demand, the way `test:benchmarks` is: `bun run check:test-durations` fails any fast-lane test that took longer than 2 s unless `scripts/test-duration-allowlist.json` lists it, and fails an allowlisted entry that is gone or took under 1 s, so the list can only shrink. The script first reruns every report-writing task with `bun run measure:test-durations` (`turbo run test:self test test:browser-fixtures --force`, covering the root reports and each package's `test`), because turbo replays cached reports; run it on a quiet host. `bun run validate` runs `bun run report:test-durations` instead, which prints the same findings as warnings and exits 0; only wiring problems (a workspace bypassing the wrapper, or holding slow files without their lane scripts) fail it. `bun scripts/check-test-durations.ts --shrink` drops stale entries, and `--seed` refuses to run once the file has entries. Adding an entry is a reviewed edit and needs a tracking issue. Process spawns inside test bodies are a separate rule with its own guard (COR-1507); the duration check also sees the in-process work that guard cannot, such as ts-morph analysis and per-byte loops, and a test that a spawn fix makes fast leaves the allowlist through the stale-entry rule. Never raise the budget.
