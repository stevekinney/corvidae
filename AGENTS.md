# Project guidance

This is a pre-release, internal-only Bun and Turborepo workspace. Libraries are private source packages; applications own their executable toolchains. Do not add publishing, CI/CD, deployment infrastructure, or Git-hook installation. A Claude Code hook in the checked-in `.claude/settings.json` is not a Git hook: it runs inside the agent's session, installs nothing into `.git`, and the Git-hook ban does not apply to it. The tooling that transforms this workspace's source into the public mirror repositories used to be the one exception. It now lives in the separate private repository `stevekinney/corvidae-mirror`, which reads a corvidae checkout and writes nothing here, so no path in this workspace is exempt: publishing, CI/CD, deployment infrastructure, and Git-hook installation are prohibited everywhere in it, workflow files included. One application-owned hosting file is not infrastructure in this sense: `applications/playground/vercel.json` gives the existing Vercel project that serves cinder.website its install and build commands, response headers, and redirects, which project settings cannot express. Its `ignoreCommand` is covered the same way: `applications/playground/scripts/ignore-build.sh`, with the `ignore-build.ts` and `environment-configuration.ts` beside it, decides only whether that project builds a given commit, so that the hour-long export runs only when the deployed site could change. None of it adds a workflow, and the Vercel project's Git integration builds it.

## Workflow

- Inspect the existing workspace and nearby conventions before changing code.
- Plan non-trivial work, implement one complete testable capability at a time, and add a regression test for every defect.
- Use current official Bun, TypeScript, Turborepo, and dependency documentation for unfamiliar APIs or configuration.
- Run the relevant focused command while working, the focused checks on what you changed before opening a pull request, and `bun run validate` once a batch of merged work closes (see "Gate on local checks"). Treat warnings, console errors, and failed checks as defects.
- Treat file length as review guidance, including in imported tests. Enforce classic cyclomatic complexity of at most 100 in implementation and tests, or 300 under `scripts/`. Keep executable repository tooling in its owning workspace’s `scripts/` directory; required tool configuration and application entrypoints retain their documented locations. Require a concrete ownership, duplication, or correctness benefit before restructuring code. Keep correctness, types, tests, and builds enforced. Prefer platform and Bun primitives over new abstractions or dependencies.
- Do not add compatibility, migration, shim, adapter, or re-export layers while the template is pre-release unless the requirement explicitly demands one.

## Review guidelines

This software is pre-1.0 and still being prototyped, so the goal is to move fast on stable infrastructure: spend review effort where a mistake is expensive to undo, and keep everything else simple. These rules apply to human reviewers, review bots, and the agents answering them. `.github/copilot-instructions.md` carries the short form for Copilot.

Their tuning history (an audit of 518 bot review threads) is in `documentation/repository/review-and-parallel-run-history.md`. Findings are worth answering; the waste was comments on code the pull request did not change, whole-diff re-reviews after every push, contrived interleavings under unsupported configurations, findings that contradicted a recorded COR decision, and re-raised threads.

- Sort by reversibility. A _two-way door_ is internal code or a private source package that a later change can cheaply alter. It gets a comment only for a concrete failure under a supported configuration: name the inputs or interleaving and the wrong durable result. "Two engines under `ownership: 'none'`" or "a caller mutates its own request mid-call" is not one. A _one-way door_ is a persisted format or schema, a wire protocol, an exported surface the mirrors publish, or a published spec; review those closely and ask whether the design paints the project into a corner.
- Review the diff, not the repository. Behavior already on `main`, code from a merged dependency branch, and anything a linked COR issue or decision document specifies are out of scope; cite the document and stop. On a re-review, comment only on lines changed since the previous review, and never re-raise a thread the author answered unless the new commits changed whether it can happen. One comment per defect class.
- Check Linear before posting a finding or suggesting a change. Codex and other reviewers must read the linked COR issues and search the COR backlog for the affected behavior, symbols, and proposed work, including tickets outside the pull request's project. Read plausible matches for their scope, status, acceptance criteria, and recorded decisions; a similar title alone is not a match. When a ticket already captures the suggestion, cite its identifier and link instead of repeating the request, creating duplicate work, or demanding that an unrelated pull request implement it. An existing ticket does not excuse a concrete blocker introduced by this diff: explain the failing case and why it must be fixed before merge. If Linear is unavailable, state that the overlap check could not be completed; do not claim there is no matching ticket or block the pull request solely on that lookup.
- Accept breaking changes during pre-release. Do not request backwards compatibility, deprecation periods, compatibility wrappers, or preservation of obsolete APIs merely to protect prior behavior. Update affected in-repository callers directly and remove deprecated code in the changed path when replacing it. Review whether the resulting supported behavior works; a deliberate breaking change is not itself a defect. Persisted data, wire protocols, and published contracts still need the one-way-door scrutiny above.
- What the bots catch well, and should keep flagging: fields or parts dropped across an adapter, projection, or wire mapping; state written or exposed before its durable commit, or a post-commit failure swallowed with no repair; check-then-act without a fence on the state it read; cleanup or settlement bound to a stale generation, incarnation, or round; a retry or replay that performs a different operation than its receipt records; missing authorization on a new route or lookup; unvalidated input at an exported boundary; caller-owned input read after the first `await` without a snapshot; a published spec or schema contradicting its own text.
- Find root causes. Ask what class of defect a finding is and grep for its siblings. Fix the class once, with a regression test, lint rule, or type constraint, or decline the finding as a one-off. Do not patch instances one at a time. A finding earns this treatment only if it would plausibly recur or sits on a one-way door.
- Block on demonstrated correctness risks. A blocking finding must name a supported input or reachable interleaving, the wrong result, and its concrete consequence, such as data loss, broken authorization, invalid state transitions, or a violated persisted or published contract. A one-way door deserves scrutiny, but touching one is not itself a blocker. Style, naming, optional refactoring, personal preferences, contrived edge cases, and speculative hardening of internal code do not block a merge; omit nitpicks rather than manufacturing findings.
- Answer every thread before merge: fixed (name the commit), declined (one-line reason), or tracked (name the issue). An unanswered thread blocks the merge; the audit found 18 real defects merged unanswered.
- Cap review at three rounds. Fix every real finding in round one. In rounds two and three, fix regressions the fixes introduced, one-way-door defects, and real defects in lines this pull request changed; decline the rest with a reason. After the third round, collect anything still open that does not block into one follow-up issue instead of pushing again. Push once per round, not once per commit. Codex reviews every push to an open pull request automatically, by owner decision, so each push costs a full review round: batch a round's fixes into one commit or one push, run the focused checks on what you changed before pushing, and never push a fix for one thread while others from the same round are still open.
- Stop patching a repeating class. If a later round surfaces another instance of an earlier round's class, the causal model was wrong. Reassess the shared cause, and fix the class with a guard, instead of adding another patch. The long tails in the audit were all this: one review-id parser patched over three rounds, one settlement race over four, accessible names over eight.
- Prefer a guard to a comment. When the same class of finding recurs across pull requests, the repository is missing a guard. Add the lint rule, type constraint, or test.
- Gate on local checks, in two tiers.
  - **Per pull request:** the worker runs focused checks on what it changed before opening the pull request, and not `bun run check`: `bun test` on the touched files or directories (for example `bun test scripts/chef`), the root lint (`bun run lint:root`) and root type-check (`tsc --noEmit`, or `bun run typecheck:root`) when root or `scripts/` files changed, `bunx turbo run lint typecheck --filter=<workspace>` for each changed workspace, and `bun run format:check` on the changed files. Delivery runs no gate and never merges `main` into the branch: `main` moving is not a reason to repeat a check. `scripts/chef/deliver.ts` merges an accepted pull request when GitHub reports no conflict with its base, every review thread is resolved (read with the paginated `review-threads.ts` read), and its head is the head pinned at acceptance, with the merge itself pinned to that head. A real conflict is reported, and the worker resolves it and returns a new head. Review threads are all answered within the three-round cap, and no review thread names a serious defect. Do not wait for bots to go quiet, and do not run a full `validate` per pull request. `bun run check` remains the on-demand local reading of everything a change can reach; it runs `--shared`, outside the host lock, formatting first, but nothing requires it before a merge.
  - **Per batch:** run one `bun run validate` on `origin/main` after a batch of merges lands, or at the end of a program run, as a background command. A failure names its task, and so its package and the pull request that changed it. Fix it forward; the merge report warns while `main` is red, and nothing refuses on it.
  - **Main health:** `gate-run.ts run` records each batch validate (the command `repository.json` names as `batchCommand`) in `<main checkout>/tmp/chef/main-health.json` with its head, exit code, and time. `merge-gate.ts` reads it and warns in its report while the last batch validate at a head on `main`'s first-parent history failed; it never refuses on it, so a red `main` is the coordinator's to read and fix forward, not a lock on every merge. A fix for a red `main` is declared with `--fixes-main`, which records it in the health file. `bun scripts/chef/batch-validate.ts` runs the batch validate on `origin/main` in a dedicated worktree once at least five merges have landed since the last recorded batch head or two hours have passed, and skips when the health file already holds a green record at the current head. It applies no load gate unless `--max-load <n>` is given, and one host-wide lock in the Git common directory (`corvidae-batch-validate.lock`) keeps a single batch validate running per host, so a second coordinator exits 0 instead of starting another. A coordinator schedules it with a Claude Code scheduled task or `/loop` (`.agents/skills/chef/references/program-runs.md`), never with CI, cron files, or launchd plists.
  - **Exceptions:** run the full `validate` before merging when a pull request changes a one-way door (a persisted format, a wire protocol, a published export), the lock or concurrency infrastructure, or `turbo.json` and the root scripts, which re-key every task.

## Workspace and dependencies

- `applications/*` contains deployable applications; `components/*` contains browser component libraries; `packages/*` contains other shared libraries; `testing/*` contains verification tooling (the shared test helpers and the agent evaluator), which libraries and components may name only in `devDependencies`, never in `dependencies` or `peerDependencies` (applications, which nothing depends on, are exempt); `internal/*` contains repository configuration; `scripts/browser-fixtures` is a private workspace that only declares the workspaces the root browser fixtures import. Every workspace is named `@lostgradient/*`, except `armorer` and `conversationalist`, which carry their unscoped npm names. Repository scripts read these directories from `scripts/workspace-directories.ts` rather than spelling their own list, and `scripts/workspace-contract.test.ts` keeps that list equal to the root `workspaces` field and enforces the `testing/*` rule.
- Internal dependencies always use `workspace:*`. Shared external tool versions belong in the root Bun `catalog`; add runtime dependencies to the workspace that imports them.
- Component source uses the shared browser TypeScript configuration and root browser lint policy. Keep Bun and Node APIs in tests or scripts. Run both the browser source check and the inclusive tooling/test check.
- The `@lostgradient/typescript` configuration package under `internal/typescript` exports only `library.json` and `browser.json`; `base.json` is private composition.
- Shared source libraries export TypeScript source directly. Consumers compile it at runtime, so do not add a build step to a just-in-time package without a packaging need. Type-checking is the one exception: a TypeScript library that another package type-checks against has a `tsconfig.source.json` (composite, declarations only, into the ignored `.types/`), its `types` script builds it with `tsc -b`, and each consumer's `tsconfig.json` lists it under `references`, so the consumer reads those declarations instead of type-checking the library's source again. A consumer with references type-checks with `tsc -b tsconfig.json`, which rebuilds stale declarations first. Svelte packages still read source, because `svelte-check` does not substitute declarations.
- Use Bun commands only. `bun.lock` is authoritative, and dependency changes must update it with `bun install`.
- Keep `typescript` explicit at the root. Do not rely on a transitive or peer dependency to supply `tsc`.

## Turborepo

- Only applications have `build` tasks. Cache their declared application outputs. Lint, test, and development tasks consume library source directly and must not depend on upstream library builds; `typecheck` depends only on its dependencies' `types` tasks, whose declarations it reads.
- Declare an environment variable in `turbo.json` only when it changes that task's result. Add task outputs whenever a task writes reusable artifacts; keep watchers and mutation tasks uncached.
- Use `--filter` for focused work, for example `bunx turbo run test --filter=@lostgradient/operative`, or `bun run check` to lint and type-check only the workspaces a change can affect (Turborepo's `--affected`, against the default branch, plus the root lint and root type-check) and to run only the test files it can reach (`bun scripts/affected-tests.ts run`, which drives the same Turborepo lanes; `bun scripts/affected-tests.ts --explain` prints each selected file and why, and `--changed <path>` answers what a change to a given file would select). Selection never narrows a workspace the graph cannot attribute a change to: a changed `package.json`, `bunfig*.toml`, `tsconfig*.json`, preload or setup file, test-lane entrypoint, or data file no importer names selects its whole workspace, and a root configuration file or shared runner selects the whole repository. `check` enforces a coverage floor only for workspaces it selects whole, through `test:gate`, and skips the build, so run `bun run validate` for the complete graph; `validate` and the batch validate always run everything. The selection reaches Turborepo through `CORVIDAE_TEST_SELECTION`, declared in `turbo.json` for the narrowed tasks, so a cached result for one selection is never replayed for another. Rules and known limits: `documentation/repository/test-lanes-and-checks.md`.
- The heavy root stages—`lint`, `typecheck`, `test`, `coverage`, and `build`—run through `scripts/run-exclusively.ts`, which holds one lock in the Git common directory that every worktree on the host shares. Concurrent `bun run validate` runs queue stage by stage instead of oversubscribing the machine, which otherwise times out unrelated tests at random. A waiting stage prints which process holds the lock, and a lock whose holder died is reclaimed. Focused `bunx turbo run … --filter` commands bypass the lock on purpose, so keep them focused. `bun run check` runs the wrapper with `--shared`: it skips the lock but keeps the install check and the Turborepo defaults, at half the usual concurrency, so several sessions can run it at once without oversubscribing the host. `scripts/workspace-contract.test.ts` keeps each stage behind the lock.
- The wrapper also gives each stage three Turborepo defaults, unless the environment already sets them: `TURBO_CACHE_DIR` points at one cache in the Git common directory shared by every worktree, `TURBO_CONCURRENCY` is one task per 8 GiB of memory and per three processors, whichever allows fewer, and `TURBO_SCM_BASE` is `origin/main` (`turborepoAffectedBase` in `scripts/run-exclusively.ts`), the base that only `--affected` reads. A stage that passes `--concurrency` keeps its own value, as the serial slow lane does. Measurements are in `documentation/repository/turborepo-stage-mechanics.md`.
- `bun run validate` runs every workspace task except the applications' builds in one turbo run (`lint`, `typecheck`, `test:self`, `test:gate`, `test:browser-fixtures`), so they overlap under the concurrency cap. Run `bun run build` when a change can affect a deployed application; the Vercel project builds the playground for every commit its ignore step lets through. `test:gate` runs each package's suite exactly once, so a package's `test:coverage` does not depend on its `test`, and no root script names both in one turbo run, because some tests write fixed fixture paths in the source tree and the two runs must never overlap; `scripts/task-cache.test.ts` enforces both. Large suites run their files with `bun test --parallel=4`; keep worker counts at the cap, and measure a suite at 4 workers several times before moving it. Weft's UI suite stays serial. Coverage runs keep the worker count their Svelte floors were measured under, because Bun's Svelte function coverage moves with it. Weft's `test` runs `src/core/checkpoint-prune.test.ts` in a serial second phase, because Bun's `--parallel` isolate lane crashes in it (oven-sh/bun#29519, COR-1736); nothing is accepted as a rare failure. Per-suite worker notes and coverage-run details are in `documentation/repository/turborepo-stage-mechanics.md`.
- `scripts/run-exclusively.ts` runs `bun install --frozen-lockfile` (`bun run preflight`) before every command it wraps, so a `package.json` edit without a matching `bun install` fails `validate`, `check`, and every heavy stage before turbo runs, rather than running against a stale tree. Turbo hashes `bun.lock` but never `node_modules`, so a drifted install would otherwise cache a result under a key describing a toolchain it was not built with. The check deliberately sits outside the task graph: Turborepo always counts a task's own `package.json` among its inputs, so an install task that every task depended on re-keyed the whole repository on any root manifest edit. A bare `bunx turbo run` does not check the install, so run `bun install --frozen-lockfile` first when you have changed a manifest. A package-specific `<package>#<task>` entry replaces the generic task definition instead of merging with it, so any new override must restate `"dependsOn": ["transit"]`, which folds each upstream workspace into the task's key; `scripts/task-cache.test.ts` enforces that every cacheable package task still reaches it.
- Keep cache keys scoped to what a task can observe, so a change reruns only the packages it can affect. A manifest edit re-keys only that workspace and its dependents, and a lockfile change only the workspaces whose resolved dependencies it changes. The root package depends on no workspace except `@lostgradient/typescript`: turbo folds the files of every workspace the root depends on into the global hash, which would invalidate every cached task whenever one of them changed. Give root tooling that needs a workspace its own workspace, as `scripts/browser-fixtures` does. `globalDependencies` names individual configuration files, never directory globs; a package task that runs a root script lists that script in its own `inputs`. `scripts/task-cache.test.ts` enforces all three.

## Worktrees and agents

- Treat each worktree as an isolated checkout. From a fresh worktree, run `bun install --frozen-lockfile` before development or validation.
- Claude Code uses `claude --worktree <name>`; Codex uses its managed Worktree mode with a local-environment setup command of `bun install --frozen-lockfile`. Use native Git worktree behavior rather than custom creation hooks.
- Never copy `.env`, credentials, `node_modules`, caches, generated artifacts, or other ignored local state between worktrees. Do not add `.worktreeinclude` unless a specific non-secret ignored file is required.
- Preserve unrelated worktrees and their branches. Remove only a clean worktree created by the current task after its branch is merged or retired.

### Parallel runs

A run that delivers several issues at once is limited by this host's lock and processors, and its cost follows each agent's context more than its model (history: `documentation/repository/review-and-parallel-run-history.md`). These rules apply to every coordinator, `chef` included, and every brief a coordinator writes must state them:

- Run at most three agent sessions or implementation workers at once on this host, counting every session that edits or tests this repository. Within that, a run has at most two implementation workers; corrections wait for a slot.
- Give each issue, or each small cluster of issues that share files, its own fresh worker with a compact brief: the issue, its acceptance criteria, the files, the commands, and the decisions already made. Do not keep one long-lived worker per stream. A run has one coordinator, and nobody hands off for context size alone; Claude Code's automatic compaction is the backstop. Record `lastCtx` (`scripts/chef/transcript-usage.ts`) and tokens per merged pull request at each batch boundary as the cost signal. A context handoff, if ever chosen, is a fresh `start_session`, never `hand_off_to_session`, which forks the whole context. The default worker on Claude Code is a background `Agent` subagent, because its transcript feeds `deliver.ts --usage-log` and its completion wakes the coordinator; the Codex equivalent is a subagent per the `.codex/agents/` conventions. A separate `start_session` session is for when the owner asks for one.
- Implement with an economical coding model (Claude Sonnet, or the Codex equivalent) when the interfaces are known and the issue has tests. Reserve stronger models for review, one-way doors, and defects that survived two corrections.
- Gate each pull request as "Gate on local checks" describes: the worker's focused checks on what it changed, plus one review fix pass; delivery runs no gate. A session queues at most one full `validate` at a time, and only for an exception.
- Follow the review rules in "Review guidelines": answer every thread, cap review at three rounds, and push once per round. A comment the bot re-reports gets no new answer.
- End a turn only on a state change: merged, blocked, needs a decision, or ready for review. Wait for a check, a gate, or a review bot in a background command. Every turn a worker ends wakes its coordinator, which re-reads its whole context, so a turn that says only "still waiting" is pure cost.
- An explicit owner instruction in the current scope outranks the process rules in this section and the guards that enforce them (the repeating-class guard, the three-round review cap, the context ceiling). A guard stops the worker and hands the case to the coordinator, which decides, records the waived guard on the pull request and in its log, and files any reassessment as a follow-up; it does not ask the owner to choose between their instruction and a rule. `.agents/skills/chef/references/decisions.md` "Owner instructions outrank process rules" has the detail.
- A coordinator's broadcast to running sessions names the commit and the section that changed, for example "rules changed at `<sha>`; reread AGENTS.md "Parallel runs"". It never restates policy text. A brief for a new session still states these rules, as above.
- Start each issue's worker from a brief: `bun scripts/chef/brief.ts <ID>` writes `tmp/chef/briefs/<ID>.md` from the Linear issue (execution brief, acceptance criteria, files, verification commands, and the charter rules). The coordinator starts one fresh worker per issue from it, on Sonnet by default, and that worker ends when its pull request merges.
- The coordinator is thin: it reads verdicts only. It never edits code, never runs merges step by step, and never ingests bulk output (Linear lists, logs, diffs, thread bodies); it uses scripts or a Haiku lookup that returns a summary. A worker owns its pull request through its review threads, and the coordinator launches `bun scripts/chef/deliver.ts --pr <n> --worktree <path> --comment-file <file>` once per accepted pull request. It merges through `merge-gate.ts` (no gate, and no merge of `main` into the branch), closes the Linear issue with read-back, and removes the worktree as one background command (exit 0 merged, 1 failed step named, 2 usage). It refuses only for a conflict with the base, an unresolved review thread, or a head that is not the one pinned with `--head <sha>` at acceptance.
- Agents never run a bare `git stash` or `git stash pop`, because the stash stack is shared by every worktree. A Claude Code hook (`scripts/chef/stash-guard.ts`) enforces it; Codex follows the rule.
- Report spend at every batch boundary: tokens per merged pull request, and the share of the plan's usage. When tokens per merged pull request double from the run's earlier batches, stop dispatching and ask the owner.

## Dev Container

`.devcontainer/` is a local development environment in which `bun run validate` passes from a fresh checkout with nothing on the host but Docker. It is not CI: nothing builds, runs, or publishes it automatically. Its image is Debian 13 (`oven/bun`) with the workspace's pinned Bun, PostgreSQL 17's `initdb` and `pg_ctl` on `PATH`, Node.js 24 and its `npm` (the Node SQLite adapter's native suite runs under a real Node), node-gyp's compiler toolchain (two native dependencies build from source on linux/arm64), Playwright's Chromium and headless shell in the `bun` user's default Playwright cache (Turborepo's strict environment mode would drop a `PLAYWRIGHT_BROWSERS_PATH`) with their system libraries, and Git; it copies nothing from the checkout, so `.env`, credentials, and caches never enter it, and it has no `.dockerignore` because its build context is `.devcontainer/` alone. `scripts/dev-container.test.ts` keeps its Bun tag equal to `packageManager` and its Playwright version equal to the `playwright-core` that `bun.lock` resolves.

- Open any checkout or worktree with "Reopen in Container" (or `devcontainer up --workspace-folder .`). The checkout is mounted at its host path; `initializeCommand` links `.devcontainer/.git-common-dir` (ignored) to the host's Git common directory, the container mounts it, and `scripts/dev-container.ts` makes a linked worktree's absolute `gitdir:` resolve. The root `node_modules` and Turborepo's cache live in per-container volumes, so the host's darwin packages and cached task results never meet the container's Linux ones. With the isolated linker, the per-workspace `node_modules` links the container's install rewrites point into the root store, so run `bun install --frozen-lockfile` on the host again before using the same checkout there; a dedicated worktree for container work avoids the round trip.
- The container works as the `bun` user, because `initdb` refuses to run as root, and runs Docker's init as PID 1 (`"init": true`, or `docker run --init`): without it the zombies of killed processes are never reaped, and `scripts/run-exclusively.test.ts` sees their process groups as still alive.
- The image sets `TURBO_CONCURRENCY=1`. Measured in the image, Weft's type-check peaks near 3.5 GB and its type-contract check near 4.4 GB, so with Docker Desktop's default 8 GB virtual machine even two parallel tasks can be killed for memory (exit 137). Give Docker more memory before raising it.
- To validate a committed branch without an editor, clone it inside the image rather than mounting the host checkout: `docker build -t corvidae-dev .devcontainer`, `git bundle create /tmp/corvidae.bundle HEAD`, then `docker run --rm --init -v /tmp/corvidae.bundle:/tmp/corvidae.bundle:ro corvidae-dev sh -c 'git clone -q /tmp/corvidae.bundle ~/corvidae && cd ~/corvidae && bun install --frozen-lockfile && bun run validate'`.

What the container enables, suite by suite (live PostgreSQL and Neon, Playwright, Weft browser smoke tests, the Agent Skills validator, coverage-floor platform notes) is in `documentation/repository/dev-container-suites.md`. Playwright's browser-fixture suite is enabled and required, because `validate` fails without a browser; the full Playwright suite (`bun run test:browser`) is outside `validate` on every machine.

## Commands

```bash

bun run dev
bun run check
bun run build
bun run lint
bun run typecheck
bun run test
bun run test:slow
bun run report:test-durations

bun run --filter=@lostgradient/weft test:benchmarks
bun run --filter=@lostgradient/markdown test:benchmarks
bun run --filter=@lostgradient/ventriloquist test:benchmarks
```

Run local quality commands explicitly. This repository has no Git hooks or automated release pipeline.

`bun run audit` runs `bun audit --audit-level=high` through `scripts/check-audit-exceptions.ts`. An advisory may be tolerated only by an entry in `scripts/audit-exceptions.ts`, which needs an owner decision, a tracking issue, a review-by date, and the exact dependency chains that may reach the package; the guard fails on a stale, expired, or widened exception. Never add a bare `--ignore`.

The `test:benchmarks` commands are workspace-scoped entries, and `bun run test` excludes what they run: a suite that asserts a wall-clock or memory target measures the machine as much as the code, so it records numbers on demand instead of gating validation. A measurement is separated from a test by file name: a `*.bench.ts` is never discovered by `bun test`, and `scripts/check-wall-clock-assertions.ts` fails the build when any `*.test.ts`, including one under `scripts/benchmarks/`, asserts an upper bound on a duration or a rate derived from a timing reading. Correctness assertions never move with them: a target that depends on host load belongs outside the gate, and the correctness it was bundled with belongs inside it.

Owner decision: tests that can flake under load cannot be in the critical path. Everything `bun run check` and `bun run validate` run has one deadline, the awake-time hang guard (`HANG_GUARD_MILLISECONDS`, 120 seconds), and it is never a performance bound. Bun's per-test timeout is twice that, passed as `--timeout` by `scripts/bun-test.ts` and `scripts/bun-test-junit.ts` (`[test] timeout` in `bunfig.toml` is ignored, and `setDefaultTimeout` in a preload covers the first file only), so a `package.json` script never starts `bun test` itself. Every UI preload calls `configureAsyncUtilityDeadline` so Testing Library's `findBy*` and `waitFor` wait up to the hang guard. A wait for something that must happen uses `waitUntil` or `awakeTurns` from `@lostgradient/testing/wait-until` (root scripts import `testing/testing/src/wait-until.ts` by path, because the root package depends on no workspace; packages that cannot import the testing package keep a local poll), never a sleep, a count of turns, a wall-clock deadline or a race against a timer. A wait for something that must not happen uses `quietFor`, because load can only delay the event, never advance it. A test that deliberately exercises a short guard against work that cannot finish carries `// hang-guard-self-test: <reason>`, and a wait that load cannot flip for another reason (a pre-aborted signal, a double that never answers, timers of one clock that fire in order of their deadlines) carries `// load-proof: <reason>` that argues from determinism and never from expected speed, each of at least twenty characters directly above the statement. Manual runtime services and manual clocks inject their own timers and leave the global ones real, so a bare `Bun.sleep` beside them is still a real wait; only `useFakeTimers` patches the global `setTimeout`. `scripts/check-load-sensitive-deadlines.ts` enforces all of this from `lint:root`: it rejects a Bun or Testing Library timeout, a wait budget or a defaulted budget below the hang guard, a bounded poll, a wall-clock poll, a sleep (`Bun.sleep`, `node:timers/promises`, `waitForRealTimersForTesting`) before an assertion, a timer race (`Promise.race` or `Promise.any` against any timer promise, or a promise a timer also resolves), a `quietFor` window before a positive assertion, a single-turn yield (`sleepForTesting` under real timers, which ignores its argument, `setImmediate`, `setTimeout(r, 0)`, `Bun.sleep(0)`, and a same-file helper that is one of them) that something follows unless it waits on the state instead or carries `// load-proof:`, a timer that rejects, and a `bun test` invocation without the shared deadline. A Bun child that a test starts goes through `spawnWithHangGuard` or `runWithHangGuard`, which put `--no-install` in front of it (`withoutAutoInstall`), because a module written to the system temp directory has no `node_modules` and Bun would install what it imports from the registry, so the result would depend on the network and on which release is current. A product's own timeout option, such as `mailbox.awaitCleanup({ timeoutMs })`, is not read, and neither are event order and I/O races; the guard's header lists what it cannot see. The Playwright specs (`*.playwright.ts`, run by `test:browser`) and the opt-in `WEFT_BROWSER_SMOKE` suites are outside `check` and `validate` and are not scanned; `test:browser-fixtures` runs Bun tests, which are.

Every library and component documents its exported surface. Its `lint` runs `scripts/check-documentation-coverage.ts`, which fails when an export has no documentation comment. Exports that were undocumented when the check arrived are listed in each workspace's `documentation-coverage-allowlist.json`, which can only shrink (`--shrink` drops stale entries; `--seed` refuses to run once the file has entries). Document a new export rather than adding it to the list. The same check judges the own, non-private properties, methods, and accessors of each exported interface, class, and object-literal type alias, and each overload signature of an overloaded function or method; inherited members, enums, namespaces, and mapped, conditional, or `z.infer` aliases are not judged. Members that were undocumented when that check arrived are listed as `<entry point> <Symbol>.<member>` in each workspace's `documentation-member-allowlist.json`, which can only shrink the same way (`--shrink`; `--seed-members` writes the file once and refuses if it exists). Document a new member rather than adding it to the list.

Every library and component also type-checks the examples in its Markdown. Its `typecheck` runs `scripts/check-documentation-code-blocks.ts`, which compiles each ` ```ts ` or ` ```typescript ` fence as its own module. No attribute skips a block: give an example the context it needs through imports, `declare` lines, or an earlier `file=<name>.ts` block. Write a signature as code that references the real export, so drift breaks it.

Every library and component also runs `scripts/check-inherited-key-reads.ts` in its `lint`, which fails when `src` reads a plain record with a key the code does not control (`record[key]` or `key in record` on a `Record<string, T>`), because the record also answers for `constructor`, `toString` and `__proto__`. Test with `Object.hasOwn(record, key)` first, hold the entries in a `Map`, or build the record with `Object.create(null)`. A read that is safe for a reason the check cannot see goes in the workspace's `inherited-key-reads-allowlist.json` with its reason; the list can only shrink on its own, and adding an entry is a reviewed edit.

A test that does seconds of real work (spawning processes, bundling, git, ts-morph, instrumented loops) either becomes fast by removing redundant work, or moves to a `*.slow.test.ts` file (COR-1499). A workspace's `test` ignores those files and its `test:slow` runs only them; the root package's lanes are `test:self` and `test:self:slow`. `bun run validate` runs `bun run test:slow` with `--concurrency=1` after the fast phase, so nothing leaves the gate and no timeout is raised. A workspace that holds `*.slow.test.ts` files must define both scripts, and `scripts/check-test-durations.ts` fails `bun run validate` otherwise.

Each workspace's fast `test` writes JUnit XML through `scripts/bun-test-junit.ts` (the playground through `scripts/run-tests.ts`). `bun run check:test-durations` fails any fast-lane test that took longer than 2 s unless `scripts/test-duration-allowlist.json` lists it, and fails an allowlisted entry that is gone or took under 1 s, so the list can only shrink; run it on a quiet host. `bun run validate` runs `bun run report:test-durations`, which prints the same findings as warnings and fails only on wiring problems. Adding an allowlist entry is a reviewed edit and needs a tracking issue. Never raise the budget. Mechanics are in `documentation/repository/test-lanes-and-checks.md`.
