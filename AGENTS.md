# Project guidance

Corvidae is a public, pre-release Bun and Turborepo workspace. Libraries are private workspace source packages. Applications own their executable toolchains. Corvidae can own GitHub Actions workflows for application releases and publish verified application artifacts from its own GitHub Releases. Keep Git-hook installation out of the workspace. The checked-in Claude Code hooks run inside agent sessions.

The private `stevekinney/corvidae-mirror` repository owns the existing tooling that transforms Corvidae source for the public package mirrors. The playground's Vercel settings live in `applications/playground/vercel.json`, and its ignore command builds only when a change can affect the deployed site.

This file holds the rules; their mechanics and history live in `documentation/repository/`, linked from each rule.

## Workflow

- Inspect the existing workspace and nearby conventions before changing code.
- Plan non-trivial work, implement one complete testable capability at a time, and add a regression test for every defect.
- Use current official Bun, TypeScript, Turborepo, and dependency documentation for unfamiliar APIs or configuration.
- Run the relevant focused command while working, the focused checks on what you changed before opening a pull request, and `bun run validate` once a batch of merged work closes (see "Gate on local checks"). Treat warnings, console errors, and failed checks as defects.
- Treat file length as review guidance, including in imported tests. Enforce classic cyclomatic complexity of at most 100 in implementation and tests, or 300 under `scripts/`. Keep executable repository tooling in its owning workspace’s `scripts/` directory; required tool configuration and application entrypoints retain their documented locations. Require a concrete ownership, duplication, or correctness benefit before restructuring code. Keep correctness, types, tests, and builds enforced. Prefer platform and Bun primitives over new abstractions or dependencies.
- Do not add compatibility, migration, shim, adapter, or re-export layers while the template is pre-release unless the requirement explicitly demands one.
- A change to Interborough's interface (`applications/interborough/src/{app,routes,views,styles}`) or to Cinder (`components/cinder/src`) needs a design review before its pull request is ready for review: whoever implements it captures the screens it touches with `bun scripts/design-review-capture.ts` (in `applications/interborough`) and gets an implementation-review verdict, against the agreed design when there is one, from the read-only `design-reviewer` agent, following the `design-review` skill (`.agents/skills/design-review`), which also sweeps the existing interface and critiques a proposed design before it is built. Interborough is Cinder's only consumer, so a finding a Cinder component, default, or token can carry lands in Cinder, never as a bespoke fix in the page.
- An agreed design is a requirement. Work built from a design canvas carries each design row it implements as a binary acceptance criterion that names its board, or defers the row on the issue with a reason; a "Design source" list is context, never a substitute. `scripts/chef/design-ledger.ts` checks the mapping, and a design programme closes only after a full drift audit of the canvas against the shipped interface ([design programmes](.agents/skills/chef/references/planning-and-routing.md#design-programmes)).

## Review guidelines

This software is pre-1.0 and still being prototyped, so the goal is to move fast on stable infrastructure: spend review effort where a mistake is expensive to undo, and keep everything else simple. These rules apply to human reviewers, review bots, and the agents answering them; `.github/copilot-instructions.md` carries the short form for Copilot. Their tuning history (an audit of 518 bot review threads) is in [review and parallel-run history](documentation/repository/review-and-parallel-run-history.md).

- Sort by reversibility. A _two-way door_ is internal code or a private source package that a later change can cheaply alter. It gets a comment only for a concrete failure under a supported configuration: name the inputs or interleaving and the wrong durable result ([examples that are not](documentation/repository/review-and-parallel-run-history.md)). A _one-way door_ is a persisted format or schema, a wire protocol, an exported surface the mirrors publish, or a published spec; review those closely and ask whether the design paints the project into a corner.
- Review the diff, not the repository. Behavior already on `main`, code from a merged dependency branch, and anything a linked COR issue or decision document specifies are out of scope; cite the document and stop. On a re-review, comment only on lines changed since the previous review, and never re-raise a thread the author answered unless the new commits changed whether it can happen. One comment per defect class.
- Check Linear before posting a finding or suggesting a change: read the linked COR issues and search the COR backlog, across projects, for the affected behavior, symbols, and proposed work, judging plausible matches by scope, status, acceptance criteria, and recorded decisions, never by title alone. When a ticket already captures the suggestion, cite its identifier and link instead of duplicating it or demanding that an unrelated pull request implement it. A ticket does not excuse a concrete blocker this diff introduces: explain the failing case and why it must be fixed before merge. If Linear is unavailable, say the overlap check could not be completed; do not claim there is no matching ticket or block solely on that lookup.
- Accept breaking changes during pre-release. Do not request backwards compatibility, deprecation periods, compatibility wrappers, or preservation of obsolete APIs. Update affected in-repository callers directly and remove deprecated code in the changed path. Review whether the resulting supported behavior works; a deliberate breaking change is not itself a defect, and persisted data, wire protocols, and published contracts still get one-way-door scrutiny.
- What the bots catch well, and should keep flagging: fields or parts dropped across an adapter, projection, or wire mapping; state written or exposed before its durable commit, or a post-commit failure swallowed with no repair; check-then-act without a fence on the state it read; cleanup or settlement bound to a stale generation, incarnation, or round; a retry or replay that performs a different operation than its receipt records; missing authorization on a new route or lookup; unvalidated input at an exported boundary; caller-owned input read after the first `await` without a snapshot; a published spec or schema contradicting its own text.
- Find root causes. Ask what class of defect a finding is and grep for its siblings. Fix the class once, with a regression test, lint rule, or type constraint, or decline the finding as a one-off; do not patch instances one at a time. A finding earns this only if it would plausibly recur or sits on a one-way door.
- Block on demonstrated correctness risks. A blocking finding names a supported input or reachable interleaving, the wrong result, and its concrete consequence, such as data loss, broken authorization, invalid state transitions, or a violated persisted or published contract. Touching a one-way door is not itself a blocker. Style, naming, optional refactoring, preferences, contrived edge cases, and speculative hardening of internal code do not block; omit nitpicks. A departure from an agreed design that a pull request's issue names is a defect against a requirement, and it blocks like one.
- Answer every thread before merge: fixed (name the commit), declined (one-line reason), or tracked (name the issue). An unanswered thread blocks the merge.
- Cap review at three rounds. Fix every real finding in round one. In rounds two and three, fix regressions the fixes introduced, one-way-door defects, and real defects in lines this pull request changed; decline the rest with a reason. After the third round, collect anything still open that does not block into one follow-up issue instead of pushing again. Push once per round, not once per commit: Codex reviews every push to an open pull request automatically, by owner decision, so batch a round's fixes into one push, run the focused checks before pushing, and never push a fix for one thread while others from the same round are still open.
- Stop patching a repeating class. If a later round surfaces another instance of an earlier round's class, the causal model was wrong: reassess the shared cause and fix the class with a guard.
- Prefer a guard to a comment: when a class of finding recurs across pull requests, add the missing lint rule, type constraint, or test.
- **Gate on local checks**, in two tiers ([mechanics](documentation/repository/test-lanes-and-checks.md#gate-tiers-and-main-health)).
  - **Per pull request:** the worker runs focused checks on what it changed before opening the pull request, and not `bun run check`: `bun test` on the touched files or directories, `bun run lint:root` always, because its guards scan the tests of every workspace, the root type-check (`bun run typecheck:root`) when root or `scripts/` files changed, `bunx turbo run lint typecheck --filter=<workspace>` for each changed workspace, and `bun run format:check` on the changed files; `bun scripts/chef/focused-checks.ts` runs them as one command. A test file that starts a process, directly or through a helper, is named `*.integration.test.ts` (`lint:root` rejects it otherwise). When `bun scripts/affected-tests.ts --explain --isolated` lists a `*.integration.test.ts` or `*.slow.test.ts` file your change reaches, also run `bun scripts/affected-tests.ts run --isolated`, because no other per-pull-request check runs the isolated lane. Delivery runs no gate and never merges `main` into the branch, so `main` moving is not a reason to repeat a check; a real conflict goes back to the worker. Do not wait for bots to go quiet or run a full `validate` per pull request.
  - **Per batch:** run one `bun run validate:batch` on `origin/main` after a batch of merges lands, or at the end of a program run, as a background command: `bun run validate`, the root Playwright suite's `chromium` project, then Interborough's end-to-end suite (`bun run test:browser:interborough`), each browser suite under the host lock (COR-2007). Fix a failure forward.
  - **Main health:** `merge-gate.ts` warns, and never refuses, while the last batch validate on `main` failed; a fix for a red `main` is declared with `--fixes-main`. `bun scripts/chef/batch-validate.ts` runs the batch validate after five merges or two hours, one per host; schedule it with a Claude Code scheduled task or `/loop`, never with CI, cron files, or launchd plists.
  - **Exceptions:** run the full `validate` before merging when a pull request changes a one-way door (a persisted format, a wire protocol, a published export), the lock or concurrency infrastructure, or `turbo.json` and the root scripts, which re-key every task.

## Workspace and dependencies

- `applications/*` contains deployable applications; `components/*` contains browser component libraries; `packages/*` contains other shared libraries; `testing/*` contains verification tooling (the shared test helpers and the agent evaluator), which libraries and components may name only in `devDependencies`, never in `dependencies` or `peerDependencies` (applications, which nothing depends on, are exempt); `internal/*` contains repository configuration; `plugins/*` contains Interborough plugins, trusted in-process code authored with `@lostgradient/interborough-plugin`, whose `dependencies` may name only that package, `armorer`, Operative, Weft, Storage, Lifecycle, Memory, `zod`, and external packages (Bureau and `testing/*` only in `devDependencies`, and no application or other plugin anywhere; `scripts/plugin-dependency-rules.ts` states the rule); `scripts/browser-fixtures` is a private workspace that only declares the workspaces the root browser fixtures import. Every workspace is named `@lostgradient/*`, except `armorer` and `conversationalist`, which carry their unscoped npm names. Repository scripts read these directories from `scripts/workspace-directories.ts`; `scripts/workspace-contract.integration.test.ts` keeps that list equal to the root `workspaces` field and enforces the `testing/*` and plugin rules.
- Internal dependencies always use `workspace:*`. Shared external tool versions belong in the root Bun `catalog`; add runtime dependencies to the workspace that imports them.
- Component source uses the shared browser TypeScript configuration and root browser lint policy. Keep Bun and Node APIs in tests or scripts. Run both the browser source check and the inclusive tooling/test check.
- The `@lostgradient/typescript` configuration package under `internal/typescript` exports only `library.json` and `browser.json`; `base.json` is private composition.
- Shared source libraries export TypeScript source directly, and consumers compile it at runtime, so do not add a build step to a just-in-time package without a packaging need. Type-checking is the one exception: a TypeScript library that another package type-checks against has a `tsconfig.source.json` (composite, declarations only, into the ignored `.types/`) built by its `types` script with `tsc -b`, and each consumer's `tsconfig.json` lists it under `references` and type-checks with `tsc -b tsconfig.json`. A Svelte component library (Cinder, chat, editor, terminal) emits its declarations with `svelte2tsx` through the same `types` script, into `.types/src`, and its `exports` map names them under the `types` condition while `svelte` and `default` keep naming source, because `svelte-check` does not substitute declarations for `.svelte` files on its own.
- Use Bun commands only. `bun.lock` is authoritative, and dependency changes must update it with `bun install`.
- Keep `typescript` explicit at the root. Do not rely on a transitive or peer dependency to supply `tsc`.

## Release intent

- Per-change publishing is paused, and this workspace carries no `.changeset/` directory. Release intent for a batch backport is written in `stevekinney/corvidae-mirror`, next to the tooling that carries it to the mirrors, when the backport is made.
- `scripts/published-exports.json` (each public package's `exports` map, which Weft's documentation check and Markdown's import-graph test resolve against) is updated by hand after a backport.
- Interborough release automation belongs in Corvidae: build from a pinned source revision and verify the installed artifact on each supported target before publishing it. Corvidae GitHub Releases can host the compiled archives and checksums.

## Turborepo

Mechanics and measurements: [Turborepo stage mechanics](documentation/repository/turborepo-stage-mechanics.md).

- Only applications have `build` tasks. Cache their declared application outputs. Lint, test, and development tasks consume library source directly and must not depend on upstream library builds; `typecheck` depends only on its dependencies' `types` tasks.
- Declare an environment variable in `turbo.json` only when it changes that task's result. Add task outputs whenever a task writes reusable artifacts; keep watchers and mutation tasks uncached.
- Use `--filter` for focused work, for example `bunx turbo run test --filter=@lostgradient/operative`, or `bun run check` to lint, type-check, and test only what a change can reach (`bun scripts/affected-tests.ts --explain` says why each file was selected). Selection never narrows a workspace the graph cannot attribute a change to ([affected test selection](documentation/repository/test-lanes-and-checks.md#affected-test-selection)). Coverage is a report (`bun run coverage`) that never fails on a floor (owner decision, 2026-11-10).
- Every `bun test` holds one slot per worker in a host-wide pool (`scripts/bun-test-pool.ts`, `CORVIDAE_TEST_SLOTS` overrides its size), so Bun test workers never exceed it; `tsc`, `svelte-check` and Playwright stay outside it. The root stages run through `scripts/run-exclusively.ts` `--shared`; only the Playwright suites and `harden` take its lock. The wrapper runs `bun install --frozen-lockfile` first; a bare `bunx turbo run` does not, so run it yourself after changing a manifest.
- `bun run validate` runs every workspace task except the applications' builds in one turbo run; run `bun run build` when a change can affect a deployed application. Every suite runs through the same `test` task the per-pull-request checks run, so a suite they just ran is a cache hit. Large suites run with `bun test --parallel=4`; keep worker counts at the cap, and measure a suite at 4 workers several times before moving it. Nothing is accepted as a rare failure (COR-1736).
- Keep cache keys scoped to what a task can observe. A new `<package>#<task>` override must restate `"dependsOn": ["transit"]`. The root package depends on no workspace except `@lostgradient/typescript`, so root tooling that needs a workspace gets its own, as `scripts/browser-fixtures` does. `globalDependencies` names individual files, never directory globs, and a package task that runs a root script lists it in its `inputs`. `scripts/task-cache.integration.test.ts` enforces these.

## Worktrees and agents

- Treat each worktree as an isolated checkout. From a fresh worktree, run `bun install --frozen-lockfile` before development or validation.
- Claude Code uses `claude --worktree <name>`; Codex uses its managed Worktree mode with a local-environment setup command of `bun install --frozen-lockfile`. Use native Git worktree behavior rather than custom creation hooks.
- Never copy `.env`, credentials, `node_modules`, caches, generated artifacts, or other ignored local state between worktrees. Do not add `.worktreeinclude` unless a specific non-secret ignored file is required.
- Preserve unrelated worktrees and their branches. Remove only a clean worktree created by the current task after its branch is merged or retired.

### Parallel runs

A run that delivers several issues at once is limited by this host's lock and processors, and its cost follows each agent's context more than its model ([history](documentation/repository/review-and-parallel-run-history.md)). These rules apply to every coordinator, `chef` included, and every brief a coordinator writes must state them:

- Run at most three agent sessions or implementation workers at once on this host, counting every session that edits or tests this repository. Within that, a run has at most two implementation workers; corrections wait for a slot.
- Give each issue, or each small cluster of issues that share files, its own fresh worker with a compact brief from `bun scripts/chef/brief.ts <ID>`. Never keep one long-lived worker per stream; a worker ends when its pull request merges. The default worker is a background `Agent` subagent on Claude Code, whose transcript feeds `deliver.ts --usage-log` and whose completion wakes the coordinator, or a subagent per `.codex/agents/` on Codex; a `start_session` session only when the owner asks.
- A run has one coordinator, and nobody hands off for context size alone; Claude Code's automatic compaction is the backstop. A context handoff, if ever chosen, is a fresh `start_session`, never `hand_off_to_session`. Record `lastCtx` (`scripts/chef/transcript-usage.ts`) and tokens per merged pull request at each batch boundary.
- Implement with an economical coding model (Claude Sonnet, or the Codex equivalent) when the interfaces are known and the issue has tests. Reserve stronger models for review, one-way doors, and defects that survived two corrections.
- Gate each pull request as "Gate on local checks" describes, plus one review fix pass. A session queues at most one full `validate` at a time, and only for an exception.
- Follow "Review guidelines": answer every thread, cap review at three rounds, and push once per round. A comment the bot re-reports gets no new answer.
- End a turn only on a state change: merged, blocked, needs a decision, or ready for review. Wait for a check, a gate, or a review bot in a background command; a "still waiting" turn wakes the coordinator for nothing.
- An explicit owner instruction in the current scope outranks the process rules in this section and the guards that enforce them (the repeating-class guard, the three-round review cap, the context ceiling). A guard stops the worker and hands the case to the coordinator, which decides, records the waived guard on the pull request and in its log, and files any reassessment as a follow-up; it never asks the owner to choose between their instruction and a rule ([decisions](.agents/skills/chef/references/decisions.md#owner-instructions-outrank-process-rules)).
- A coordinator's broadcast to running sessions names the commit and the section that changed, for example "rules changed at `<sha>`; reread AGENTS.md "Parallel runs"", and never restates policy text.
- The coordinator is thin: it reads verdicts only. It never edits code, never runs merges step by step, and never ingests bulk output (Linear lists, logs, diffs, thread bodies); it uses scripts or a Haiku lookup that returns a summary. A worker owns its pull request through its review threads, and the coordinator delivers each accepted one with one background `bun scripts/chef/deliver.ts --pr <n> --worktree <path> --comment-file <file>`, which merges through `merge-gate.ts`, closes the Linear issue with read-back, and removes the worktree ([review and deliver](.agents/skills/chef/references/review-and-deliver.md)).
- Agents never run a bare `git stash` or `git stash pop`, because the stash stack is shared by every worktree; `scripts/chef/stash-guard.ts` enforces it in Claude Code.
- Report spend at every batch boundary: tokens per merged pull request, and the share of the plan's usage. When tokens per merged pull request double from the run's earlier batches, stop dispatching and ask the owner.

## Dev Container

`.devcontainer/` is a local development environment, not CI, in which `bun run validate` passes from a fresh checkout with only Docker on the host. Give Docker more memory before raising its `TURBO_CONCURRENCY=1`, and rerun `bun install --frozen-lockfile` on the host before using a checkout the container installed into. Details: [the dev container](documentation/repository/dev-container-suites.md).

```bash

bun run build
bun run lint
bun run typecheck

bun run coverage
bun run release:check

bun run format:check

bun run validate:batch
bun run harden
bun run audit
bun run --filter=@lostgradient/weft test:benchmarks
bun run --filter=@lostgradient/markdown test:benchmarks

```

Run local quality commands explicitly; this repository has no Git hooks or automated release pipeline. Guard details: [guards](documentation/repository/guards.md), [test lanes and checks](documentation/repository/test-lanes-and-checks.md).

- `bun run audit` tolerates an advisory only through an entry in `scripts/audit-exceptions.ts` (an owner decision, a tracking issue, a review-by date, and the exact dependency chains); never add a bare `--ignore`.
- A wall-clock or memory target is a `*.bench.ts` measurement, run by `test:benchmarks` outside `bun run test`; `scripts/check-wall-clock-assertions.ts` fails a `*.test.ts` that asserts an upper bound on a duration. Correctness assertions stay in the gate.
- Owner decision: tests that can flake under load cannot be in the critical path. Everything `bun run check` and `bun run validate` run has one deadline, the awake-time hang guard (`HANG_GUARD_MILLISECONDS`, 120 seconds), never a performance bound; Bun's per-test timeout is twice that, passed by `scripts/bun-test.ts`, so a `package.json` script never starts `bun test` itself. Wait for what must happen with `waitUntil` or `awakeTurns`, never a sleep, a count of turns, a wall-clock deadline, or a timer race, and for what must not happen with `quietFor`. An exception carries `// hang-guard-self-test: <reason>` or `// load-proof: <reason>` (twenty characters or more, directly above the statement). `scripts/check-load-sensitive-deadlines.ts` enforces this from `lint:root` ([load-sensitive deadlines](documentation/repository/guards.md#load-sensitive-deadlines)).
- Every library and component runs `scripts/check-inherited-key-reads.ts` in `lint`; guard a read with `Object.hasOwn`, a `Map`, or `Object.create(null)` instead of adding to its allowlist, which only shrinks. `bun run release:check`, run before a backport, checks that every library and component documents its exported surface and members (`scripts/check-documentation-coverage.ts`), type-checks the TypeScript examples in its Markdown (`scripts/check-documentation-code-blocks.ts`, where no attribute skips a block), and passes `check:test-durations`.
- A test that does seconds of real work becomes fast or moves to a `*.slow.test.ts` file (COR-1499). A test file that starts a process, directly or through a helper, is a `*.integration.test.ts` file (`scripts/check-test-process-spawns.ts`). Both form the isolated lane: a workspace's `test` ignores them, its `test:slow` runs only them, and a workspace holding either defines both scripts. `bun run validate` runs `bun run test:slow` with `--concurrency=1`.
- `bun run check:test-durations` (a step of `release:check`) fails a fast-lane test over 2 s unless `scripts/test-duration-allowlist.json` lists it; the list only shrinks, an entry needs a tracking issue, and the budget is never raised.

Test tiers. The quick tier, `bun run check`, runs in-process tests only; the full tier is `bun run validate` and the batch validate; `bun run harden` runs the isolated lanes under load, never per pull request. A test that fails in the full tier or in `harden` is never rerun until green, retried, or allowlisted: compare it against the base with `bun scripts/chef/gate-run.ts control`, and file a flake's fix (the mechanism, never a longer deadline) as a COR issue ([test tiers](documentation/repository/test-lanes-and-checks.md#test-tiers-and-the-hardening-pass)).
