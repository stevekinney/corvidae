# Terminal runtime, engine, workspace, and session contract

Status: accepted COR-436 candidate. This document is the source of truth for the terminal implementation issues. Runtime and engine evidence is generated by `scripts/terminal/runtime-probe.ts` and `scripts/terminal/engine-probe.ts`; reports live under ignored `tmp/terminal-probes/` and are never committed.

## Decision

The first release uses `@xterm/xterm@6.0.0`. The engine probe installs `ghostty-web@0.4.0`, `@xterm/xterm@6.0.0`, and `@wterm/dom@0.5.1` at exact versions in separate fresh isolated temporary directories. Each candidate receives its documented browser entrypoint and assets under a candidate-specific CSP; WebAssembly candidates use `script-src 'self' 'wasm-unsafe-eval'` and Ghostty's explicit `/ghostty-vt.wasm` path. Xterm and WTerm reach a resolved Chromium state; Ghostty Web is rejected by the measured soft-wrap metadata gate because its 0.4.0 row metadata is not trustworthy for retained soft-wrap extraction. Selection is derived from candidate cell results; the preferred Ghostty tie-break is applied only after all hard gates pass. There is no runtime engine selector, fallback engine, consumer addon API, fork, vendored parser, or new VT implementation.

The selected engine is private behind the terminal controller. The controller exposes deliberate typed operations and events, never the parser, renderer, option bag, raw write queue, or engine instance. The selected engine's WASM and CSS assets are served by the example application's Bun build using the existing `scripts/build-browser.ts` browser/WASM handling. Xterm uses `script-src 'self'`; Ghostty Web and WTerm use `script-src 'self' 'wasm-unsafe-eval'`; all candidate profiles keep `connect-src 'self'` and serve candidate assets with their documented MIME types.

## Runtime and supported matrix

The pinned runtime is Bun `1.4.2`. The supported host matrix is macOS and Linux on x64 and arm64. The v1 browser matrix is desktop Chromium, which is the browser hard-gated by the committed engine evidence; Firefox and WebKit remain unproven. Named shells are `sh`, `bash`, `zsh`, and `fish` when present on the host; a missing shell is a named startup failure, not a fallback. Windows is unsupported in v1 because `Bun.spawn({ terminal })` is POSIX-only and rejects with `unsupported-runtime`; a pipe never silently upgrades to a PTY.

Pipe mode preserves stdout and stderr as separate channels and reports no resize, terminal query, shell line discipline, or process-terminal capability. PTY mode uses `Bun.spawn({ terminal })`, owns terminal dimensions, accepts input and resize, and reports process exit separately from PTY EOF. Output-only sources may be a finite or live `ReadableStream` or async byte iterable; they advertise no input, resize, or kill capability and report source completion rather than inventing exit code zero.

The engine's Unicode data and width policy are selected from the probed `@xterm/xterm` release. Input and protocol text are UTF-8; invalid framing is rejected while invalid UTF-8 bytes remain data for the engine. Width follows the engine's Unicode tables for combining marks, ZWJ sequences, and CJK wide characters. Logical-order RTL text is retained and rendered according to the engine; arbitrary consumer `wcwidth` implementations are not promised. Applications must expect known width differences for fonts and browser shaping. Locale is inherited from the host only for shell behavior; protocol decoding is locale-independent. Mobile and interactive narrow layouts are out of v1.

Dependency evidence: the probe independently installs `ghostty-web@0.4.0`, `@xterm/xterm@6.0.0`, and `@wterm/dom@0.5.1` in fresh temporary directories. Xterm and WTerm pass the resolved browser gates; Ghostty Web is rejected by its measured retained soft-wrap metadata gate. Xterm and WTerm serve their package CSS as `text/css`; Ghostty serves its explicit `ghostty-vt.wasm` as `application/wasm`. WebAssembly candidates use `script-src 'self' 'wasm-unsafe-eval'`; all candidate profiles keep `connect-src 'self'`. Install lockfile, package, artifact, export, entrypoint, notice, diagnostic, and browser request identities are retained in `tmp/terminal-probes/engines.json`.

## Component and controller contract

`Terminal` composes Cinder's `TerminalFrame` and owns only view binding, focus, fit measurement, accessible output, and unbinding. An externally supplied controller is borrowed: component unmount never terminates it. A controller constructed with an ephemeral source owns its attachment and disposes the source on explicit controller disposal. A terminal can be read-only or writable by server authority; read-only mode suppresses user input and automatic terminal query replies.

The controller accepts byte output and byte input, `resize(columns, rows)`, `clear()`, bounded `readText()`, literal `search()`, `attach()`, `detach()`, and explicit `dispose()`. Events distinguish output, capability changes, operation acknowledgement, operation failure, process exit, source completion, attachment revocation, transport failure, and cleanup result. No consumer receives the engine instance or raw parser hooks.

The frozen controller surface is `TerminalController.attach(source): Promise<void>`, `write(data: Uint8Array | string): Promise<InputResult>`, `resize(columns: number, rows: number): Promise<ResizeResult>`, `clear(): void`, `readText(options?: ReadTextOptions): Promise<string>`, `search(query: string, options?: SearchOptions): SearchResult[]`, `detach(): void`, and `dispose(): Promise<CleanupResult>`. Its events are `output`, `capabilities`, `operation-ack`, `operation-failure`, `process-exit`, `source-complete`, `attachment-revoked`, `transport-error`, and `cleanup-result`. `TerminalWebSocketClient` has `connect(): Promise<Capabilities>`, `sendInput(bytes): Promise<InputResult>`, `sendResize(columns, rows): Promise<ResizeResult>`, `stop(): Promise<CleanupResult>`, and `close(): void`. The Svelte component accepts `controller`, `readOnly`, `ariaLabel`, `fit`, and `announceOutput` props and emits no raw engine events.

## Session lifetime and ownership

Each session has one active attachment and one immutable attachment generation. Creation reserves the ownership slot atomically; a second attachment is rejected without disturbing the current attachment. The attachment is connection-owned and ephemeral. Unexpected disconnect disables input immediately, revokes authority, and starts documented host cleanup. The transport never reconnects, respawns, replays keystrokes, or implies that a process survived.

Restart is an explicit new session after previous cleanup is complete. Incomplete or unknown cleanup quarantines the ownership slot and blocks replacement. View disposal only unbinds the view; controller disposal closes its attachment. Borrowed sources are unsubscribed but never terminated. Owned streams are canceled through their reader and owned async iterators receive `return()` when available. A failed connection is not a successful process exit; PTY closure is not a subprocess exit code.

## Versioned wire schema

Every application frame is version `1`, contains a kind, direction, payload length, session identifier, attachment generation, and sequence, and is rejected if truncated, oversized, malformed, or sent in the wrong direction. Control messages are JSON with UTF-8 strings; output and input payloads use binary bytes. WebSocket fragmentation is handled by the WebSocket implementation, while this schema validates complete application frames. The maximum frame payload is 64 KiB; the bounded host FIFO is 256 operations; sequence numbers are unsigned 53-bit integers and must increase strictly within one attachment. Session identifiers are opaque UUID strings. Unknown versions fail closed with `protocol-version-unsupported`.

Message kinds are `hello` (client to server), `capabilities` (server to client), `output` (server to client), `input` (client to server), `resize` (client to server), `operation-ack` (server to client), `operation-failure` (server to client), `output-consumed` (client to server), `process-exit` (server to client), `attachment-error` (server to client), `terminate` (client to server), and `cleanup-result` (server to client). Input and resize share one ordered operation sequence and FIFO. An input acknowledgement means acceptance into that bounded host FIFO, never backend consumption or command execution. A submitted operation can still fail later. A lost acknowledgement is unknown delivery and is never retried.

Stop revokes authority immediately, cancels queued but unsubmitted operations with explicit results, and uses reserved control capacity for cleanup. Submitted operations cannot be retracted. Terminal-generated query replies count as input and obey the same authority rules. No acknowledgement survives connection loss, and v1 makes no exactly-once command claim.

The WebSocket server callback signatures are frozen as `handleOpen(socket, request): Promise<void>`, `handleMessage(socket, frame: Uint8Array | string): Promise<void>`, and `handleClose(socket, code, reason): Promise<void>`. The handshake payload is `{ version: 1, sessionId, requestedMode: 'read-only' | 'interactive', token }`; the response is `{ version: 1, sessionId, attachmentGeneration, capabilities, maxFrameBytes: 65536, maxQueuedOperations: 256 }`. Origin and token authorization happen before generation issuance.

## Failure and cleanup table

| Code | Direction and operation | Result and attachment | WebSocket close | Drain and cleanup |
| --- | --- | --- | --- | --- |
| `protocol-version-unsupported` | server, handshake | reject; no generation issued | 1002 | discard frame; close transport |
| `malformed-frame` | either, decode | reject; current generation revoked | 1002 | drain bounded queue; kill owned process |
| `frame-too-large` | either, decode | reject; current generation revoked | 1009 | drain bounded queue; kill owned process |
| `stale-generation` | either, operation | explicit failure; authority unchanged | 1008 | leave current attachment live |
| `read-only` | client, input/query | explicit failure; authority unchanged | 1008 | operation is not queued |
| `fifo-full` | client, input/resize | explicit failure; authority unchanged | 1013 | preserve existing queue; no process action |
| `unsupported-runtime` | server, startup | startup failure; no attachment | 1011 | close PTY/pipe handles |
| `spawn-failed` | server, startup | startup failure; generation revoked | 1011 | terminate descendants; quarantine if uncertain |
| `backend-failed` | server, submitted operation | operation failure; generation revoked | 1011 | cancel unsent operations; cleanup |
| `transport-failed` | either, live session | unknown delivery; generation revoked | 1011 | disable input; cleanup |
| `cleanup-incomplete` | server, disposal | explicit incomplete result; slot quarantined | 1000 | retain quarantine record; no replacement |

Code `1006` is reserved for a locally observed abnormal closure and is never sent in an application-initiated WebSocket close frame.

## Worked lifecycle examples

Normal output: `hello` produces `hello` bytes tagged with session and generation, then the client may acknowledge consumed output; the host acknowledgement does not alter process state. Invalid input: stale generation or read-only input receives `operation-failure` and is never placed in the FIFO. Startup failure: unsupported runtime or missing shell produces `attachment-error` with no process-exit success. Exit: the host emits PTY EOF or source completion, then the distinct process-exit result when known, revokes the generation, and emits cleanup-result. Cleanup: stop revokes authority first, cancels unsent operations, terminates owned descendants, closes handles, and reports complete, incomplete, or unknown; incomplete and unknown quarantine the slot.

## Fixture and evidence identity

The runtime report is `tmp/terminal-probes/runtime.json`; the engine report is `tmp/terminal-probes/engines.json`; both validate against `scripts/terminal/evidence.schema.json` and include schema version, report kind, source SHA, run ID, timestamp, expected cell IDs, per-cell results, metrics with units where measured, and an overall result. The committed JSON Schema owns structural validity, while the production validator additionally owns exact cell identity, candidate completeness, nested/top-level agreement, and passed-result consistency that JSON Schema cannot express across records. Missing or duplicate required cells fail closed. The matrix owner is `contract`. Later issues consume these paths and report cell IDs without renaming them. The example application's server-owned command profiles are the only commands exposed to the browser; arbitrary command execution, durable resume, shared viewers, recordings, SSH, graphics, Windows, NVDA, mobile interaction, publication, and desktop bridging remain outside v1.

The browser failure-classification regression is an explicit opt-in gate: run `bun run test:terminal-browser` after provisioning the Playwright Chromium binary with `bunx playwright install chromium`. It is intentionally outside `test:self`, which remains browser-independent for fresh worktrees.

The frozen fixture corpus IDs are `utf8-split-alpha`, `control-split-sgr`, `combining-and-zwj`, `cjk-width`, `rtl-logical-order`, `soft-wrap-retention`, `alternate-screen`, `cursor-and-attributes`, `invalid-utf8`, and `query-reply`. Runtime matrix IDs are `pipe-launch-input-output-exit`, `pipe-capabilities-and-pause`, `pty-launch-input-output`, `pty-resize-and-eof`, `pty-cancellation`, and `descendant-cleanup`; engine matrix IDs are qualified as `<candidate>:<cell>`. Evidence paths are `tmp/terminal-probes/runtime.json` and `tmp/terminal-probes/engines.json`. Example command profiles are server-owned `shell`, `readonly-output`, and `diagnostic` profiles; clients select a profile identifier and never send an arbitrary executable command.
