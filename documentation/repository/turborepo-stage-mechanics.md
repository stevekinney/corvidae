# Turborepo stage mechanics

The detail behind AGENTS.md "Turborepo". The rules stay in AGENTS.md; this file holds the measurements, the per-suite worker-count notes, and the mechanics of the host lock, the install check, and cache keys.

- Every turbo run uses one cache and one task-concurrency cap, wrapped or not. **Cache:** Turborepo 2.10.13 keeps its local cache for every linked worktree in the main checkout's `.turbo/cache` (it prints "using shared worktree cache"), so a task any worktree has run replays in every other one, whether it ran through the wrapper or through a bare `bunx turbo`. Measured on 2026-11-10: an unwrapped `turbo run lint --filter=@lostgradient/cryptography` in a linked worktree wrote `5f461d88ea48999a` into `<main checkout>/.turbo/cache`, created no `.turbo/cache` in the worktree, and the next run, wrapped with `--shared`, reported `cache.status` `HIT`, source `LOCAL`. Nothing sets `TURBO_CACHE_DIR` or `cacheDir`: the wrapper used to point wrapped runs at `<git common dir>/turbo-cache`, which split the cache in two (wrapped runs never saw what a focused check had run, and the reverse). The dev container still sets its own `TURBO_CACHE_DIR` for its volume. **Cap:** `turbo.json` sets `"concurrency": "34%"`, which reaches every run, including a bare `bunx turbo`, `scripts/chef/focused-checks.ts`, and `scripts/affected-tests.ts`, where an environment variable set by a script cannot. Turborepo's precedence is measured, not documented: `--concurrency` beats `TURBO_CONCURRENCY`, which beats the `turbo.json` value, which beats the default of ten. So the wrapper's host-derived value below, and the serial slow lane's `--concurrency=1`, still win. The percentage is of logical processors and rounds down to at least one: 34% runs 4 tasks on a 12-core host (the wrapper's processor term gives the same) and 1 on a 4-vCPU runner. It cannot see memory, which the wrapper also bounds. The key adds nothing to a package task's hash, but the root `//#` tasks that take `$TURBO_DEFAULT$` as an input hash `turbo.json`, so adding it re-keyed `//#test:self` and `//#test:self:slow` once. `scripts/turbo-concurrency.integration.test.ts` runs eight timed tasks through each path and asserts the overlap.
- The wrapper also gives each stage two Turborepo defaults, unless the environment already sets them. `TURBO_CONCURRENCY` is one task per 8 GiB of memory and per three processors, whichever allows fewer: 4 on a 12-core, 32 GB host (2 for a `--shared` run) and 1 on a 4-vCPU, 16 GB runner (`min(1, 2)`). Measured on 2026-10-22 with a forced validate at four tasks on a 12-core, 32 GB host, the largest task peaked at 7.8 GB and all tasks together at 13.3 GB, while the load average reached 58: processors bind first, because a test task runs up to four Bun workers. A stage that passes `--concurrency` keeps its own value, as the serial slow lane does. `TURBO_SCM_BASE` is `origin/main`, the ref `scripts/affected-tests.ts` already merge-bases against, so `turbo run … --affected` and the test selection cannot disagree about the base; left unset, Turborepo picks its own. Turborepo reads it itself and only under `--affected`, so `turbo.json` neither declares it (it changes which tasks run, not a task's result) nor needs to. Nothing fetches the ref: a stale `origin/main` moves the base, and a missing one fails an `--affected` run, which names the unknown revision.

- `bun run validate` runs every workspace task except the applications' builds in one turbo run (`lint`, `typecheck`, `test:self`, `test:gate`, `test:browser-fixtures`), so they overlap under the concurrency cap instead of running stage by stage. The builds stay out because the playground's static export takes about five minutes and would otherwise set the floor for any change upstream of the playground; run `bun run build` when a change can affect a deployed application, and the Vercel project builds the playground for every commit its ignore step lets through; only the root checks before it and the serial slow lane, duration report, formatting, and audit after it stand alone. Large suites also run their files in parallel with `bun test --parallel=4` (Cinder, chat, editor, terminal, bureau, the playground, Weft's engine suite, and the root `test:self`). Weft's UI suite stays serial: under `--parallel`, Bun 1.4.2's workers load the default `bunfig.toml` preload on top of the one `--config` names, so the UI tests would run under the engine's preload. Bun's JavaScriptCore marking crash under `--isolate` (oven-sh/bun#29519, about 2 in 67 runs, both in `src/core/checkpoint-prune.test.ts`) is kept out of the gate rather than accepted (COR-1736): Weft's `test` script ignores that file in its `--parallel=4` phase and runs it in a second, serial `bun test` phase (`bun-test-junit.ts --report-name=checkpoint-prune`, with no `--parallel`, so no isolate workers), which honors `CORVIDAE_TEST_SELECTION` and writes its own JUnit report. Weft's coverage run stays one instrumented process with no `--parallel`, so it is already serial and counts that file: `readTestScriptPathIgnorePatterns` in `packages/weft/scripts/check-coverage.ts` drops from the mirrored exclusions any file a later phase of `test` runs, and a second coverage shard would have nothing to merge, because Bun's lcov carries per-file function totals (`FNF`/`FNH`) but no per-function records. `test:gate` runs each package's suite exactly once: a package with a `test:coverage` runs only that, since it runs the same files as its `test`, and every other package runs `test`. Interborough's coverage run measures its UI suite only, so its gate adds `test:host`, the first half of its `test`. A package's `test:coverage` therefore does not depend on its `test`, and no root script names both in one turbo run, because some tests write fixed fixture paths in the source tree and the two runs must never overlap; `scripts/task-cache.integration.test.ts` enforces both. In chat and terminal the gate's one run is the coverage run's serial, non-isolated pass; their isolated `--parallel=4` pass runs only in `bun run test`, because `bun run check` and `bun run validate` run `test:gate`. Coverage runs keep the worker count their Svelte floors were measured under (chat's uses Bun's default), because Bun's Svelte function coverage moves with it. Measure a suite at 4 workers several times before moving it, and keep worker counts at the cap: ten workers on this ten-core host made Cinder's scroll-settling tests fail deterministically.

## The host lock and the install check

The heavy root stages (`lint`, `typecheck`, `test`, `coverage`, and `build`) run through `scripts/run-exclusively.ts`, which holds one lock in the Git common directory that every worktree on the host shares. Concurrent `bun run validate` runs queue stage by stage instead of oversubscribing the machine, which otherwise times out unrelated tests at random. A waiting stage prints which process holds the lock, and a lock whose holder died is reclaimed. Focused `bunx turbo run … --filter` commands bypass the lock on purpose, so keep them focused. `bun run check` runs the wrapper with `--shared`: it skips the lock but keeps the install check and the Turborepo defaults, at half the usual concurrency, so several sessions can run it at once without oversubscribing the host. `scripts/workspace-contract.integration.test.ts` keeps each stage behind the lock. `TURBO_SCM_BASE`'s value is `turborepoAffectedBase` in `scripts/run-exclusively.ts`.

`scripts/run-exclusively.ts` runs `bun install --frozen-lockfile` (`bun run preflight`) before every command it wraps, so a `package.json` edit without a matching `bun install` fails `validate`, `check`, and every heavy stage before turbo runs, rather than running against a stale tree. Turbo hashes `bun.lock` but never `node_modules`, so a drifted install would otherwise cache a result under a key describing a toolchain it was not built with. The check deliberately sits outside the task graph: Turborepo always counts a task's own `package.json` among its inputs, so an install task that every task depended on re-keyed the whole repository on any root manifest edit. A bare `bunx turbo run` does not check the install, so run `bun install --frozen-lockfile` first when you have changed a manifest.

## Cache keys

A package-specific `<package>#<task>` entry replaces the generic task definition instead of merging with it, so any new override must restate `"dependsOn": ["transit"]`, which folds each upstream workspace into the task's key; `scripts/task-cache.integration.test.ts` enforces that every cacheable package task still reaches it.

Keep cache keys scoped to what a task can observe, so a change reruns only the packages it can affect. A manifest edit re-keys only that workspace and its dependents, and a lockfile change only the workspaces whose resolved dependencies it changes. The root package depends on no workspace except `@lostgradient/typescript`: turbo folds the files of every workspace the root depends on into the global hash, which would invalidate every cached task whenever one of them changed. Give root tooling that needs a workspace its own workspace, as `scripts/browser-fixtures` does. `globalDependencies` names individual configuration files, never directory globs; a package task that runs a root script lists that script in its own `inputs`. `scripts/task-cache.integration.test.ts` enforces all three.

## Test selection in `check`

`bun run check` lints and type-checks only the workspaces a change can affect (Turborepo's `--affected`, against the default branch, plus the root lint and root type-check) and runs only the test files it can reach (`bun scripts/affected-tests.ts run`, which drives the same Turborepo lanes). Selection never narrows a workspace the graph cannot attribute a change to: a changed `package.json`, `bunfig*.toml`, `tsconfig*.json`, preload or setup file, test-lane entrypoint, or data file no importer names selects its whole workspace, and a root configuration file or shared runner selects the whole repository. A workspace `check` selects whole runs its whole `test`, one selected in part a narrowed `test`, and it never runs `test:gate`, `test:coverage`, the build, or the isolated lanes (`test:slow`, `test:self:slow`) unless a changed file is itself a slow or integration test or `--isolated` is passed. The selection reaches Turborepo through `CORVIDAE_TEST_SELECTION`, declared in `turbo.json` for the narrowed tasks, so a cached result for one selection is never replayed for another. Rules and known limits: [test lanes and checks](test-lanes-and-checks.md#affected-test-selection).

## Type-check references

A consumer whose `tsconfig.json` lists a library's `tsconfig.source.json` under `references` reads the library's declarations (built into the ignored `.types/`) instead of type-checking the library's source again. It type-checks with `tsc -b tsconfig.json`, which rebuilds stale declarations first, and its `typecheck` task depends on its dependencies' `types` tasks, whose declarations it reads.
