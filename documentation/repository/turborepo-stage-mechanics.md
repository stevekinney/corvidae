# Turborepo stage mechanics

The detail behind AGENTS.md "Turborepo". The rules stay in AGENTS.md; this file holds the measurements and the per-suite worker-count notes.

- The wrapper also gives each stage three Turborepo defaults, unless the environment already sets them. `TURBO_CACHE_DIR` points at one cache in the Git common directory, so a task any worktree has run replays in every other one. `TURBO_CONCURRENCY` is one task per 8 GiB of memory and per three processors, whichever allows fewer. Measured on 2026-10-22 with a forced validate at four tasks on a 12-core, 32 GB host, the largest task peaked at 7.8 GB and all tasks together at 13.3 GB, while the load average reached 58: processors bind first, because a test task runs up to four Bun workers. A stage that passes `--concurrency` keeps its own value, as the serial slow lane does. `TURBO_SCM_BASE` is `origin/main`, the ref `scripts/affected-tests.ts` already merge-bases against, so `turbo run … --affected` and the test selection cannot disagree about the base; left unset, Turborepo picks its own. Turborepo reads it itself and only under `--affected`, so `turbo.json` neither declares it (it changes which tasks run, not a task's result) nor needs to. Nothing fetches the ref: a stale `origin/main` moves the base, and a missing one fails an `--affected` run, which names the unknown revision.

- `bun run validate` runs every workspace task except the applications' builds in one turbo run (`lint`, `typecheck`, `test:self`, `test:gate`, `test:browser-fixtures`), so they overlap under the concurrency cap instead of running stage by stage. The builds stay out because the playground's static export takes about five minutes and would otherwise set the floor for any change upstream of the playground; run `bun run build` when a change can affect a deployed application, and the Vercel project builds the playground for every commit its ignore step lets through; only the root checks before it and the serial slow lane, duration report, formatting, and audit after it stand alone. Large suites also run their files in parallel with `bun test --parallel=4` (Cinder, chat, editor, terminal, bureau, the playground, Weft's engine suite, and the root `test:self`). Weft's UI suite stays serial: under `--parallel`, Bun 1.4.2's workers load the default `bunfig.toml` preload on top of the one `--config` names, so the UI tests would run under the engine's preload. One known, rare failure comes with parallel Weft and is accepted: Bun's JavaScriptCore marking crash under `--isolate` (oven-sh/bun#29519, about 2 in 67 runs, both in `src/core/checkpoint-prune.test.ts`). `test:gate` runs each package's suite exactly once: a package with a `test:coverage` runs only that, since it runs the same files as its `test`, and every other package runs `test`. Interborough's coverage run measures its UI suite only, so its gate adds `test:host`, the first half of its `test`. A package's `test:coverage` therefore does not depend on its `test`, and no root script names both in one turbo run, because some tests write fixed fixture paths in the source tree and the two runs must never overlap; `scripts/task-cache.test.ts` enforces both. In chat and terminal the gate's one run is the coverage run's serial, non-isolated pass; their isolated `--parallel=4` pass runs only in `bun run test`, because `bun run check` and `bun run validate` run `test:gate`. Coverage runs keep the worker count their Svelte floors were measured under (chat's uses Bun's default), because Bun's Svelte function coverage moves with it. Measure a suite at 4 workers several times before moving it, and keep worker counts at the cap: ten workers on this ten-core host made Cinder's scroll-settling tests fail deterministically.
