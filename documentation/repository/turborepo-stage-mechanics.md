# Turborepo stage mechanics

The detail behind AGENTS.md "Turborepo". The rules stay in AGENTS.md; this file holds the measurements, the per-suite worker-count notes, and the mechanics of the test slot pool, the host lock, the install check, and cache keys.

- Every turbo run uses one cache and one task-concurrency cap, wrapped or not. **Cache:** Turborepo 2.10.13 keeps its local cache for every linked worktree in the main checkout's `.turbo/cache` (it prints "using shared worktree cache"), so a task any worktree has run replays in every other one, whether it ran through the wrapper or through a bare `bunx turbo`. Measured on 2026-11-10: an unwrapped `turbo run lint --filter=@lostgradient/cryptography` in a linked worktree wrote `5f461d88ea48999a` into `<main checkout>/.turbo/cache`, created no `.turbo/cache` in the worktree, and the next run, wrapped with `--shared`, reported `cache.status` `HIT`, source `LOCAL`. Nothing sets `TURBO_CACHE_DIR` or `cacheDir`: the wrapper used to point wrapped runs at `<git common dir>/turbo-cache`, which split the cache in two (wrapped runs never saw what a focused check had run, and the reverse). The dev container still sets its own `TURBO_CACHE_DIR` for its volume. **Cap:** `turbo.json` sets `"concurrency": "34%"`, which reaches every run, including a bare `bunx turbo`, `scripts/chef/focused-checks.ts`, and `scripts/affected-tests.ts`, where an environment variable set by a script cannot. Turborepo's precedence is measured, not documented: `--concurrency` beats `TURBO_CONCURRENCY`, which beats the `turbo.json` value, which beats the default of ten. So the wrapper's host-derived value below, and the serial slow lane's `--concurrency=1`, still win. The percentage is of logical processors and rounds down to at least one: 34% runs 4 tasks on a 12-core host (the wrapper's processor term gives the same) and 1 on a 4-vCPU runner. It cannot see memory, which the wrapper also bounds. Turborepo refuses to start a persistent task unless its concurrency exceeds the number of persistent tasks, so the root `dev` script, which runs one outside the wrapper, passes `--concurrency=2` (the flag beats the variable and `turbo.json`, so it also starts under the dev container's `TURBO_CONCURRENCY=1` and on a host of five or fewer processors); a test pins it. The key adds nothing to a package task's hash, but the root `//#` tasks that take `$TURBO_DEFAULT$` as an input hash `turbo.json`, so adding it re-keyed `//#test:self` and `//#test:self:slow` once. `scripts/turbo-concurrency.integration.test.ts` runs eight timed tasks through each path and asserts the overlap.
- The wrapper also gives each stage two Turborepo defaults, unless the environment already sets them. `TURBO_CONCURRENCY` is one task per 8 GiB of memory and per three processors, whichever allows fewer: 4 on a 12-core, 32 GB host (2 for a `--shared` run) and 1 on a 4-vCPU, 16 GB runner (`min(1, 2)`). Measured on 2026-10-22 with a forced validate at four tasks on a 12-core, 32 GB host, the largest task peaked at 7.8 GB and all tasks together at 13.3 GB, while the load average reached 58. A stage that passes `--concurrency` keeps its own value, as the serial slow lane does. `TURBO_SCM_BASE` is `origin/main`, the ref `scripts/affected-tests.ts` already merge-bases against, so `turbo run … --affected` and the test selection cannot disagree about the base; left unset, Turborepo picks its own. Turborepo reads it itself and only under `--affected`, so `turbo.json` neither declares it (it changes which tasks run, not a task's result) nor needs to. Nothing fetches the ref: a stale `origin/main` moves the base, and a missing one fails an `--affected` run, which names the unknown revision.

- `bun run validate` runs every workspace task except the applications' builds in one turbo run (`lint`, `typecheck`, `test:self`, `test`, `test:browser-fixtures`), so they overlap under the concurrency cap instead of running stage by stage. The builds stay out because the playground's static export takes about five minutes and would otherwise set the floor for any change upstream of the playground; run `bun run build` when a change can affect a deployed application, and the Vercel project builds the playground for every commit its ignore step lets through; only the root checks before it and the serial slow lane, formatting, and audit after it stand alone. Large suites also run their files in parallel with `bun test --parallel=4` (Cinder, chat, editor, terminal, bureau, the playground, Weft's engine suite, and the root `test:self`). Weft's UI suite stays serial: under `--parallel`, Bun 1.4.2's workers load the default `bunfig.toml` preload on top of the one `--config` names, so the UI tests would run under the engine's preload. Bun's JavaScriptCore marking crash under `--isolate` (oven-sh/bun#29519, about 2 in 67 runs, both in `src/core/checkpoint-prune.test.ts`) is kept out of the gate rather than accepted (COR-1736): Weft's `test` script ignores that file in its `--parallel=4` phase and runs it in a second, serial `bun test` phase (`bun-test-junit.ts --report-name=checkpoint-prune`, with no `--parallel`, so no isolate workers), which honors `CORVIDAE_TEST_SELECTION` and writes its own JUnit report. `validate` runs every package's `test` task, the same one `bun run check` runs, so a suite the per-pull-request checks just ran is a cache hit; no `test:gate` task or per-package gate override exists (COR-2370). Coverage is a separate report (`bun run coverage`) that no gate depends on: Weft's coverage run is one instrumented process with no `--parallel`, so it counts `src/core/checkpoint-prune.test.ts` with every other file, and chat's and terminal's use a serial, non-isolated pass while their isolated `--parallel=4` pass runs in `test`. Measure a suite at 4 workers several times before moving it, and keep worker counts at the cap: ten workers on this ten-core host made Cinder's scroll-settling tests fail deterministically.

## The test slot pool, the host lock, and the install check

Every `bun test` holds one slot per Bun worker in a pool of N slots in the Git common directory (`corvidae-test-slots`), which every worktree on the host shares, so the Bun test workers on the host never exceed N, however many sessions, worktrees and turbo tasks start at once (COR-2371). The wrappers (`scripts/bun-test.ts`, `bun-test-junit.ts`, `bun-test-selected.ts`) take the slots, and so do the three runners that start `bun test` themselves in the gate (the playground's `run-tests.ts`, Interborough's `run-coverage.ts`, `verify-curated-build.ts`); Cinder's memory canary and the coverage reproduction script are on-demand and stay outside. N is `max(4, min(processors − 2, floor(memory / 3 GiB)))`: 10 on a 12-core, 32 GB host and 4 on a 4-vCPU, 16 GB runner. `CORVIDAE_TEST_SLOTS` overrides it (declared pass-through in `turbo.json`), and a `--parallel` above N is clamped to N. Waiters take slots in arrival order. Bun's `--parallel` workers each lead a process group of their own and outlive a `bun test` leader killed with SIGKILL, so the wrapper records the leader's worker descendants (pid and start time) in its slots, every quarter second until all are seen and every second after. A slot is held while its run's wrapper, its `bun test` process group, or a recorded worker lives, judged by pid and start time; the wrapper terminates its recorded workers when it exits, and a reclaimer terminates those of a holder whose wrapper and group are gone, so a killed run frees its slots the moment its workers are gone. The remaining window: a worker started after the last refresh and before the leader is killed is not recorded. `bun scripts/bun-test-pool.ts status` prints the holders and the free slots. The pool replaced the load backoff, so nothing reads the load average. The mechanics and the outcome matrix are in the header of `scripts/bun-test-pool.ts` and its integration test.

The host lock serializes the heavy stages, `validate`, `validate:batch`, `lint`, `typecheck`, `build`, `release:check`, the Playwright suites and `harden`: three validates at once would need about 40 GB at 13.3 GB each. `tsc`, `svelte-check`, oxlint and Playwright start no Bun test worker, so the lock and the turbo cap bound them, not the pool. `test`, `test:slow`, `coverage` and `bun run check` run `--shared`, outside the lock at half concurrency, since the pool bounds their Bun workers; a locked `validate`'s tests still take slots, and a pool holder never waits on the lock. The lock is a directory in the Git common directory; a waiting stage prints which process holds it, and a lock whose holder died is reclaimed. Focused `bunx turbo run … --filter` commands bypass the lock, so keep them focused. Every stage, locked or `--shared`, keeps the install check and the Turborepo defaults. `scripts/workspace-contract.integration.test.ts` pins which stages take the lock. `TURBO_SCM_BASE`'s value is `turborepoAffectedBase` in `scripts/run-exclusively.ts`.

`scripts/run-exclusively.ts` runs `bun install --frozen-lockfile` (`bun run preflight`) before every command it wraps, so a `package.json` edit without a matching `bun install` fails `validate`, `check`, and every heavy stage before turbo runs, rather than running against a stale tree. Turbo hashes `bun.lock` but never `node_modules`, so a drifted install would otherwise cache a result under a key describing a toolchain it was not built with. The check deliberately sits outside the task graph: Turborepo always counts a task's own `package.json` among its inputs, so an install task that every task depended on re-keyed the whole repository on any root manifest edit. A bare `bunx turbo run` does not check the install, so run `bun install --frozen-lockfile` first when you have changed a manifest.

## Cache keys

A package-specific `<package>#<task>` entry replaces the generic task definition instead of merging with it, so any new override must restate `"dependsOn": ["transit"]`, which folds each upstream workspace into the task's key; `scripts/task-cache.integration.test.ts` enforces that every cacheable package task still reaches it.

Keep cache keys scoped to what a task can observe, so a change reruns only the packages it can affect. A manifest edit re-keys only that workspace and its dependents, and a lockfile change only the workspaces whose resolved dependencies it changes. The root package depends on no workspace except `@lostgradient/typescript`: turbo folds the files of every workspace the root depends on into the global hash, which would invalidate every cached task whenever one of them changed. Give root tooling that needs a workspace its own workspace, as `scripts/browser-fixtures` does. `globalDependencies` names individual configuration files, never directory globs; a package task that runs a root script lists that script in its own `inputs`. `scripts/task-cache.integration.test.ts` enforces all three.

## Test selection in `check`

`bun run check` lints and type-checks only the workspaces a change can affect (Turborepo's `--affected`, against the default branch, plus the root lint and root type-check) and runs only the test files it can reach (`bun scripts/affected-tests.ts run`, which drives the same Turborepo lanes). Selection never narrows a workspace the graph cannot attribute a change to: a changed `package.json`, `bunfig*.toml`, `tsconfig*.json`, preload or setup file, test-lane entrypoint, or data file no importer names selects its whole workspace, and a root configuration file or shared runner selects the whole repository. A workspace `check` selects whole runs its whole `test`, one selected in part a narrowed `test`, and it never runs `test:coverage`, the build, or the isolated lanes (`test:slow`, `test:self:slow`) unless a changed file is itself a slow or integration test or `--isolated` is passed. The selection reaches Turborepo through `CORVIDAE_TEST_SELECTION`, declared in `turbo.json` for the narrowed tasks, so a cached result for one selection is never replayed for another. Rules and known limits: [test lanes and checks](test-lanes-and-checks.md#affected-test-selection).

## Type-check references

A consumer whose `tsconfig.json` lists a library's `tsconfig.source.json` under `references` reads the library's declarations (built into the ignored `.types/`) instead of type-checking the library's source again. It type-checks with `tsc -b tsconfig.json`, which rebuilds stale declarations first, and its `typecheck` task depends on its dependencies' `types` tasks, whose declarations it reads.
