# Test lanes and documentation checks

The detail behind AGENTS.md "Commands". AGENTS.md states the rules every session needs; this file holds the rest of the rules, the mechanics, and the history.

The `test:benchmarks` commands are workspace-scoped (`bun run --filter=<workspace> test:benchmarks`, in each workspace that defines one), because each belongs to a single package and `bun run --filter` is how the root invokes one workspace's script. `bun run test` excludes what they run: a suite that asserts a wall-clock or memory target measures the machine as much as the code, and on a host running several agents at once those measurements swing far enough that they cannot gate validation. They record numbers on demand instead. Their targets are unchanged. A root lint guard, `scripts/check-wall-clock-assertions.ts`, fails the build when a `*.test.ts` or `*.test-support.ts` anywhere, `scripts/benchmarks/` included, asserts an upper bound on a duration or a rate it can derive from a timing reading.

`bun run release:check` is the on-demand sweep run before a backport (owner decision, 2026-11-10, COR-2370): the checks that protect the published surface, which no gate runs, because publishing is paused and a gate that fails on them blocks work that no one publishes. It runs the `release:check` task in every library and component (documentation coverage and documentation code blocks, below; one cacheable turbo task keyed on both checkers, the published surface, and the workspace's files, after its dependencies' `types`), then `bun run check:test-durations` (it reruns every `test` serially, so it is not cached). Interborough's `release:check` runs only the documentation coverage check. Markdown's import-graph test, which also resolves against `scripts/published-exports.json`, stays in Markdown's `test`, because it is a test. `check-inherited-key-reads.ts` stays in `lint`, because it checks correctness, not the published surface.

Every library and component documents its exported surface. Its `release:check` runs `scripts/check-documentation-coverage.ts`, which follows each entry in the workspace's `exports` map to the declaring symbol and fails when that symbol has no documentation comment. It also judges the own, non-private properties, methods, accessors, and constructor parameter properties of each exported interface, class, and object-literal type alias, and each overload signature, with the existing debt in each workspace's `documentation-member-allowlist.json` (a static member is keyed `<Symbol>.static.<member>`). It skips symbols another workspace declares and Svelte components, which Cinder's component metadata documents. `testing/*` is out of scope, and so are applications except where `--entries <glob>…` names the files to judge (a leading `!` excludes; keys use the file's path): Interborough's `release:check` does that for `src/host` and `src/lib`, minus test files. Exports that were undocumented when the check arrived are listed in each workspace's `documentation-coverage-allowlist.json`, data this check reads; a new undocumented export fails it, and so does an entry for an export that is now documented or gone, so the list only shrinks. Run `bun ../../scripts/check-documentation-coverage.ts --shrink` from the workspace to drop stale entries; `--seed` refuses to run once the file has entries. Document a new export rather than adding it to the list. Inherited members, enums, namespaces, and mapped, conditional, or `z.infer` aliases are not judged. Members that were undocumented when the member check arrived are listed as `<entry point> <Symbol>.<member>` in `documentation-member-allowlist.json`, which can only shrink the same way (`--shrink`); `--seed-members` writes the file once and refuses if it exists. Document a new member rather than adding it to the list.

Every library and component also type-checks the examples in its Markdown. Its `release:check` runs `scripts/check-documentation-code-blocks.ts`, which compiles each ` ```ts ` or ` ```typescript ` fence in the workspace's Markdown, outside dependencies and generated output, as its own module under the workspace's `tsconfig.json`. Fences in other languages, `svelte` included, are not checked. Imports of the workspace's own name resolve through its entry in `scripts/published-exports.json` when that entry is an exports map, so a guide cannot import what the mirror does not publish, and through its `package.json` `exports` otherwise; other workspaces resolve as they do for any consumer. One fence attribute may follow the language: `file=<name>.ts` names a block so a later block in the same document can import it relatively. Any other attribute fails, and no attribute skips a block: every TypeScript example is checked. Give an example the context it needs instead, through imports, short `declare` lines for values the reader supplies, or an earlier `file=` block. Write a signature as code that references the real export, so drift in the export breaks it, and type a third-party client the workspace does not install against a small structural interface the package's real API must accept.

Correctness assertions never move with them. Weft keeps its benchmark directory's unit tests in the default suite, and Markdown's pathological-document and diff-identity checks stayed behind in `src/` when its timing assertions left. Every package names its benchmarks `*.bench.ts` under `scripts/benchmarks/`, which Bun's default discovery skips on its own, so no `test` script keeps a list of path-ignores (Weft's was one until COR-1739). Weft's `test:benchmarks` is `scripts/run-benchmarks.ts`, which globs `scripts/benchmarks/*.bench.ts`; the other packages list their files. The rule is the same everywhere: a target that depends on host load belongs outside the gate, and the correctness it was bundled with belongs inside it.

A test that does seconds of real work (spawning processes, bundling, git, ts-morph, instrumented loops) is a different class: its assertion is correctness, so it stays in the gate, but it contends with every other test for the host, so it runs serially (COR-1499). Such a test either becomes fast by removing redundant work, or moves to a `*.slow.test.ts` file. (It once also sat near Bun's 5-second per-test limit and host contention pushed it over; the shared test timeout below ended that.) A test file that starts a process anywhere (a real `git`, `tsc`, a crash child, a server subprocess, a PostgreSQL server), directly or through a helper, is the other isolated class: it is a `*.integration.test.ts` file, because a process's boot and scheduling depend on how loaded the host is. `scripts/check-test-process-spawns.ts` fails `lint:root` on a `*.test.ts` file that does, except where a `// spawn-free:` marker names the stub a test injects. A workspace's `test` ignores both suffixes (`--path-ignore-patterns='**/*.slow.test.ts' --path-ignore-patterns='**/*.integration.test.ts'`, or the playground runner's own lane split) and its `test:slow` runs only them (`bun-test-selected.ts … .slow.test.ts .integration.test.ts`; Interborough runs its host and UI files in two invocations, as its fast lane does); the root package's lanes are `test:self` and `test:self:slow`. `bun run validate` runs `bun run test:slow` with `--concurrency=1` after the fast phase, so nothing leaves the gate and no timeout is raised. A workspace that holds either kind must define both scripts, and `scripts/check-test-durations.test.ts` fails `test:self` (inside `validate`) otherwise. Integration files stay in `test:coverage`, the on-demand coverage report, so it counts what they exercise.

Each workspace's fast `test` runs through `scripts/bun-test-junit.ts` (the playground through `scripts/run-tests.ts`), which writes JUnit XML to `test-output/junit/`. A per-test time budget depends on host load, which AGENTS.md keeps out of the gate, so it is enforced on demand, the way `test:benchmarks` is: `bun run check:test-durations` fails any fast-lane test that took longer than 2 s unless `scripts/test-duration-allowlist.json` lists it, and fails an allowlisted entry that is gone or took under 1 s, so the list can only shrink. The script first reruns every report-writing task with `bun run measure:test-durations` (`turbo run test:self test test:browser-fixtures --force`, covering the root reports and each package's `test`), because turbo replays cached reports; run it on a quiet host. It is a step of `bun run release:check` and `validate` does not run it; every finding fails it. The lane wiring half (a workspace bypassing the wrapper, or holding slow or integration files without their lane scripts) does not need a measurement, so `scripts/check-test-durations.test.ts` asserts it for the real workspaces in `test:self`, which `validate` runs. `bun scripts/check-test-durations.ts --shrink` drops stale entries, and `--seed` refuses to run once the file has entries. Adding an entry is a reviewed edit and needs a tracking issue. Process spawns inside test bodies are a separate rule with its own guard (COR-1507); the duration check also sees the in-process work that guard cannot, such as ts-morph analysis and per-byte loops, and a test that a spawn fix makes fast leaves the allowlist through the stale-entry rule. Never raise the budget.

Load-proof deadlines. Tests that can flake under load cannot be in the critical path, and the ways load flips a test are all deadlines or races: a Bun per-test timeout, a Testing Library `asyncUtilTimeout`, a budget passed to a wait helper, a count of turns, a wall-clock deadline, a sleep that stands in for a signal, a timer raced against work. Bun 1.4 offers one dependable lever for its own timeout, `--timeout`: `[test] timeout` in `bunfig.toml` is not read, and `setDefaultTimeout` in a preload applies to the first test file of a run and then resets. `scripts/test-deadlines.ts` therefore fixes `TEST_TIMEOUT_MILLISECONDS` at twice the hang guard, `scripts/bun-test.ts` and `scripts/bun-test-junit.ts` pass it, and the guard rejects a script, or a script's spawn, that starts `bun test` without it. Testing Library's default comes from `configureAsyncUtilityDeadline`, which each UI preload calls. A genuinely broken wait now fails after the hang guard rather than after a second (about two minutes of polling), which is the intended trade, not a regression. The rules and their blind spots are in the header of `scripts/check-load-sensitive-deadlines.ts`; the two marker comments it accepts (`hang-guard-self-test` and `load-proof`) each need a reason of at least twenty characters and cover one statement. The same guard reads the single-turn yield: `sleepForTesting(n)` waits one scheduler turn under real timers whatever `n` is, so it, `setImmediate`, `setTimeout(r, 0)` and `Bun.sleep(0)` must either be followed by nothing load-dependent (a marker with the reason) or be replaced by a wait on the state or event; a same-file helper that is one of them carries the marker at its definition. Calls to the exported one-turn helpers (`yieldToEventLoop`, `yieldToPortableEventLoop`, `yieldEventLoopTurn`) are resolved through the file's imports and read at every call exactly as a same-file yield is, so there is no allowlist; where only microtasks are pending, `drainMicrotasks` (`@lostgradient/testing/fake-timers`, Operative's `src/testing/drain-microtasks.test-support.ts`) is a drain that cannot be too short on a loaded host. A Bun child that a test starts runs with `--no-install` (`withoutAutoInstall` in the hang guard), so a fixture written outside the workspace fails to resolve a package instead of installing it from the network. The browser suite follows the same rule: `test:browser` runs outside `check` and `validate`, but Interborough's and `scripts/browser-fixtures`' `playwright.config.ts` take `expect.timeout` from `HANG_GUARD_MILLISECONDS` and the per-test `timeout` from `TEST_TIMEOUT_MILLISECONDS`, and `scripts/check-load-sensitive-deadlines.ts` reads those configurations (`playwright-configuration`) and Interborough's specs (`playwright-timeout`), so a spec cannot name a shorter `timeout` on a matcher, poll, `toPass`, `waitFor*` or action, or in `test.setTimeout` or `describe.configure`, without `// hang-guard-self-test:` or `// load-proof:` and a reason.

## Test tiers and the hardening pass

The detail behind AGENTS.md "Test tiers". Day-to-day work runs the quick tier, `bun run check`, whose tests are in-process only (no child process, no out-of-process service), so host load cannot fail them short of the hang guard. The full tier is `bun run validate` and the batch validate, which add the isolated lane, the browser fixtures, and (batch only) the Playwright suite's `chromium` project. Every suite runs through the same `test` task `check` runs, so a suite `check` just ran is a cache hit in `validate`. Coverage is a report, `bun run coverage`, which prints each workspace's numbers and never fails on a floor (owner decision, 2026-11-10, reversing the 2026-11-09 decision to judge floors in `validate`); it fails only when a test fails. `bun run release:check` is the pre-backport sweep, outside both tiers.

`bun run harden` is the battle-hardening pass: it runs the isolated lanes three times, uncached, beside busy-loop load generators on half the processors, then the fast lanes once under the same load, and records each round in `tmp/harden/`. It never runs per pull request; a coordinator schedules it ([program runs](../../.agents/skills/chef/references/program-runs.md)).

Flaky tests: a test that fails in the full tier or in `harden` is never rerun until green, retried, or allowlisted. Compare it against the base with `bun scripts/chef/gate-run.ts control`; a test that fails on the base too, or passes on a second run of the same head, is a flake, and its fix (the mechanism, never a longer deadline) is a COR issue. Because the quick tier holds no isolated test, a flake there never blocks day-to-day work.

## Gate tiers and main CI

The mechanics behind AGENTS.md "Gate on local checks".

`bun run check` is the quick tier, the on-demand local reading of what a change can reach: format, the root lint and type-check, lint and type-check of the affected workspaces, and the fast-lane tests the change reaches, with no coverage run and no isolated lane (AGENTS.md "Test tiers"). It runs `--shared`, outside the host lock that serializes the heavy stages, at half concurrency, and nothing requires it before a merge. Its Bun test workers, like every lane's, locked or not, take slots of the host-wide test slot pool ([mechanics](turborepo-stage-mechanics.md#the-test-slot-pool-the-host-lock-and-the-install-check)).

Delivery runs no gate and never merges `main` into the branch. `scripts/chef/deliver.ts` merges an accepted pull request when GitHub reports no conflict with its base, every review thread is resolved (read with the paginated `review-threads.ts` read), and its head is the head pinned at acceptance, with the merge itself pinned to that head. A real conflict is reported, and the worker resolves it and returns a new head. Review threads are all answered within the three-round cap, and no review thread names a serious defect. Do not wait for bots to go quiet.

GitHub Actions is the full tier and the source of `main`'s health. `merge-gate.ts` and `direct-merge.ts` read the latest completed `main.yml` run on `main` (`gh run list --workflow main.yml --branch main --status completed`, newest conclusive run: a `cancelled` run, which a newer push replaces, says nothing) and warn in their report while it is red; they never refuse on it, so a red `main` is the coordinator's to read and fix forward, not a lock on every merge. When GitHub cannot be read the report says `main health unknown` and the merge proceeds. A fix for a red `main` is declared with `--fixes-main`. The root Playwright suites (`bun run test:browser:chromium`, `bun run test:browser:interborough`) are not part of `validate` and not run by `main.yml`; nothing gates them today, so a change to a browser fixture or an end-to-end spec is not checked by CI. Interborough's suite runs on a free block of seven ports and never reuses a server another checkout left listening (`applications/interborough/scripts/run-gated-browser-suite.ts`).

An exception validate (a one-way door, the lock or concurrency infrastructure, `turbo.json` and the root scripts) is `gh workflow run main.yml --ref <branch>`: the `workflow_dispatch` trigger of the `main` workflow runs every job of `validate` on the branch. A dispatched run takes a concurrency group of its own (per branch), so it neither waits behind nor replaces a pending run from a push to `main`.

The `main` GitHub Actions workflow (`.github/workflows/main.yml`) shares one concurrency group across every push, without cancelling a run in progress, so GitHub keeps at most one pending run and replaces it with the newest commit (COR-2396). A `main` run therefore covers every push since the previous run, and a red run names a range of commits, not one.

The pull-request workflow (`.github/workflows/pull-request.yml`) runs the affected fast lanes with `bun scripts/affected-tests.ts run --isolated`, so a change that reaches a slow or integration test runs that test before merge, and a workflow-only change selects no test. A failing affected test turns that check red; the only `continue-on-error` left in the workflows is on the duration report below and its artifact uploads. Its lint and type-check, and the `main` workflow's, run with `--concurrency=4` on the 4-vCPU runner, because the root `turbo.json` cap of 34% is one task there; the test shards stay at one task, since the test pool (`scripts/bun-test-pool.ts`) already sizes itself to 4 slots on such a host. Each `main` test shard uploads its JUnit reports, and a final job downloads them and runs `bun scripts/check-test-durations.ts` as a report: the job is `continue-on-error`, because a duration on a shared runner never turns the run red (`bun run release:check` enforces durations), and the output names a shard that left no report. A failed report upload is tolerated: each upload step is `continue-on-error`, so an artifact-service error never turns a test shard red, and the missing shard shows in that output.

## Affected test selection

`bun run check` runs only the test files a change can reach, where it once ran every test in each affected workspace and its dependents (`--affected` works per package, so a one-file change in Weft reran Weft, Bureau, Interborough, and the rest). The selector is `scripts/affected-tests.ts`, with `affected-tests-graph.ts` (the import graph), `affected-tests-selection.ts` (the rules), and `affected-tests-manifest.ts` (the hand-off to the runners). `validate` is unchanged and runs everything. `check` is the quick tier (AGENTS.md "Test tiers"): it never runs a coverage task or the isolated lanes (`test:slow`, `test:self:slow`) unless a changed file is itself a slow or integration test or `--isolated` is passed.

The changed set is every file that differs between `git merge-base origin/main HEAD` and the working tree, including staged, unstaged, and untracked files that Git does not ignore. A rename counts as a deletion and an addition, so the old path still reaches the tests whose importers name it.

The graph covers the repository's TypeScript, JavaScript, Svelte, and CSS. Specifiers come from `Bun.Transpiler#scanImports`, which drops type-only imports (they leave no runtime edge, but they do mark a file as used); a Svelte file contributes the imports of every `<script>` block and its CSS `@import`s. Relative specifiers resolve with TypeScript's extension and `index` rules. `@lostgradient/*`, `armorer`, and `conversationalist` specifiers resolve through the target workspace's `exports` map to a source file, and one the map does not name resolves to that workspace's `package.json`. There are no `tsconfig` `paths` or `package.json` `imports` outside test fixtures, so neither is read. String literals in code that look like paths to files (`'../fixtures/case.json'`, `new URL('./x.ts', import.meta.url)`) count as edges when they resolve against the file's directory, its workspace root, or the repository root, which attributes data and scripts a test reads at run time. A template literal anchored to the file (`${import.meta.dir}/chat.css`, `${import.meta.dirname}/…`) counts the same way, and one with a run-time part (`${dir}/${name}.css`) attaches the file to every changed file of that extension in its workspace. A changed data file is attributed through every route at once: an importer does not stop a test that also reads it by name from running. Comments never make an edge.

A test file runs when it is changed, or when its transitive imports reach a changed file. Everything the graph cannot attribute widens the selection and never narrows it:

- **A workspace's own configuration:** a changed `package.json` selects the workspace and seeds every code file in it, so dependents that import it run too. A changed `bunfig*.toml` or `tsconfig*.json` selects the workspace.
- **Root configuration:** a root `package.json`, `bun.lock`, `bunfig.toml`, `turbo.json`, `tsconfig.json`, or `.bun-version` selects the whole repository.
- **Test preloads and setup files:** the files a workspace's `bunfig*.toml` (or a `--preload` flag in a lane script) names, and everything they import, select that workspace.
- **Lane entrypoints:** a file a lane script (`test`, `test:slow`, `test:coverage`, `test:self`, `test:browser-fixtures`) runs, and what it imports from `scripts/` directories, selects its workspace, or the whole repository when another workspace runs it (`scripts/bun-test-junit.ts`, `scripts/affected-tests.ts` and what they import).
- **Data no importer or reference names:** a changed JSON, CSS, fixture, or other file that nothing imports and no literal path names selects its workspace, or the whole repository when it sits outside every workspace. Unattributed documentation (`.md`, `.mdx`, `.txt`, images) outside a fixtures or tests directory instead reaches only the code below that reads the tree. A `.snap` file selects the test it belongs to. The one exception is `.github/`: its workflows and templates run only on GitHub, so a changed file there selects nothing unless a test names it, in which case that test runs.
- **A code file nothing imports or names:** an entrypoint run by a process the graph cannot see selects its workspace.
- **Code that reads the tree or loads code the graph cannot see:** a test or tooling file that globs or lists directories is selected by any change in its workspace; one that does `import(variable)`, or any file that calls `Bun.build`, is selected by a change in its workspace or any workspace it declares as a dependency; one that uses the shared workspace list and anchors to its own checkout (`import.meta.dir`) is selected by any change at all. Library source that calls `import(variable)` or lists directories on behalf of its callers does not count, because the tests that call it name the paths it reads.

Known limits, which only `validate` closes: a test that scans the tree with a glob built at run time inside library source, or that spawns a process which reads a file nothing names, is attributed only through the rules above; and a static import graph is coarse around barrels, so a change deep in a workspace's core still reaches most tests that import its entry.

A selection in which a workspace has every test file reached, or a fallback fired for it, is selected whole. Whole workspaces run their whole `test`. A workspace selected in part runs `test` with `CORVIDAE_TEST_SELECTION` set to the digest of the selection manifest (`tmp/affected-tests/<digest>.json`), and a workspace with nothing selected runs nothing. Neither measures coverage, which is a report (`bun run coverage`) with no floor.

The runners narrow themselves. `scripts/bun-test-junit.ts` and the new `scripts/bun-test-selected.ts` (which the `test:slow` scripts and `test:self:slow` run through) intersect the manifest with the roots and `--path-ignore-patterns` on their own command line and with the `bunfig` `pathIgnorePatterns` in force, keep every other flag, and pass `bun test` explicit files. They never widen a lane, so Interborough's host and UI invocations keep their own configuration, and a lane with nothing left exits 0 without starting `bun test`. The playground's `scripts/run-tests.ts` filters its discovered files the same way before it plans processes. A digest that does not match its manifest fails the run.

Turborepo keeps its role. The task inputs name every root script the runners execute or import (`bun-test-junit.ts`, `bun-test-selected.ts`, and what they import), and `scripts/task-cache.integration.test.ts` fails when a package task runs a root script, or one it imports, that its inputs omit. `turbo.json` declares `CORVIDAE_TEST_SELECTION` in the `env` of `test`, `test:slow`, the root `test:self`, `test:self:slow`, and `test:browser-fixtures`, and in each package-specific override of them: strict environment mode passes a task only the variables it declares, and hashes them, so a result cached for one selection is never replayed for another. `test:coverage` never runs narrowed, does not declare it, and keeps its cache key. The browser fixtures' lane also runs when their workspace or anything it depends on changed, because it verifies the curated build as well as running tests.

`bun scripts/affected-tests.ts --explain` prints, per workspace, each selected file with its reason: `changed`, `imports <chain>` back to a changed file, or `fallback: <rule>`. `--changed <path>...` replaces the Git-derived changed set, `--json` prints the selection for tools, and `--base <rev>` replaces `origin/main`. `scripts/affected-tests.test.ts` holds a unit test for every rule on synthetic trees.

## A crashed `--parallel` worker

When a `bun test --parallel` worker process dies, Bun records the file it was running as a one-test suite named `(worker crashed)` and the lane fails with no failing assertion. `scripts/bun-test-junit.ts` and the playground runner now read the JUnit report afterwards, print the file, and list any Bun crash report macOS wrote during the run (`~/Library/Logs/DiagnosticReports/bun-*.ips`). The wrapper never retries and never changes the exit code.

The incident that prompted this (2026-10-27, Bureau's fast lane failing on `session-input-crash-recovery.integration.test.ts` at host load 35–40, passing alone and on retry) most likely is a Bun 1.4.2 runtime trap rather than a signal the test sent: `session-input-crash-child.ts` kills only its own pid. Eleven Bun crash reports in `~/Library/Logs/DiagnosticReports` from 2026-10-19 to 2026-10-27, including one captured at 15:29:17 on the incident day, share one signature: `EXC_BREAKPOINT` on the main thread at image offset `0x2b09f2c` of the installed binary (UUID `4C4C447C-5555-3144-A138-DBD9C49417A3`). Disassembling that offset shows a `brk` beside the message "Do not call JSObject::realm() on objects with realmless structures (e.g., WebAssembly GC objects)", and the frames above it run through `bun_jsc::event_loop` and its promise handling. The crashed process's parent is a `bun` process and its pid is within a few of the parent's, which is how a `bun test --parallel` coordinator launches workers; on 2026-10-23 two such siblings crashed together. The report does not say which test file was running, so the link to the incident's file is circumstantial.

No local reproduction exists: two Bureau crash-lane runs under synthetic load above 100, and 25 runs of a minimal module-scope spawn-and-SIGKILL repro at `--parallel=4`, all passed. Treat a lane that fails with `(worker crashed)` and a matching report as a Bun bug to report upstream with the `.ips` file, not as a flaky test.
