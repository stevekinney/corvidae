# Host admission for heavy work outside `bun test`

Two controls bound the work this repository puts on a development host. The host lock (`scripts/run-exclusively.ts`) serializes the heavy root stages, and the test slot pool (`scripts/bun-test-pool.ts`) bounds the Bun test workers on the host, whoever starts them. On 2026-11-11, with both in place, the 12-core, 32 GB host still ran at 0.3% idle CPU, with 34% system time and 11 GB of memory compressed. What it was running then: the Docker VM of a `corvidae-baselines-*` container at 137%, `chrome-headless-shell` at 118%, and several Cinder `preview-shard.ts` processes at 30 to 76% each (COR-2398). This document lists the entry points that start a browser, a container or a fan-out of worker processes outside `bun test` and outside the locked stages, and what admits each one.

## Admission

`scripts/host-slots.ts` admits the work in the table through the test slot pool, with no new mechanism. A run takes one slot for each process it keeps busy at once, from the same pool and through the same arrival-order queue as every `bun test` worker, so the pool bounds the two together. The pool's size, its admission rule for `bun test` and the host lock are unchanged.

- `withHostSlots(count, run)` holds `count` slots while an in-process `run` resolves, and tells `run` how many it holds. This process is the holder. If it is killed outright, the next waiter reclaims its slots, judged by pid and start time. A holder that leads its own process group (its pid is its process group id) also records that group, so its slots stay held while anything in the group, such as a browser or a shard it started, lives.
- `runWithHostSlots(count, argv)` and `bun scripts/host-slots.ts --slots=<n> -- <command>` run a command in a process group of their own while holding the slots, and record the group in them, as a pooled `bun test` does. A wrapper killed outright keeps its slots for as long as anything in the group lives, and frees them once the group is gone.
- A run started inside one that holds slots finds the holder's token in `CORVIDAE_TEST_SLOTS_TOKEN` and runs inside the holder's slots: the pool's nested-run rule. A command run under host slots gets the token, so a `bun test` or a wrapper it starts runs inside them too.
- A request above the pool's size is clamped to the pool, and the run is told so. Where there is no Git checkout, as inside the renderer container, the run warns and goes ahead without a slot.
- A slot holder never waits on the host lock, so the pool and the lock cannot deadlock. No wrapped command starts a locked stage. A lock holder may wait on slots: `test:browser:interborough` holds the lock and its gated suite then takes a slot.

What each entry point holds now:

- **Covered now.** `test:browser:update:docker` and `test:browser:visual:docker` hold 4 slots (`CONTAINER_CPUS`) through `scripts/host-slots.ts`, from `docker build` until the container exits. `docker run` gets `--cpus` of 4, or of the Docker VM's processor count when that is smaller. The slots are taken in `package.json`, not in the scripts themselves, because the browser-fixtures test task's cache inputs list every root file its scripts import, and that list lives in `turbo.json`, which this change leaves alone.
- **Covered now.** The Cinder design-system build holds 4 slots (`SHARD_COUNT`) while its preview shards run, and runs no more shards than it was granted. It then holds 1 slot for each of its three Chromium phases.
- **Covered now.** `bun run capture:chat-stress`, `design-review-capture.ts`, `design-review-render-boards.ts` and `test:terminal-browser` each hold 1 slot for the run, since each runs one browser at a time.
- **Covered now (COR-2404).** Interborough's `run-gated-browser-suite.ts` holds 1 slot however it is started: directly, as an agent runs one end-to-end spec, or under the host lock from `test:browser:interborough`. It and `design-review-capture.ts` run Playwright in a process group of their own and record it in the slot, so the slot stays held while Playwright or its web server lives.
- **Covered now.** Root `test:browser` (and so `test:browser:visual`), `test:browser:preview` and `test:browser:terminal` hold 4 slots, and pin Playwright to `--workers=4`. In the renderer container they run without a slot, inside its `--cpus` limit.
- **Covered now.** The `test:browser` scripts of Interborough, the playground and the terminal example hold 1 slot each, matching their `workers: 1`.
- **Already covered.** The locked root stages hold the host lock, and Interborough's UI shards hold test slots. So do the lifecycle tests that drive `run-linux-lifecycle.ts` and `check-static-playground.ts`.
- **Not covered.** The playground's `test:production`, run by hand, is not covered: its `fullyParallel` run uses Playwright's default worker count, so holding a fixed number of slots needs the worker count pinned inside the gate the lifecycle tests share.
- **Not covered.** `memory-canary.ts` starts `bun test` directly, because it reads the child's peak memory from `resourceUsage()`. Routing it through the pool's runner means restructuring how it measures.
- **Not covered.** The playground measurement scripts, the terminal engine probes, the Weft benchmarks, the PTY stress script, the A2A test kits and `dev-container.ts` are research and diagnosis tools, run by hand one at a time. They are left for a change that has a reason to touch them.
- **Not covered.** `test-installed-release-browser.ts` runs on a CI runner, which has no other session to share with.

`scripts/host-slots.integration.test.ts` proves the behavior:

- A second holder waits while the first holds the pool, and proceeds when it releases.
- A nested run does not acquire again.
- A token that names no live holder does not bypass the pool.
- A holder killed outright has its slots reclaimed.
- A killed wrapper keeps its slots while its command group lives.
- Every Playwright script outside the host lock takes host slots.

## Still outside admission

- The browser-fixtures entry points run directly rather than through their `package.json` scripts: `update-snapshots-docker.ts`, `run-browser-docker.ts`, `capture-chat-stress.ts` and `run-terminal-browser.ts`. Each takes no slot that way. Moving the slots into the scripts means adding `scripts/host-slots.ts` to the inputs of the `//#test:browser-fixtures` task in `turbo.json`, which `scripts/task-cache.integration.test.ts` requires of any root file they import.
- A holder that only belongs to a group, as a script run from a non-interactive shell or from another process does, records no group, because that group may be a parent's and outlive the work for ever. If it is killed outright, its slots are reclaimed with its pid while a Playwright process or shard it started may still run. The Cinder design-system build and `design-review-render-boards.ts` are in-process holders of this kind unless started as a group leader. `design-review-capture.ts` and `run-gated-browser-suite.ts` record their Playwright group in the slot.
- Work started by hand without the scripts: a bare `bunx playwright test`, `docker run` or `chromium` invocation takes no slot. Neither does any tool outside this repository: another repository's tests, a browser the developer uses, Spotlight and `fseventsd` indexing the worktrees.
- Work inside a container belongs to the Docker VM, which the slots bound only through `--cpus` on the renderer's `docker run`. A wrapper killed outright frees its slots once its own process is gone, while the container keeps running until `docker run --rm` ends or someone runs `docker kill`. A capture killed outright likewise frees its slot, while a browser it launched exits only when its pipe to the capture closes.
- A slot stands for one busy process, not one processor. The design-system build peaked at 657% while holding at most four slots, so a phase of it uses more processors than it holds; the sampler did not say which phase. The pool's size, left at processors minus two, absorbs part of that.
- Nothing times out a host-slot holder whose session lives. A Docker renderer run holds 4 of the pool's slots for its whole length, and a hung capture keeps its slot until someone ends it. Waiters, `bun test` runs among them, wait that long. A run whose session is gone ends after the hang guard (see [Orphaned runs](#orphaned-runs-and-finished-worktrees)).
- In update mode, the renderer container starts Playwright directly (`update-snapshots.ts`) with its default worker count, half the Docker VM's processors, under the 4-processor `--cpus` limit. Only the visual mode runs through `test:browser`, which pins 4 workers.
- The memory check bounds when a stage starts, not what it uses once running. The pool's size allows for 3 GiB per slot, but a browser suite's workers and its web server can use more, and memory taken by tools outside the repository after a stage starts is not seen.

## Memory

On 2026-11-11 the host starved on memory with both controls in place: swap 14.2 of 15.4 GB in use, `fseventsd` holding about 7.5 GB, and 23 chromium tests that pass alone in 30 seconds timed out together (COR-2404). The lock and the pool count stages and processes, so a heavy stage now also reads the host's memory before it starts (`awaitMemory` in `scripts/run-exclusively.ts`).

- **What is read.** On macOS, `sysctl` gives the kernel's pressure level (`kern.memorystatus_vm_pressure_level`, whose values are the dispatch levels of `<dispatch/source.h>`: 1 normal, 2 warning, 4 critical), the share of memory it counts free (`kern.memorystatus_level`), swap and the memory size. On Linux, `/proc/meminfo` gives `MemAvailable` and swap. `bun scripts/bun-test-pool.ts status` prints the reading.
- **What blocks a start.** A warning or critical pressure level, or less than 4 GiB free (`minimumAvailableMemory`). Swap is reported but never judged: macOS keeps swap in use long after pressure ends, and on 2026-11-12 this host had 10.6 of 12.3 GB of swap in use at normal pressure with 59% free. The 4 GiB floor is a first estimate; the COR-2404 load sample is what tunes it.
- **Waiting and refusing.** A short host makes the stage wait, reading again every 5 seconds and printing the measurement when it starts waiting and once a minute after. After 10 minutes of polls it refuses with exit code 75 (`EX_TEMPFAIL`) and a message naming the measurement. It never starts and then fails for starvation. A host whose memory cannot be read starts every stage.
- **Where.** Every `scripts/run-exclusively.ts` stage, locked or `--shared`, once it holds the lock: `validate`, `validate:batch`, `test:slow`, `check` and the rest. `withHostSlots`, once it holds its slots: every browser suite and capture above. `bun scripts/affected-tests.ts run --isolated`, before its first isolated lane.
- **One admission per script.** A script with several host-slot phases, or one that exits with a code, reads once through `withMemoryAdmission` in `scripts/host-slots.ts`: the Cinder design-system build, `design-review-capture.ts`, `design-review-render-boards.ts`, `run-gated-browser-suite.ts` and `runWithHostSlots` (so `bun scripts/host-slots.ts`). It checks memory before any work starts, and a refusal exits 75 with no phase started, where it used to surface as an uncaught error and exit 1. It then marks the environment admitted, so each `withHostSlots` phase inside it, and every child, skips the read. By default the mark goes on `process.env`; a caller that passes an environment gets a marked copy and its own is left as it was.
- **CI and tests.** On CI (`CI=true`) a stage never waits or refuses: it reads once, reports the reading and starts, because a runner is not shared. A test that passes no `readMemory` is admitted without reading, so no test reads the host's real memory by accident.
- **Nesting.** An admitted stage sets `CORVIDAE_MEMORY_ADMITTED` for what it starts (Turborepo passes it through), and a run nested in host slots is admitted with its holder, so a stage inside `validate` never waits on memory its own parent is using. Setting `CORVIDAE_MEMORY_ADMITTED=1` by hand skips the check.

## Runaway test runs

On 2026-11-12 a `bun test` over an unbounded Svelte render loop grew to 144 GB in 13 minutes and pushed a 64 GB host to 46 GB of swap; the same test, run again in another worktree that afternoon, reached 86 GB in three and a half minutes. Admission could not have refused it, since the host was healthy when it started, and the per-test deadline never fired, because it runs inside the test process and a synchronous loop never returns to the event loop. So the wrapper that starts every `bun test` (`runPooledBunTest`) watches its run from outside, once a second (`scripts/test-watchdog.ts`).

- **The memory ceiling.** Each sample adds up the `bun test` leader, its descendants and its process group. A run above the ceiling is killed, by process group and by pid, and exits 70 after one line naming the test files, the memory reached and the ceiling. The default is 24 GiB (`defaultMemoryCeilingBytes`), a little over twice the heaviest lane: measured on 2026-11-12, the UI half of Interborough's coverage run, one instrumented process, peaked at 10.4 GiB, Cinder's full suite at 9.4 GiB and chat's at 6.0 GiB on four workers each, Interborough's host lane at 4.3 GiB and each of its UI shards at 2.8 to 3.6 GiB, no slow lane above 4.9 GiB. `CORVIDAE_TEST_MEMORY_CEILING_MEGABYTES` overrides it (declared pass-through in `turbo.json`).
- **What is read.** On macOS, each process's physical footprint from `proc_pid_rusage` through `bun:ffi`, the number Activity Monitor shows, in about 30 microseconds a process. Resident memory is the wrong number: the kernel compresses a runaway's pages, and the second run above showed 11.7 GB from `ps -o rss` against a footprint of 86 GB. `top -l 1` reports the footprint too, but takes over four seconds. On Linux, `VmRSS` plus `VmSwap` from `/proc/<pid>/status`. A process whose footprint cannot be read counts as its resident memory.
- **The stall guard.** A lane that writes a JUnit report prints nothing while its tests pass, so output cannot show progress. The wrapper preloads `scripts/test-heartbeat.ts` into every test process, which rewrites one small record, a counter and the current test file, before and after each test. A process whose record has not changed for the per-test deadline plus the hang guard (360 seconds of awake time, credited a sample at a time as `afterAwakeTime` credits it, so a host that slept trips nothing) while that process burned processor time for at least half of it is stalled: its event loop is blocked and the deadline could not fire. The run is killed with a line that says so. An idle process is never stalled. The processor share is a heuristic: a spinning process on a host so loaded that it gets under half a core is not reported, and the memory ceiling and the orphan watch below still bound it.
- **Measuring.** `CORVIDAE_TEST_WATCHDOG_REPORT=1` makes each run print its peak memory, how many test processes recorded heartbeats, and the most processor time one of them burned without starting or finishing a test. On 2026-11-12 the longest such stretch in any lane was 34 seconds, in the UI half of Interborough's coverage run, where a stall needs 180.

## Orphaned runs and finished worktrees

A design-review capture sat at 0% CPU for over three hours, and a `bun test` from a finished worktree lived for over ten (COR-2404).

- **Orphaned runs.** `runInProcessGroup`, which starts every locked stage, every host-slots command, every pooled `bun test`, and the gated suite's and the capture's Playwright, notes the wrapper's ancestors from one `ps` snapshot and checks every 5 seconds that they live. the primitives that wait (`awaitMemory`, `acquireHostLock` and `acquireTestSlots`) take that snapshot (`snapshotParents`, cached for the process) synchronously before their first `await`, so every wrapper that goes through one is covered, `withMemoryAdmission` and `runWithHostSlots` included (`runExclusively`, `withHostSlots` and `runPooledBunTest` also take it first). It matters because a session that ends while a run is queued for the lock or its slots leaves the process reparented to pid 1, and a snapshot taken after the wait would find nothing to watch. An explicit `orphanWatch.ancestors` wins, and a parent of pid 1 is never counted as orphaned. Once one exits (the agent or shell that started the run is gone), the run has the awake-time hang guard (`HANG_GUARD_MILLISECONDS`, 120 seconds) to finish, and is then sent SIGTERM like a forwarded signal, its stragglers SIGKILL. So no test process outlives its session by more than the hang guard. A run started with `nohup` from a shell that then exits is ended the same way.
- **Orphaned servers.** A server a test run starts (Playwright's `webServer`, a capture's fixture host) is stopped by its starter, and a starter killed with SIGKILL stops nothing: on 2026-11-12 ten `e2e-server.ts` processes and five fixture preview servers had run for one to five days under pid 1. `exitWhenOrphaned` (`testing/testing/src/exit-when-orphaned.ts`) notes the server's ancestors once and checks them every second; once one is gone the server sends itself SIGTERM, which runs its own shutdown, and kills itself if it is still running after the hang guard. It watches the whole chain because Playwright starts its server through `sh -c`, and that shell outlives a killed Playwright. Interborough's `e2e-server.ts`, the fixture host's `serve.ts`, and the playground's `serve-static-export.ts` and `static-playground-server.ts` call it. A server started by hand keeps working, and ends with its terminal. The remaining window: a starter killed before the server has read its ancestors (while it still loads its modules) is not noticed.
- **The audit.** `bun run audit:processes` (`scripts/agent-process-audit.ts`) lists the processes in any worktree of this repository, by working directory or by a path in the command line, whose parent is pid 1, and the toolchain processes (Bun, Node, Turborepo, a Playwright browser) older than six hours (`--older-than <hours>`), with pid, age, memory and command. It exits 1 when it lists any and stops nothing. `--kill` stops exactly the listed orphans, each only while its start time still matches; an old process whose parent is alive is listed and left to its session.
- **Delivered worktrees.** `deliver.ts` appends each delivered head to `tmp/chef/delivered-heads.log` in the main checkout and then runs `worktree.ts stale --remove`, keeping every branch. `stale` also counts a tip as delivered when it equals, or is an ancestor of, a ledger head or a merged pull request's head (one `gh pr list` for the sweep; a failure falls back to the ledger and says so), on a branch or detached. A lock in the Agent tool's form names the parent session's process, which outlives the worker, so it is released (and restored with its reason if the removal then fails or throws) only for a delivered, clean worktree with no process at all inside it, none of its Git files (`HEAD`, `index`, `logs/HEAD`, `locked`) modified in the last 6 hours (`Agent lock, used <n> minutes ago`, as the agent may be between tool calls), and no ignored file outside `node_modules/`, `.turbo/`, `dist/`, `.svelte-kit/`, `.playwright/` and `coverage/`; any other lock still keeps it.
- **Finished worktrees.** `deliver.ts` ends the processes whose working directory is inside the delivered worktree before removing it, since the worker is done. `worktree.ts stale --remove` does the same for an unlocked worktree whose branch was squash-merged (`changes-in-default`); it never ends a process in a locked one. A live process still keeps a worktree whose tip is a commit of `main`, because a worktree a session has just created looks exactly like that. Each ends by working directory only, matched on the resolved path (equal, or below it with a separator, so a sibling sharing a prefix never matches), never this process or its ancestors, SIGTERM and then SIGKILL to whatever a fresh listing still shows inside after a grace. Only once nothing else refuses the removal; a file held open inside by a process elsewhere still refuses it.

## Agent places

The pool and the lock bound processes inside a session; they do not bound how many sessions and workers exist. On 2026-11-13 three coordinator sessions each ran workers: swap was 33.5 of 34.8 GB and 42 test or Turborepo processes ran at once (COR-2455). AGENTS.md "Parallel runs" allows three agent sessions or implementation workers on a host, and `scripts/host-sessions.ts` enforces it through Claude Code hooks in `.claude/settings.json`.

- **What holds a place.** Each `chef-worker` dispatch holds one from its admission, and its agent holds it while it runs. Its session holds one more, the coordinator's, while it has any worker: the main agent and every subagent of one session are one coordinator. The cap is `hostPlaceCap`, three, so one coordinator with workers at a time (owner decision, 2026-11-14). Read-only agent types, `chef-reviewer`, `design-reviewer`, Explore and the rest, take none (`placeTakingAgentTypes`).
- **Counting, not binding.** `SubagentStart` carries no `tool_use_id`, so no event says which dispatch a starting agent belongs to, and binding the one to the other was a guess that two background dispatches could get wrong (COR-2455). Within one session worker places are interchangeable, so the session counts them (`scripts/host-sessions-model.ts`): one place for each admitted dispatch whose agent has not started, one for each agent that runs. Running comes only from `SubagentStart` and `SubagentStop` by `agent_id`. A start takes the place of a pending dispatch: the one its `PostToolUse` named, else the oldest; a later `PostToolUse` naming the agent moves it, which changes which dispatch shows as started, never the count. A start that finds no pending dispatch still counts: a resume by `SendMessage` (which fires `SubagentStart` again, with no `Agent` call), or a start after its dispatch was reclaimed. `status` marks such a run over the cap when the host had no place for it. A property test runs every interleaving of two dispatches' events (background, foreground, failed, and foreground without a stop, with repeated stops) and, in the slow lane, of three.
- **Events.** `SubagentStop`, and `StopFailure` in a worker (an API error ends its run without `SubagentStop`), end a run; a repeated stop, or one for an agent never started, changes nothing. A completed foreground call's `PostToolUse` ends its agent's first run too, since `SubagentStop` does not fire after an interrupt or an API error. `PostToolUseFailure`, and `PermissionDenied` (auto mode's denial), return a pending dispatch's place once. A denial by the user or by another hook fires neither, so the reclaim below covers it.
- **Where.** `corvidae-agent-places` in the Git common directory, beside the test slot pool: one ledger per session under `sessions/`, naming the session's own process (the nearest `claude` ancestor of the hook) by pid and start time, and its events, each the next numbered file, linked into place so no two share a number. Admission, its reclaims and its expiries hold one short lock (`admission`, naming the hook's process), never across a wait.
- **Waiting and refusing.** A `PreToolUse` hook on the `Agent` tool (`"if": "Agent(chef-worker)"`) admits a dispatch once its places fit: one, or two when its session has no worker. Waiters are admitted oldest first among those whose need fits, so a coordinator's second worker never waits behind another session's first. It looks every 5 seconds, up to 20 minutes (`placeWaitLimitMilliseconds`), then denies the call with the holders and the instruction to retry later. When the wait starts, the hook prints the holders to standard error; its `statusMessage`, shown while it runs, names `status`. A dispatch that waited gets the holders in its context. The hook's `timeout` is 1,260 seconds, above the wait. Claude Code documents no ceiling on `timeout`; this one has not been exercised at full length.
- **Reclaiming.** The next admission removes the ledger of a session whose process is gone, and expires a dispatch admitted 10 minutes ago (`neverStartedLimitMilliseconds`) whose agent never started. Since starts are counted rather than matched, the dispatches left unstarted are the newest.
- **Seeing and freeing it.** `bun scripts/host-sessions.ts status` lists the places: per session its process, then per place the dispatch, its age, and whether an agent started for it ("admitted, never started" past the limit), then the waiters. `bun scripts/host-sessions.ts release <target>` frees a place by hand: a session id (or its first eight characters or more) frees the whole session, a dispatch's `tool_use_id` or an agent id frees that one.
- **The owner's bypass.** A session whose environment sets `CORVIDAE_AGENT_CAP_BYPASS` to text in a dispatch's description or prompt, such as its issue, admits that dispatch at once, past the cap, and says so; the place it takes counts. The match is on a substring, so `COR-9` also admits a `COR-90` dispatch, and it holds for every such dispatch while the session's environment carries it. The denial message names the variable.
- **Failing open or closed.**

  | Failure | Result |
  | --- | --- |
  | The hook throws, or `ps` cannot be read or does not show the session's process | Admits, and tells the session the cap was not checked |
  | `bun` is missing, or the `PreToolUse` hook times out | Blocks the dispatch (`"onFailure": "block"`; a timed-out `PreToolUse` hook otherwise lets the call through) |
  | A `SubagentStart`, `SubagentStop` or `PostToolUse` hook fails | Nothing is recorded: a missed start leaves the dispatch pending until it expires, a missed stop leaves the run counted until `release` or the session's exit |

- **Not covered.** A Workflow's agents (`.claude/workflows/*.js`, `agent()` with `agentType: 'chef-worker'`) pass through no hook and are not capped. A foreground worker cancelled by the user fires no stop and no result, and a `PostToolUseFailure` after its agent started is read as a failure before the start: such a run stays counted until `release` or its session's exit, and `status` shows it. Sessions on other machines take no place.
