# Dev container

The detail behind AGENTS.md "Dev Container": the image, how a checkout is mounted, validating a committed branch, and what each suite does there.

## The image and the mounts

`.devcontainer/` is a local development environment in which `bun run validate` passes from a fresh checkout with nothing on the host but Docker. It is not CI: nothing builds, runs, or publishes it automatically. Its image is Debian 13 (`oven/bun`) with the workspace's pinned Bun, PostgreSQL 17's `initdb` and `pg_ctl` on `PATH`, Node.js 24 and its `npm` (the Node SQLite adapter's native suite runs under a real Node), node-gyp's compiler toolchain (two native dependencies build from source on linux/arm64), Playwright's Chromium and headless shell in the `bun` user's default Playwright cache (Turborepo's strict environment mode would drop a `PLAYWRIGHT_BROWSERS_PATH`) with their system libraries, and Git; it copies nothing from the checkout, so `.env`, credentials, and caches never enter it, and it has no `.dockerignore` because its build context is `.devcontainer/` alone. `scripts/dev-container.test.ts` keeps its Bun tag equal to `packageManager` and its Playwright version equal to the `playwright-core` that `bun.lock` resolves.

- Open any checkout or worktree with "Reopen in Container" (or `devcontainer up --workspace-folder .`). The checkout is mounted at its host path; `initializeCommand` links `.devcontainer/.git-common-dir` (ignored) to the host's Git common directory, the container mounts it, and `scripts/dev-container.ts` makes a linked worktree's absolute `gitdir:` resolve. Host and container therefore share the test slot pool and the host lock from different pid namespaces, and each can reclaim the other's live holders, so do not run suites on both at once. The root `node_modules` and Turborepo's cache live in per-container volumes, so the host's darwin packages and cached task results never meet the container's Linux ones. With the isolated linker, the per-workspace `node_modules` links the container's install rewrites point into the root store, so run `bun install --frozen-lockfile` on the host again before using the same checkout there; a dedicated worktree for container work avoids the round trip.
- The container works as the `bun` user, because `initdb` refuses to run as root, and runs Docker's init as PID 1 (`"init": true`, or `docker run --init`): without it the zombies of killed processes are never reaped, and `scripts/run-exclusively.integration.test.ts` sees their process groups as still alive.
- The image sets `TURBO_CONCURRENCY=1`. Measured in the image, Weft's type-check peaks near 3.5 GB and its type-contract check near 4.4 GB, so with Docker Desktop's default 8 GB virtual machine even two parallel tasks can be killed for memory (exit 137). Give Docker more memory before raising it.
- To validate a committed branch without an editor, clone it inside the image rather than mounting the host checkout: `docker build -t corvidae-dev .devcontainer`, `git bundle create /tmp/corvidae.bundle HEAD`, then `docker run --rm --init -v /tmp/corvidae.bundle:/tmp/corvidae.bundle:ro corvidae-dev sh -c 'git clone -q /tmp/corvidae.bundle ~/corvidae && cd ~/corvidae && export CORVIDAE_PLUGIN_IDENTITY_BASE=HEAD && bun install --frozen-lockfile && bun run validate'`.

## What each suite does there

What the container enables, suite by suite:

- Live PostgreSQL (`packages/storage-postgres/src/postgres.integration.test.ts` and `postgres-concurrent-setup.slow.test.ts`) and live Neon driver (`packages/storage-neon/src/neon-live.integration.test.ts`, through `neon-proxy.test-support.ts` to the same disposable cluster): enabled. They need only `initdb` and `pg_ctl`, and they are what makes `@lostgradient/storage-postgres#test:coverage` report `postgres.ts` and `@lostgradient/storage-neon#test:coverage` report `neon.ts` and its two test-support modules as covered. The cluster is `initdb --no-locale -E UTF8`, so no system locale is needed; the C collation the key-value schema depends on is pinned in its DDL. PostgreSQL 17 is Debian 13's server major and the release the host-side fix used.
- A real Neon endpoint: not provisioned. The live Neon suite tests the real driver's wire protocol against the local cluster, and a hosted database would need credentials the container must not carry.
- Playwright's browser-fixture suite (`test:browser-fixtures`, part of `bun run test`): enabled, and required. It launches Chromium's headless shell, so `validate` fails without a browser.
- Weft's real-browser smoke tests (`WEFT_BROWSER_SMOKE=1`: WebExtensionStorage, IndexedDB, HttpClient, Service Worker): runnable, still opt-in. The image carries full Chromium as well as the headless shell because WebExtensionStorage loads an unpacked extension, and all four suites pass in it with `bun run --filter=@lostgradient/weft test:browser`, `bun run --filter=@lostgradient/storage-indexeddb test:browser`, and `bun run --filter=@lostgradient/storage-web-extension test:browser` (the IndexedDB and WebExtensionStorage suites are those packages'). They stay outside `validate` here exactly as on the host.
- The full Playwright suite (`bun run test:browser`): not enabled. Its Firefox and WebKit keyboard projects need `npx playwright install --with-deps firefox webkit` (as root), and in this linux/arm64 image some Chromium cases fail (observed in a partial run, which included the `markdown-editor-template-placeholders` assertions and a few accessibility and scrolling checks; no complete run's counts are recorded), so treat its results there as advisory. It is outside `validate` on every machine. Its `chromium` project and Interborough's own end-to-end suite (`bun run test:browser:interborough`) run on GitHub Actions (`.github/workflows/browser-suites.yml`, the fixture suite on the linux/arm64 baseline renderer); a Chromium failure seen only in this linux/arm64 image is not a failure there, and the Firefox and WebKit projects remain ungated.
- The Agent Skills reference validator (`AGENT_SKILLS_REFERENCE_VALIDATOR`): not installed. It is opt-in and fetches a pinned Python tool with `uvx`.
- Coverage is a report with no floor (COR-2370), so a platform that measures Svelte or Weft coverage differently, as the container's linux/arm64 does on Apple silicon, changes the numbers `bun run coverage` prints and fails nothing.
