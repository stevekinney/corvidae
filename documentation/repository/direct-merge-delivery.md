# Delivering a branch without a pull request

Owner decision, 2026-11-11: a pull request is optional. A worker pushes its branch, and the coordinator verifies and merges it into `main` with `bun scripts/chef/deliver.ts --branch <branch> --head <sha> --worktree <path> --message-file <file> --run <id> --project <name>`; `scripts/chef/direct-merge.ts` holds the logic. The other options are those of `--pr` (including `--issue`/`--completion-file` and `--closes <ID>`, which alone moves an issue to Done), and exactly one of the two is required. A branch merge takes the same merge lock as a pull request merge, runs no test gate, changes no working tree, and names its own failed steps, in this order:

- **`lease`** (before any merge step; `deliver.ts` only): `--run` does not hold the Linear lease of `--project` (`linear.ts lease`), or the lease is released, expired or unreadable. Both flags are required for a merge of either route.
- **`verification`** also covers the landing evidence of `scripts/chef/landing-evidence.ts`, read from GitHub on the exact head (a pull request merge runs the same check): workflow runs exist and are all on that SHA; each CI evidence identity of the request resolves to one authenticated run with the pinned plan digest; no `main.yml`, `pull-request.yml` or `targeted-checks.yml` run is unfinished or red with a failure `main` lacks (`ci-compare.ts`), and a plan that needs the full run has a green `main.yml` run (`evidence-plan.ts`); an interface path (`applications/interborough/src/{app,routes,views,styles}`, `components/*/src`) has a design verdict, `design-verdicts/<head>.verdicts` beside the execution state, in the row-verdict format of the design-review skill with every row `matches` or `deferred`; a one-way door in the plan needs a pull request, so a branch merge refuses it. Every read fails closed.
- **`head`**: `origin/<branch>` is not exactly `--head`, or a fetch failed. Re-run the acceptance checks on the new head.
- **`revert`**: the branch sets a file back to the state it had before a recent commit on `main` (`scripts/chef/revert-check.ts`). The worker rebuilt its tree from a stale base; it merges `main` in properly.
- **`conflict`**: `git merge-tree --write-tree` found a conflict with `main`. It goes back to the worker like a pull request's.
- **`queue`** (`scripts/chef/land-queue.ts`, inside the merge lock): commits that reached `main` after the head's evidence and touch what its evidence plan reaches mean the evidence never saw them, so the merge is refused with the files named and the head needs a new evidence run. A full-run plan reaches the whole tree. Owner decision, 2026-11-21: a commit that main's own CI has already verified does not make the evidence stale. A commit is _verified_ when a `main.yml` run triggered by a `push` to `main` completed successfully at that commit or at a later commit on `main`, since a green run at a later commit covers every commit before it. The queue counts only the commits after the newest verified one, plus any commit no green run covers yet, so a run that failed, was cancelled or is still in progress at a newer commit verifies nothing for that commit. It reads the runs with `gh run list` (injectable as `mainRuns`) and only when some commit on `main` reaches the plan; a provider read that fails verifies nothing and refuses with "the queue could not verify main", never a landing. A landing that relied on verified commits reports them in `verifiedOnMain`, one line per run with the commits it covered, and `deliver.ts` prints them. When `main` moved, the integration-tree check (`acceptMovedMain`) holds a verified commit to the same proof as one outside the plan: the attested base is an ancestor of the current one, the head merged onto the attested base reproduces the attested tree, and the pushed tree differs from the attested tree only at the paths main's new commits touch, where it holds exactly what main holds. The pull-request route (`merge-gate.ts`) uses the same rule through `scripts/chef/moved-base.ts`: when `origin/main` is not the base its verification request names, it accepts the new base only when the attested base is an ancestor of it, the queue classifies every commit between them (outside the plan, or verified), and the tree about to land is the attested tree plus exactly those commits; otherwise it refuses at `verification` with "verification request has a stale base" and the reason. The coordinator's approval still names the attested base, and the receipt keeps it, adding `landedBase` and `landedTree`.
- **`guards`**: a guard of `bun run lint:guards` fails on the tree that would be pushed. The one squash commit is made first (`git commit-tree`, an object until it is pushed), checked out as a detached `git worktree add` in a temporary directory, with the repository's `node_modules` linked in, so Git works there and `origin/main` resolves, as two guards need (`check-plugin-identities`, and the allowlist ratchet of `check-load-sensitive-deadlines`). Each guard in the root `package.json`'s `lint:guards` runs as its own process, all of them even after a failure, and the failing guard is the one whose process exited non-zero. The worktree is removed afterwards, `git worktree remove --force` in a `finally`; a removal that fails refuses the merge, named. The guards take about 35 to 40 seconds on a busy host, plus about two seconds to add the worktree and one to remove it. A failure refuses the merge only when the squash commit has a finding `origin/main` does not (owner decision, 2026-11-11): another run on this repository lands code untested, so `main` can fail a guard for a while, and a change that added nothing must not be held for it. Every failing guard is run again on the base commit, in its own worktree, and its failure is the base's own when each of its output lines (file, line and message of a finding) is also a line of that guard's output on `origin/main`; a guard that fails on both with a finding the base lacks, one that passes on the base, one with no output, or a base run that could not clean up after itself is the change's own. No declaration is needed. A merge that passes only on that comparison reports `guardsAlreadyFailing`, each such guard with its count of output lines, and a `WARNING guards: already failing on main` line says so; nothing is waived silently. Workspace links in the guards' `node_modules` resolve into the checkout the merge runs from, as they do there.
- **`merge`**: the push of the one squash commit (`git commit-tree <tree> -p <main> -F <message file>`) was rejected because `main` moved, or the branch changes nothing. A rejected push changes nothing: launch it again.
- **`delete`**: merged, but the remote branch is still there; delete it by hand and close the issues with `scripts/chef/linear.ts`.

A branch merge has no `--fixes-main`, and `deliver.ts` refuses it with `--branch` (exit 2) rather than ignore it: the flag records a pull request as a repair of a red `main` in the health file, which keys its records by pull request number, and the baseline comparison above needs no declaration. The usage-log line of a branch merge holds `branch:<name>` where a pull request's holds its number. A red `main` is a warning in the report, as for a pull request.
