# Delivering a branch without a pull request

Owner decision, 2026-11-11: a pull request is optional. A worker pushes its branch, and the coordinator verifies and merges it into `main` with `bun scripts/chef/deliver.ts --branch <branch> --head <sha> --worktree <path> --message-file <file>`; `scripts/chef/direct-merge.ts` holds the logic. The other options are those of `--pr` (including `--issue`/`--completion-file` and `--closes <ID>`, which alone moves an issue to Done), and exactly one of the two is required. A branch merge takes the same merge lock as a pull request merge, runs no test gate, changes no working tree, and names its own failed steps, in this order:

- **`head`**: `origin/<branch>` is not exactly `--head`, or a fetch failed. Re-run the acceptance checks on the new head.
- **`revert`**: the branch sets a file back to the state it had before a recent commit on `main` (`scripts/chef/revert-check.ts`). The worker rebuilt its tree from a stale base; it merges `main` in properly.
- **`conflict`**: `git merge-tree --write-tree` found a conflict with `main`. It goes back to the worker like a pull request's.
- **`guards`**: a guard of `bun run lint:guards` fails on the tree that would be pushed. The one squash commit is made first (`git commit-tree`, an object until it is pushed), checked out as a detached `git worktree add` in a temporary directory, with the repository's `node_modules` linked in, so Git works there and `origin/main` resolves, as two guards need (`check-plugin-identities`, and the allowlist ratchet of `check-load-sensitive-deadlines`). Each guard in the root `package.json`'s `lint:guards` runs as its own process, all of them even after a failure, and the failing guard is the one whose process exited non-zero. The worktree is removed afterwards, `git worktree remove --force` in a `finally`; a removal that fails refuses the merge, named. The guards take about 35 to 40 seconds on a busy host, plus about two seconds to add the worktree and one to remove it. A failure refuses the merge only when the squash commit has a finding `origin/main` does not (owner decision, 2026-11-11): another run on this repository lands code untested, so `main` can fail a guard for a while, and a change that added nothing must not be held for it. Every failing guard is run again on the base commit, in its own worktree, and its failure is the base's own when each of its output lines (file, line and message of a finding) is also a line of that guard's output on `origin/main`; a guard that fails on both with a finding the base lacks, one that passes on the base, one with no output, or a base run that could not clean up after itself is the change's own. No declaration is needed. A merge that passes only on that comparison reports `guardsAlreadyFailing`, each such guard with its count of output lines, and a `WARNING guards: already failing on main` line says so; nothing is waived silently. Workspace links in the guards' `node_modules` resolve into the checkout the merge runs from, as they do there.
- **`merge`**: the push of the one squash commit (`git commit-tree <tree> -p <main> -F <message file>`) was rejected because `main` moved, or the branch changes nothing. A rejected push changes nothing: launch it again.
- **`delete`**: merged, but the remote branch is still there; delete it by hand and close the issues with `scripts/chef/linear.ts`.

A branch merge has no `--fixes-main`, and `deliver.ts` refuses it with `--branch` (exit 2) rather than ignore it: the flag records a pull request as a repair of a red `main` in the health file, which keys its records by pull request number, and the baseline comparison above needs no declaration. The usage-log line of a branch merge holds `branch:<name>` where a pull request's holds its number. A red `main` is a warning in the report, as for a pull request.
