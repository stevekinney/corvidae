# Repository guards

The detail behind the guards AGENTS.md "Commands" names in one sentence each. The rules stay in AGENTS.md, in short; this file holds their full text where AGENTS.md shortens it, what each guard rejects, its markers, and its allowlists. The test-lane, documentation-coverage, and test-duration guards are described in [test lanes and checks](test-lanes-and-checks.md).

## The text guards alone

`bun run lint:guards` runs exactly the `scripts/check-*.ts` guards that `lint:root` chains after oxlint (wait-for-element assertions, wall-clock assertions, load-sensitive deadlines, promise assertion modifiers, test process spawns, process-identifier test paths, tool-result payload reads, runtime detection, plugin identities, middle-dot separators, hidden labels, combined signal listeners, touch-target sizing, separate box reads, and the [owner-rule guards](#owner-rules): sidebar headings, shadows, visible text, empty states), and `lint:root` calls it for that part, so the list lives in one script. The expensive parts of `lint:root` are `prepare-manifest` and oxlint, neither of which `lint:guards` runs. `bun run lint:guards` stops at the first failing guard; `bun scripts/chef/deliver.ts --branch` runs each guard as its own process on the tree it is about to push and runs all of them, so it reports every failing guard at once ([direct-merge delivery](direct-merge-delivery.md)). Measured 2026-11-11 on a busy host, with every guard passing or failing in turn: about 35 to 40 seconds in all, of which `check-load-sensitive-deadlines` is about 14 and `check-test-process-spawns` about 8. Two guards need a Git repository: `check-plugin-identities` compares a plugin with `origin/main` and fails when it does not resolve, and `check-load-sensitive-deadlines` reads its allowlist baseline with `git show origin/main:...` and checks nothing when there is none. Run them in a checkout or a `git worktree`, never in an extracted archive.

## Load-sensitive deadlines

Owner decision: tests that can flake under load cannot be in the critical path. Everything `bun run check` and `bun run validate` run has one deadline, the awake-time hang guard (`HANG_GUARD_MILLISECONDS`, 120 seconds), and it is never a performance bound. Bun's per-test timeout is twice that, passed by `scripts/bun-test.ts`, so a `package.json` script never starts `bun test` itself.

- Bun's per-test timeout is twice the hang guard, passed as `--timeout` by `scripts/bun-test.ts` and `scripts/bun-test-junit.ts` (`[test] timeout` in `bunfig.toml` is ignored, and `setDefaultTimeout` in a preload covers the first file only), so a `package.json` script never starts `bun test` itself.
- Every UI preload calls `configureAsyncUtilityDeadline` so Testing Library's `findBy*` and `waitFor` wait up to the hang guard.
- A wait for something that must happen uses `waitUntil` or `awakeTurns` from `@lostgradient/testing/wait-until` (root scripts import `testing/testing/src/wait-until.ts` by path, because the root package depends on no workspace; packages that cannot import the testing package keep a local poll), never a sleep, a count of turns, a wall-clock deadline or a race against a timer. A wait for something that must not happen uses `quietFor`, because load can only delay the event, never advance it.
- A test that deliberately exercises a short guard against work that cannot finish carries `// hang-guard-self-test: <reason>`, and a wait that load cannot flip for another reason (a pre-aborted signal, a double that never answers, timers of one clock that fire in order of their deadlines) carries `// load-proof: <reason>` that argues from determinism and never from expected speed. Each reason is at least twenty characters, and the comment sits directly above the statement.
- Manual runtime services and manual clocks inject their own timers and leave the global ones real, so a bare `Bun.sleep` beside them is still a real wait; only `useFakeTimers` patches the global `setTimeout`.
- A Bun child that a test starts goes through `spawnWithHangGuard` or `runWithHangGuard`, which put `--no-install` in front of it (`withoutAutoInstall`), because a module written to the system temp directory has no `node_modules` and Bun would install what it imports from the registry, so the result would depend on the network and on which release is current.

`scripts/check-load-sensitive-deadlines.ts` enforces all of this from `lint:root`. It rejects:

- a Bun or Testing Library timeout, a wait budget (including a window passed to any helper that races a timer on that parameter, such as `withTimeout(work, 500)`), or a defaulted budget below the hang guard;
- a bounded poll and a wall-clock poll;
- a sleep (`Bun.sleep`, `node:timers/promises`, `waitForRealTimersForTesting`) before an assertion;
- a timer race (`Promise.race` or `Promise.any` against any timer promise, or a promise a timer also resolves);
- a `quietFor` window before a positive assertion;
- a single-turn yield (`sleepForTesting` under real timers, which ignores its argument, `setImmediate`, `setTimeout(r, 0)`, `Bun.sleep(0)`, and a same-file helper that is one of them) that something follows, unless it waits on the state instead or carries `// load-proof:`;
- a timer that rejects;
- a `bun test` invocation without the shared deadline.

A product's own timeout option, such as `mailbox.awaitCleanup({ timeoutMs })`, is not read, and neither are event order and I/O races; the guard's header lists what it cannot see.

The Playwright specs (`*.playwright.ts`) and the opt-in `WEFT_BROWSER_SMOKE` suites are outside `check` and `validate`, and the rules above do not scan them. The root Playwright suite's `chromium` project and Interborough's end-to-end suite (`test:browser:interborough`, its one `chromium` project) are run by hand and gated by no workflow, and the root suite's Firefox and WebKit projects are gated nowhere; `test:browser-fixtures` runs Bun tests, which are scanned. The browser suites follow the hang guard all the same: Interborough's and `scripts/browser-fixtures`' `playwright.config.ts` set `expect.timeout` to `HANG_GUARD_MILLISECONDS` and `timeout` to `TEST_TIMEOUT_MILLISECONDS`, and the guard's `playwright-configuration` and `playwright-timeout` rules reject a configuration that does not and an Interborough spec that names a shorter one without a `// hang-guard-self-test:` or `// load-proof:` comment (the specs of `scripts/browser-fixtures/tests` still name their own, which COR-2001 left).

The history and the single-turn-yield details are in [test lanes and checks](test-lanes-and-checks.md) ("Load-proof deadlines").

## Inherited key reads

Every library and component runs `scripts/check-inherited-key-reads.ts` in its `lint`, which fails when `src` reads a plain record with a key the code does not control (`record[key]` or `key in record` on a `Record<string, T>`), because the record also answers for `constructor`, `toString` and `__proto__`. Test with `Object.hasOwn(record, key)` first, hold the entries in a `Map`, or build the record with `Object.create(null)`. A read that is safe for a reason the check cannot see goes in the workspace's `inherited-key-reads-allowlist.json` with its reason; the list can only shrink on its own, and adding an entry is a reviewed edit.

## Audit exceptions

`bun run audit` runs `bun audit --audit-level=high` through `scripts/check-audit-exceptions.ts`. An advisory may be tolerated only by an entry in `scripts/audit-exceptions.ts`, which needs an owner decision, a tracking issue, a review-by date, and the exact dependency chains that may reach the package; the guard fails on a stale, expired, or widened exception. Never add a bare `--ignore`.

No advisory is currently tolerated.

## Middle-dot separators

After the guards, `lint:root` runs `scripts/check-playwright-collection.ts`, which runs `playwright test --list` on the root fixture configuration (`scripts/browser-fixtures/playwright.config.ts`) and on each component package's `browser/playwright.config.ts`, and fails when any configuration cannot load every spec it collects. A spec that imports a module which has moved stops the whole suite before a test runs, and nothing else imports the specs locally: six specs merged from `main` still imported `./overlay-fixture.ts` after it moved to `@lostgradient/testing/playwright/overlay-fixture`, and only a Chromium shard on CI found it. Listing starts no browser and no web server, so the four listings take a few seconds; the guard prints each configuration's `Total:` line.

`lint:root` runs `scripts/check-middle-dot-separators.ts`, which fails on a middle dot (U+00B7) anywhere in `components/cinder`, `applications/playground` and `applications/interborough` (owner standing order, 2026-11-10; COR-2335, COR-2336). The scan is textual: it reads every non-binary file under those roots, and it also reports the escaped spellings (`·`, `\u{b7}`, `\xb7`, CSS `\00b7`, `&middot;`, `&#183;`, `&#xb7;`), because they draw the same glyph. Write a comma, give each piece its own element, break the line, or use a description list for label and value metadata ([Cinder's README](../../components/cinder/README.md#content)). A test that asserts the glyph's absence builds it with `String.fromCodePoint(0xb7)`. A line with a real non-separator use carries a `middle-dot-allowed: <reason>` marker, on the line or the one above, with a reason of at least twenty characters; none does today.

## Hidden control labels

`lint:root` runs `scripts/check-hidden-labels.ts`, which fails on a new `labelVisible={false}` (or `labelVisible: false`) in `applications/interborough` (sweep W44, COR-2022). A field that hides its visible label leaves nothing on screen that says what it is once a value is typed, and Cinder's `Toggle` draws its own visible label, so a page never adds a hidden one beside it. Pages that hid a label before the guard are listed in `scripts/hidden-label-allowlist.json` with the file, how many sites it holds and a reason; the list only shrinks, so a file that holds more sites than its entry fails, and an entry that names more sites than remain is reported so it can be lowered or removed. A line with a real need carries a `hidden-label-allowed: <reason>` marker, on the line or the one above, with a reason of at least twenty characters.

## Touch-target sizing

`lint:guards` runs `scripts/check-touch-target-sizing.ts`, which fails when a stylesheet or Svelte component outside Cinder sizes something (`width`, `height`, `inline-size`, `block-size`, with or without `min-` or `max-`) with `--cinder-touch-target-min` or `--cinder-button-height-*`. Either token paints the control 44 pixels tall on a touch screen, which is the owner's "giant buttons" complaint (2026-11-11): a control is painted compact and reaches 44 pixels through a hit area that takes no layout, from Cinder's `Button` or a pseudo-element positioned with `inset`. `ALLOWED_DECLARATIONS` in the script holds an exact count per file for the declarations that remain (full-width rows, and sizes a coarse pointer overrides); a file over or under its count fails, so the list only shrinks. It replaces the Chat-only test that COR-2289 added.

## Separate box reads

`lint:guards` runs `scripts/check-separate-box-reads.ts`, which scans only `applications/interborough/tests/e2e/` and fails when one `expect(...)` assertion, `return` or `if` comparison, or computed value uses geometry from two or more separate reads: `boundingBox()` calls (a call inside a `.map` callback counts as several), or `.evaluate(...)` calls whose callback calls `getBoundingClientRect`. A `=== null` check of a read is not a comparison, and the guard follows variables within one file, not a helper with a block body that returns a read or a `for...of` variable. Each read is its own round trip, so a page that is still moving can lay out differently between two reads. `chat-responsive.spec.ts` read a row and two buttons about 10 ms apart while the page centred a newly opened approval row, and the buttons appeared 22px apart (COR-2459, the class of COR-2412). The fix is to wait for the settled state (`await expect(row).toBeFocused()`), then read every box together with `readBoxes(page, { deny, approve })` from `applications/interborough/tests/e2e/read-boxes.ts`, which takes all the rects in one in-page evaluation. The guard names the file and line. `ALLOWED_INSTANCES` in the script holds an exact count per spec file, each with a reason, for the instances present when the guard was added and not yet converted to `readBoxes` (some compare a box before and after an action on purpose); a file over or under its count fails, so the list only shrinks. The browser-fixture suites under `scripts/browser-fixtures/tests/` render pages where nothing moves and are not scanned.

## Swallowed catches in the lock code

`lint:guards` runs `scripts/check-swallowed-catches.ts`, which scans the host lock files (`run-exclusively.ts`, `host-sessions.ts`, `bun-test-pool.ts`, `host-slots.ts`). It fails on a `catch` with no binding whose block does not open with a comment saying why every failure is safe to treat alike. Such a catch cannot look at the error's code, and two review rounds on COR-2463 found a permission error read as "released" or "not removed" one instance at a time: a real fault became a lock taken twice or a wait that never ended. Catch `(error)`, handle the codes you expect (`ENOENT`, `ENOTEMPTY`, `ESRCH`) and rethrow the rest, or write the reason as the block's first line.

## Waiting on a workflow run

`lint:guards` runs `scripts/check-workflow-dispatch.ts`, which fails on a raw `gh workflow run main.yml` or `targeted-checks.yml` (a raw targeted dispatch drops lanes; or the same words as an argument list) in `scripts/`, `.claude/agents/`, `.codex/agents/` and `.claude/workflows/`, except in a sentence that says never; `scripts/chef/targeted-run.ts` is the one dispatcher of `main.yml` on a branch, sending a plan there only when it requires a full run. The coordinator documents under `.agents/skills/` are not scanned and name the command only as `targeted-run.ts`. Workers dispatched full runs by hand twice (runs 44108166839 and 44114059046), and each full run is about 19 jobs that targeted runs queue behind.

`lint:guards` runs `scripts/check-gh-run-watch.ts`, which fails when `gh run watch` appears in `.agents/`, `.claude/`, `.codex/`, `scripts/` or `documentation/`, except in a line that says never or not to use it. Loops of it from many sessions drained the account's 5000-call GitHub API limit on 2026-11-17. Wait with `bun scripts/chef/wait-run.ts <run id>`: one status call per interval (180 seconds by default, 60 at least), and a wait for the rate limit's reset when fewer than 500 calls remain.

## Owner rules

A rule the owner states twice becomes a guard in the change that fixes it, never a memory file or a line of prose a worker may not read (owner decision, 2026-11-19). [`owner-rules.json`](owner-rules.json) is the register: each row holds the rule's id and wording, the date and source it came from, the guard that enforces it (script, test and allowlist) and the directories the guard scans. `scripts/owner-rules.test.ts` fails when a row names a guard script, test or allowlist that does not exist, a guard that `lint:guards` does not chain, or scans that differ from the guard's own `SCANNED_DIRECTORIES`; a row with no guard states why in `unguardedReason`.

The guards below share `scripts/owner-rule-guard-support.ts`. Each scans source text, counts the sites that break its rule per file, and judges the count against an allowlist of today's offenders (`scripts/<name>-allowlist.json`, `{ "<path>": <count> }`). The allowlist only shrinks: a file with more sites than its entry fails, a count above the same allowlist on `origin/main` fails, and an entry that names more sites than remain is reported so it can be lowered or removed. Fixing an offender is product work and lands in its own change, which also lowers the allowlist.

- **Sidebar headings** (`check-sidebar-no-headings.ts`): every `<SideNavigationGroup>` in a non-test Svelte file under `applications/interborough/src` must be `collapsible={false}` with `labelVisibility="hidden"`, which names the list for a screen reader and draws no header. Its allowlist is empty: the sidebar's own section now passes.
- **Shadows** (`check-light-shadows.ts`, which the dark-shadows work landed and this guard absorbed): in `components/cinder/src/tokens/resolved/{light,dark}.json` every shadow colour is black in both themes, and in light no layer is heavier than the agreed alpha in `AGREED_LIGHT_SHADOWS` (a new shadow token needs a ceiling in the same change). In CSS, Svelte and TypeScript source under `components`, `applications`, `packages` and `plugins`, a `box-shadow`, `boxShadow`, `--*shadow*` or `drop-shadow(...)` drawn from `--cinder-text-*`, an ink token, `currentColor` or white in any spelling (`white`, 3, 4, 6 and 8-digit hex, `rgb`/`rgba` 255 255 255 with any separators and alpha, `hsl` lightness 100%, `oklch` lightness 100%) is reported, because it glows in dark mode. It has no allowlist: the offenders it started with were fixed by the dark-shadows work. The one exemption is the color picker's `--_cinder-color-picker-thumb-shadow-support-dark` (`rgba(255, 255, 255, 0.65)`), exempt by name in `WHITE_ON_PURPOSE`: the outer ring of the thumb's outline on dark chrome, white on purpose so the thumb stays visible over a dark surface.
- **Visible text** (`check-visible-text-leaks.ts`): the string literals of `applications/interborough/src/app/copy/**` and the text nodes and `label`, `title`, `description`, `placeholder`, `aria-label` and `alt` attributes of Interborough's Svelte templates must hold no absolute or relative file path, 26-character ULID, `secret:` reference, `${{ secrets` expression or `workspace:` reference. Module specifiers are not text. It starts with four copy files that name a path.
- **Empty states** (`check-empty-state-layout.ts`): in Interborough's Svelte files an empty state is Cinder's `EmptyState` with its defaults. The guard reports an element whose class holds the word `empty`, an element whose only content is an expression naming `empty`, and an `<EmptyState>` that passes `layout`, `size` or `align`. It starts with the offenders of 2026-11-19, which the owner counted as six patterns.
- **Middle dots** (`check-middle-dot-separators.ts`): see [Middle-dot separators](#middle-dot-separators).

## Process documentation

The process documents carry word budgets and checked references, so they cannot regrow or rot unnoticed. `scripts/process-docs-budget.test.ts` holds AGENTS.md, which every agent session pays for on every request, to 2,250 words and 16,000 characters, the chef `SKILL.md` to 1,500, and each `.agents/skills/chef/references/*.md` to its own budget, which every reference must have. `scripts/process-docs-references.test.ts` checks that every `scripts/...` path and `bun scripts/...` command named in AGENTS.md, `.agents/skills/**/*.md`, `.claude/agents/*.md`, and `documentation/repository/*.md` exists, that every relative Markdown link in them resolves, anchors included, and that every AGENTS.md section another document or script cites by name in quotes exists. Move mechanics, history, and rationale into a document under `documentation/repository/` and link it, rather than raising a budget.

## Agent edits and worker briefs

`scripts/chef/edit-guard.ts` is a Claude Code `PreToolUse` hook for Bash (`.claude/settings.json`), beside the stash guard. It denies the two shell edits that leave a change half applied: an interpreter fed a script on standard input by a heredoc (`python3 - <<'EOF'`, and the same for `node`, `bun`, `ruby`, `perl` and `deno`) when that script writes a file, and `sed` or `perl` with an in-place flag, wherever it runs in a pipeline. In one day's run workers twice used a Python heredoc for a multi-site edit; a later assertion failed, and the earlier replacements were lost with nobody told. An in-place substitution that matches nothing also reports success. Edit and Write fail loudly, one site at a time.

The guard allows a heredoc script that only reads and prints, a heredoc that is data for a script run by name, a heredoc into `cat` or `git commit`, and `sed` and `perl` that print. It does not catch a script kept in a file and run by name, and it fails open. Codex has no project hook here, so its `chef-worker` carries the rule as an instruction only.

A brief holds five to eight items, each with the file it touches. Seven workers in one day reached their context limit mid-brief, mostly from reading two 28K review reports and many screenshots. What worked:

- Leave long reports on disk with a tag per finding (`NEW-2`, `A10`) for the worker to search instead of read.
- Tell the worker to commit after each item, and cap the images a brief asks it to open.
- Run long captures and checks from the coordinator, in the background, where they cost it almost no context.

A worker watches what it starts. A test stuck in a synchronous loop never reaches the hang guard, which runs inside the test's own process: one such test grew to 144 GB, almost all of it compressed, in 13 minutes, and `ps -o rss` showed 3 GB. `top -l 1 -o mem -n 5 -stats pid,mem,cpu,command` lists the largest processes by physical footprint, which counts compressed memory.

## Unused code inventory

`bun run knip` checks both test-inclusive and production reachability. The production scan excludes colocated test, benchmark, and fixture source. The test-inclusive scan includes Bun test files, browser fixture and end-to-end specs, and directly runnable benchmarks. Browser specs are explicit entries because their Playwright configurations require provisioned test infrastructure. Component fixture manifests are test-only entries because the browser fixture server discovers them by filename. Workspace manifests supply package exports, executables, and commands, including root and release scripts. The Interborough release builder compiles the CLI, and the supervisor spawns the development and server entrypoints. Generated component inputs are prepared by the ordinary root workflow before scanning.

Each accepted baseline entry identifies one category, file, and symbol. The report directory under `test-output/knip/` holds the fresh raw findings and the retained rows. A new finding fails the check. `bun run knip --production` writes a production-only report and preserves the scanner exit status. Inspect the owning manifest, runtime registrations, and external export obligations before deleting a candidate. Test-only reachability and the absence of a static consumer are evidence for investigation.
