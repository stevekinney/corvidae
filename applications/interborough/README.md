# Interborough

Interborough is Corvidae's main application. One process on one loopback origin serves the browser application, Weft's engine API for the Engine console, and a Bureau, with no sign-in. It is a private application: nothing here is published.

The browser application is the Weft operator console, moved here from `packages/weft/src/ui` (Weft no longer exports `./ui`, `dashboard()`, or a UI of any kind), with a new shell around it. The Weft console's coverage of Weft's operations is recorded in [`documentation/weft-console/coverage-matrix.md`](documentation/weft-console/coverage-matrix.md).

## Running it

Run every command from the repository root.

```bash
bun run --filter=@lostgradient/interborough dev
bun run --filter=@lostgradient/interborough build
bun run --filter=@lostgradient/interborough start
bun run --filter=@lostgradient/interborough test
bun run --filter=@lostgradient/interborough test:slow
bun run --filter=@lostgradient/interborough test:browser
bun run --filter=@lostgradient/interborough test:coverage
bun run --filter=@lostgradient/interborough lint
bun run --filter=@lostgradient/interborough typecheck
```

- `dev` runs the supervisor (below) around `bun --watch src/host/dev.ts`. It builds the browser application into `build/`, starts the host on `http://127.0.0.1:7234`, and rebuilds when the source changes. It runs under `bun --watch`, which restarts the host when its own modules change, and builds the browser application in a child process because the bundler fails inside the watched process. `INTERBOROUGH_PORT` picks another port, and `0` asks for a free one. Open pages reload themselves after each successful rebuild (and when the host restarts): the development host injects a small client into `index.html` that listens on `/__dev/reload`. A production host serves neither, and `build/` never contains the client.
- `build` writes the production build into `build/`: `index.html` and content-hashed JavaScript, CSS, and WebAssembly under `build/assets/`. The host serves that directory. A build replaces `build/` only once it succeeds.
- `start` runs the supervisor around `bun --no-install src/host/serve.ts`, which serves the existing `build/` with `development: false`. It builds nothing and watches nothing. Without `build/index.html` it exits 1 and tells you to run `bun run build` first. `INTERBOROUGH_BUILD_DIRECTORY` names another build directory for `start` and `dev`.
- **Restarting the host.** `POST /host/restart` (through the same Host and Origin guard as every route) answers `202`, shuts the Bureau down with its runs left parked, stops the host, and exits with code 75. The supervisor (`src/host/supervisor.ts`, `bun src/host/supervisor.ts <serve|dev>`) starts the host again on exactly that code and ends with the child's own code on any other; SIGINT and SIGTERM go to the child. A run waiting on a signal is still waiting after the restart. A source edit under `dev` restarts the host inside `bun --watch` without the supervisor. A supervisor killed with SIGKILL cannot forward the signal, so it leaves its host running.
- `test` runs the host's suite under `bunfig.toml`, then the browser application's under `bunfig.ui.toml`, whose preload installs happy-dom, the Svelte compile plugin from `@lostgradient/testing`, and the jest-dom matchers. The browser suite stays serial: under `--parallel`, Bun 1.4.2's workers load the default `bunfig.toml` preload on top of the one `--config` names. The tests in a `*.slow.test.ts` file bundle for seconds, so `test:slow` runs them.
- `test:browser` runs the Playwright suite in `tests/e2e` against a host it starts on port 7399 with the console's fixtures registered. The barrier's control listens on the next port, and the three hosts described under "Schedules, goals, and the audit trail", "The journey" and "First run" on the three after it, so the suite holds five consecutive ports. Set `INTERBOROUGH_E2E_PORT` to run the suite beside another checkout's, which holds 7399. `bun run --filter=@lostgradient/interborough test:browser -- tests/e2e/90-journey.spec.ts` runs the journey alone.
- `test:coverage` runs the browser suite under coverage and compares each area with the floor in `scripts/coverage-baseline.ts`.

## The host

`src/host/host.ts` starts everything:

- **State** lives in Bungalow's directory, `~/.interborough` or `INTERBOROUGH_HOME`, or in Postgres and S3 (see "Running on Postgres and S3"). Locally the Bureau runs on Bun SQLite at Bungalow's database path with `BureauOptions.id` set to Bungalow's `deploymentId`, so a restart keeps its tasks, sessions, schedules, and goals. The host takes Bungalow's single-instance lock, so a second host on the same directory refuses to start.
- **One caller.** There is no sign-in, and the host binds `127.0.0.1` only. Every request without a credential acts as `anonymous:local`, which holds every Weft scope and every Bureau scope. `weft.system.principal` reports that subject, and the shell names it in its top bar. The one credential the host knows is the operator's A2A key, which only A2A uses (see [A2A](#a2a)).
- **Routes** on the public origin:
  - `/api/*`, `/v1/*`, `/jsonrpc`, `/mcp`, and Weft's discovery documents are Weft's engine operations.
  - `/bureau/*` is `createBureauHandler` with the prefix removed, and `agUi: {}` mounts its AG-UI adapter at `/bureau/ag-ui`, which Chat talks to. It does not share Weft's root because both catalogs claim `/jsonrpc` and `/v1/…`.
  - `/assets/*` and every route in `src/app/routes.ts` serve the build.
- **Why there are two listeners.** Weft's server reports its own shared `unauthenticated-local` caller for a request with no credential. To make both halves of the application name `anonymous:local`, Weft's server listens on a private loopback port that answers only a per-process key, and the public listener relays to it (`src/host/engine-proxy.ts`), attaching the key and dropping any credential the caller sent.
- **One engine.** The Engine console serves the Bureau's own durable engine (`bureau.durableEngine()`), so a cancel from the console is fenced by the engine that owns the run and the live feed sees the Bureau's runs. Only the end-to-end fixtures replace it, through `createConsoleEngine`, because they register workflows of their own; the suite's second host keeps the default.
- **The demo plugin's agents call no model.** A fresh host defines no agent of its own. The `demo` plugin (`plugins/demo`, off by default: turn it on in Settings or with `plugins.demo.enabled` in `configuration.json`, and restart) contributes six agents, `demo:assistant`, `demo:tool-runner` (a read-only tool and a mutating tool held for approval), `demo:request-human-input` (free text, no schema), `demo:echo` (repeats the text of the last message it was sent, so a quoted reply shows exactly what the agent received), `demo:model-switcher` (a selectable agent over `claude-sonnet-5` and `claude-haiku-4-5`, whose reply names the model that answered; the host offers a model only when its provider is configured, so Chat shows the picker on a host that has both and none on a fresh one), and `demo:internal` (a plain agent that answers with a scripted bookkeeping reply), plus the `demo:lookup-order` and `demo:issue-refund` tools, two goal validators, one schedule and one goal. Every one answers from `createScriptedGenerate`, whatever providers are configured. `demo:tool-runner` answers from where the turn has got to, so the run that follows an approval reports what the refund came to, and each turn's calls carry the turn's number. The plugin's `afterStart` creates the schedule and the goal once, recorded under `plugin:demo:seeded-schedule` in the plugin's own storage. `HostOptions.extraAgents` adds agents of a test's own, which is how the end-to-end suite brings an agent that waits on a barrier. Real models come in through the catalog below.

The only module that reads the environment is `src/host/environment-configuration.ts`.

## Running on Postgres and S3

By default the state is a directory on one machine. Set two variables and it is a PostgreSQL database and an S3-compatible bucket instead, so several hosts can run on the same state at once. A rolling deploy is the case this is for: the old release and the new one are both up for a while, they share one deployment, and a run the old release parked is finished by the new one. Remote mode is chosen only by the variables below, which the host reads from its environment (through Bungalow, `@lostgradient/bungalow`). An empty variable counts as unset, and `INTERBOROUGH_HOME` is not read in remote mode. Setting exactly one of the two selecting variables is an error that names the other.

| Variable | What it is |
| --- | --- |
| `INTERBOROUGH_DATABASE_URL` | The Postgres connection URL. Selects remote mode, with `INTERBOROUGH_BUCKET`. It carries the password, so keep it out of logs and commands. |
| `INTERBOROUGH_BUCKET` | The bucket that holds the configuration, the agent and workflow definitions, and the deployment ID. Selects remote mode. |
| `INTERBOROUGH_BUCKET_PREFIX` | Optional. A folder in the bucket, such as `production`, so several installations share one bucket. A leading `/` is dropped and a trailing `/` is added. A prefix with an empty, `.`, or `..` segment is refused. |
| `S3_ENDPOINT` | The S3 endpoint URL. Required. |
| `S3_REGION` | The region. Required. |
| `S3_ACCESS_KEY_ID` | The access key ID. Required. |
| `S3_SECRET_ACCESS_KEY` | The secret access key. Required. |
| `S3_SESSION_TOKEN` | Optional. A session token for temporary credentials. Bungalow refuses to open when the host's process itself carries an `AWS_SESSION_TOKEN` or `S3_SESSION_TOKEN` (an aws-vault or SSO shell, say) and the environment given to the host sets no `S3_SESSION_TOKEN`, because Bun would sign every request with the ambient token. |
| `INTERBOROUGH_SECRET_APPROVAL_SECRET` | Required in remote mode. The secret that signs the approvals a file agent's tools raise. Give every host the same value: an approval one host signed must verify on another. A host without it does not start (the error names this variable, and nothing is listening yet). Locally the host creates it on first use. The host keeps it for itself: a plugin that declares it is refused. |
| `INTERBOROUGH_SECRET_DEMO_APPROVAL_SECRET` | Needed in remote mode only when the `demo` plugin is enabled. It signs the approvals `demo:tool-runner` raises, with the same value on every host. A remote host cannot create it, so the plugin stays `needs-setup` and its agents refuse to run until it is set. Locally the host creates it the first time the plugin is enabled. |
| `INTERBOROUGH_SECRET_ANSWER_ENCRYPTION_KEY` | Required in remote mode. The key secret answers are sealed with: base64url of 32 random bytes (for example `bun -e "console.log(Buffer.from(crypto.getRandomValues(new Uint8Array(32))).toString('base64url'))"`). Give every host the same value, or an answer one host sealed cannot be read on another. A host without it does not start. Locally the host creates it on first use. |
| `INTERBOROUGH_SECRET_ANTHROPIC_API_KEY`, `INTERBOROUGH_SECRET_OPENAI_API_KEY`, `INTERBOROUGH_SECRET_GEMINI_API_KEY` | A model provider's API key, in place of the file in `secrets/`. |
| `INTERBOROUGH_SECRET_TYPESAFE_API_KEY` | The optional TypeSafe key for Bureau's typed decisions (see "Decisions"). |
| `INTERBOROUGH_SECRET_A2A_API_KEY` | The optional A2A key every A2A caller presents (see "A2A"). Give every host the same value. Without it A2A stays on loopback with no key. |

Interborough reads none of the `S3_*` variables itself. Bungalow builds the `Bun.S3Client` from them and the host hands it to the definition sources. `bun run dev` passes all of these variables through Turborepo, so `bun run dev` can start remote mode.

**The bucket layout.** With the prefix `P` (empty, or ending in `/`), the bucket holds:

| Object or folder | What it is |
| --- | --- |
| `P` + `deployment-id` | The deployment's identifier, written once with `If-None-Match: *`. Hosts that start together agree on the one value the store kept. Do not edit it. |
| `P` + `configuration.json` | The plugins' choices, with each provider plugin's allowlist, and the catalog edits (see "Model providers" and "Plugins"). A missing object means every plugin's defaults, and no model is offered until a provider has a key. Put it there yourself; a remote host cannot write it. |
| `P` + `agents/<id>.md` | One agent per object, in the Markdown file format of "Agent files". The agent editor writes here. |
| `P` + `workflows/<id>.json` | One workflow per object, in the format of "Workflow files". The Workflows pages write here. |

The Settings page and the editors show these as `s3://<bucket>/<prefix>...`, and show a provider's key as its variable name. They never show the database URL or an S3 credential, and neither does `/host/paths`. It reports the `mode` and the `database` (a SQLite file's path, or a Postgres server's host, port, and database name), the same `database` the host hands its embedder.

**Durability is locked.** In remote mode the host locks the `durableOwnership.ownership`, `maintenance`, `durable`, `engine.workflowClaimTtl`, and `engine.workflowClaimRenewInterval` settings, which the Settings page shows under Durability as locked and disabled. Bureau reports each as locked for the reason `shared-storage`; a key the host's caller locks reports `deployment`. Each is held to Bureau's code default (automatic maintenance, a durable engine, and a claim TTL above the renew interval), because a stored `maintenance: 'manual'` would start no scheduler on the next release, and a run parked by the old release would never finish on it. Several hosts share a run only because each holds a lease on the runs it works on. Turning that off (`none`) from one host's Settings page would make every host run every task, so the setting stays at Bureau's lease default and a stored change is refused. A local host keeps the control editable. To make a run one host detached run on another host, the other host needs no restart and no call: it claims the run on its next claim-renewal tick, at most 5 seconds (`workflowClaimRenewIntervalMs`) after the first host closes and releases its claims. It is the renewal interval, not the claim TTL, so nothing waits for a crashed host's claim to expire in this path.

**What polling costs.** The agent and workflow sources have no change feed to subscribe to, so each polls its prefix. A tick lists the prefix twice (the poll's scan, then Bureau's `load()`), so Bureau's default of one second would send about 172,800 `LIST` requests a day per source per host (two sources per host: agents and workflows). The host sets the interval to 30 seconds (`REMOTE_POLL_INTERVAL_MILLISECONDS` in `src/host/locations.ts`), about 5,760 requests a day per source per host. A change made from the application applies at once; a change made in the bucket by hand shows up within 30 seconds. Count the hosts you overlap when you read a bill: a rolling deploy doubles it for a while.

**Conditional writes and deletes.** The sources write and delete with `If-Match` on the ETag they just read, so two hosts or a host and a person do not overwrite each other. The in-process S3 server the tests run against (`@lostgradient/testing/s3-server`, modeled on a Railway bucket) honors `If-Match` on `DELETE`, and `host-remote.test.ts` probes it. AWS S3 honors it on `DELETE` only for directory buckets, so on a general-purpose bucket a delete is unconditional after the source's own hash check. Probe the store you use before relying on it.

**The overlap test.** `src/host/remote-overlap.slow.test.ts` starts two hosts at once on one fresh Postgres database and one bucket. Both define an agent that calls a counting tool and then `requestHumanInput`. It asserts that both hosts start, that one schedule exists (the enabled `demo` plugin seeds it from both hosts), that both report one `deploymentId`, that a task started on the first parks with the counter at 1, that after the first closes the review is resolved through the second and the task completes, and that the counter is still 1. Run it with `bun run --filter=@lostgradient/interborough test:slow`. It needs `initdb` and `pg_ctl` on `PATH` or `WEFT_TEST_POSTGRES_URL`, and skips without either.

## Model providers

The Bureau's model catalog holds the models of the providers the loaded plugins contribute that have an API key, and only those. The workspace ships three provider plugins, `anthropic`, `openai` and `gemini` (`plugins/*`), each of which contributes its provider and its catalog rows. With no key set the host starts, the catalog is empty, and the demo plugin's scripted agents (when it is on) run as always. The host reads no environment variable for a key.

A provider needs only its key. To limit the models a provider offers, set an allowlist in `configuration.json` in the state directory, `~/.interborough/configuration.json` or `$INTERBOROUGH_HOME/configuration.json`, as the `models` of the provider plugin's configuration. A missing file means no allowlists.

```json
{
  "plugins": {
    "openai": { "configuration": { "models": ["gpt-4.1", "o3"] } }
  }
}
```

- `models` is an optional allowlist. Each entry names a model or one of its aliases, such as `claude-sonnet-5` or `sonnet`. Leave it out to offer every current model of the provider. An empty list, or an entry that matches no current model of that provider, skips the provider's plugin at startup with a `configuration-invalid` problem that names the field, for example `models[1]`; the host still starts, and the plugin's row in Settings › Plugins shows the problem. The plugin routes refuse such an entry while the plugin is loaded. Retired models are never offered. The host reads it on every catalog load, so a change applies without a restart.
- Turning a provider's plugin off (`"enabled": false`) removes its provider from the catalog on the next start. A top-level `providers` key is not read.
- A question field the agent marks secret (`x-secret`) is encrypted before Bureau keeps it, under the Bungalow secret `answer-encryption-key`, which the host creates on its first local start. To rotate it, move its value to `answer-encryption-key-<keyId>`, where `<keyId>` is the 24-character id every sealed answer's `keyId` names, and write a new key to `answer-encryption-key`; answers sealed under the old key stay readable while that file exists, and are `secret-unavailable` once it is deleted. See [Bureau's secret answers](../../packages/bureau/documentation/secret-answers.md).
- Each provider's API key is the first secret its plugin declares: `anthropic-api-key`, `openai-api-key`, and `gemini-api-key`, one file each in `secrets/` (mode `0600`). Surrounding whitespace is trimmed. A provider with an allowlist and no key is left out of the catalog, and the host logs one warning that names the provider and the secret it expects, never a value. The plugin is `needs-setup` until the key is set.

```bash
mkdir -p ~/.interborough/secrets
printf '%s' "$YOUR_KEY" > ~/.interborough/secrets/anthropic-api-key
chmod 600 ~/.interborough/secrets/anthropic-api-key
```

The host gives the Bureau a `models.catalog` factory, which builds the rows from the providers the plugins contributed once their setup has run, so no boot step plans against a provider without a key, and `bureau.models.replace(rows)` is the only way the rows change afterwards. `host.generateFor({ provider, model })` is the generate for an agent assigned a catalog model: it resolves through Bureau's `resolveProviderGenerate` with the contributed provider definitions and the provider's key, and refuses a model the catalog does not hold or one that is turned off.

### Changing providers without a restart

A local host writes the configuration and a provider's key itself, and applies them at once. Editing the files by hand and asking the host to read them again works the same way.

| Request | What it does |
| --- | --- |
| `GET /host/providers` | Each provider a loaded plugin contributes, whether it is set up (it has a key or an allowlist) and whether it has a key (never the key), its allowlist, and the catalog edits. Carries `lockReason` when writes are refused. |
| `PUT /host/providers/<name>` `{ "apiKey", "models"? }` | Connects the provider, or replaces its key: the key goes to the plugin's declared secret, such as `secrets/<name>-api-key` (mode `0600`), and the allowlist to `plugins.<name>.configuration.models` in `configuration.json`. Without `models` an existing allowlist stays; `"models": null` clears it. |
| `DELETE /host/providers/<name>` | Disconnects the provider: its key is removed, so its models leave the catalog and no run that begins afterwards can call it. Its allowlist and the catalog edits stay for a later connect. |
| `PUT /host/catalog` `{ "edits": [...], "base"? }` | Replaces the catalog edits (below). An empty list removes them. `base` is the list of edits the caller read before it changed them: when it is given and the stored edits are not equal to it, nothing is written and the host answers `409` with `error: "conflict"` and the stored edits as `catalog`. Settings › Models always sends it. |
| `POST /host/providers/reload` | Reads the configuration and the keys again, for a person who edited them by hand. |

Every change is checked against the keys the host holds, and against the models of the provider plugins that are loaded, before any byte is written, and the check and the write run as one step in the configuration queue, so another writer cannot change what it was checked against. An allowlist for a provider plugin that is not loaded (turned off, or skipped) cannot be checked against models the host has not seen: it is stored as given, and the next start skips that plugin with a `configuration-invalid` problem at `models[<index>]`, never refusing to start. Fix the allowlist through the plugin's route or by hand and restart. The files are then read back, the rows become the Bureau's catalog (`bureau.models.replace`), and the agent files are rebuilt before the request answers. A run that began earlier finishes with the key it started with. The first run that begins after the answer uses the new key. The same operations are `host.providers.connect`, `.disconnect`, `.editCatalog`, `.reload`, and `.snapshot`.

The configuration is written atomically (Bungalow's `writeConfiguration`: a temporary file, synced, renamed over `configuration.json`, mode `0600`), so a crash mid-write leaves the previous file whole. An error names the field, such as `apiKey` or `plugins.openai.configuration.models[0]`, and never a value. No response, warning, log line, or diagnostic holds a key.

### Plugins

To write a plugin, start with [the authoring guide](../../packages/interborough-plugin/README.md); this section is the host's side.

The host loads the workspace's plugins (`src/host/plugins.ts`; `HostOptions.plugins` replaces the list for a host that must load others) and composes them into the Bureau with `createBureau({ plugins, pluginConfiguration, pluginSecrets })`. The owner's choices live under `plugins.<name>` in `configuration.json`; a plugin the key does not name takes its descriptor's `enabledByDefault` (`true` when the descriptor leaves it out), and `setup` receives only that entry's `configuration`.

```json
{ "plugins": { "example": { "enabled": true, "configuration": { "limit": 3 } } } }
```

| Request | What it does |
| --- | --- |
| `GET /host/plugins` | Each plugin in load order: the Bureau's listing (status, problems, contributions), the stored `enabled` and `configuration`, `restartRequired`, and each declared secret with `generated`, `set`, and where it lives. Never a value. Carries `lockReason` when writes are refused. |
| `PUT /host/plugins/<name>` `{ "enabled"?, "configuration"? }` | Stores the choices, after the configuration passes the plugin's own schema (a `400` names the field, such as `configuration.limit`, and writes nothing). A field left out keeps what is stored, and `"configuration": null` removes it. A `required` plugin cannot be turned off. The Bureau composes plugins once, so the change applies on the next start (`restartRequired`). |
| `PUT /host/plugins/<name>/secrets/<key>` `{ "value" }` | Stores a secret the plugin declared (mode `0600`; a key it did not declare is a `400`). The plugin uses it at once: one that was `needs-setup` becomes `running` with no restart. |
| `GET /host/mcp-apps` | The panels the running plugins contribute (COR-1894): each one's plugin, app, title, `ui://` URI, and the Bureau tool it opens from. The run page mounts the one that opens from `bureau.tasks.inspect`. |
| `GET /host/plugins/<name>/apps/<app>` | `{ "html", "ui" }`, the built page and its deny-by-default security metadata, which is what Chat's `McpApp` loads. It is JSON, never navigable HTML. |
| `POST /host/plugins/<name>/apps/<app>/tool-calls` `{ "name", "arguments"? }` | Runs a tool for the panel. Only a Bureau MCP tool (`bureau.*`) that is spelled exactly as in the app's `allowedTools` is run, in process, as the local owner, with none of the browser's headers; any other name is a `403` that reaches nothing, an unknown plugin or app a `404`. |

A declaration with `generated: true` is created by the host, a random value in the secret's `0600` file, the first time its plugin is enabled (at start, or when `PUT /host/plugins/<name>` turns it on). A remote host cannot write secrets, so it leaves the plugin `needs-setup` until the deployment sets the variable, and refuses every plugin write with the reason `deployment`. A plugin that declares a secret the host cannot honor (one it keeps for itself, such as the approval secret, the A2A key, the answer-encryption keys or the tool sources' credentials, or a key Bungalow cannot store) is skipped with the problem `secret-refused`, listed `skipped`, and refuses every secret write; the host starts. Every route runs the request guard first, and no response, listing, or log line holds a secret's value.

Folder plugins (COR-1881) load after the workspace's, from each folder of `<bungalow>/plugins/` in name order (`node_modules` and dot-folders are not plugins). A folder holds a `plugin.ts` whose default export is `definePlugin(...)`. The host links `<bungalow>/plugins/node_modules` to this package's `node_modules`, so a folder plugin imports `@lostgradient/interborough-plugin` and the host's other packages with no install of its own (a real `node_modules` directory there is left alone). The host runs with `--no-install`, so an import that nothing provides fails with a message naming the specifier and contacts no registry. Plugin code loads once, at startup; the first plugin loaded keeps a name and a later one is `skipped` with `name-clash`. A folder that cannot load (no `plugin.ts`, no plugin as its default export, an import that fails) has no descriptor and is listed in the `unloaded` array of `GET /host/plugins` with `load-failed`, and the host starts. The host logs one line per plugin at startup, `Plugin <name>@<version> (<source>: <location>): <status>; <problem codes>`.

`bun run dev --plugin <path>` (repeatable) loads that folder as well and lists it with the problem `development-source`. An edit to its `plugin.ts` restarts the host in place under `bun --watch`.

The plugins' embedders and memory detectors reach governed memory through `BureauOptions.memory`'s factory (`src/host/memory.ts`), and `/host/paths` reports the secret file of each provider a plugin contributes.

**Catalog edits.** A `catalog` list in `configuration.json` turns a model off, corrects its price or limits, or adds a row the built-in list lacks:

```json
{
  "plugins": { "openai": { "configuration": { "models": ["gpt-4.1", "o3"] } } },
  "catalog": [
    { "provider": "openai", "model": "gpt-4.1", "off": true },
    {
      "provider": "openai",
      "model": "o3",
      "pricing": { "inputPerMillionTokens": 2, "outputPerMillionTokens": 8, "currency": "USD" },
      "contextWindowTokens": 200000,
      "maxOutputTokens": 100000
    },
    { "provider": "openai", "model": "gpt-next", "basedOn": "gpt-4.1" }
  ]
}
```

An edit that names a built-in model (by `model` or alias) changes that row. A price edit keeps the row's `longContext` rates unless its `pricing` names them: `"longContext": { "inputTokensAbove", "inputPerMillionTokens", "outputPerMillionTokens" }` replaces them and `"longContext": null` removes them. An off model stays listed as `unavailable`, which keeps it from agents and plans, and `host.generateFor` refuses it. An edit that names no built-in model adds a row: `basedOn` names a current model of the same provider whose capabilities it copies, and it may set its own price and limits. An edit with no match and no `basedOn`, a second edit for one model (under the same name or another, such as `claude-haiku-4-5` and `haiku`), or an output limit above the context window fails with the field, for example `catalog[0].model`.

An allowlist (`plugins.<plugin>.configuration.models`) may name an added row by its model, and applies to added rows as to built-in ones: an added row the allowlist does not name is left out.

**Other writers of `configuration.json`.** A write reads the file, changes the part it owns, and writes the whole file back, so writers must not overlap. `host.configurationQueue.run(work)` is the one queue they share (`src/host/configuration-queue.ts`): run the whole read-change-write inside `work`. The provider manager uses it, and any other part of the host that writes the file must too.

**A failed key change.** The key is written before the configuration. When the configuration cannot be written, the previous key is put back and the host keeps using it. If the key itself cannot be written, nothing changed and the answer is a plain `500` with `{ "error": "failed" }`. If the previous key cannot be put back either, the answer is `500` with `{ "error": "partial", "inUse": ... }`, where `inUse` is what the host loaded afterwards: `true` when the host loaded the new key, `false` when it could not read it back (the key is stored but not known to be in use).

**Remote mode refuses.** A remote home keeps its configuration in the bucket and its keys in the environment, which the host cannot write. `PUT` requests answer `403` with `{ "error": "locked", "reason": "deployment" }`, `/host/paths` reports `locked: { configuration: "deployment", providerKeys: "deployment" }` (the reason codes `settings.get` gives a locked key), and `host.providers.connect` and `.editCatalog` throw `ProviderWriteLockedError`. Reload still works, since it only reads.

### Executable skills

An executable Agent Skill is a directory with a `SKILL.md`; the descriptive skills an agent file declares (`skillDescriptors`) are another thing. The host finds skills in the directories `configuration.json` names under `skills`, and trusts only the ones it lists:

```json
{
  "skills": {
    "sources": [
      { "id": "home", "kind": "user", "path": "/Users/me/.agents/skills" },
      { "id": "workspace", "kind": "project", "path": "/Users/me/work/app/.agents/skills" }
    ],
    "trusted": ["home"]
  }
}
```

A source is a directory whose subdirectories are skills: `id` is letters, digits, `.`, `_` and `-`, `kind` is `user` or `project`, and `path` is absolute. Configuring a directory does not trust it, for either kind: a source is trusted only when `trusted` lists its `id`, and `trusted` may name only configured sources. The key is optional, so a file written before it existed loads with no skills, and every other key is left alone. A mistake stops the host and names the field, such as `skills.sources[0].path`.

`bureau.skills.list` shows each skill with its source, trust and allowed tools. A skill from an untrusted source is listed and cannot be activated: the skill client answers `source-untrusted`.

| Route | What it does |
| --- | --- |
| `PUT /host/skills/sources/<id>/trust` `{ "trusted": true }` | Trusts a configured source, or stops trusting it (`false`): writes `skills.trusted` to `configuration.json` through `host.configurationQueue`, applies it at once, and records `skill.source.trusted` or `skill.source.untrusted` in the audit trail, filed under `skill-source:<id>` with the owner. A source that already has the trust asked for changes and records nothing. `404` for a source the file does not list, `400` for a body or a file that cannot be used. |
| `POST /host/skills/refresh` | Reads the configuration and the directories again, for a person who edited a file or added a skill by hand. |

Remote mode refuses a trust change: `PUT` answers `403` with `{ "error": "locked", "reason": "deployment" }` and `host.skills.setTrust` throws `SkillWriteLockedError`, since the bucket's configuration belongs to the deployment. Listing and refreshing still work. If the change is applied but the audit trail cannot take the record, the answer is `500` with `{ "error": "partial" }` and the change stands.

### Saved tool sources

An agent file may list tools from an MCP server or an OpenAPI service the host has saved. Sources are the `toolSources` key of `configuration.json`; each entry holds Armorer's description under `source` (plain JSON from `armorer/tool-sources`, which names a credential and never holds one) and, beside it, any settings of the host's own under `tools`, keyed by the tool's own name. `tools` has one field, `acceptsSecrets` (see below), and a field it does not know is refused, not ignored:

```json
{
  "toolSources": [
    {
      "source": {
        "id": "tracker",
        "kind": "mcp",
        "transport": {
          "type": "http",
          "url": "https://mcp.example.com/mcp",
          "authentication": { "type": "bearer", "credential": "token" }
        }
      }
    }
  ]
}
```

**`acceptsSecrets` per tool.** A tool receives the plaintext of a secret answer (COR-1816) only when its metadata says `acceptsSecrets: true`; any other tool that is handed a `{ secretRef }` fails with `secret-not-accepted` before it runs. A source's tools declare nothing, so the owner opts a tool in under `tools`, keyed by the tool's **own name as the server lists it**, not the `<id>__<tool>` name an agent file uses (the raw name is stable across the naming rules below):

```json
{ "source": { "id": "tracker", "…": "…" }, "tools": { "create_issue": { "acceptsSecrets": true } } }
```

It is off unless `true`: an absent entry, `{}` and `false` are the same. When the source loads, the host sets `metadata.acceptsSecrets: true` on each flagged tool and leaves every other tool exactly as Armorer made it, so only a flagged tool reaches the Bureau's secret-answer resolver. A name the server does not list (or lists but the host does not offer, such as a skipped duplicate or an operation `allowOperations` leaves out) is not an error: the source stays loaded, the setting reaches no tool, and `GET` lists it under `unmatchedSettings` with a reason (the host also logs one line). `acceptsSecrets` must be a boolean; anything else stops the host naming `toolSources[<n>].tools.<tool>.acceptsSecrets`.

`id` is 1 to 20 lowercase letters, digits and hyphens, starting with a letter (a tool name that began with a digit would be refused by Gemini), because it names the Bungalow secret `tool-source-<id>` that holds the source's credentials. A mistake stops the host and names the field, such as `toolSources[0].source.id`. The key is optional, and every other key is left alone.

**The name an agent file uses.** A source's tool is `<id>__<tool>`: the source's `id`, two underscores, and the tool's own name. An `id` never holds `_`, so the first `__` ends it: two sources, or a source and a built-in tool such as `lookup-order` or Bureau's `workflows-*`, can never share a name. The whole name stays within 64 characters, the shortest limit a model provider sets. An agent file stores the name, and a tool approval hangs on it, so the name is a contract that depends on the tool's own name alone, never on what else the server lists or in which order:

- A name made only of letters, digits, `_` and `-`, short enough, and not ending in `-` and eight hex digits is used as it is: `tracker__create_issue`, and an OpenAPI source's `list-pets` is `pets__list-pets`.
- Any other name is `<id>__<readable>-<digest>`: each character outside that set becomes `_`, the readable part is cut so the whole fits in 64 characters, and `<digest>` is the first eight hex digits of the SHA-256 of the tool's raw name. `foo_bar` is `files__foo_bar` and `foo.bar` is `files__foo_bar-` plus its digest, so the two stay apart, and dropping or reordering either never moves the other's name. A name that already ends in `-` and eight hex digits takes a digest of its own, so a plain name and a digested one never meet.
- If two tools of a source would still get one name (a server that lists a name twice, or a digest collision), neither is offered: both are skipped and listed under `skipped` with the reason, and the rest load. Neither the first nor the last wins, since that would let the server's listing order decide which tool a stored name means. A tool with no name is skipped the same way.

Renaming a source's `id` renames its tools. MCP has no allow-list in Armorer, so a source offers every tool its server lists; an OpenAPI source narrows with `allowOperations` and `namePrefix` in its description.

**Loaded at boot, listed after a restart.** The host loads every source before it builds the Bureau, with each tool's capability tier from Armorer (an MCP tool's annotations; an OpenAPI operation's HTTP method), so `bureau.agents.catalog` lists `tracker__…` beside the built-in tools and an agent file may name them. Each tool also carries a version, a digest of what a person approves of it: the source's `id`, where its calls go (an MCP server's URL or command line, an OpenAPI service's resolved base URL), the tool's name and input schema, and its capability (an MCP tool's annotations; an OpenAPI operation's method and path). It leaves out descriptions, a server's own name and version, and credentials, so an unchanged tool has the same version at every start. An approval, and a chat's remembered tool, are bound to that version: a tool whose schema, capability or destination changed asks again. A source added or changed later reads `pending-restart` until the host starts again. One source that cannot load, because it is unreachable, names a credential nobody stored, holds credentials that cannot be read, or does not answer within 30 seconds (at which point a local command's process is stopped, and so is one that is still connecting when the host closes), is reported on its own entry (`failed`, with a message that names no URL or value) and never stops the host or another source. An OAuth source with no tokens is not contacted: it reads `needs-authorization`.

**Credentials are encrypted.** Bearer tokens, API keys, a local command's environment secrets, and an MCP source's OAuth state (tokens, client registration, the PKCE verifier and `state` of a sign-in in progress, discovery state) are encrypted with the AES-GCM helper of `@lostgradient/cryptography`, under the same installation key secret answers are sealed with (`answer-encryption-key`, so a rotation keeps earlier values readable), and kept in `secrets/tool-source-<id>` as JSON: the credential names in the clear, every value ciphertext, each ciphertext bound to its source and name. Rotating the key (see "Secret answers" above) keeps them readable while the retired key exists; once it is deleted the source reads `failed` with "cannot be read" until it is connected again. Nothing else holds them: not `configuration.json`, an error, a log line, the audit trail, or a response.

**Credentials go only where they were given.** A stored credential is carried over to a later `PUT` only when the source goes to the same place: the same kind and, for an MCP server, the same URL (or, for a local command, the same command, arguments and working directory), or, for an OpenAPI service, the same `baseUrl` and specification URL (or inline document's servers). Change any of those and every stored credential and any OAuth sign-in is dropped; the request must supply new credentials, or is refused with `400` naming `credentials.<name>`. Changing something else, such as `allowOperations` or an OAuth scope, keeps them. A new source never starts from a secret an earlier source with the same id left behind, and removing a source clears its secret. Until the host restarts, the tools a replaced or removed source loaded stay connected to the old address and are given no credential or sign-in at all, so a call fails rather than carry the new address's token to the old server; a rotated credential for the same address is picked up at once. The per-tool `acceptsSecrets` flags follow the same rule: they are kept only while the source still goes to the same place, and a change to any of those drops every flag. Connecting a source again also repairs a secret that cannot be read (a retired key that is gone), even for an OAuth source that names no credential.

| Route | What it does |
| --- | --- |
| `GET /host/tool-sources` | Each configured source with its `state` (`loaded`, `failed`, `needs-authorization`, `pending-restart`), `tools` (`name`, `tool`, `tier`, `acceptsSecrets`), `skipped`, `unmatchedSettings` (`tool`, `message`), `settingsPending: true` when the saved tool settings differ from the ones the running host applied, stored credential `credentials` names, and, for OAuth, `authorized`. Carries `lockReason` when changes are refused. |
| `PUT /host/tool-sources/<id>` `{ "source": { … }, "credentials": { "<name>": "<value>" } }` | Connects a source or replaces it: stores the credentials the description names (one already held may be left out), then lists the source in `configuration.json` through `host.configurationQueue`. `source.id` must be `<id>`. Answers `{ id, changed, restartRequired: true }`. With `"create": true` it only connects: a source already saved under `<id>` answers `409` `{ "error": "exists", "field": "id" }` and nothing changes, so a page that lists the sources never replaces one another tab saved a moment before. |
| `POST /host/tool-sources/<id>/probe` `{ "source": { … }, "credentials": { "<name>": "<value>" } }` | Contacts a source that is not saved, as the dialog's Test connection does, with the credentials in the body and none from the vault, and answers `200` with `{ "outcome": "listed", "tools": [{ "name", "tool", "tier" }], "skipped": […] }`, `{ "outcome": "needs-authorization" }` for an OAuth server that asks for a sign-in, or `{ "outcome": "failed", "message": "…" }` for a source that did not answer as it should, in words that hold no address, command or value. It runs against its own deadline (`toolSourceProbeTimeoutMilliseconds`, ten seconds by default), saves, stores and records nothing, and closes the connection before it answers. | `PUT /host/tool-sources/<id>/tools` `{ "tools": { "<tool>": { "acceptsSecrets": true } } }` | Sets the host's own settings for the named tools of a configured source (`<tool>` is the server's own name for it). Answers `{ id, changed, restartRequired: true }`; `404` for a source that is not configured, `400` naming the field (`tools.<tool>.acceptsSecrets`) for a value it cannot use. Recorded in the audit trail as `tool.source.tools-configured`, whose detail lists the tool names `granted` and `revoked` (names only). Loaded at the next start. |
| `GET /host/tool-sources/<id>/affected-agents` | Lists the agent files that name a tool the host loaded from the source, or any tool whose name starts with `<id>__` (so a source that failed, awaits a sign-in, or was added since the host started is covered), in `tools` or only in `toolApproval`, as `{ id, tools: […], affectedAgents: [{ id, name, tools, toolApproval }] }`, without changing anything. Works on a remote host. `404` for a source the configuration does not list. |

It exchanges the code, stores the tokens, and answers a small page that repeats nothing from the request, taking its turn with every other change to the configuration and to that source's secret, so a removal that arrives during the exchange waits for it. The exchange is cancelled after the 30-second load timeout. The tools are listed after a restart. |

URLs in a description (an MCP `url`, an OpenAPI `specification.url`, `baseUrl`) must be http or https without a username or password: the route refuses anything else with `400` and the field, such as `source.transport.url`, and never repeats the URL. A failed configuration write is repaired: the credentials the file still describes are put back, a write that threw after it replaced the file is read back and taken as done, and if the put-back fails too the answer is `500` with `{ "error": "partial" }`. A change that is applied but cannot be recorded in the audit trail answers `500` with `{ "error": "partial" }` and stands.

**Removing a source breaks the agents that use it, and edits none of them.** Read `GET /host/tool-sources/<id>/affected-agents` first. An agent counts as affected when its file names a tool the host loaded from the source, or any tool whose name starts with `<id>__`, so a source that failed, awaits a sign-in, or was added since the host started is covered too. A removal never rewrites an agent file: the files stay byte for byte as they were, and the audit entry (`tool.source.removed`) names the affected agents (`affectedAgents`, comma-joined identifiers, and `affectedAgentCount`). The agents change at the next start, like every other change to a source: the tool catalog the Bureau runs with is fixed when the host starts, so until then the removed tools stay in it but every one refuses to run (whatever the kind of source: a key an OpenAPI source read at load, a local command's environment and an open MCP session can no longer be used, and the connection is closed and a local command stopped), so an agent that calls one gets an error, and the agents stay `ready`. After the restart each affected file reads `invalid` with `unknown-tool`, naming the tool, until the owner detaches it from `tools`; a file that named a tool only in `toolApproval` was already `invalid` (`unknown-approval-tool`) and stays so until that entry is removed. The source's secret is cleared with it, which also clears the OAuth state of a sign-in that was still waiting; a callback that arrives afterwards finds no sign-in and answers `400`.

**A local command is the owner's.** A source whose transport is `stdio` spawns a process on this machine, so only the owner principal may add it; anyone else gets `403` with `{ "error": "owner-only" }` (`ToolSourceOwnerOnlyError`), and nothing is written. Every connect, removal, sign-in and tool-settings change is recorded in the audit trail under `tool-source:<id>` (`tool.source.connected`, `tool.source.removed`, `tool.source.authorized`, `tool.source.tools-configured`), and a local command's record carries its `commandLine`: the executable and its arguments, never its environment or credentials.

**Remote mode refuses.** The bucket's configuration and the environment's secrets belong to the deployment, so every change answers `403` with `{ "error": "locked", "reason": "deployment" }` and `host.toolSources.connect`, `.configureTools`, `.remove`, `.authorize` throw `ToolSourceWriteLockedError`. Reading (including the affected-agents preview), and loading what the deployment configured, still work.

### Decisions

Bureau answers typed questions (`bureau.decisions.decide`, and the `decide` tool a task can call) with a decision model, chosen by the `decisions.model` setting. The `typesafe` plugin (`plugins/typesafe`) contributes TypeSafe's Jev as `typesafe:jev`, which answers `boolean`, `choice`, and `scale` questions, and the host makes it the default while the plugin is enabled. The plugin needs the `typesafe-api-key` secret (a file in `secrets/`, mode `0600`, whitespace trimmed): until it is saved the plugin is `needs-setup` and a decision routed to `typesafe:jev` fails with `PluginNeedsSetupError`, and saving it applies to the next decision with no restart. Switching `decisions.model` to `catalog` on the Settings page sends every question to the language-model fallback instead; the next decision uses the new choice. A `structured` question always goes to the catalog's fallback row (`anthropic/claude-haiku-5-5`, else the cheapest priced row with structured output), which needs a configured provider. With neither, `decide` fails with `NOT_CONFIGURED`.

## Agent files

Agents can be Markdown files in `agents/` under the state directory, `~/.interborough/agents/` or `$INTERBOROUGH_HOME/agents/`. The host creates the directory and passes it to the Bureau as an `agentSource` (`agentFileDirectory` from `@lostgradient/bureau/sources`), so a file `researcher.md` is the agent `researcher` and a change to the directory takes effect without a restart.

```md
---
name: Researcher
description: Finds and cites sources
model: anthropic/sonnet
tools: [lookup-order]
---

You are a careful researcher.
```

- `model` is `<provider>/<model-or-alias>` and must be a row of the model catalog above, so it needs a configured provider with a key. The agent runs with that key through `host.generateFor`. A model that is not in the catalog leaves the file `invalid`.
- `tools` names tools from the host's tool catalog, which holds the read-only `lookup-order` tool. Anything else leaves the file `invalid`.
- A file that cannot be used stays in `bureau.agents.list()` with `state: 'invalid'` and a typed `problem`, and never runs. A file may share its name with a demo agent, since the plugin's agents are named `demo:<name>`.
- Every file agent belongs to the local owner, `anonymous:local`.

The host serves every ready agent to chat. An agent's `a2a` opt-in decides whether it is also served over A2A, as [A2A](#a2a) describes. See the Bureau's `documentation/agent-files.md` for the format.

### The agent editor

`/agents/new` creates an agent and `/agents/:agent/edit` edits and deletes one, through the Bureau's `bureau.agents.definitions.*` and `bureau.agents.catalog` operations (`src/lib/agent-definitions.ts`). The page lives in `src/routes/agent-editor` and renders in its own view, `agent-editor`, whose states are loading, error, forbidden, and not found.

- **The fields** are name, identifier, description, model, tools, and the instructions body. The tool list is exactly what `bureau.agents.catalog` returns. The **model** is a grouped list (`agent-editor-model-field.svelte`): the catalog's models under their provider, each with the abilities the catalog declares for it (context window, tool use, images, structured output, streaming; the catalog already carries them, and `src/lib/agent-definitions.ts` reads them), and the abilities of the chosen model under the field. A model is listed and disabled, with its reason, when the model policy forbids it (the `deployment` and `bureau` layers of the `modelPolicy` setting, matched the way Operative's selector matches them: a denied provider by name, a denied model by its own name; the `users` layer is a preference and binds no agent; the Bureau refuses a save that names such a model, with a `model-policy-denied` problem the page shows as it shows any other refusal, and fails any run step on one, so the list marks in advance what a save would be refused for), when it is turned off in Settings › Models, or when it is retired. A provider the host can call and has no key for (`/host/providers`) has no row in the catalog, so it is listed as one disabled option with a link to Settings › Models. The model an agent's file already names stays selected even when none of that holds now, with a notice ("no longer offered" when the catalog lacks it, under its own provider's group, connected or not), and the field says what a save does with it: a model that is only turned off is written back as the file had it, and one that is retired, gone from the catalog, or forbidden by the model policy is refused until the person chooses another (the file stays listed and editable). With no provider configured the catalog has no model and the page shows no form. It shows where to add a provider instead (the configuration file, an example `plugins` entry, and the file that holds each provider's API key) with a reload that asks the Bureau again. `skillDescriptors` has no field: a save sends the loaded `skillDescriptors` back unchanged. The A2A switch is the one control beside the form's footer.
- **The identifier** is the file name without `.md`. On `/agents/new` it fills in from the name as a slug and can be edited until the first save, and after that it is read-only. A taken identifier, whether another file or an agent defined in code, shows on the field and writes nothing.
- **The A2A switch** sets the agent's `a2a` opt-in. It travels with a save like any other field, so turning it changes nothing until the person saves.
- **Conflicts.** Every write names that `hash`. A file that changed on disk since is refused as `StaleRevision`, and the page says the agent changed outside Interborough, with a reload that discards unsaved edits. A file that was deleted on disk is the not-found state, and so is an identifier that names no agent or an agent defined in code. A file the Bureau cannot use opens the editor in an error state with its problem and its path.
- **The file path** comes from the host's `/host/paths`, which names the agent directory and the workflow directory, the `configurationFile` where model providers are configured, and the `providers` the loaded plugins contribute, each with the `secretFile` that holds its API key. The revision history under the form lists the versions that have run, each by its short hash and last-run time, most recently run first. A save alone does not add a row.
- **Entry points.** The agent list has a New agent action, and an agent's page has an Edit action when the agent is a file; an agent defined in code has no Edit, because the editor would not find it. The list also shows each invalid agent file, with its error, its path, and a link to its editor, because `bureau.agents.list` leaves invalid files out and the list reads `bureau.agents.definitions.list` for them. A deleted agent leaves the list.
- **The identifier `new`** is refused, because `/agents/new` is the page that creates an agent and an agent called `new` could never be opened.
- **After a write** a save lands on `/agents/:agent`, and a delete lands on `/agents`.

The Playwright suite gives its host a provider configuration and a fixture key in the temporary home, and a fake provider client, so its catalog holds `anthropic/claude-sonnet-5` and `anthropic/claude-haiku-4-5`, and saving, conflicts, history, and deletion run against the real Bureau (`tests/e2e/e2e-server.ts`, `src/host/fake-provider.test-support.ts`).

## A2A

The host mounts Bureau's A2A 1.0.1 handler under `/bureau/a2a/<agent>` (COR-1819), so another agent or tool can read an agent's card and send it work. Only an agent that opted in is served:

- A file agent opts in with `a2a: true` in its own file (the agent editor's A2A switch). Turning it off takes the card down and refuses new tasks, and the agent keeps serving the tasks it already has until the last of them is past its retention.
- A code agent opts in by name through `HostOptions.a2aAgents`. The default is none, so the demo agents are not served; naming an agent the host does not define stops the host at start.
- The card is at `http://127.0.0.1:<port>/bureau/a2a/<agent>/.well-known/agent-card.json` and names the interface URL `http://127.0.0.1:<port>/bureau/a2a/<agent>`. Both are derived from the origin the listener ended up on, so a host started on port 0 names the port it got.
- **Without an A2A key** A2A has no authentication, as the rest of the host has none: it is reachable only on the loopback listener, behind the same request guard as the rest of the host, and every call acts as the owner (`anonymous:local`). A caller therefore sees what the owner sees, including `bureau.agents.list`, `bureau.agents.models`, and `bureau.deployment.get`.
- **With an A2A key** (COR-1904) every A2A JSON-RPC call must present it as `X-API-Key: <key>` or `Authorization: Bearer <key>`, on loopback too, and a call without it or with another key is a 401. The key is the Bungalow secret `a2a-api-key`: `~/.interborough/secrets/a2a-api-key` locally, `INTERBOROUGH_SECRET_A2A_API_KEY` in remote mode. The operator chooses it; the host never makes one up, never logs it, and compares it in constant time, and a secret that is blank once trimmed stops the host. The key acts as `api-key:a2a`, which holds the asset scopes a file part needs and no operator scope, so it can name only the agents that opt in, and on loopback, where it also reaches the management plane, `bureau.agents.list` and `bureau.agents.models` show it only those agents and `bureau.deployment.get` refuses it. Every holder of the key owns its tasks as that one principal, so they see each other's tasks. The cards stay public, as the A2A specification has them, and advertise the API-key schemes. The host's own pages send no credential and keep acting as `anonymous:local`.
- **Reaching A2A from elsewhere.** The host still binds loopback only; a reverse proxy on the same machine forwards to it. `INTERBOROUGH_A2A_PUBLIC_ORIGIN` names the origin the proxy serves, such as `https://agents.example.com` (an `https` origin with no path, or the host does not start), and the proxy must pass that `Host` through. A proxy that rewrites `Host` to the upstream's own address (nginx's `proxy_pass` does unless `proxy_set_header Host $host` says otherwise) exposes the whole host, every page and the engine included, to its callers as the owner, because the guard cannot tell its requests from a local one. A request naming that `Host` (with or without `:443` written out, and no other port) is let through the request guard for `/bureau/a2a/*` and `/bureau/assets/*` only, with no `Origin` or that origin's own; every other path refuses it with 403, as the guard refuses any other foreign `Host`. The cards then name the public origin. A public origin needs the A2A key, or the host does not start. Generated media and file parts name the asset route `<public origin>/bureau/assets/<id>/content`, which a remote caller reads with the key: the Bureau serves an asset only to its owner, so the key reads the media of its own tasks and another owner's asset is a 404. An asset request from the public origin without a credential is a 401 at the guard, because the Bureau would serve it as the owner.
- **Push notifications** are off by default. The `a2a.push.enabled` setting turns them on and `a2a.push.sweepIntervalMs` sets how often configurations of vanished tasks are swept (default one hour, at most 2147483647). Both apply at restart: the host reads them once when it builds the handler. With the setting on, a card declares `pushNotifications`, configurations and deliveries are kept in the host's database, and a delivery loop runs until the host closes (`src/host/a2a-push.ts`). Delivery uses Weft's default egress policy, which allows HTTPS to public addresses only, so a configuration naming a loopback or private address is refused at delivery. Settings › A2A (`/settings/a2a`) shows both, saved through `bureau.settings.update` like the rest of Settings, with a note that they apply at restart.
- **Settings › A2A** lists the agents that opted in, each with the address of its card. The address is read from the card itself (`GET /bureau/a2a/<agent>/.well-known/agent-card.json`, which is public), because the card names the public origin when `INTERBOROUGH_A2A_PUBLIC_ORIGIN` is set and the browser cannot know it; a card that declares a security scheme is marked as needing the A2A key. The opt-in is the agent's file, so each row links to the agent's editor and the page writes no agent file of its own. With no agent opted in, the page says so and links to Agents.

## Workflow files

Workflows are JSON files in `workflows/` under the same directory, `~/.interborough/workflows/` or `$INTERBOROUGH_HOME/workflows/`. The host creates the directory and passes it to the Bureau as a `workflowSource` (`workflowFileDirectory`), so a file `nightly-digest.json` is the workflow `nightly-digest`: it runs on the schedule its `trigger` names, its `agent` steps run any agent above, and a change to the directory takes effect without a restart. Every workflow belongs to the one local owner. See the Bureau's `documentation/workflow-files.md` for the format.

The host keeps what a workflow writes with `ctx.log` beside its run (COR-1811): the newest 500 lines per run (`logs.maximumLinesPerRun`), each line (message and attributes together) held to 2 KiB, for 7 days after a finished run last wrote one (`retention.logs`, swept by the maintenance pass; a run that is still active, such as one parked on a signal or a review, keeps its lines), with the count of lines the cap evicted. Both keys are on the Settings page. Read them through the engine API, `GET /v1/workflows/<id>/logs` (`weft.workflows.logs.list`), optionally narrowed with `?step=<n>` to the lines logged before that durable step. The sink is buffered and flushed on shutdown, so a crash can lose the last turn's lines. The Run page does not show them yet.

The bell reads the Bureau's notifications (COR-1941): a failed run and a run over its budget come from `bureau.notifications.list`, written by the Bureau for top-level runs only, so a run that fans out into children notifies once. Reading one in the bell marks it read in the Bureau (`bureau.notifications.markread`, in calls of 100), so another browser agrees; the bell holds it as read at once and as unread again, with a notice, if the Bureau does not accept it. A list the bell could not read says so, with Try again, and never shows the empty state. A schedule that missed a fire is an item too, from `bureau.schedules.missed` for the schedules whose `missedFireCount` is not zero, for a day (the Bureau writes no notification for a missed fire). The panel ends with links to Notification settings (the Settings page, where `retention.notifications` is) and Hooks, where email or webhooks are set up. The bell still derives what is waiting on you from the pending reviews, not from the Bureau's `review.waiting` notifications, because a decision made anywhere has to remove the row at once; the two describe the same wait, and the bell shows it once. The host keeps notifications for 30 days (`retention.notifications`, on the Settings page). It keeps settled webhook hook delivery records for 30 days too (`retention.hookDeliveries`, COR-1943); a pending delivery is never removed.

## The Workflows area

`/workflows` joins two services (`src/lib/workflow-catalog.ts`): the engine's catalog, which lists every workflow type it can run (`weft.workflows.definitions.*`), and the Bureau's workflow files (`bureau.workflows.*`, `src/lib/workflow-files.ts`). The Bureau's file `digest.json` is loaded by the engine as a source named `digest`, so the two are joined on that name. Five routes share one view, `workflows`, and one component, `src/routes/workflow-definitions/index.svelte`:

- `/workflows` lists the workflows a person can read as a table, under the records toolbar (the count, a search and a status filter, Internal workflows, and New workflow). A row says what the workflow is for (the file's `description`, else the engine's), its kind (`Agent-authored` for every Bureau file, `Code` for a type code registered), the agent that owns a file (monospace), what starts it in words (`Every hour`, `On the signal deploy`, a code type's schedules), how many instances began in the last 24 hours and how many are running, when the last began, and its status in one of the seven words (`src/lib/status.ts`; Failed for a file the Bureau cannot use or a source that failed to load, then Paused, Running, Scheduled, or none). A file's trigger and counts come from `bureau.workflows.list` (`trigger`, and `runs` when the call passes `includeRuns: true`, counted from the engine's own totals; the schedules page's overlay does not ask, because each count reads the engine); a code type's from `weft.workflows.list` with `limit: 1` (its `total`) and its schedules, read apart from the list so a count the engine would not give is left out, never shown as zero. The types the Bureau registers itself to run agents, goals, and its heartbeat (`RUN_ENGINE_WORKFLOW_TYPES`) are not workflows a person starts, so they have a page of their own, `/internal-workflows`, linked from the toolbar as "Internal workflows (n)", which lists each with a line on what it does. It is a path of its own, so a workflow named `internal` keeps its page. With none besides them the page says there are no workflows yet and where one is written (the host's `workflowDirectory`), and New workflow in the toolbar opens `/workflows/new`. A file the Bureau cannot use is listed with its error, its issues, and its path, and a source that failed to load shows the category of its failure. A source the engine holds that has no file is a deleted file the engine has not yet forgotten, so it is left out and the list reads the same before and after a restart.
- `/workflows/new` is the JSON editor seeded with a template (a name, a description, a schedule trigger, one agent step), saved through `bureau.workflows.create`. The `name` in the text is the identifier and is not sent; one that is not an identifier, is taken, or is `new` (the address of this page, so a workflow called `new` could never be opened) is refused with the reason and nothing is written. A save lands on the new workflow's page.
- `/workflows/:workflow` leads with what a person acts on: what the workflow is for, what starts it and whether it is active, its steps (for a file), its last five runs (`bureau.workflows.runs.list` for a file, the engine's `weft.workflows.list` for a code type) with a link to all of them, and the schedules that start it: the active and the paused, never a cancelled generation (`weft.schedules.list` with `workflowType`). A file offers pause or resume, edit, delete, and send signal. A Details disclosure holds the file's path, its trigger as written, and what the engine's contract declares (signals, updates, queries, input and output schemas); a fact the workflow does not have is not a row, and a code type that declares nothing has no Details. A collapsed Engine disclosure holds the engine's revision panel and its install form (a code type), or the versions that have run (`bureau.workflows.revisions`, which does not list a version that was saved and never ran, and offers no activation; a file); a type the Bureau registers itself has none. An invalid file shows its problem and path, offers only delete and edit, and has no definition, runs, or status; one with no `hash` offers nothing.
- `/workflows/:workflow/runs` is the list from `/runs`, narrowed to the type (`weft.workflows.list` with `type`). Each row links to `/runs/:run`, whose type links back.
- `/workflows/:workflow/edit` edits an agent-authored file's JSON in Cinder's `JsonEditor`. The text shows the file's `name`, and the update does not send it, because the Bureau's update schema rejects a key it does not know. Text that is not JSON, and a document the Bureau refuses, show the error and save nothing. An invalid file opens with its problem above the editor, so it can be fixed.

A type exists when the Bureau has its file, or when the engine has it as code. When the Bureau has no file and the engine has no definition, or has one it loaded from a source, the type is not found, so a deleted file is not found both before and after a restart. A failure of either service is a failure and never a missing type.

Every write names the `hash` of the file the page read. A file that changed on disk since is refused as `StaleRevision`: the page says the workflow changed outside Interborough, with a reload that discards unsaved edits, and changes nothing. After a pause or resume the page takes the file's new hash at once, so the next action is not stale against its own write. Send signal calls `bureau.workflows.signal` with a name, which starts as the trigger's signal name or the first one a step awaits, and an optional JSON payload, and says how many instances it started and delivered to. The file path comes from `/host/paths`, which names `workflowDirectory` beside `agentDirectory`.

The Playwright host serves its console from the fixtures' engine, not the Bureau's (see "One engine" above), so a Bureau file has no engine definition, schedule, or run there. The list, a file's page, its actions, its signal, and its editor run against the real Bureau through three seeded files (`tests/e2e/seeded-workflow-files.ts`); the definition, schedules, revisions, and runs of a type run against a fixture type, `inventory-sync-sweep`.

## Schedules, goals, and the audit trail

There is one scheduler, Weft's, and `/schedules` lists every schedule it holds. A Bureau schedule is a native Weft schedule that fires the built-in `agentRun` workflow, and an agent-authored workflow's schedule is the trigger in its file, so each row says what it starts and links to it (`src/lib/schedule-kinds.ts`, `src/routes/schedules/schedule-target.svelte`). The kind decides which service writes it:

- An **agent run** (`workflowType` `agentRun`) is the Bureau's. `bureau.schedules.pause`, `resume`, `cancel`, and `update` each name the `revision` of the schedule the page read, which Weft compares inside its serialized write, and the row links to `/agents/<agent>` from `agentName` on the Bureau's view. Its edit page (`/schedules/:schedule/edit`) holds the cadence, the description, and an overlap policy of `skip` or `allow`, the fields `bureau.schedules.update` takes. It is created on the new schedule page by choosing Chat with an agent, which takes an agent, the message each fire sends, an optional chat to continue (chosen from the chats the Bureau lists, which also fixes the agent), a cadence, a description, and an overlap policy (`bureau.schedules.create`).
- A **workflow file's schedule** is the one the Bureau lists with its own id (`bureau-workflow-schedule:<file>:<n>`) and with no agent. The Bureau decides by that id and never by the type, so a schedule the engine made for a file's type is the engine's, and the page does the same. It is paused and resumed through `bureau.workflows.pause` and `resume` with the hash of the file the page read, as the Workflows area does, and everything else about it is edited in the workflow, so it has a link to `/workflows/:workflow/edit` in place of Edit and Cancel. It is never created here.
- Any **other** schedule is the engine's, through `weft.schedules.*`, with the full edit page. The engine compares nothing inside its own write, so a write to one reads the schedule again just before it and refuses, as stale, when its revision or status moved. Its writes do not wait on the Bureau: a type that is not a workflow file's is the engine's whether or not the Bureau answered, and when the Bureau's files did not answer, a type the engine holds as code is not a file's.

`/schedules/new` makes a schedule in the order the sentence does: which workflow, with what input, and when. The workflow is chosen from a searchable picker grouped Built in (Chat with an agent), Recent (the workflows the newest schedules start) and All workflows, each named in words (`humanizeIdentifier`) with its description. It offers code-defined types only: the agent-authored ones, whose schedule is the trigger in their file, are listed disabled with that reason, and every type the Bureau's run engine registers (`RUN_ENGINE_WORKFLOW_TYPES`, read from `@lostgradient/operative/run-engine-workflow-types`: `agentRun`, `durableHeartbeatTick`, and `goalRun`), which only the Bureau starts, with the owner, agent, and validator checks a schedule made here would skip, are not listed, so a type added to that list is reserved with no edit here. Only the built-in chat asks for an agent and a message; any other workflow asks for its own input, drawn from its schema by the same component the run setup page uses (`workflow-input.svelte`), or says it takes none. When is the block both pages share (`schedule-when.svelte`): a cadence field that is out of range refuses the save, because the builder keeps the last valid cadence it emitted. The page is not a form, so Enter in a field never makes a schedule; only Create does. A schedule is made in the zone the builder shows, which the next runs and the detail page name.

A write whose revision or hash is no longer current is refused and nothing is written; the page says the schedule changed since it was loaded, reads it again, and leaves the next move to the person. A schedule only the Bureau can place (a schedule of a workflow file's type that it did not list as the file's own) is of no known kind while it has not said, and nothing is written to it. `/schedules` is a table (the schedule and what it runs, how it repeats with the zone a cron is read in, its next run, its last run, and one of the seven status words, `scheduleStatusWord` in `src/lib/status.ts`), whichever way each schedule was made. `/schedules/:schedule` is a schedule's page: its status and a sentence of what it runs and when; the next runs in the zone the schedule is read in, with the zone named, and Skip the next one; the past runs, which are the runs it started and the fires it missed in one table, read from what the engine persisted (`weft.workflows.list` with a `scheduleId`, and `bureau.schedules.missed` or `weft.schedules.missed`), so they are the same after a reload; and the details beside them. The header has the On switch (pause and resume), Run now, and Edit. Skip the next one and Run now go through `bureau.schedules.skipnext` and `runnow` for an agent run, and through the engine for a code-defined schedule (`skip-next` is the REST call, because the JSON-RPC client reads its empty answer as invalid); a workflow file's schedule offers neither, because the Bureau answers them as not found. A fire moves neither a schedule's revision nor its status, so a skip names the run the page showed (`occurrence`, an ISO 8601 instant to the Bureau and milliseconds since the epoch to the engine) and the service compares it inside its own write (COR-1985): a run that is no longer the next one is refused as `occurrence-not-next` (the Bureau's `Conflict`) or `ScheduleOccurrenceNotNextError` (the engine's), which the page shows as the schedule having changed since it was read, and reads the schedule again. `/schedules/:schedule/edit` edits a schedule.

`/goals` is in the sidebar after Schedules (`g` then `l`). It lists the caller's goals (`bureau.goals.list`) as a table, each status in one of the seven words (a goal that spent its attempts has Failed), with a toolbar of the count, a status and agent filter, and New goal. A goal's identifier opens `/goals/:goal` (`bureau.goals.get`), which lists its attempts, each linking to its run. `/goals/new` creates one, replacing the drawer, from an agent chosen from the agents the Bureau lists, a prompt, an identity, a validator named by free text, and a maximum number of attempts (`bureau.goals.create`), and cancels one that has not ended, after a confirmation and with the revision it read. The Bureau needs a bound on all the attempts together besides how many it may make, so the form also asks for the most steps, which starts at 50. A validator the Bureau lacks is `Unprocessable`, said on the page. The host seeds a validator that never passes (`never-passes`, version `1`), which waits until it is cancelled, so a goal that names it stays going until a cancel ends it as `canceled`.

`/capabilities` (`g p`) lists what agents can use, read only. Its Tools tab lists every tool of `bureau.agents.catalog` with its tier (reads only, changes things, dangerous, or not classified), whether an agent's call is approved by default, where the tool comes from, its input schema and the agents that use it. Its Skills tab lists the executable skills of `bureau.skills.list` with their source and trust: a skill whose source the host does not trust is marked and says why agents are refused it. A skill's users are read from the agents defined in code (`codeDefinition.skills`), because an agent file names none. Trust is changed in the host's `skills` configuration, not on this page. Its Sources tab (`?tab=sources`) lists the tool sources the host saved (`GET /host/tool-sources`), MCP servers and OpenAPI services, with where each stands (connected, failed, needs a sign-in, or starts next time), the tools it offers with their tier and whether each asks first by default, and the credentials it holds by name, never by value. Each tool has an Accepts secrets switch, off by default, that writes `PUT /host/tool-sources/<id>/tools` at once and reads back from the saved setting (`savedAcceptsSecrets`), because the running host loads it at its next start. Sign in starts an MCP OAuth sign-in and opens the authorization address in a new tab; Remove lists the agent files that name the source's tools before it removes the source. The open item is the address's `tool`, `skill` or `source` parameter, and the tab is `?tab=skills` or `?tab=sources`.

`/health/audit` searches the Bureau's trail (`bureau.audit.query`) by a `since` time, a free-text `type`, and a resource sent as `runId`, which takes a run id or `schedule:<id>`, `session:<id>`, `agent:<id>`, or `workflow:<id>`. The host keeps the trail 90 days (`retention.audit`, replaced by a value stored on the Settings page), and the maintenance sweep prunes older records. Records come oldest first, as the Bureau returns them, and Load more follows `nextCursor`. The address holds the filters. The page is a list with the open record beside it (the record's key is the `record` parameter): who, what and when on each line, and the record, with a link to the thing it is about, in the pane. The operation takes no actor, so Who narrows the records already loaded and is never sent. Export reads every page the filters match and saves them as JSON Lines (`audit-log-<date>.jsonl`), and `G` then `U` opens the page. `/health/audit` and `/goals` hold no console scope: the Bureau shows each caller what it owns, so owner scoping is the gate and a principal holding no scope sees its own records.

`/health/storage` is the key explorer, behind `storage:admin`: a table of keys (Key, Group, Size) with the selected key's pane beside it, a Group select, and a search that keeps the keys containing its text. Storage is read in key order from a cursor, so Load more continues from the last key read, and a search reads up to ten requests of a hundred keys before it offers Load more; storage keeps no time a key was written and no count per group, so the table has no Updated column and the select lists groups without counts. The line under the title names the backend (`/host/paths`: SQLite and its file, or Postgres and S3) and opens the six facts the storage reports. Writes are per key, after a confirmation, and refused for a key under a Weft prefix (`WEFT_RESERVED_KEY_PREFIXES`) or a Bureau prefix (`BUREAU_RESERVED_KEY_PREFIXES`, which only the host can import, so the page reads it from `GET /host/storage`); until that list is read, no key is editable. A storage that reports `conditionalBatch` writes a key only if it still holds the value the pane read, and a changed key writes nothing. `G` then `T` opens the page.

The Playwright suite runs a second host (`E2E_BUREAU_PORT`, `tests/e2e/e2e-server.ts`) whose console is the Bureau's own engine, because the main host's console is the fixtures' engine and cannot see a schedule the Bureau holds. The schedules specs for an agent run and a workflow file's schedule open it, and the specs for an engine schedule open the main host.

## Hooks

`/hooks` is in the sidebar after Goals (`g` then `h`). A hook does something when a published Bureau event happens, and the host turns them on for every home (`src/host/hook-options.ts`). A remote home keeps its secrets in the environment and its private-network addresses are not the person's own, so its secret port refuses a write with the reason `deployment` and `urlPolicy` sets `allowPrivateNetworks: false`: it cannot send a signed message, the editor does not offer one, and it can start a workflow, notify, or run a plugin's action. `/hooks` lists the caller's hooks (`bureau.hooks.list`) as one table: the hook as a sentence ("When Review requested, send a signed message to ..."), what it is Only for, when it last delivered, and an On switch (`bureau.hooks.update`, naming the revision read). The list carries each hook's newest delivery, so a page of hooks is one read, and a hook whose last delivery failed is listed first. A search over the sentences and filters by event and by agent narrow the list, and the address holds them. An agent's Hooks tab (`?tab=hooks`) is this table narrowed by the Bureau to the hooks limited to that agent, and its New hook opens `/hooks/new?agent=<name>`, which starts limited to it. `/hooks/new` and `/hooks/:hook` are the editor, three labelled steps: 1 When (a searchable picker over every event `bureau.events.catalog` describes, grouped by area, each in plain words with its raw kind beside it, matched by words, kind, area and meaning, then Only for, which adapts to the events chosen: it offers the subjects every one of them can be told by, from `scopes` in `bureau.events.catalog` (an agent, a workflow, a schedule), and says so instead for events about the whole system), 2 Then (send a signed message to a web address with a signing secret, start a workflow that is ready and not paused, or notify the owner, or run an action kind a running plugin contributes, with its fields drawn from the schema `bureau.plugins.kinds` reports), and 3 Check (the hook as a sentence, a name, Save, Send a test event, Delete). An event the chosen action cannot listen to is listed but cannot be chosen: a notification hook cannot listen to `notification.created`, and a workflow hook only to events a run names or that no run can cause. The kind of action is fixed once a hook is made. The signing secret is write-only: it goes out with a create or an update and is never loaded back, so an existing hook opens with the field empty and an empty field keeps the secret. Send a test event is a real request: it posts one signed `hook.test` message to the saved address (`bureau.hooks.test`), and only a webhook hook can send one, because a test would otherwise start a real run or write a real notification. The hook's recent deliveries sit beside the steps as plain lines (status, the event (its plain words with the raw kind beside them) or a test, what the receiver answered or why there was no answer, attempts, when). Weft's own events are not hookable, because the Bureau does not subscribe to the engine's feed.

## Settings

`/settings` is the Bureau's runtime settings (`bureau.settings.get`, `schema`, and `update`), drawn from the schema the Bureau publishes, so a key it adds appears with no change here. Settings has seven sections, each a route (`src/routes/settings/settings-sections.ts`): General (every setting but the model policy, `decisions.*` and `a2a.*`), Models (`/settings/models`), Model policy (`/settings/model-policy`), A2A (`/settings/a2a`), Plugins, Data and retention, and API reference. Settings › API reference is one page with a side list of four groups, not tabs: Operations, Discovery documents (`?document=` names the open one), Your scopes, and Workflow sources (the registered workflow types and the dynamic sources); `?group=` names the open group. Settings › Models is one page with three parts and no tabs: Providers (`GET /host/providers`: a provider with a key shows a Connected dot and Manage, one without only Connect, and the connect form `PUT`s the key to `/host/providers/<name>`, which stores it and adds the provider's models with no restart; the key is held in the field only until the request settles and is never echoed), Models (the catalog table: context, abilities and price per row, an On switch, Edit, and Add a model, kept as unsaved catalog edits until Save models sends the whole list in one `PUT /host/catalog`), and Decisions (`decisions.model`, `decisions.fallbackModel` and `decisions.maximumPerTask`, saved through `bureau.settings.update` like the rest). TypeSafe has no Connect control on this page yet: its key is saved through the plugin secret route (`PUT /host/plugins/typesafe/secrets/typesafe-api-key`) or its secret file. Which control a key gets is read from the shape of its schema node (`src/routes/settings/settings-controls.ts`): a Cinder switch for a boolean, a select for an enum, an input for a string, a number input for a number, and a select of the model catalog's rows for the keys that name a model (`decisions.fallbackModel`, `context.summarizerModel`; `decisions.model` chooses among the decision models a host registers). Every object, and every union with one (the retention windows, `engine.history`), is a Cinder `SchemaForm` over the node, with Zod's `anyOf` read as the `oneOf` the form draws as a choice; `tools.humanInput` is a switch and a form for its options. Only a node nothing else reads falls to the JSON editor. A description is inline Markdown, and a setting with no value reads Not set. The page is not a `<form>` (a `SchemaForm` is one), so Save is a button marked `data-changes`, and ⌘Enter saves from anywhere on the page (the shortcut registry's `modifier: 'mod'`). Only a key that needs a restart says so, and the page sums up the keys that wait for one. Settings › Model policy edits the `modelPolicy` setting in plain words, Allowed models (the shared layer) and Your preferences (the entry for `anonymous:local` under `users`); its revision is raised by the save, never typed. Keys are grouped by their first segment, with `durable`, `maintenance`, `durableOwnership.ownership`, and `workflowVersion` under Durability. A key the deployment locked (`HostOptions.settings.locked`, a map of key to reason; a local host locks none, and a remote one locks `durableOwnership.ownership`, `maintenance`, `durable`, and the workflow claim TTL and renew interval) is shown and disabled, with its reason.

Save sends the keys that changed in one `bureau.settings.update` with the `expectedRevision` the page read; the Bureau applies all of them or none. A `StaleRevision` fault, or a read that finds the revision moved while there are unsaved edits, shows a prompt to reload, and a reload discards the edits. The page subscribes to `bureau.settings.events` over Server-Sent Events and reads the settings again on each event, and again when the window regains focus, which is how it catches up when the stream is down. Below the form the host's own paths (`/host/paths`) are shown read-only: they are the host's and not settings. Nothing about the page is persisted by the page; the Bureau keeps the record.

The Playwright suite locks `workflowVersion` on the main host to show a locked key against the real Bureau, and turns `tools.humanInput` off and on to show that a chat with `demo:request-human-input` then asks nothing, and asks again (`tests/e2e/settings.spec.ts`).

## First run

A new installation shows a checklist on Chat's empty state until it is done (`src/app/first-run-checklist.svelte`, `first-run.ts`): connect a provider, create an agent, say hello. Each step is done by the host's own answer, not by a flag the checklist keeps. A provider is connected once `GET /host/providers` says one holds a key, an agent exists once `bureau.agents.list` lists one defined in a file (the agents a plugin or the host ships in code do not count), and a chat exists once `bureau.contexts.list` lists one the person started. An open step links to the page that does it (Settings › Models, New agent, New chat). The steps appear only once all three answers are in, and never echo a key. Dismiss keeps `interborough:first-run:dismissed` in this browser's `localStorage`, and a dismissed checklist asks the host nothing. The agent editor with no model to offer opens with Connect a provider, which goes to Settings › Models with `?return=` naming the form, and Models then offers a way back to it (`src/lib/provider-return.ts` accepts only the new-agent and edit pages). `tests/e2e/first-run.spec.ts` runs against a fifth host (`E2E_FIRST_RUN_PORT`) that is a fresh installation, on the port after the journey's.

## The journey

`tests/e2e/90-journey.spec.ts` is one Playwright journey through the application as the single local principal, with no sign-in. It is serial, with one `test()` per stage, and it runs last because of its number. Each stage builds on the ones before it:

- It chats with the `barrier` agent, sends a follow-up while the run is held, and sees the same run answer it.
- It starts from `/` and lands in the session it just made, starts a second session with the same agent from the agent's page, and returns to the first from `/chats`.
- It reloads while `demo:request-human-input` waits on its question and answers it from `/reviews`.
- It defines an agent in the editor with the `bureau:workflows-create` tool, sets that tool to `never` in the agent's `toolApproval` through `bureau.agents.definitions.update` (a tool that changes something asks before each call by default, and nothing in the journey answers the inbox for it), and chats with it until it writes `journey-digest`, a workflow with a 5 second schedule.
- It opens the workflow from `/workflows`, waits until its schedule's fire is listed as a run, and opens that run at `/runs/:run`. A runs page that opens before the first fire says there are none, and asks again every five seconds (`recheckMs` on its view probe) until there is one, so the stage waits for the first row on the page itself.
- It follows the schedule's "Edit workflow" action from `/schedules`, changes the trigger to `1h` in the editor at `/workflows/journey-digest/edit`, and sees the one-hour cadence on `/schedules`, which also stops the 5 second fires for the rest of the run.
- It attaches an image to `echo-image`, sees `Echoed 1 image.` and the returned image decode.
- It chats with `echo-recall`, which stores the label it is sent as a memory. It sees that text on `/agents/echo-recall/memories`, corrects it, and sees a new chat answered with the correction and not the original.
- It starts a `barrier` task it never releases, reaches `/tasks/:id` from the chat's task link, cancels it, and sees `TASK_COPY.cancel['cleaned-up']`.
- It opens Health from the sidebar, and `/health/workers` from Health's section links.

It opens a third host (`E2E_JOURNEY_PORT`, `tests/e2e/e2e-server.ts`) of its own, whose console is the Bureau's engine, as the second host's is, because the Workflows area can only show a fire of a workflow the Bureau's engine runs. The journey's host has a home of its own, with one provider so the editor can save an agent, and a barrier of its own, under `/journey` on the barrier's control port, so no run another specification leaves held changes what the journey counts. Every model is scripted and no provider key is read: the agents come in through the host's `extraAgents` (`barrier`, `echo-image`, `echo-recall`), and `createJourneyProviderResolver` (`tests/e2e/journey-agent.ts`) scripts the one agent the journey defines in the editor, so a first message that carries the journey's marker gets one call to `bureau__workflows-create` and then a fixed text, and any other first message gets the provider stub the other specifications use. The journey removes the agent and the workflow it writes, and forgets what `echo-recall` remembers, before it starts.

## Runs

`/runs` is one table of what the agents have done, each status one of the seven words (**Running**, **Waiting on you**, **Done**, **Failed**, **Canceled**, **Scheduled**, **Paused**; `src/lib/status.ts`, drawn as a StatusDot of the word's tone). The chat's sentence about its runs and a run's page still use the task words in `TASK_COPY.states`, through `src/lib/task-status.ts`. Each row says which agent ran, what started it (Started by), a line about how it stands (the question it waits on, its last words, or why it failed), when it started, and how long it took. It joins two sources (`src/routes/workflows/runs/run-rows.ts`): the Bureau's tasks (`bureau.tasks.list`, with each chat's title from `bureau.contexts.list`) and the goals' attempts (`bureau.goals.list`), which add the attempts recorded before attempts were tasks (COR-1868) and name the session an attempt ran in. **Started by** is the origin the Bureau records on a task (COR-1867), not a guess from its chats and goals, and `STARTED_BY_LABELS` in `run-rows.ts` has a label for each kind: a chat, a person (with where they started it), a schedule (linking to the schedule, and noting a fire by hand), the API, an agent (linking to the run that started it), a goal, and a workflow (linking to the instance whose step it is). Only a task recorded before origins were kept has none, and then the row falls back to the task's own `actor` and `kind`, or says Not recorded. The label list is typed against the Bureau's `TaskOriginKind`, so a new kind fails to compile until it has a label. Cancel is not offered on an attempt of a goal or a step of a workflow, because the goal stops an attempt, and a step of a workflow is not canceled on its own. The toolbar under the heading has the count, the filters (status, agent, started by, when) and Start run, and the filters are the address's (`?status=`, `?agent=`, `?startedBy=`, `?since=`). The engine's own table of workflows is not here: it belongs to the Engine area, and `/workflows/:workflow/runs` still uses it.

`/runs/:run` is one page with one header and one status, and no tabs. The header names what ran, with **Open chat** and **Cancel run** (after a confirmation) as buttons of one size and a More menu (copy the run ID, and, for a run the workflow engine holds, suspend, resume, force a timeout, cancel, restart). Below it: what the run waits on a person for, answered in place with the chat's own question control (`run-wait.svelte`; a tool approval is decided under its call); Input and output (the workflow's payloads, and the answer rendered as Markdown, which `bureau.tasks.events` carries because the task view has none); Activity (the tool calls in the chat's style, read from the chat thread by `run-tool-calls.ts`, then the timeline, with events, checkpoints and logs in disclosures); and Change or ask this run, where a signal, an update and a query are sent from forms that open in place. A 320 px Details rail holds the facts, each label above its value, beginning with the list of what started the run (`run-lineage.svelte`). The workflow engine's sections are there for a caller who holds `workflows:read` and each is gated again on the scope its own reads need (`events:read`, `signals:write`, `updates:write`, `queries:read`, `attributes:read`, `tags:write`, `streams:read`); a caller without engine access still has the whole page the Bureau can fill in. A run that is not a task (a goal's attempt started before attempts were tasks, COR-1868) is shown from its goal. `/tasks` goes to `/runs?startedBy=chat`, and `/tasks/:id` to `/runs/:run`.

- **Following** (`task-follower.svelte.ts`) keeps the last position the Bureau gave. A stream that drops or fails to open is opened again with that position in `Last-Event-ID`, after the shared reconnect backoff and at once when the browser reports it is back online. A stream the Bureau ends cleanly is not a drop, and the follower tells the cases apart: after a terminal status it is the end; a session run's stream, which the Bureau ends at the subscription route's time limit, is resumed from its cursor after one second; and a task started with `bureau.run()` streams one snapshot and ends while it is still going, so each snapshot is applied to the task the page shows, the page reads it every five seconds until it is over, and one more stream then collects its answer. A position and the answer are kept in `sessionStorage` under the task, so a reloaded page resumes from there. A snapshot's position (`-1`) names nothing to resume from and is never kept.
- **Cancelling** calls `bureau.tasks.cancel`. Each of the eight receipts has its own words (`TASK_COPY.cancel`). While the task's `cleanup` is `cancel-requested` or `cleanup-pending` the page reads the task every second, and says where the cleanup stands until it is final.

## Reviews

`/reviews` is everything waiting on the caller in one inbox: a list with the open review beside it (ListDetail), the longest-waiting first, with a Waiting tab (its count in the tab) and a Done tab (`?tab=done`) of what was decided, the latest decision first. One merged list from `bureau.reviews.list` (`pageReviews`) holds the Bureau's tool approvals and questions and, for a caller who may read them, the engine's workflow reviews; Waiting asks it for `pending`, Done for `resolved`, a page of 25 at a time. The open review is in the address (`?review=<source>:<id>`). The open review is read in `reviews-panel.svelte`:

- a **tool approval** shows the question (the tool's own sentence when it declares one, else the tool and its arguments, `src/lib/tool-text.ts`), one source line (`review-source.svelte`: Asked by the agent in the chat, waiting since, each part a link), what the call was given and, for a command or a patch, what it would run, and the decision: Approve, Deny with an optional note the agent reads (a rejection that carries it; without one a plain denial), and Allow for the rest of this chat, which approves with `remember`.
- a **question** is `ChatQuestion` from the chat package, drawn from the review's own `inputSchema`: choices as full-width options with Something else…, a form for a structured answer, a text box when there is no schema. It is answered through `bureau.tasks.respond`, with one line saying the agent continues with the answer.
- a **workflow review** shows its artifact and the engine's own decision form (`client.submitReview`), which needs `reviews:write`.
- a review that is **done** shows what became of it (who, when, the reason) and no form; an answer is never shown, only that it was sent.

Keys: J, K and Enter are ListDetail's own. A approves and D denies the open tool approval (D sends the note typed), and 1 to 9 pick the numbered choice of the open question, in the order the options are drawn (Something else… takes no number). They are registered for `/reviews` in the shortcut registry (`src/lib/shortcuts.ts`), so the `?` map lists them and none acts while a field is typed in. A chat that waits on a question draws it above the transcript from the answer schema the Bureau sent on the interrupt (`HumanRequest.schema`, read from `responseSchema.properties.answer`): the same `ChatQuestion` controls, a file uploaded to the Bureau's assets, 1 to 9 picking a numbered choice (registered for `/chats/:chat`), and free text (or no schema) answered through the composer. An answer given in a control is held with the others and goes in the one resume (`ChatSessionState.answerQuestion`), as a turn over a hidden row, since no row of the person's carries it. After a decision the list opens the review that followed it. There are no Live toggle and no Timed out state: the engine drops a review whose deadline has passed.

A decision whose outcome the Bureau could not write into the conversation (`APPROVAL_OUTCOME_NOT_WRITTEN`) took effect, and the page says so, in a dismissible alert above the tabs, as does an approval that could not be remembered. In a chat, Allow for the rest of this chat is not sent to `bureau.reviews.resolve`: it resumes the run with `remember: true` on the round the person was shown, as Approve resumes it, so the turn continues, and the chat says so (a toast) when the Bureau's `bureau.tool-grant-settled` announcement reports the grant was not stored or did not loosen the tool. The list, and the count in the navigation, ask again every five seconds and at once after each decision this application makes (`src/lib/review-queries.ts`). A chat that is already open reads the Bureau's pending reviews every three seconds while it waits on a person, and reads its thread again when a review it shows is no longer pending (`chat-session.svelte.ts`'s `refresh`), so a decision made here shows there with no reload. The view is `reviews` with no console scope: the console drops the Bureau's scopes, and a refused list is the frame's forbidden state.

## The shell

The sidebar is one ordered list (`src/app/shell/destinations.ts`): Chat, Reviews, Agents, Workflows, Runs, Schedules, Goals, Hooks, Health, and Settings pinned to the bottom. Health is the engine's overview at `/health`; its dot is the engine's status, and its links open Workers, Storage and the audit log, all under `/health`, and below the overview sit the metrics, alerts, lease and recovery (and Realms, when the engine runs them) that the System page used to hold. The rest of the System page is under Settings: `/settings/data-and-retention` and `/settings/api-reference`, with a section navigation between them and `/settings`. There are no redirects from the paths before the nesting. Chat is the home screen, sessions live at `/chats/:chat`, and runs live at `/runs` and `/runs/:run` (see "Runs"). `/workflows` is the catalog of workflow definitions (see "The Workflows area" above), and `/health/audit` is the audit trail (see "Schedules, goals, and the audit trail"). The button at the top of the sidebar folds it to its icon rail, and the shell remembers that in `localStorage` (`src/app/layout-preferences.svelte.ts`).

The top bar is the page's breadcrumb trail, the search trigger, the notification bell, and quick settings. The trail comes from the route table (`crumb` on each route in `src/app/routes.ts`, read by `src/app/breadcrumbs.svelte.ts`), and a page may give a parameter a better label with `usePageLabel`, as an agent's page does with its name. Quick settings hold the theme, the density (Comfortable shows each view at its own density, Compact shows every view compact, kept in `localStorage` like the theme), and the sidebar's icon rail.

A page's width follows its kind of page, not its area: each route names a `kind` (`list-detail`, `table`, `editor`, `form`, or `reading`), and `pageWidth` in `src/app/views.ts` gives the first three the whole outlet and the last two the reading column.

Every keyboard shortcut is in one registry (`src/lib/shortcuts.ts`): an entry is `{ keys, label, group, scope, handler }`, where the scope is `'global'`, a route pattern, or a focus region (`data-shortcut-region`). The same keys may be registered in scopes that are never active together, and a registration that overlaps another throws. The shell registers ⌘K (the search palette, held with ⌘ or Control, from a field too), `c` for a new chat, `g` then a letter for each destination (`c` Chat, `v` Reviews, `a` Agents, `p` Capabilities, `w` Workflows, `r` Runs, `s` Schedules, `l` Goals, `h` Hooks, `e` Health, `n` Settings, and `o`, `t` and `u` for Workers, Storage and the audit log) and `?` for the map of every shortcut, which Cinder's `KeyboardShortcuts` renders from the registry. `src/app/shell/keyboard-map.test.ts` holds the registry to the design's full set (⌘K, ?, C, every G letter, J and K, A and D, 1 to 9, ⌘Enter) and the map to exactly what is registered. ⌘K searches in one order: what is waiting on you, then chats, workflow types, runs by ID (with schedules, workers and reviews), agents, tools, and the actions with their shortcuts, which are the registry's global shortcuts (`ShortcutRegistry.actions()`) and "New chat with an agent". `>` narrows it to actions and `@` to agents, and a domain the principal's scopes do not cover (`workflows:read`, `schedules:read`, `reviews:read`, `system:read`) is not read. Keys a Cinder component handles itself, such as ListDetail's `LIST_DETAIL_SHORTCUTS`, are described in the registry so the map lists them and no application key can shadow them.

Every view renders in a frame (`src/app/view-frame.svelte`) that is loading, empty, failing (Cinder's `ErrorState`, with a retry), forbidden, not found (for a view that opens one item by its address), or showing its content, and says which in `data-state` beside a `data-view` naming the view. Its words are in `src/app/copy.ts`, and its one request is in `src/app/view-probes.ts`. A probe whose empty answer is about to change by itself sets `recheckMs`, and the frame asks again that often while the view is empty and stops when it has something to show; the runs of a workflow type do, so a page opened before the first run shows it without a reload.

The agent is a searchable `Combobox` pill inside the composer (the header holds only the title), starting from `?agent=` or the default agent (`src/lib/default-agent.ts`): the first agent the Bureau lists that can run, which is not an agent of a plugin that needs setup, and with none the view says no agent is ready and points at Settings › Plugins; changing it replaces `?agent=`. A first run that is refused stays on `/chats/new` with the row failed and a retry.

The toolbar has the count, a search, and New agent. `/agents/:agent` shows one agent's details (a file agent's model, tools and skills from `bureau.agents.definitions.get`), a New chat action, and the chats had with it.

### Memory

An agent remembers across every chat the caller has with it. The host composes governed memory for the Bureau (`src/host/memory.ts`): records and the governance ledger in Bungalow's database, the default policy, and `createHashingEmbedder()`, a deterministic embedder that makes no network call, so memory works with no model provider configured. Each chat run stores its final answer under the Bureau's identifier, its owner of record (`anonymous:local` here), and the agent's identifier; a later chat with the same agent recalls it, and a chat with another agent does not. Memory stored before this keyed it by session and is not migrated.

`/agents/:agent/memories` (`src/routes/agents/agent-memory.svelte`, linked from an agent's page) is a list of what the agent remembers, newest first, with the open memory beside it (Cinder's `ListDetail`, the open memory kept in the address as `?memory=`). The list's header holds the title, Add a memory, Export, a search that runs as you type and ranks every memory by relevance (ranking has no score floor, so a search is judged by which memories hold a word of the query), and a kind filter in plain names (Facts, From chats, How-to, From you) that works over the pages loaded so far and says so. Its loading, failing, locked, and not-found states are the Agents view's (`VIEW_COPY.agents`, by pattern); the list's own empty states are Cinder's `EmptyState` (`first-use` with Add a memory for an agent that has none, which is why the frame does not stand in for it, and `filtered` for a search or kind that matches nothing). Add a memory (`bureau.memory.remember`) saves the person's own words as an operator memory that is kept until it is corrected or forgotten and opens it; a refused add stays in its dialog with the words still in the field. Text the content rules flag is stored by the Bureau, quarantined and in no list, and `bureau.memory.remember` answers `held` with that record's identifier instead of a memory; the dialog says the text was held back and removes the stored copy (`bureau.memory.forget`) on Remove the held copy, on saving again, and on closing, so a reworded retry never leaves a second copy. The open memory leads with its text at reading size and a context line (kind, when, and the Correct and Forget icon buttons), with its facts below in three columns (where it came from, trust and time, and correction history) and the governance actions under them. Correct edits the text in place and saves a correction, a new operator memory that replaces the old one; the original is kept and is reached from the correction's history. Forgetting asks first, naming the memory, and is a source deletion that words each state the deletion can answer with (completed, held by a legal hold, pending, failed, unknown); the host declares `not-retained` only for the targets it keeps nothing in, and leaves `durable-snapshots` pending because a copy of recalled text persists in the conversation. The governance actions go through the memory API (`bureau.memory.share`, `share.revoke`, `hold`, `hold.release`, `quarantine`, `export`): Share and Stop sharing name another owner, Place and Release legal hold show the hold only once it is known (it has no read of its own, so it is learned from a hold, a release, or a forget that ran into one), Quarantine asks for a reason and says it cannot be undone, and Export saves every memory of the agent as a JSON file. The governed memory's ledger records each of them under the caller's owner, and publishes them on the event feed as `memory.governance`; they are not records of `bureau.audit.query`. The page needs the server's `bureau.memory:read` scope, changing memory needs `bureau.memory:write`, and a legal hold needs `bureau.memory:govern`.

### The conversation

`/chats/:chat` (`src/routes/chat/`) is `@lostgradient/chat` over the Bureau's AG-UI mount. A session is a Bureau context, and its conversation id is the AG-UI thread id. `chat-session.svelte.ts` holds one session's state and its `createChatSessionController`; `run-wiring.ts` is the transport. A turn is a start (`POST /bureau/ag-ui/agents/<agent>/run`, read through `@ag-ui/client`), a resume that carries the user's decision on a tool approval together with the turn that opened the run (never a follow-up row), or an attach (`GET /bureau/ag-ui/threads/<thread>/run`) to a run the page did not start, which restores the transcript from the stream's snapshot. A message typed while the run is going is a follow-up: the controller sends it through `bureau.contexts.input` under the id of its own row. A turn's tool calls are one row each, folded to a line ("Used 2 tools · 1 needs you") when there are several; a call that needs a decision is never inside the fold, and its approval is one flat row directly under it with Deny and Approve (`tool-calls.svelte`, `tool-activity.ts`). The header says which agent, and one sentence under it says how the chat's runs stand and links to the run. A session the caller cannot see is `not-found`.

A finished session's transcript is read back from the mount (`GET /bureau/ag-ui/threads/<thread>/messages`, owner-scoped like the attach route), so reopening a session, by reload or by returning to it from the list, shows every turn in order.

Quoting is `@lostgradient/chat`'s, turned on here with `capabilities.quote`. Selecting text inside one agent reply opens a Quote popover, every agent reply has a Quote message action for the keyboard, and each quote gathers as a chip above the composer. Sending puts the quotes at the top of the message as Markdown block quotes (each line prefixed with `> `, one blank line between quotes), then the typed text, through the same send path as any message, so the agent receives them and a reloaded transcript shows them. A quote is the selected text, not a link back to the reply it came from, so quoting works within one session. `tests/e2e/34-chat-quotes.spec.ts` quotes from two replies to `demo:echo` at 375 and 1280 pixels, with axe passing.

The model picker sits in the composer (`Chat`'s `composerActions`, `src/routes/chat/model-picker.svelte`). It lists `bureau.agents.models` for the session's agent, shows the session's own model (`bureau.contexts.get`'s `model`) or else the agent's default (the one model an agent allows when the Bureau names no default), and is always shown: for an agent that allows one model, or none, it is disabled on that model, or on "Agent default". Choosing a model calls `bureau.contexts.steer` with the `configVersion` it read as `expectedRevision`, and the model is used from the session's next step. An admitted switch (or an exact replay) keeps the choice; a refusal for a stale revision reads the session again and shows the model it has now; any other refusal, or a fault, restores the previous selection, each with its own copy in `CHAT_COPY.modelPicker`. A model is a catalog row, so an agent offers a model only when a configured provider holds it: `demo:model-switcher` names `claude-sonnet-5` and `claude-haiku-4-5`, and a host with no provider offers it no choice. `tests/e2e/35-chat-model-switch.spec.ts` switches `demo:model-switcher` between two messages, reloads to see the choice kept, and sees the picker disabled for an agent that allows one model (`single-model`) or none (`demo:echo`), at 375 and 1280 pixels with axe passing.

An open chat's header and composer carry its settings (COR-1967, `src/routes/chat/chat-conversation.svelte`). The header is Cinder's `PageHeader`: the title, the agent (and where a branch came from) and the context-window ring, with a line under it that always says the model, the reasoning effort and the permission mode the chat runs with (`bureau.contexts.get`). The composer holds the three controls: the model picker, and `setting-select.svelte` for the effort (`low` to `max`, or "Agent default" before one was set) and the permission mode (Always ask, Ask on changes, Allow all, Read-only). Each calls `bureau.contexts.steer` with the `configVersion` it read, ends every way a request can end as `steer-change.ts` says, and is marked `data-changes`; the three share one revision, so while one change is in flight the others are disabled. A change says when it applies, in `role="status"` under the header: a mode from the run's next tool call, a model or effort from its next step, and for a chat with no run going, its next run. A mode other than Ask on changes is explained there too, in the words `bureau.contexts.steer` defines it (Allow all skips the asks Ask on changes would raise; a tool set to always ask still asks, a blocked tool is still refused, and a child agent keeps its own stricter mode). The ring (`context-window-ring.svelte`) reads `bureau.contexts.window` when the chat opens, when a run ends and when the model is switched: the estimate of the next prompt over the model's window, in whole percent (the token count alone when the model's window is not known), with a popover that splits it into instructions, tools, messages, memory and attachments, one Cinder `Meter` each, and the provider's own count for the latest step. Cinder has no ring, so the ring is drawn in the app. `tests/e2e/chat-header.spec.ts` changes each setting against the real host, reloads to see it kept, and opens the breakdown, at 375 and 1280 pixels with axe passing.

The header's More menu (COR-1968, `chat-more-menu.svelte`) holds the actions on the chat itself. **Rename** opens a dialog (`chat-rename-dialog.svelte`) over `bureau.contexts.rename`: the field starts at the title the header shows, an empty field asks for the title taken from the first message again, and a title that changes on the Bureau while the dialog is open is taken when nothing was typed and otherwise offered as "Use the new title" beside the typed text. **Branch** is Branch from here on the last finished reply, held back with its reason while a run is going. **Export** saves the conversation as a Markdown file (`chat-export.ts`: the title, the agent, and each message the person sent or the agent replied with; tool calls and hidden rows are left out). **Delete** asks first, naming the chat, saying that a run that is going is stopped and that chats branched from it keep their own copy, and calls `bureau.contexts.delete`; it returns to `/chats`, and says when the run was still stopping (`cleanup-pending` and the receipts after it). Editing a message the person sent resends by fork (`edit-fork.ts`): the page replaces the controller's in-place edit, branches the chat at the reply before the message (or before the first message) with `bureau.contexts.fork`, and the branch's page sends the edited text as its next turn; the edited text travels in memory, not in the address. A message sent while a run was going follows no finished reply, and one that carries files would leave them behind, so neither can be edited. A file cancelled while it uploads is discarded on the Bureau too (`bureau.assets.uploads.abort` from `uploadAsset`; `src/host/host-upload-abort.test.ts` runs it against the real routes). `tests/e2e/chat-header.spec.ts` covers each against the real host.

The final agent message of each completed turn offers Branch from here (`Chat`'s `messageActions`; `branch-points.ts` picks the messages: an agent message followed by a user message, or the last message while no run is going). It calls `bureau.contexts.fork` and opens `/chats/:newSessionId`, which holds the history through that reply and runs on the parent's model. The Bureau decides whether a message is a branch point, and a refusal says why in `CHAT_COPY.branch.refused` and leaves the person on the parent. A branch's header says "Branched from" with a link to the parent (`parentContextId`), or the same words without a link once the parent has been deleted. `tests/e2e/36-chat-branch.spec.ts` branches from the first of two replies and follows the link back, and sees a refused branch leave the page where it was, at both widths with axe passing.

An agent reply the Bureau recorded as a step of a run (a row named `<runId>:step:<n>`) offers **Reply details** (COR-1983, `reply-details.svelte`, in `Chat`'s `messageActions`): a popover that reads `bureau.tasks.inspect` for that run and step when it opens, and prints why the step ran on its model (the plan reason's code and line, and the models the plan passed over) and what the model saw (its message count, whether older messages were left out, and each source with whether it was included). When this page watched the run end, the popover adds the tokens the run's `RUN_FINISHED` event reported, under a note that they count every step of the run. It prints only what those two sources carry: no model name, effort, cost or time is shown, because neither source gives one, and nothing is estimated. A part with no source is left out, and a reply with none says no details were recorded. It adds nothing to the wire.

Files are attached in the composer and returned as assets. What a person may attach comes from the selected agent's model: `bureau.agents.list` carries each agent's `media` (`modalities`, `mimeFamilies`, per-part `mediaLimits`, and `null` for an agent that names no model), `src/lib/chat-attachments.ts` maps the families to the file picker's types (`image/*`, `audio/*`, `video/*`, `application/pdf` for documents, `text/*`), and a type with no stated limit falls back to the Bureau's 100 MiB asset ceiling. The picker is off for an agent with no model, while a run streams, and while the run waits on the person's answer, because a follow-up and an answer carry text only. A file uploads as it is attached (`src/lib/bureau-assets.ts`: `bureau.assets.uploads.create`, `append` in 512 KiB chunks, `complete`), shows `uploading`, `ready` or `error` in its preview's `data-state`, and keeps Send disabled until every upload settles. A file over its type's limit or of a type the model does not take is shown as an `error` attachment and never uploaded, and each fault has its own words in `CHAT_COPY.attachments`. The message goes out with each uploaded file as a `file` part from the provider `bureau` whose `value` is the asset id. An agent's returned assets arrive as `bureau.asset-part` events, which `run-wiring.ts` stamps on the assistant row as `bureau:assetParts` (the key a reloaded thread's snapshot carries), and `chat-assets.svelte` shows them, and the person's own attachments, under their rows by kind: an image with Cinder `Image`, audio with `AudioPlayer` (a native `<audio>` driven by `MediaControls`), video with `VideoPlayer`, and anything else as a `Link` download, all from `/bureau/assets/<assetId>/content`.

## Runtime configuration

`readRuntimeConfig` reads the `weft-ui-config` JSON element from the host document. A missing or empty element defaults to same-origin requests and automatic transport. Invalid JSON or an invalid configuration shape throws.

```html
<script type="application/json" id="weft-ui-config">
  { "baseUrl": "", "eventTransport": "auto" }
</script>
```

| Field | Meaning |
| --- | --- |
| `baseUrl` | Required string. An empty string uses the page origin, a root-relative path selects an API prefix, and an absolute URL selects another origin. |
| `eventTransport` | Optional `auto`, `websocket`, or `sse`; defaults to `auto`. |
| `token` | Optional bearer token held in the client's memory. |
| `headers` | Optional string-valued request headers. An explicit authorization header takes precedence over `token`. |
| `assetBase` | Validated configuration data for host asset handling. The client does not use it to rewrite asset URLs. |

Dynamic-source diagnostics belong to the engine process answering the request. Durable catalog installation and process-local load history have different lifetimes, so a console pinned to a stable engine endpoint reads one process's loading state.

The interface enables controls according to the principal's scopes. The Weft server remains responsible for authorizing each operation; a disabled control is not an authorization boundary.

## Layout

- `src/host`: the host, its relay, and `dev.ts`.
- `src/app`: the shell, the router's route table, the view frame, and the sidebar.
- `src/lib`, `src/routes`, `src/views`, `src/styles`: the console's client, query helpers, live sources, router, area routes, and styles.
- `fixtures`: the deterministic demo workflows the console's tests and Playwright suite run against. They are append-only.
- `tests`: the DOM preload, the deployment-mode tests, and the Playwright suite in `tests/e2e`.
- `scripts`: the build and the coverage ratchet.
