# Equipment connector staging

These isolated, single-instance fixtures serve synthetic equipment for the hosted connector acceptance. The catalog uses `/api/mcp`; the standalone Armorer service uses `/mcp`. Each has its own persistent SQLite volume, public origin, OIDC registration, and reader and editor identities. Neither service accesses production data.

Configure each service with `PUBLIC_ORIGIN`, `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `READER_SUBJECT`, `EDITOR_SUBJECT`, and `SQLITE_PATH`. Register the exact `${PUBLIC_ORIGIN}/auth/callback` with the OIDC provider. The subjects must be distinct immutable subject identifiers from that issuer, not email addresses. Store client secrets in Railway and obtain the synthetic account credentials from the owner's approved credential manager. Set `SQLITE_PATH=/data/equipment.sqlite` on each service's own mounted volume. Railway supplies `PORT`.

Build from the repository root using the service's Dockerfile and root build context. The catalog image runs `bun run --cwd applications/equipment-catalog build` and starts with `bun run --cwd applications/equipment-catalog start`; the native image uses the equivalent commands in `applications/equipment-armorer`. Keep each service at one instance because its SQLite volume is local to that service.

From outside the deployment, check the profile's `/.well-known/oauth-protected-resource` document with `/api/mcp` or `/mcp` appended. Its `resource` must equal the full MCP URL. Send an unauthenticated initialization request to that URL and check for HTTP 401 with a `WWW-Authenticate` header pointing to that metadata document.

Run `bun run --cwd applications/equipment-catalog probe:deployment <MCP URL>` for each profile. Open the printed loopback link in a separate private browser window for each role and sign in using that synthetic account. Before approving the requested permissions, compare the subject on the consent page with that role's subject in the credential manager, then confirm the match in the terminal. The probe retains the authorization code, PKCE verifier, and token only in process memory and prints role outcomes without those values. The reader must be refused a rename and observe the original name; the editor must rename and observe the new name. The editor check restores the original value and verifies the restoration, including after an unsuccessful rename check when the connection remains usable.

For each receipt, record the deployed revision shown by Railway alongside the profile, canonical MCP URL, role, and probe outcome. Verify that the deployment is the intended source revision before recording a pass.

Keep both services and their volumes available until COR-2630 has verified all four hosted-client journeys. After that issue is complete, remove the two service deployments and their dedicated volumes, revoke their OIDC registrations and synthetic accounts, and remove their credential-manager records through the provider's normal controls.
