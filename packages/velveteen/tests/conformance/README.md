# Conformance harness

Install the pinned toolchains with `bun install --frozen-lockfile` and `bun run prepare:reference`. Install Chromium with `bun node_modules/@playwright/test/cli.js install chromium` if the browser is absent. Run `bun run test:first-batch` for the complete first-batch acceptance matrix.

The harness launches the actual pinned Kit reference and candidate independently in development and production. Both fixtures signal hydration before the browser clicks. `bun run test:harness` requires all four cells to pass, deliberately changes the candidate endpoint, rejects an empty case selection, and restores all four cells. A failed control must fail for its expected reason. The inventory contains source files and executable package scripts, not a count of passing upstream tests.

Candidate processes run with a PATH containing only Bun. The harness records executable, runtime version, process identifier, entry-file hash, completed exit status, stdout/stderr hashes, and immutable production artifact identity in `.velveteen/evidence/commands.jsonl`. `bun run audit:dependencies` checks installed transitive dependencies, lock identities, emitted bundle inputs/outputs, completed command evidence, and the actual package tarball. Vite and Kit remain in the separately installed reference boundary.

P05–P07 use isolated copies of the source fixture. The generated development graph publishes separate JavaScript, CSS, and source maps so Bun can apply a CSS change without reinitializing the Svelte component. JavaScript and rune edits intentionally reinitialize component state. P08 maps generated browser stack positions using served production maps and original source contents; it does not rely on automatic remapping of `Error.stack`.

P09 watches actual entry files and republishes native routes. P10 uses experimental `Bun.ModuleGraph`, an explicit application resource registry, request draining, and `server.reload()`. Its scope is buffered SSR. Streaming graph disposal and general memory bounds remain outside this proof.

`bun run probe:native-hot` is the retained diagnostic for the rejected raw `--hot` lifecycle mechanism. On Bun 1.4.4 it exits 1 because the admitted old request remains unsettled and retired callbacks survive. Its assertions are preserved; it is a mechanism investigation, not the selected P10 acceptance implementation. `bun run test:development` runs the passing ModuleGraph alternative and all development acceptance tests.

Evidence is written under `.velveteen/evidence`. `EXECUTION.md` records reviewed scope, versions, commands, and final results.

## Application runtime comparison

`bun run test:batch-ef` verifies the shared data protocol, server hooks and loads, security boundaries, browser navigation, and the real application lifecycle before running the complete accepted D/C/N/A/B gate. The focused entrypoints are `test:server`, `test:security`, `test:browser`, and `test:runtime-lifecycle`.

Run `bun run test:conformance -- --mode=development` or `--mode=production` for the shared application matrix. `--group=server`, `--group=navigation`, `--target=reference`, `--target=candidate`, and `--case=<id>` select a boundary; empty selections fail. The source identities and intentional API differences are recorded in `tests/inventory/runtime-cases.json`. These are derived fixtures with literal expectations for both implementations, including the explicit development CSRF difference below. They do not claim that the complete upstream suite was ported.

The candidate uses the actual `buildProduction` output and a bundled Bun host in both modes. Development selects development compilation, runtime conditions, and unminified output. Production selects production compilation and minification. The reference uses the pinned Kit Vite development server and actual `adapter-node` production output, with its explicitly configured loopback `ORIGIN`. Kit's pinned streaming tests document that Vite preview buffers responses; production streaming is therefore tested through the generated adapter handler. No test timeout or assertion is weakened to accommodate preview buffering.

The shared fixture covers nested server/universal loads, CSS and static assets, SSR, fetch replay on hydration, retained layouts, preload/invalidation, SPA/no-client modes, redirects/errors, initial and navigation promise streaming, history/scroll/focus, stale refreshes, and preload races. The separate lifecycle fixture imports real emitted registries through `Bun.ModuleGraph`, hydrates an interactive page, publishes B on the existing listener while A is admitted, observes B through browser-originated data fetches, drains A, cancels a native stream, and preserves B after a failed compilation. The host owns module-graph disposal; arbitrary application side effects and general memory bounds are not certified.

`bun run test:runtime-controls` checks every selected source identity, rejects an empty selection, deliberately corrupts the candidate endpoint, requires the literal data assertion to fail, and restores the production fixture. Process and case results are recorded in `.velveteen/evidence/runtime-*`; the complete batch result additionally records source hashes.

## Runtime entrypoints

An application host calls `buildProduction` from `src/build/index.ts`, then `createApplication({ generation, hooks })` from `src/server/index.ts`. Compose its `fetch` with the host's `Bun.serve` listener; `routes` exposes exact native asset handlers. Call `dispose()` to cancel application-owned requests before disposing an injected registry's module graph. The framework does not create a second listener or supervisor.

Server hooks receive native requests, responses, URLs, an abort signal, scoped cookies, locals, matched route metadata, and enhanced fetch. `getRequestEvent()` accesses the current asynchronous request context. Generated `$types` declarations use those actual runtime event types. Universal loads receive tracked URL/parameter dependencies, `depends`, `untrack`, `parent`, own server data, and fetch replay. Cookies require an explicit path. Response headers used during replay require explicit `filterSerializedResponseHeaders` opt-in; credentials and Set-Cookie are excluded.

Components call `getNavigation()` from `src/client/navigation-context.ts` during initialization and use its methods from event handlers. `goto(url, { replace, noScroll, keepFocus })` uses native history; `preloadCode(routeId)` takes a route identifier, matching the pinned Kit 3 API, while `preloadData(url)` takes a URL. `invalidate`, `invalidateAll`, and `refreshAll` rerun tracked loads. Preload attributes use `data-velveteen-preload-code` and `data-velveteen-preload-data`. Application hosts may call `startClient` directly to provide navigation callbacks and own disposal.

Bun 1.4.4 normalizes some `Request` policy fields before application code can read them. Enhanced fetch preserves explicit `RequestInit` policy and supplies browser defaults; callers requiring explicit credentials should supply `fetch(url, { credentials })`. Intent already lost by a separately constructed native `Request` cannot be recovered. Request cancellation can stop framework coordination and signal cooperative application work; JavaScript that ignores its signal cannot be forcibly terminated.

## Actions, remotes and static artifacts

G/H adds four shared action cases and one route-option case, bringing the selected runtime comparison to sixteen cases in each runtime/mode cell. Actions run from real emitted `+page.server.ts` modules. Native and enhanced forms preserve default/named dispatch, validation, files, submitter overrides, redirects and errors; enhanced cross-page results retain the document and update post-action loads. `getNavigation().enhance` is a Svelte action for `use:enhance`. `fail(status, data)` returns a branded failure; generated `Actions`, `ActionData` and `PageProps.form` retain result inference. Enhanced submissions use the existing page-data protocol, so they do not introduce a second action serializer.

The host passes an explicit `remotes` allowlist to `createApplication`. Each `defineRemote({ kind, validate, handle })` uses a synchronous validator accepting `unknown`; authentication remains in hooks and handlers. The browser imports only the registry's type and calls `createRemoteClient<typeof remotes>({ baseURL, invalidate, redirect? }).call(name, input, { signal? })`. The server runs through the existing request context and hooks, requires same-origin POST with the exact remote content type, and validates before invoking application code. The shared devalue protocol supports rich values and cycles while rejecting functions, symbols, promises, files, accessors and arbitrary classes. Successful commands await the supplied invalidation callback. Explicit HTTP(S) redirects use the supplied navigation callback. This authoring API replaces compiler-transformed experimental remote modules; complete Kit remote-function coverage is not claimed.

Use `client.query(name, input)` to read or refresh a cached query with `get()` and `refresh()`. Subscribe with `subscribe(observer)` and call its cleanup function when the view unmounts. A client shares equal entries and groups reads initiated in one browser turn. `defineBatchQuery({ validate, handle })` receives distinct validated inputs and returns a resolver for each input. A command's `refresh(input, result)` can return query names and inputs to resolve in its response.

The `remoteForms` allowlist contains handlers created with `defineRemoteForm({ validate, handle })`. Use `remoteFormAction(url, name)` for the form's POST destination, and `use:enhance` for same-document submissions. Native and enhanced forms both expose results and validation issues through the page's form data. The helper preserves ordinary query parameters.

`prerender({ generation, outputDirectory, entries?, origin? })` consumes only the emitted registry. It evaluates inherited options, expands declared route entries using the canonical matcher, crawls same-origin links, and writes HTML, data, endpoint, redirect and public-asset representations. Invalid routes/options, missing required entries, actions, cookies, failed renders, corrupt/missing assets and collisions fail before updating the accepted pointer. The result is an immutable generation with a static manifest and a content version. `createStaticHandler(directory, manifest)` serves exact manifest URLs using Bun files. The actual copied-artifact test starts from an unrelated temporary directory after deleting application source, with no installed dependencies.

`buildServiceWorker({ outputDirectory, base, build, files, prerendered, install })` bundles the application's worker initializer and explicit metadata. The exported `install(metadata)` function runs synchronously at worker evaluation and must return `undefined`; it registers native `install`, `activate` and `fetch` event handlers. Application handlers own `event.waitUntil`, cache policy, activation and cleanup. The browser witness waits for the native `activated` state before asserting cache retirement, matching the [service-worker lifecycle](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorker/state). It verifies two offline documents, interaction, CSS, a public file, a failing cache miss, activation of changed bytes, retention of an unrelated cache, and rejection of a failed new installation while preserving the active worker.

Run `bun run test:actions`, `bun run test:remote`, `bun run test:prerender`, `bun run test:build-errors`, `bun run test:security`, `bun run test:types` and `bun run test:batch-gh`. The complete gate also retains every E/F/D/C/N/A/B command. Runtime controls deliberately corrupt both a fetched value and an action result, require the unchanged literal assertions to fail, and restore each fixture. Expected HTTP validation errors and the deliberate offline cache miss are identified explicitly; unrelated browser diagnostics fail.

Pinned Kit deliberately skips CSRF checks when `__SVELTEKIT_DEV__` is true (`packages/kit/src/runtime/server/respond.js` at the pinned revision). Velveteen enforces the same-origin form policy in both modes. `G01-errors` asserts the reference development action executes with status 200, while the candidate in both modes and reference production reject it with 403. This is an explicit security-policy difference, not a skipped assertion.
