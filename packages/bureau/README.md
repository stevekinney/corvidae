# Bureau

`@lostgradient/bureau` is Corvidae's fleet composition layer. `createBureau()` assembles providers, tools, memory, skills, session persistence, durable execution, guardrails, and multi-agent behavior from one configuration surface, then exposes the runtime through a single `Bureau` object.

## Workspace usage

Declare `"@lostgradient/bureau": "workspace:*"` in the consuming workspace's dependencies. Install dependencies from the Corvidae root with `bun install`. Import the private package through `@lostgradient/bureau`; it exports TypeScript source directly and has no library build or publication step.

## Overview

Everything else in the workspace is a library: `operative` runs one agent loop, `armorer` executes tools, `memory` recalls facts, `skills` catalogs procedures. `bureau` is where those libraries become a fleet—a runtime that can create runs, resume them across a crash, hold live sessions, run scheduled and durable schedules, and route requests to more than one named agent.

Applications own HTTP and browser integration. `createBureau()` has no HTTP dependency and can be called directly from a Bun process. `createBureauHandler(bureau, options)` returns a `(request: Request) => Promise<Response>` that serves the Bureau's event feeds, review queue, and management plane (`weft.system.principal`, `bureau.deployment.get`, `bureau.agents.list`, `bureau.tasks.list`/`get`/`cancel`/`respond`/`events`, and `bureau.contexts.delete`); the application still binds the port, for example with `Bun.serve({ fetch: handler })`. Authentication is `resolveApiKeyPrincipal` (static `apiKeys` throw at construction) or `unauthenticatedAccess: 'allow'`, which serves every request as one local caller owned as `anonymous:local`. A principal reaches the reviews and run events it owns without any Bureau scope, the kind's operator scope (`bureau.reviews:read`, `bureau.reviews:resolve`, `bureau.tasks:read`, `bureau.tasks:write`, `bureau.contexts:write`) grants cross-owner access, `bureau.events` needs `bureau.events:observe-all`, and a caller who may not see a resource is answered as if it did not exist. See [Owner of record](#owner-of-record-cor-718).

## What It Does

- Composes a runtime from `BureauOptions`: a single provider, a fallover/routing provider set, tools, memory, skills, session persistence, durable execution, guardrails, cache, identity, and scheduler configuration.
- Creates and tracks runs (`createRun`, **deprecated**—see AB-242), aborts and deletes them, and lists them by status.
- Persists sessions through a `SessionStore` and recovers in-flight durable runs after a process restart (`engine.recoverAll()`), reattaching bureau-owned runs and monitoring native scheduled fires.
- Exposes durable primitives when a durable engine is composed: `signalSession` delivers a real fire-and-forget signal; `updateSession`/`querySession` are kept but unconditionally throw `BureauError('UNSUPPORTED_CAPABILITY')` (AB-192—the built-in `agentRun` workflow registers no `ctx.onUpdate`/`ctx.onQuery` handler; see `bureau.sessionVerbCapabilities`); `submitSessionInput` runs AB-42's fixed pre-admission checks (authorization, then session lifecycle, then capability/capacity), and an authorized request on a session that is not terminal reaches the durable session mailbox (`admitted`, `replayed`, `conflict`, or `backlog-exhausted`); it returns `{ outcome: 'unsupported-capability', reason: 'durable-mailbox-unavailable' }` only when no session mailbox, durable storage, or key-value store is composed (AB-194, COR-435); `submitSteeringCommand` admits `pause`, `resume`, `agent-identity`, `route`, `model`, `provider`, and `effort` for authorized in-memory and durable sessions, persisting durable commands before applying them; `policyRef` resolves configuration coordinates through `modelPolicy.users`, while an `agent-identity` `policyRef` remains `unsupported-capability` with `selector-unavailable`; plus full CRUD over durable schedules (`createSchedule`, `getSchedule`, `listSchedules`, `pauseSchedule`, `resumeSchedule`, `cancelSchedule`).
- Emits a typed event surface (`BureauEventMap`) and live WebSocket/SSE-ready frames (`ServerFrame`) via `subscribeLiveFrames` and `streamEventToFrame`.
- Records a durable, append-only audit trail of tool, run, and step lifecycle events when persistence is configured.
- Gives the runs it composes governed memory (COR-41): recall through mandatory recall admission and persistence through write admission, both under an authority derived from the run's persisted request (see [Governed memory](#governed-memory-cor-41)).
- Exposes a typed `AgentDefinitions` catalog (`bureau.agents`) and a synchronous `bureau.run(name, input, options?)` for dispatching to a statically named agent, alongside the session/durability-backed `createRun`.
- Records durable parent-child relationships (`bureau.children`): dispatch a catalog agent as a child of a known run, then list, inspect, wait on, signal, and cancel it by a stable identifier, including after a restart, with optional signed delegation grants that bound how deep and how wide the tree below each child may grow. A top-level parent holds no grant, so its own dispatches are neither checked nor budgeted.

## How It Works

`createBureau(options)` is async because composing the runtime may involve resolving a Weft storage backend, building a durable engine, and loading a session store. The returned `Bureau` object wraps an `@lostgradient/operative` `Store` (the live run/action registry), an optional `GovernedMemory`, an optional `Scheduler`, and the resolved runtime composition (generate function, toolbox, session store, durable engine).

`createRun(request)` (**deprecated**, not yet removed—see AB-242's decision record and the removal issue it names, AB-352) loads or creates a session, appends the request message to its conversation, builds an `ActiveRun` via `operative`'s `createActiveRun`, and registers it with the store. If a durable engine is composed, the run is routed through it instead of the in-memory loop, so it can crash and resume from its last completed step. Terminal run events (`run.completed`, `run.aborted`) persist the session's status with a bounded retry.

On boot, if durable execution is configured, `bureau` sweeps suspended scheduler-origin residue and calls `engine.recoverAll()`. Each recovered handle is classified—`reattach` (a bureau-owned, in-flight, session-confirmed run becomes a live `ActiveRun` again), `monitor` (a native scheduled fire gets a detached result monitor but no live run surface), `cancel` (a positively unowned or unidentifiable run is terminalized), or `skip` (ownership can't be confirmed, so recovery leaves it alone rather than risk cancelling a legitimate resume).

## Project role

`@lostgradient/bureau` composes the agent packages and `@lostgradient/weft`. A host application can put HTTP routes, a browser interface, or a live transport around that runtime; Bureau itself stays transport-agnostic.

## Quick Start

This example demonstrates the `BureauOptions.provider` + `Bureau.createRun` path, which is **deprecated** (not yet removed—see AB-242's decision record and the removal issue it names, AB-352). New code should give `agents` a catalog entry built with `createAgent` and dispatch through `bureau.run(name, input, options?)` instead.

```typescript
import { createBureau } from '@lostgradient/bureau';

const bureau = await createBureau({
  agents: {},
  provider: { provider: 'anthropic', model: 'claude-sonnet-4.5' },
  storage: { type: 'sqlite', path: 'bureau.sqlite' },
});

const run = await bureau.createRun({ message: 'Summarize the Q3 report.' });
console.log(run.status); // "running"

// Wait for completion via the live event surface. A run records many actions
// before it finishes, so keep the subscription open until this run's terminal
// action arrives, then close it.
await new Promise<void>((resolve) => {
  const subscription = bureau.subscribe('action', ({ action }) => {
    if (action.runId !== run.id) return;
    if (action.type === 'run.completed' || action.type === 'run.aborted') {
      subscription.unsubscribe();
      resolve();
    }
  });
});

const detail = bureau.getRun(run.id);
console.log(detail?.finishReason); // "stop-condition" | "maximum-steps" | …

await bureau.dispose();
```

Without `storage`, runs are ephemeral: nothing is persisted, and a crash loses in-flight work. Pass a `sqlite` or `lmdb` `storage` configuration to get session persistence and, by default, durable crash-and-resume execution.

## Public API

### Selection, steering, and capability boundaries

The full provider matrix, `SelectionPlan` field map, steering example, ownership table, and durable capability boundaries live in [Runtime contracts across Corvidae](../../documentation/runtime-contracts.md).

`bureau.planSelection(request)` is a synchronous read of the current model catalog and policy. It returns a versioned `SelectionPlan` describing the requested, supported, allowed, selected, fallback, and effective model and effort values without starting a run or refreshing the catalog. Use the plan as an explanation and pass it into the run boundary that owns execution; a plan is not a reservation.

`submitSteeringCommand()` admits the seven shipped steering targets for authorized, non-terminal sessions. `pause` and `resume` bind to a run; `agent-identity` is deferred to the next run; and `route`, `model`, `provider`, and `effort` apply at the next step boundary. Durable sessions persist the command before entering desired state, so recovery can replay it. Unsupported policy references return a typed `unsupported-capability` outcome, and a command that is accepted still applies at its named boundary rather than interrupting a provider call halfway through. Read the resulting steering event or run snapshot to confirm application.

Durable session input, update, query, schedules, and human review are separate capabilities. A composed Bureau advertises them through its capability surface and returns an explicit unsupported outcome when the backing engine or mailbox is absent. Treat `unsupported-capability` as a deployment fact to surface to the host, not as a transient provider error to retry.

### `createBureau(options)`

```typescript
function createBureau<const D extends AgentDefinitions = AgentDefinitions>(
  options: BureauOptions<D>,
): Promise<Bureau<D>>;
```

Composes and returns a `Bureau`. `agents` is the only required field—pass `{}` for a bureau that only uses the session/durability-backed `createRun` surface below (**deprecated**, not yet removed—see AB-242) and doesn't dispatch through the typed catalog at all. Without a `generate`/`provider`/`providers` + `routing` (all agent-owned fields, **deprecated** per AB-242), the result has no generate function configured (`bureau.ready === false`) and `createRun` throws `BureauError('NOT_CONFIGURED')` until one is provided.

### Per-agent guardrails and skills (COR-1367)

`createAgent` accepts `guardrails` and `skills`, the per-agent counterparts of the deprecated `BureauOptions.guardrails`/`skills`. For a catalog agent dispatched with `bureau.run`, the guardrails a run applies resolve most specific first:

| Agent `guardrails` | `BureauOptions.guardrails` | The run applies |
| --- | --- | --- |
| omitted | omitted | the AB-40 preset, once, in the agent's tier |
| omitted | a configuration | the bureau configuration (inherited), instead of the preset |
| a configuration | anything | the agent's configuration only |
| `false` | anything | no guardrails |
| omitted | `false` | no guardrails |

Bureau hands its value down through `AgentRunContext.inheritedGuardrails` to agents that carry `OPERATIVE_RESOLVES_GUARDRAILS` (every `createAgent` result), and then registers no guardrail invariant of its own for that run, so the policy runs exactly once and a recovered run resumes under the same composition its fresh dispatch used. A hand-written `RunnableAgent`, or a `createLazyAgent` wrapper, keeps Bureau's own guardrail invariant as before and is handed `false`, so a `createAgent` behind a lazy wrapper does not add the preset a second time.

Skills do not inherit: `BureauOptions.skills` only ever composed `createRun` runs. A catalog agent offers exactly the catalog its own `skills: createAgentSkills({ catalog })` names, scanned by its own guardrails.

`createAgentSkills({ catalog, includeTools?, loadArtifact?, events? })` is exported by this package. It implements operative's `AgentSkills` seam over Bureau's skills subsystem, which [documentation/skills.md](./documentation/skills.md) describes and the `@lostgradient/bureau/skills` subpath exports. The composition lives here because operative cannot import a private Bureau module, and the skills subsystem must not import operative. Each run gets a fresh skill client bound to the catalog, so activations never leak between runs. Active skills are not snapshotted for durable recovery on this path: a catalog-dispatched run has no Bureau session to hold them, so a recovered run starts with an empty active set.

```typescript
import { createAgentSkills } from '@lostgradient/bureau';
import { createAgent } from '@lostgradient/operative';
import { discoverSkills } from '@lostgradient/bureau/skills';

const catalog = await discoverSkills({
  sources: [{ id: 'user', kind: 'user', location: './skills', precedence: 20 }],
});
const agent = createAgent({ generate, skills: createAgentSkills({ catalog }) });
```

Removing the two deprecated fields later is therefore not a behavior change for an agent that says nothing: with no bureau value to inherit, it still resolves to the AB-40 preset.

`durableExecution: true` cannot be combined with a custom `persistence` value—`persistence` shadows `storage`, and the durable engine needs a raw `Storage` backend to checkpoint against. Provide `storage` without `persistence` for durable runs.

`onLog` and `onDiagnostic` cover different sources: `onLog` carries only `ctx.log` records emitted _by durable workflow code itself_, while `onDiagnostic` carries bureau's own operational diagnostics—the sites that write to `console.error`/`console.warn` today (recovery failures, live-frame listener exceptions, dispose errors, persistence failures). Route `onDiagnostic` into a structured logger to capture those without monkeypatching `console`:

```ts
import pino from 'pino';

const logger = pino();

const bureau = await createBureau({
  agents: {},
  onDiagnostic: ({ level, scope, message, cause }) => logger[level]({ scope, cause }, message),
});
```

### The `Bureau` Object

The most commonly used members:

| Member | Returns | Purpose |
| --- | --- | --- |
| `agents` | `BureauAgentCatalog<D>` | The typed, read-only agent catalog. See [`AgentDefinitions` and the Agent Catalog](#agentdefinitions-and-the-agent-catalog). |
| `modelCatalog` | `ModelCatalogService` | AB-246—the model-catalog refresh service, present regardless of `D`. `dispose()` awaits any in-flight refresh before reporting rather than aborting it. |
| `planSelection(request)` | `SelectionPlan` | AB-64/AB-250—builds a full `SelectionPlan` for `request` against this bureau's CURRENT model catalog and `BureauOptions.modelPolicy` configuration. Synchronous and side-effect-free: starts no run, refreshes no catalog, dispatches no event. `request.principal` selects the per-principal `UserModelConfiguration`, the same value `BureauRunOptions.principal` carries for an actual run. |
| `run(name, input, options?)` | `AgentRun<...>` | Synchronous dispatch to a named catalog agent. |
| `memory` | `GovernedMemory \| undefined` | COR-41—the governed memory passed as `BureauOptions.memory`, for host-side reads, legal holds, retention sweeps, deletions, and deletion propagation under the host's own authority. See [Governed memory](#governed-memory-cor-41). |
| `children` | `BureauChildren` | COR-772—dispatch a catalog agent as the child of a run this bureau knows, then `list`/`get`/`wait`/`signal`/`cancel` it by its stable identifier, including after a restart. See [Parent-child topology](#parent-child-topology-cor-772). |
| `goals` | `BureauGoals` | COR-851—create a durable goal, then `get`/`list`/`active`/`cancel`/`close` it and `recover` every unfinished one after a restart. Needs a durable engine. See [Durable goals](#durable-goals-cor-851). |
| `createRun(request)` **(deprecated)** | `Promise<CreatedRunSummary>` | Create and start a run against a session. With `runCreationRequestId`, resolves with a durable `receipt` and replays exact retries (see [Run-creation receipts](#run-creation-receipts-cor-424)). Deprecated, not removed, per AB-242; migrate to `bureau.run(name, input, options?)` with a catalog `RunnableAgent`. |
| `locateRunCreationReceipt(request)` | `Promise<RunCreationReceiptLocation>` | COR-424: report where a `runCreationRequestId`'s receipt stands, scoped to its `principal` and `agentName`: `recorded`, `pending`, `expired` once the binding's retention window has passed, or `not-found`. Needs a durable engine. See [Run-creation receipts](#run-creation-receipts-cor-424). |
| `submitSchedulerTask(request)` | `Promise<SubmitSchedulerTaskResponse>` | Queue a task on the in-process scheduler. |
| `locateSchedulerTask(taskId)` | `SchedulerTaskLocation` | Resolve a receipt's `taskId` to `in-progress`, `terminal` (with a `PromiseSettledResult` outcome), `expired`, or `not-found`. Synchronous; throws `BureauError` (`NOT_CONFIGURED`) when the scheduler is not enabled. In-process and in-memory only: a restart loses it. |
| `awaitSchedulerTask(taskId)` | `Promise<RunResult \| null>` | Await a task's settlement from its `taskId` alone, mirroring what the scheduler's `submit()` promise settled with. An `expired` or unknown id rejects with `SchedulerTaskLookupError` (`reason: 'expired' \| 'not-found'`). Throws `BureauError` (`NOT_CONFIGURED`) synchronously when the scheduler is not enabled. |
| `listRuns(status?)` | `RunSummary[]` | List tracked runs, optionally filtered by status. |
| `getRun(id)` / `abortRun(id)` / `deleteRun(id)` | `RunDetail \| undefined` / `RunSummary` / `void` | Read, abort, or remove a tracked run. A tracked run is a `createRun` run or a `bureau.run()` run, by the `id` on its handle. A `bureau.run()` run is tracked from the moment `bureau.run()` returns until it settles, and is then released on its own: `getRun` returns `undefined` and `abortRun` throws `NOT_FOUND` for it, and `deleteRun` is never needed. ### The Audit Trail

```typescript
import { createAuditTrail } from '@lostgradient/bureau';

const trail = createAuditTrail(bureau, kv);
const records = await trail.query({ runId, since: Date.now() - 3_600_000, limit: 100 });
await trail.dispose();
```

`createBureau()` builds an audit trail automatically whenever persistence is configured—it's exposed as `bureau.auditTrail`. It listens to the bureau's `action` events and, for a fixed set of event types (`tool.started`, `tool.settled`, `tool.error`, `run.completed`, `run.error`, `run.aborted`, `run.tripwire`, `step.completed`, plus, as of AB-228, `budget.exceeded` (the bare `BudgetExceededEvent` class has no production emitter—AB-231, merged, reclassifies to `run.completed`'s `finishReason` instead), and the toolbox-forwarded `toolbox.loop-warning`/`toolbox.loop-blocked`/`toolbox.budget-exceeded` (the toolbox's OWN real budget rejection, a distinct production path the bare `budget.exceeded` entry does not cover—Codex review finding, PR #566)—see `AUDIT_EVENT_TYPES`), writes an append-only `AuditRecord` into the key-value store under an `audit:v1:` prefix, key-encoded so natural sort order is chronological. AB-228 also added dedicated listeners for the schedule-DEFINITION lifecycle (`schedule.created`/`paused`/`resumed`/`cancelled`) and for `session.deleted`, none of which traverse `'action'` at all (same reason `durable-event-history.ts`'s own producer needs its own listeners for the schedule family)—`deleteSession` dispatches `SessionDeletedEvent` on the bureau emitter (there was previously no production emission point at all, despite `session.deleted` sitting in `SESSION_DURABLE_ACTION_TYPES`—Codex review finding, PR #566), replayed from the session commit outbox by `drainOutbox` rather than dispatched directly from `deleteSession` itself as of AB-389 (see "Session commit outbox" below), and this trail records it under a synthetic `session:<sessionId>` owner, the same convention `schedule:<scheduleId>` uses, since neither a schedule definition nor a session deletion has a run of its own to attribute to. The seven `review.*` `ReviewStatus` outcomes are NOT in `AUDIT_EVENT_TYPES` at all: they already reach this trail through `AuditTrail.record()`'s out-of-band path (`create-bureau.ts`'s `recordReviewDecision`/`recordReviewStatusTransition`, kind-namespaced as `review.<kind>.<status>`), which bypasses the allowlist entirely—see `AUDIT_EVENT_TYPES`'s own doc comment for the full accounting.

This is a second, durable layer alongside the in-memory `@lostgradient/operative` ring buffer (which is bounded by `maxActions` and lost on restart): the operative store is the live/glass-box view, the audit trail is the durable/queryable one. `trail.query(options)` filters by `since`, `runId`, and `type`, returning up to `limit` records (default 500) oldest-first. Without a `kv` store, the trail still subscribes (so `dispose()` is always safe) but writes nothing. Every write is fire-and-forget from its dispatching caller's perspective (`pauseSchedule`/`resumeSchedule`/`cancelSchedule`/`deleteSession` all return once the synchronous event dispatch completes, not once the underlying `kv.set` commits), so `query()` first awaits a snapshot of every write already in flight at call time (AB-228)—giving read-your-writes for a query immediately following a schedule transition or session deletion, even against a `TextValueStore` whose `set()` resolves asynchronously.

`encodeAuditEntryKey(timestampMs, sequence, runId)` (also exported from `bureau`) reconstructs the exact `audit:v1:...` key a queried `AuditRecord` was written under from its own public fields—used by `bureau/test`'s `selectAuditWriteFaultTarget` (AB-263) rather than a second, drifting reimplementation of the key encoding.

`trail.dispose()` returns `Promise<void>` (AB-207)—it resolves only after every write already in flight has settled, and accepts an owner-issued `AbortSignal` (threaded in by `bureau.shutdown()`) that tells the trail to stop _starting new writes_ once aborted; a write already in flight when the signal fires cannot be cancelled (there is no cancellation hook for the underlying `kv.set`), so `dispose()` still fully awaits it rather than racing the KV store's own close. `bureau.shutdown()`/`bureau.dispose()` await this the same way they await the webhook notifier and online-eval sampler's own async `dispose()`.

### `AuditRecord` schema versioning (AB-370)

`AuditRecord.sequence` is one monotonic counter shared by every write path this trail has—the action-stream listener above AND every out-of-band write (`record()`, the schedule-definition listeners, the `session.deleted` listener) all draw the next value from the same per-bureau counter, allocated at the moment a write is dispatched (before its `kv.set` even starts). `createBureau()` seeds that counter above the highest `sequence` already persisted under `audit:v1:` at boot (`computeInitialAuditSequence`, also exported from `bureau`), so a fresh process never re-issues a value a prior process lifetime already used. Readers order by `timestampMs` first and `sequence` second: `sequence` only breaks a genuine same-millisecond tie, so a query's order for two records that do not share a millisecond is unaffected by this field. Before AB-370, an action-stream record's `sequence` was a straight copy of the operative store's own per-process `Action.sequence`, and an out-of-band record's `sequence` was a second, deliberately huge and disjoint counter (`writeOutOfBandRecord`'s old `manualSequence`, seeded near `Number.MAX_SAFE_INTEGER`)—two numbering domains that could never be compared for true relative order, so a same-millisecond collision between (for example) `session.deleted` and a released run's own terminal action always resolved in the out-of-band record's favor regardless of which one genuinely happened first. That bias is gone: both paths now draw from the identical counter, so a same-millisecond tie sorts by true dispatch order.

`sequence` is optional on `AuditRecord`—a record written before this field existed at all carries none, and `query()`'s sort comparator maps that absence to `-1` (below every real `sequence`, which is always `>= 0`) so a same-millisecond tie against such a record still uses a genuinely transitive comparator, rather than the `0`-for-either-side special case an earlier round of this fix used (non-transitive, and not guaranteed to produce the claimed order by every sort algorithm).

`AuditRecord.actionSequence` is present only on records written from the action stream. It preserves the originating operative-store `Action.sequence`, which lets a host merge live and durable views without showing the same action twice. Out-of-band records such as `session.deleted`, `schedule.*`, and `review.*` have no live action counterpart, so they do not carry `actionSequence`.

### Audit trail retention (AB-388)

`BureauOptions.auditRetention` controls whether the durable audit trail is ever pruned. It defaults to `'forever'`—unbounded, exactly the behavior described above—so a long-lived deployment must opt in before any postmortem evidence is ever removed:

```typescript
const bureau = await createBureau({
  // ...
  auditRetention: { olderThan: 30 * 24 * 60 * 60 * 1000 }, // 30 days
});
```

`options.auditRetention.olderThan` must be a finite, non-negative number—validated at `createBureau()` construction time (`BAD_REQUEST` otherwise), since `NaN` or a negative value feeding the cutoff arithmetic could otherwise prune far more than intended (Codex review, PR #597, "Reject non-finite and negative retention durations").

`retentionFloorTimestamp()`'s protection depends on a schedule/session dedicated event's durable-event `emittedAtMs` never diverging from that SAME event's own audit record `timestampMs`—`createAuditTrail` and `createDurableEventProducer` share one `emittedAtMs` resolver (`createEventTimestampResolver`, `event-timestamp.ts`), keyed by event-object identity, so whichever of the two subsystems' listeners for a `schedule.created`/`paused`/`resumed`/`cancelled` or `session.deleted` event runs first stamps a single clock reading that the other reuses, instead of each independently calling `runtime.clock.now()` and risking two different readings for the exact same event (Codex review, PR #597, "Reuse event timestamps for dedicated lifecycle listeners").

With `{ olderThan: milliseconds }` configured, a pruning pass deletes any audit record whose `timestampMs` is older than `olderThan` by the runtime clock—but never a record at or after the Weft fleet feed's own retention floor (`DurableEventHistory.retentionFloorTimestamp()`: the earliest `emittedAtMs` across every durable event the feed currently retains), even when `olderThan` alone would have allowed pruning it sooner. That clamp means audit evidence always outlives the durable events it describes: as long as the fleet feed still retains a run's own durable history, that run's audit records survive too, regardless of how old they are by the wall clock. Critically, this protection applies even while the floor is still `0`—nothing has ever been retired from the fleet feed yet is the normal, common state (`FleetEventFeed.retain()` is called by every durable maintenance pass under `eventRetention`, 7 days by default, so the floor does advance; with `eventRetention: 'forever'` it stays at `0`), not "nothing to protect" (Codex review, PR #597, "Preserve audit records while the fleet feed floor is zero"). The effective cutoff each pass uses is `min(now - olderThan, retentionFloorTimestamp)`, or just `now - olderThan` when the feed currently retains no events at all (an ephemeral bureau, a persistent backend with no durable event history, or one where every retained event has aged out). The global floor timestamp alone cannot express "protect this specific run's ENTIRE audit history" when that run's only currently-retained durable event is a single, later terminal transition (`run.completed`/etc.)—a pass also asks `DurableEventHistory.retainedRunOwnerIds()` for the full set of run ids the fleet feed still retains at least one event for, and never prunes a record whose `runId` names one of those runs, regardless of `timestampMs` (Codex review, PR #597, "Protect earlier audit records for retained owners"). Reading the floor and the retained-owner set both waits for any `DurableEventProducer` write already in flight for the SAME action first (`waitForAllActiveWrites()`), so an audit record that already committed can never have its protection computed from a snapshot that omits the still-in-flight durable event describing that same action (Codex review, PR #597, "Wait for durable event writes before reading the floor").

Retention also reaches a KV-backed bureau with no durable engine at all—a persistent storage backend configured with `durableExecution: false`, or a custom KV-only `persistence` value (`ConditionalTextValueStore`)—not only one with `runtime.durable` composed (Codex review, PR #597, "Run audit retention for KV-backed non-durable bureaus"); such a bureau has no durable event history to consult, so its effective cutoff is always the unclamped `now - olderThan`. The automatic-profile background timer itself only starts for a KV-only bureau when `auditRetention` is actually active (not the default `'forever'`)—with no durable engine and no active retention policy, that bureau has nothing for the timer to do, so it is never started at all rather than ticking uselessly forever (Codex review, PR #597, "Start the KV-only timer only for active retention"); a durable bureau's timer still always starts regardless of `auditRetention`, since `pruneStaleRunOwnership` has its own, independent work to do.

Pruning is never driven on a schedule of its own—it runs inside the SAME durable maintenance pass `lastRunOwningPrincipals` pruning already uses (AB-363, described under "The Durable Event History Store" below): `bureau.runDurableMaintenance()` for a `durableBackgroundTasks: 'manual'` host's own alarm/Cron trigger, and, under the default `'automatic'` profile, the same background interval that already prunes stale run ownership every five minutes. The two sub-passes are independent—each runs under its own try/catch, on BOTH the manual and automatic paths, so a failure in one (diagnosed under its own message) never prevents the other from running that tick (Codex review, PR #597, "Isolate the manual audit-retention sub-pass"). A rejected `engine.runMaintenance()` call is isolated the same way: `runDurableMaintenance()` still runs both `pruneStaleRunOwnership()` and `pruneAuditTrail()` even when the engine's own maintenance rejects, re-throwing the captured engine failure only after both sub-passes have run, so a failed alarm no longer silently also skips audit retention (Codex review, PR #597, "Isolate audit pruning from engine maintenance failures"). Every manual `runDurableMaintenance()` call still in flight is tracked and awaited by `shutdown()` before backend teardown, alongside the automatic timer's own in-flight pass—a manual host's own alarm/Cron trigger racing `shutdown()` can no longer have its storage disposed mid-prune (Codex review, PR #597, "Await manual pruning before storage teardown").

A pass that actually prunes at least one record writes exactly one `audit.pruned` record back into the trail itself, `detail: { count, cutoffMs }`, naming how many records it removed and the effective cutoff it used; a pass that prunes nothing writes no record at all, so an idle retention policy never grows the trail it exists to bound. This summary write is strict (its failure rejects the pass, rather than the best-effort swallow every other out-of-band audit write uses) and bypasses `dispose()`'s "refuse new writes" abort check for a pass that was already admitted before `shutdown()` began (Codex review, PR #597, "Propagate failures to persist the prune summary" / "Finish the prune summary after shutdown begins")—permanently deleting records without the promised evidence, or losing that evidence to a mid-shutdown abort, would be worse than surfacing the failure. Each pass also persists the highest `sequence` it ever pruned—BEFORE deleting any record (Codex review, PR #597, "Persist the sequence watermark before deleting records"), so a crash partway through a pass never loses track of a sequence it already started removing—under a separate, non-`audit:v1:`-prefixed key, so it is invisible to `query()` and to the normal boot scan; `computeInitialAuditSequence` consults that persisted floor in addition to its usual scan, so a restart's shared sequence counter resumes correctly even when every one of the surviving records at boot postdates every pruned one (or nothing at all survived). Two overlapping `prune()` calls on the same `AuditTrail` instance (e.g. a manual host's own call landing mid-automatic-tick) are serialized through an internal queue rather than racing each other's reads and deletes (Codex review, PR #597, "Serialize concurrent audit-pruning passes"). A cross-process race between two Bureau instances sharing the same KV store is closed separately, via a CAS-guarded lease (`ConditionalTextValueStore.conditionalBatch`): only the instance whose lease-acquisition batch commits first actually lists, deletes, and updates the watermark for that tick, and every other instance skips the tick entirely rather than racing its own reads and deletes against the holder's—a lease older than its own TTL (a prior holder that crashed before releasing it) is taken over rather than blocking pruning forever (Codex review, PR #597, "Coordinate pruning across shared-store instances"). If `kv.delete()` rejects partway through a multi-record pass, the records deleted before the failure are still named in a partial `audit.pruned` summary (`detail.partial: true`) before the failure is re-thrown, so an already-committed deletion is never left with no corresponding evidence (Codex review, PR #597, "Record successful deletions when a later delete fails").

### Checkpoint retention and terminal-run cleanup (COR-625)

`BureauOptions.checkpointRetention` controls whether a durable run's Weft checkpoint history is ever pruned once that run reaches a terminal state. It defaults to `'keep-all'`—unbounded, exactly the behavior described above—so a long-lived deployment must opt in before any checkpoint is ever removed:

```typescript
const bureau = await createBureau({
  storage: { type: 'sqlite', path: './bureau.sqlite' },
  checkpointRetention: { keepLast: 5 },
});
```

`keepLast` must be a positive integer, and `timeoutMilliseconds`, when supplied, a finite non-negative number—both validated at `createBureau()` construction time (`BAD_REQUEST` otherwise), the same boundary `auditRetention` uses. Zero is rejected even though Weft's own `Engine.pruneCheckpoints` accepts it: retaining nothing would discard the newest checkpoint a postmortem needs, which is not what configuring _retention_ asks for.

Every terminal transition of a durable run—completion, error, abort, or `cancelDurableRun`—runs exactly ONE cleanup step for that run, however many of those triggers fire. The step is memoized per run id, which is what makes `cancelDurableRun` followed by the run's own terminal event a single step rather than two, and what covers a run cancelled while this process holds no live `ActiveRun` for it at all (no terminal listener ever fires there, so the cancellation path owes the step directly). Only a `'requested'` cancellation outcome reaches the step: the others describe a run that call never genuinely terminated.

The step re-reads the run's durable record through `engine.get()` and prunes only once the engine itself reports a terminal status. A Bureau terminal listener fires on operative's own event emitter, which is not proof the engine's final checkpoint write has committed, and Weft's prune rejects on a compare-and-swap race with a concurrent write—so pruning on the event alone would both risk removing a checkpoint ahead of the transition it belongs to and manufacture spurious failures out of a race that is really just "too early".

Each settled step writes exactly one `run.cleanup-settled` audit record, `detail: { acknowledgement }`, whatever the outcome—including the `not-required` of the default `'keep-all'` policy. An operator can only answer "did cleanup finish?" from a record that exists for every run, not only for the ones that pruned something.

The acknowledgement is operative's `CleanupAcknowledgement`: `{ status: 'completed' }` when the prune succeeded, `{ status: 'not-required' }` when no policy is configured or the bureau is not durable, `{ status: 'unresolved', reason: 'persistence-failed' }` when the store rejected the prune or the run was not terminal, and `{ status: 'unresolved', reason: 'timed-out' }` when a configured bound elapsed first. There is no `failed`-plus-`persistence-failed` pairing: `reason` exists only on `unresolved`, and `failed` stays reserved for a definite, observed teardown failure.

Weft exposes no engine-wide operation timeout to inherit, so `timeoutMilliseconds` is opt-in. When set, the bound sleeps on `BureauOptions.shutdownTimeoutSleep`—`RuntimeServices.timers`-backed, never a real timer—and its abort signal is passed into `pruneCheckpoints({ signal })`, so Weft aborts before issuing any delete. Abandoning only the wait would leave unowned deletes running behind a cached `'timed-out'` result. Omitted, the step is unbounded and a caller bounds its own wait through `closed({ signal })`.

The step also folds into the durable run's `closed()`, where it only ever _downgrades_: a step reporting `completed` or `not-required` leaves a `completed` run `completed`, while `unresolved` or `failed` surfaces in its place. The run's own cleanup genuinely did finish; a retention step with nothing to prune is a separate fact, and it belongs in the audit record rather than in the run's acknowledgement. The hook is registered on a run's `closed()` only when a retention policy is actually configured—registering it disqualifies `closed()`'s `not-required` fast path (a run with cleanup registered does have cleanup left to do), which would otherwise change `closed()`'s answer for every bureau that never asked for retention. The audit record is written either way.

### Run-creation receipts (COR-424)

A `createRun` request that names `runCreationRequestId` goes through a durable command ledger (`command-ledger.ts`) and resolves with a `RunCreationReceipt`: `{ runId, requestId, createdAt, status }`, where `status` is the run's status when the receipt was recorded. The request must also carry a non-blank `principal`; without one it is a `BAD_REQUEST`. Receipts need a bureau with storage and a durable engine, because a receipt promises that a retry after a restart finds the original run. Without a durable engine the request is rejected with `BureauError` (`NOT_CONFIGURED`, subject `durable`). The restart guarantee holds only as far as the storage itself persists.

The ledger keys each entry on `(principal, agentName, runCreationRequestId, operationVersion)`, with surrounding whitespace trimmed from the request id. The principal is keyed exactly as the run records its owner, so a receipt only ever replays to the principal that owns the run. `agentName` is the published agent the run is for, defaulting to `bureau`, so one request id sent to two agents creates two runs rather than a conflict. Beside the key, the ledger stores a SHA-256 digest of the payload that decides the run: `message`, `sessionId`, `systemPrompt`, `maximumSteps`, and `maximumTokens`, each taken at the value the run will use. A retry that spells out a default it first omitted is therefore the same command. The request context is not part of the digest, because its credentials and tracing legitimately differ between retries. Entries live in the same key-value store as the bureau's sessions.

- **Exact retry.** The same principal, agent, request id, and payload return the original run and the original receipt. Nothing is written, and flow control is not consulted, so a retry is never rejected as a duplicate trigger. Concurrent identical requests in one process create one run.
- **Conflicting retry.** The same identity with a different payload rejects with `BureauLedgerConflictError` (`requestId`, `reason: 'payload-mismatch'`, and `originalReceipt` once the original has one). The attempt is recorded as its own failed entry, and the original entry is never changed. This is not a `BureauError`.
- **Retry while pending.** The ledger claims the identity, with the run and session identifiers it minted, before flow control admits the run, and records the receipt once the run is durably started. A retry that finds the claim pending waits for the attempt when it is in flight in the same process. Otherwise (after a restart) it looks for the claimed run. When the run exists, live or in the durable engine, the retry records the receipt with the status it observed, and every later retry receives that same receipt.
- **A claim whose run never started.** When the claiming process died before the run reached the durable engine, retries report the claimed run as `pending` and start nothing. Without a lease, a crashed claimant cannot be told apart from a slow one, so the request id stays bound to that claim until the retention window, measured from the claim, has passed. A caller that needs the run sooner must use a new request id.
- **Failure.** When no run results (flow control rejects it, or a session or durable write fails), the claim is released and a retry starts afresh. When the run was durably started but its receipt could not be recorded, `createRun` rejects with `RunCreationReceiptUnrecordedError`, which names the `runId`. The run keeps executing, and a retry of the same request records and returns its receipt.

**Retention.** Each rule above holds only while the binding is retained. A binding is kept for `BureauOptions.runCreationTerminalRetentionMs` after its run settles: a positive integer, 86,400,000 (24 hours) by default, the same as Weft's mailbox `terminalRetentionMs`. Time is the bureau's injected runtime clock. A run still in progress holds its binding however old it is, so a delayed retry of a long-running run never starts a second one. The window runs from the run's terminal action, as the bureau's run store recorded it, whether or not anyone queried the run in the meantime. The one exception is a run that settled before a restart and was not reattached: the ledger cannot see when it settled, so it records the first retry, receipt query, or prune that observes it settled, and the window runs from that moment. A claim whose run never started is measured from the claim.

Once the window has passed, `bureau.locateRunCreationReceipt({ principal, agentName?, runCreationRequestId })` reports `{ status: 'expired', requestId, expiredAt }`, and the same request id creates a new run as a fresh attempt, whatever its payload. The new claim replaces the expired entry and deletes its conflict records in the same compare-and-swap. Until then, those conflict records are ignored, because the binding they conflicted with no longer holds. Durable maintenance deletes expired bindings and their conflict records: `runDurableMaintenance()` on a `'manual'` host, and the bureau's own maintenance interval under the default `'automatic'` profile. A query for a pruned binding reports `not-found`. Before expiry, the query reports `recorded` with the original receipt, or `pending` for a claim with no started run. Like a retry, a query that finds the claimed run started records its receipt.

`run-creation-fault-points.test.ts` covers the crash-before-claim, after-claim, after-work-start, after-effect-before-ack, and during-cancellation fault points over both SQLite and LMDB. Session-input admission, schedule mutation, review resolution, and cancellation do not use this ledger yet.

### The Durable Event History Store (AB-91)

```typescript
const page = await bureau.eventHistory({ kind: 'run', id: runId });
if ('outcome' in page) {
  // 'unsupported-capability' (ephemeral bureau) or 'gap' (since predates retention)
} else {
  console.log(page.events, page.hasMore, page.nextCursor);
}
```

`createBureau()` builds a durable event-history store over the workspace version of Weft's `FleetEventFeed` whenever a genuinely **persistent** storage backend is configured. It shares `runtime.durable.engine.storage`—there is no second durable log. `bureau.eventHistory(owner, options?)` provides a bounded, sequence-ordered read over one run's or session's events after an exclusive `since` cursor, while `bureau.subscribeEventHistory(owner, listener, options?)` provides a replay-then-live subscription over the same events. If `since` predates the retention floor, `eventHistory()` returns a typed `DurableEventGap` (its pre-existing `firstRetainedSequence` is a sequence number), and `subscribeEventHistory()` delivers one `history.gap` event (`DURABLE_HISTORY_GAP_KIND`) through the listener, then continues from the floor. The event's payload is `{ requestedCursor, firstRetainedCursor }`, both cursor strings, and `firstRetainedCursor` is the canonical shape for a subscriber; `requestedCursor` is the cursor of the last event the listener received (a previous gap event included), or the `since` it started from when it has received nothing. The envelope `cursor` is the last cursor before the first retained event, so resuming from it lands on the floor. A subscription whose undelivered backlog the floor overtakes while it is open gets the same event before any later one; a subscription drained to the tail never does. The gap event is synthesized, never stored: `record()` rejects the reserved kinds `history.gap` and `frames.dropped` with `ReservedDurableEventKindError`.

`BureauOptions.eventRetention` (default `{ olderThan: 604800000 }`, 7 days; `'forever'` opts out) bounds the history: each durable maintenance pass, manual or automatic, advances the floor over the contiguous prefix of events emitted before `now - olderThan`, never past an event that is not older than the window, and deletes the dedupe markers of the events it removed. The `run.removed` event that records a deletion is an ordinary event and ages out under the same window, after which a deleted run reads as an unknown one. `BureauOptions.taskRetention` (default 30 days, `'forever'` opts out) bounds tasks: a pass removes each run that is older than the window through `deleteRun()`, so the run store's `run.removed` fires and everything keyed on the run releases its state. A run counts as old from its closing `run.completed` or `run.aborted` action, never from `run.error` alone (it is followed by `run.completed`). It stays while its COR-424 run-creation binding is stored, expired or not, so the pass ahead of the receipt sweep keeps it one more pass; one unreadable binding record makes the pass fail closed, deleting nothing and diagnosing it, until the record is repaired. The pass runs from `runDurableMaintenance()` and from the automatic maintenance timer, which starts only for a durable bureau or one with KV-backed audit retention; an ephemeral bureau with neither keeps its terminal tasks until something calls `runDurableMaintenance()`. Only runs in this process's run store are candidates: a terminal run from before a restart is never reattached, so it is never deleted by this pass and never receives `run.removed` from it. An ephemeral Bureau returns `no-persistent-storage` from `eventHistory()` and a closed subscription from `subscribeEventHistory()`.

`eventHistory(owner, { principal })` authorizes a `{ kind: 'run', ... }` owner against the run's owner of record (see [Owner of record](#owner-of-record-cor-718)) and fails CLOSED (`{ outcome: 'not-found' }`) whenever that ownership cannot be verified, including for a deleted run (AB-313). This holds across a process restart: the owner recorded at `createRun` time is persisted on the run's owning session (`lastRunOwningPrincipals`) and rehydrated into the same in-memory attribution a live run uses the moment a durably recovered run is reattached, so a recovered run's real owner reads its durable history exactly as it did before the crash (AB-359). A `{ kind: 'session', ... }` owner is authorized by `isSessionHistoryReadAuthorized`: only the session's owner passes, and a session written before owners existed belongs to `anonymous:local`. A session whose recorded owner is malformed fails closed (`{ outcome: 'not-found' }`) for every principal. The same rule applies before the page is read, after a gap, and after the page resolves. A caller that states a principal reads only a live session it owns: a deleted session's history is `not-found` to it, its former owner included, because history is keyed by id alone and a deleted session has no owner left to compare, and only a trusted call (no `principal`) gets the `deleted-aggregate` outcome with the events. Every durable session event records the incarnation it was recorded for (`session.created`, `session.saved`, and `session.deleted` from their outbox entries; a `session.*` action from the `incarnation` its detail states), and a principal-stated read, page or subscription, keeps only the events recorded for the live session's incarnation, whatever `since` and `limit` it passes. An event recorded for no incarnation, which includes every event stored before the field existed, is never shown to a principal. This holds however an earlier incarnation ended: `deleteSession`, or `SessionStore.cleanup()`, which also appends one `session.deleted` outbox entry per expired session so an expiry leaves the same deletion marker and audit entry a deletion does. Omitting `principal` entirely still bypasses the check for every owner kind (an internal/trusted caller).

This is a THIRD layer, distinct from both the operative store (Layer A, live) and the audit trail above (Layer B, KV-based, `AUDIT_EVENT_TYPES`-scoped—see that section for the exact set): the event history store is restart-durable by construction (proven by reopening the same SQLite/LMDB file across two independently constructed store instances—see `durable-event-history.test.ts`), owner-scoped rather than a flat log, and cursor/gap-aware for reconnect-safe paging.

A producer (`createDurableEventProducer`, wired into `createBureau()` alongside the audit trail) sinks the run/session/schedule-fire/schedule-definition families AB-87's matrix classifies as durable into `record()`—`run.completed`/`error`/`aborted`/`tripwire` (owner: the action's `runId`) and the durable `session.*` lifecycle rows (owner: the action detail's `sessionId`) from the bureau's own action stream; `schedule.completed`/`schedule.failed` (a scheduled fire is "an ordinary run" per AB-87, so these are recorded under the fired run's own `{ kind: 'run', id: runId }` owner) and, as of AB-320, `schedule.created`/`paused`/`resumed`/`cancelled` (recorded under `{ kind: 'schedule', id: scheduleId }`, the schedule's own owner kind) from the bureau's own schedule-lifecycle events. A schedule's durable page carries its four definition events only—never a fire; the fired run's own page carries the fire only—never a definition event. `schedule.attempted`/`schedule.skipped` (COR-660) are deliberately absent from both: one event per tick per schedule is a liveness pulse rather than a durable transition, and AB-87's matrix excludes high-rate pulses from cursor advancement, so they dispatch live on the bureau emitter and are recorded nowhere. Whether a dropped occurrence specifically deserves a durable row — it is the only observable trace of a tick that produced no run — is settled by COR-1224: neither is durable as an event row, and a dropped occurrence is instead recorded on Weft's own schedule record as `skippedCount` and `lastSkippedAt`. A schedule whose fires outlast its cadence collides on every tick, so a durable row per drop would grow without bound and advance the durable cursor for a fact whose content is that nothing happened; a counter answers the operator's question — is this schedule colliding, and when last — in constant space, and survives a restart that a live listener would not. AB-224 adds a fourth source, the same shape as `schedule.*`: the `review.*` lifecycle events (`review.requested`, when a review becomes pending, and `review.approved`/`denied`/`rejected`/`expired`/`revoked`/`canceled`/`superseded`), recorded under the reviewed run's own `{ kind: 'run', id: runId }` owner with a minimal, privileged payload (`reviewId`/`runId`/`principal`/`kind`; `review.requested` adds the `signalName` of a human wait or the `callId` of an approval, never a prompt or an argument). AB-372 adds a fifth, dedicated listener rather than another `'action'`-stream case: `deleteSession` dispatches `SessionDeletedEvent` on the bureau emitter (never through the action stream—as of AB-389, replayed from the session commit outbox by `drainOutbox` rather than dispatched directly by `deleteSession` itself; see "Session commit outbox" below), so this producer listens for it directly and records the same `{ kind: 'session', id: sessionId }` / `session.deleted` durable event `Bureau.eventHistory`'s deleted-aggregate detection reads—closing the gap where that detection was previously only ever exercised by synthetic records the test suite constructed directly. It de-duplicates a same-process duplicate dispatch (concurrent `deleteSession` calls racing to delete the same session) with an in-flight `Map` keyed by owner AND `AgentSession.incarnation` (AB-384—before it, the key was owner alone, which conflated a session id recreated and deleted again WHILE the prior incarnation's own write was still pending with a duplicate dispatch of that prior deletion; see `SessionDeletedEvent`'s own doc comment), checked and set synchronously before any `await`; it does not scan the durable page for a prior record, so a session recreated under the same id and deleted again writes a second, later `session.deleted` row rather than being suppressed as a duplicate—the two dispatches are for different incarnations, not the same one, and now produce two records even when their writes overlap. This producer also exposes `waitForActiveWrites(owner): Promise<void>`, a snapshot-only sibling to `hasActiveWrite`: it awaits every write in flight for that owner AT THE MOMENT OF THE CALL (never one started afterward) and never rejects, so `resolveEventHistory` can await it before paging to close the read-your-writes race against this producer's own fire-and-forget writes without risking an unrelated caller's write leaving it hanging.

AB-384 adds a sixth and seventh source, closing a dead entry each: `SESSION_DURABLE_ACTION_TYPES` has listed `session.created`/`session.saved` since AB-91, but nothing ever dispatched either onto the `'action'` stream. `@lostgradient/operative`'s `SessionStore` dispatches both on the bureau-level emitter—as of AB-389, replayed from the session commit outbox, never dispatched directly by `save()`/`update()` themselves (see "Session commit outbox" below)—and this producer's two dedicated listeners record them under the same `{ kind: 'session', id: sessionId }` owner `session.deleted` already uses. Every one of these three listeners' `history.record()` calls now also passes an `options.dedupeKey` (the outbox entry's own `ordinal`, stringified) and `options.emittedAtMs` (the entry's own `committedAtMs`, so a delayed replay never misdates the event as happening "now")—never embedded in the recorded `payload` itself, so a caller's own payload carrying a same-named `dedupeKey` field is unaffected. `record()` writes the dedupe identity as an atomic storage compare-and-swap alongside the event append itself (in the SAME `conditionalBatch` `FleetEventFeed.append` commits), not a read-before-write scan: two processes racing to record the identical `(owner, kind, dedupeKey)` can never both succeed, closing the redelivery race a scan alone cannot (a crash between a durable write settling and the entry being acknowledged, or two drains racing over one shared backend, resolves to a no-op read of the winner's own record, never a second durable append).

### Owner of record (COR-718)

Every resource has one **owner**: the principal that owns it, stored once when the resource is created. The **actor** is whoever performed an action, and is recorded on the audit entry's `principal`. A service principal (`system:scheduler`, `system:recovery`, `system:expiry`) is only ever an actor: work the scheduler, recovery, or expiry starts or changes keeps the owner of the resource it acts on.

An owner is a string. An API-key caller served by `createBureauHandler` owns as `api-key:<encodeURIComponent(subject)>`, and an in-process host states it with `CreateRunRequest.principal`, `DurableScheduleDefinition.principal`, or the goal request's `principal`. A host that states none owns as `anonymous:local` (`ANONYMOUS_LOCAL_OWNER`), and so does a record persisted before owners existed. That is a read rule, not a migration. A principal that is neither text nor absent is refused before anything is persisted: `BAD_REQUEST` from `createRun`, `createSchedule`, `bureau.run`, and `children.dispatch`, and the `invalid-configuration` rejection from `bureau.goals.create`. The `system:` and `anonymous:` namespaces never come from a credential.

`bureau.getOwner(resource)` reads an owner back. The kinds, and where each owner lives:

- **run** (an A2A task is a run): session metadata `lastRunOwningPrincipals`, rehydrated into the in-memory attribution after a restart, and `LivenessSnapshot.owner`.
- **session**: the owner of the run that created it, in the session's `sessionOwner` metadata. It is written once and never replaced, so it survives the pruning of `lastRunOwningPrincipals`. A different principal starting a run on the session (`createRun` throws `NOT_FOUND`), submitting session input, or reading its history gets the answer a session that does not exist gets.
- **child run**: its own child record, equal to its parent's owner.
- **goal**: the goal record's `principal`.
- **schedule**: `ScheduledAgentRunInput.principal`, written by `createSchedule`. A fire's run, and the session the fire creates, are owned by the schedule's owner; a fire into a recurring session another principal owns is refused as a session that was not found, but it is still recorded: its run keeps the schedule's owner and it writes its `schedule.fired` entry. Each fire records one `schedule.fired` audit entry with `principal: 'system:scheduler'`.
- **review**: its run's owner.
- **audit entry**: derived from its `runId`, never stored. A run id gives that run's owner, `schedule:<id>` the schedule's, and `session:<id>` (a `session.deleted` entry) the `owner` its `detail` records. Bureau writes that owner to its own store before it deletes the session and removes it once the audit entry is written, so the answer never reads the live session, which may be gone or recreated under another owner. An entry for a deletion that bypassed Bureau has no `detail.owner`, so its owner is undefined and only operator scopes can see it. A run reattached after a restart keeps its owner and records one `run.recovered` entry with `principal: 'system:recovery'`; an expired review keeps its run's owner and records `principal: 'system:expiry'`.

An in-process host must restate the session's owner on every later `createRun`: an omitted `principal` is a trusted call for children and goals, but for `createRun` it means `anonymous:local`, which is refused on a session another principal owns.

Session-scoped memory, transcripts, and events belong to their session or run. Agent-, skill-, and experience-scoped memory, delivery records, delegation grants, the steering log, the command ledger, session-input identity, asset upload sessions, and skills and proposals have no owner of record.

### Parent-child topology (COR-772)

`bureau.children.dispatch({ parentRunId, agentName, input, childRunId?, parentCancellation?, authority? })` starts a catalog agent as the child of a run Bureau already knows—a `createRun` run, a durable `bureau.run` run, or another child—and writes the relationship to Bureau's key-value store before the child starts. The record carries the parent and child run identifiers, both agent names, the status, `createdAt`/`updatedAt`/`settledAt`/`reattachedAt` timestamps, and the child's workflow identity (`{ kind: 'durable', workflowType: 'agentRun', workflowId }` when the durable engine runs it, `{ kind: 'process-local' }` otherwise). Every later transition is a compare-and-swap on the record's revision, so a stale writer changes nothing, and supplying the same `childRunId` twice—even concurrently—returns `duplicate` instead of starting a second workflow. A `childRunId` becomes the child's durable run identifier, so one that already names another run or workflow Bureau knows is rejected as `child-run-id-conflict` before anything is reserved, recorded, or started; it can never take over that run's attribution, recovery record, or place in the topology. An identifier beginning `goal:`, `goal-`, or `bureau-goal-audit:` belongs to durable goals and is rejected as `reserved-child-run-id` (see [Durable goals](#durable-goals)).

A parent is a `createRun` run (its `RunSummary.id`), a durable `bureau.run` run (its handle's `snapshot().id`), or another child (its `childRunId`). The handle `bureau.run` returns reports a placeholder snapshot until the durable dispatch resolves: its `id` is the agent name and its `durability` is `'process-local'`. Then `id` is the durable run identifier and `durability` is `'durable'`, and children can be dispatched under it once `bureau.getDurableRun(id)` returns the workflow. `bureau.listDurableRuns()` is not a way to find a parent: it lists every durable run newest first, including other callers' runs and every durable child. A non-durable `bureau.run` run cannot own children: dispatching under its `snapshot().id` returns `not-found`. A child is durable—a Weft workflow recovery can reattach—when Bureau has a durable engine and the catalog agent supports definition resolution (every `createAgent` or `createLazyAgent` result does); otherwise it is process-local and dies with its process. The same condition decides whether a `bureau.run` run is durable enough to be a parent. For the cross-package contract, including what is unsupported, see [Multi-agent lifecycle and communication](../../documentation/multi-agent-lifecycle.md).

- **Addressing.** `list(parentRunId)`, `get`, `wait`, `signal`, and `cancel` all name the owning parent, and naming an unrelated parent reads as `not-found`. A child's record carries its parent's owner of record, which is `anonymous:local` for a parent started with no principal. `dispatch` compares the caller's principal with the parent's; `list`, `get`, `wait`, `signal`, and `cancel` compare it with the child record's. A mismatch reads as `not-found`, and omitting the principal is a trusted internal call. So under a parent without a principal, only `anonymous:local` (or a trusted call) can dispatch, and every child belongs to it.
- **Signals.** A child whose agent has a contract in `BureauOptions.children.signals` gets a typed COR-814 channel; `signal` resolves to `acknowledged` or the channel's typed rejection.
- **Parent cancellation.** A child never receives its parent's abort signal. `abortRun`, a committed `cancelDurableRun`, aborting a durable `bureau.run` parent through its own `AgentRun` handle, or `children.cancel` on a child that is itself a parent applies each running child's `parentCancellation`: `'cascade'` (the default) cancels it and its own cascade children, `'detach'` leaves it running. From the moment its cancellation is requested, a parent admits no new child (`parent-terminal`), even while its own run still reads as running, so no child escapes a cascade that recovery would apply. A `children.cancel` that fails, or finds the child already finished, cancels nothing below it; a cascade the engine cannot perform is diagnosed, leaves that subtree running, and is retried when the parent settles. During `dispose()`, shutdown ends every live run itself, and boot recovery applies the policy to whatever it left running from the cancelled parent's durable state.
- **Recovery.** Boot recovery never starts a child workflow. A child whose workflow is still running is reattached (its signal channel reopened before the workflow resumes); one that finished while nobody was watching is recorded with its real outcome; a process-local child, or one whose workflow is missing, is recorded as failed. A child of a parent that was cancelled, or that cannot be recovered, follows its `parentCancellation`, with one exception: a child that holds a grant is cancelled when its parent cannot be recovered, even under `'detach'` (see **Delegation grants** below). Under an unrecoverable parent, only a `'detach'` child without a grant keeps running.
- **Audit.** When persistence is configured, `child.started`, `child.completed`, `child.failed`, `child.aborted`, and `child.reattached` are written to the audit trail under the child's run identifier, plus `delegation.revoked`/`delegation.rejected` on recovery. A dispatch rejected before the child's record is registered (`unknown-agent`, `parent-terminal`, `child-run-id-conflict`, `reserved-child-run-id`, `delegation-invalid`, `depth-exhausted`, `authority-exceeded`, or `budget-exhausted`) returns its outcome to the caller and writes no audit entry. `start-failed` is decided after registration: it writes `child.started` and `child.failed` and leaves a `'failed'` record, so a retry with the same `childRunId` returns `duplicate`.
- **Delegation grants.** Without `BureauOptions.children.delegation`, a dispatch's `authority` is ignored, not rejected: it is not validated, no grant is issued, nothing is budgeted, and depth, fan-out, and capabilities are unbounded. With it, each dispatch issues a signed `DelegationGrant` (`@lostgradient/operative`), attenuated from the parent's own grant, and reserves `concurrentChildren`/`totalDescendants` in a durable reserve/release ledger keyed by dispatch attempt, so an attempt that loses a registration race releases only its own reservation. A request for more depth, budget, or capability than the parent's grant allows is rejected, never clamped; a requested `delegatedAuthority` is intersected with the parent's instead. A top-level parent (a `createRun` or `bureau.run` run) holds no grant, so its dispatches are neither checked against a grant nor budgeted, and its own fan-out is unbounded. There, `authority` sets the child's ceilings as given rather than narrowing them, and an omitted capability list or budget ceiling is unrestricted. `authority.depth` defaults to `0` under a top-level parent and to the parent's `depth - 1` below it, so pass `depth` on the top-level dispatch to allow grandchildren. Recovery re-verifies each running child's grant (signature, expiry, revocation) and reconciles its ledger before reattaching it; a child whose parent cannot be recovered has its grant revoked on recovery and is cancelled, whatever its `parentCancellation`.

Expected results are values, not exceptions. Malformed input (an empty identifier, an unknown `parentCancellation`, invalid agent input, or an invalid `authority` when delegation is configured) throws `BureauError` with `BAD_REQUEST`, and a failure of the underlying key-value store rejects the returned promise.

| Operation | Resolves |
| --- | --- |
| `dispatch(request)` | `started` (with the record and, with delegation, a `grant` summary), `duplicate`, `not-found`, or `rejected` with `code` `unknown-agent`, `parent-terminal`, `child-run-id-conflict`, `reserved-child-run-id`, `delegation-invalid`, `depth-exhausted`, `authority-exceeded`, `budget-exhausted`, or `start-failed` |
| `list(parentRunId, { principal? })` | Every `BureauChildRecord` under that parent the principal may see; `[]` for an unknown parent |

| `signal({ ...reference, name, payload })` | `acknowledged` (`signalId`, `sequence`), `rejected` (the channel's `code`, `reason`, `delivered`), `not-found`, `child-terminal`, or `unsupported` (`no-signal-contract` or `child-not-live`) |

The public types are `BureauChildren` (the `bureau.children` surface); `BureauChildrenOptions` (`BureauOptions.children`) and `BureauChildDelegationOptions` (its `delegation` field); the requests `BureauChildDispatchRequest`, `BureauChildAuthorityRequest` (`authority`), `BureauChildReference`, `BureauChildSignalRequest`, and `BureauChildCancelRequest`; the outcomes `BureauChildDispatchOutcome` (with `BureauChildDispatchRejection` codes and a `BureauChildGrantSummary`), `BureauChildWaitOutcome`, `BureauChildSignalOutcome`, and `BureauChildCancelOutcome`; and the record types `BureauChildRecord`, `BureauChildStatus`, `BureauChildTerminalStatus`, `BureauChildOutcome`, `BureauChildParentCancellation`, and `BureauChildWorkflowIdentity`. `CHILD_AGENT_RUN_WORKFLOW_TYPE` (`'agentRun'`) is the `workflowType` a durable child's record names.

A child's `status` is `'completed'` when its run ends with `finishReason: 'stop-condition'`, `'aborted'` when it ends aborted, and `'failed'` for every other finish reason; `outcome.finishReason` keeps the original. A parent that finishes normally does not stop its children—they keep running and stay addressable through its identifier—but it admits no new child.

A grant's summary carries `grantId`, `policyVersion`, `depth`, `expiresAt`, and `artifactDigest` (present when the input is a conversation), plus `budget` only under a `'full'` `disclosurePolicy`; the default is `'redacted'`. The stored grant is always complete. `timeToLiveMilliseconds` defaults to `children.delegation.defaultTimeToLiveMilliseconds` (one hour), and a child's `expiresAt` never outlives its parent's. Bureau enforces the signature, revocation, expiry, `depth`, `concurrentChildren`, and `totalDescendants`. It signs and attenuates the capability lists, the grant's `delegatedAuthority`, and the `steps`, `tokens`, `cost`, `toolCalls`, and `duration` ceilings, but does not apply them to the running child. Expiry and revocation are checked when a descendant is dispatched and during recovery; neither stops a child already running. There is no public revoke operation. Rotating `children.delegation.secret` invalidates every existing grant.

```typescript
import { createBureau } from '@lostgradient/bureau';

// `planner` is a long-running `createAgent` agent, `delegationSecret` comes
// from the host's secret store (and must not change across restarts), and
// `durableRunId` waits until `root.snapshot().id` is the durable run
// identifier and `bureau.getDurableRun` finds its workflow (see the
// multi-agent guide's durable example).
const bureau = await createBureau({
  agents: { planner },
  storage: { type: 'sqlite', path: 'bureau.sqlite' },
  children: { delegation: { secret: delegationSecret } },
});

const root = bureau.run('planner', 'Plan the corvid report');
const parentRunId = await durableRunId(bureau, root);

const lead = await bureau.children.dispatch({
  parentRunId,
  agentName: 'planner',
  input: 'Lead the research',
  childRunId: 'lead',
  authority: {
    depth: 1,
    budget: { concurrentChildren: 1 },
    capabilities: { tools: ['search'] },
  },
});
// { outcome: 'started', child, grant: { grantId, policyVersion: 'bureau-delegation/1', depth: 1, expiresAt } }

const helper = await bureau.children.dispatch({
  parentRunId: 'lead',
  agentName: 'planner',
  input: 'Collect sources',
  childRunId: 'helper',
});
// { outcome: 'started', grant: { depth: 0, ... } } — attenuated from lead's grant

const widened = await bureau.children.dispatch({
  parentRunId: 'lead',
  agentName: 'planner',
  input: 'Run a shell command',
  authority: { capabilities: { tools: ['shell'] } },
});
// { outcome: 'rejected', code: 'authority-exceeded' }

const secondHelper = await bureau.children.dispatch({
  parentRunId: 'lead',
  agentName: 'planner',
  input: 'Collect more sources',
});
// { outcome: 'rejected', code: 'budget-exhausted' } — lead allows one concurrent child

const grandchild = await bureau.children.dispatch({
  parentRunId: 'helper',
  agentName: 'planner',
  input: 'Go one level deeper',
});
// { outcome: 'rejected', code: 'depth-exhausted' }

root.abort('report planned');
await bureau.children.wait({ parentRunId: 'lead', childRunId: 'helper' });
await bureau.dispose();
```

`src/bureau-children-guide.test.ts` runs this example, and the lifecycle example in the [multi-agent guide](../../documentation/multi-agent-lifecycle.md#durable-example), asserting each commented result. Aborting `root` cascades to `lead` and then to `helper`, because both use the default `'cascade'` policy.

Not supported: observing a child's signal `events` (Bureau only sends signals; a child's `emit` buffers until it is refused as `buffer-full`), replaying signals that were unacknowledged when a process died, messaging between siblings or any peer (communication is parent-mediated only, per COR-807), and recovering a process-local child, which recovery records as `'failed'`. Bureau children are not registered in the parent `AgentRun`'s `ChildRunRegistry`, so the parent's `children()` and `closed()` do not see them.

### Durable goals (COR-851)

`bureau.goals` runs one goal across attempts and keeps it across a process restart. An attempt is one durable run of a catalog agent, followed by one validator execution that decides whether the goal is met; the attempt is the retry unit, and the decisions (when to retry, when a budget is spent, which terminal reason a goal ends with) are the same ones the in-memory `startGoal` controller makes, because both call the same pure functions.

```ts
const bureau = await createBureau({
  agents: { worker },
  validators: [testsPass], // identity: { name: 'tests-pass', version: '1' }
  storage: { type: 'sqlite', path: './bureau.sqlite' },
  durableExecution: true,
});

const created = await bureau.goals.create({
  agentName: 'worker',
  prompt: 'Make the failing tests pass.',
  identity: { name: 'fix-tests', version: '1' },
  validator: { name: 'tests-pass', version: '1' },
  bounds: { maximumAttempts: 3, maximumTotalDurationMs: 600_000 },
  retryPolicy: { retryOn: ['validator-fail-retryable'] },
  goalRunId: 'fix-tests-1',
});
// { outcome: 'created', goal, controller: { status: 'started' } }

await bureau.goals.active('fix-tests-1'); // { kind: 'attempt', runId: 'goal-fix-tests-1-a0', ... }
await bureau.goals.cancel('fix-tests-1'); // { outcome: 'canceled', goal }
```

Three things hold a goal together. Its record (`GoalState`, in Bureau's key-value store) is the truth: every transition is a revision compare-and-swap, and a controller transition carries a sequence number and an id, so a replayed or duplicated commit is recognized and a late one is refused. Its controller is a Weft workflow named `goalRun`, one per goal under the id `goal:<goalRunId>`, which Weft's workflow lease fences to a single engine; it holds no state of its own and re-reads the record before every decision. Each attempt is a durable run under the deterministic id `goal-<goalRunId>-a<n>`, so a restart that repeats a start finds the run instead of starting another.

Those ids, the goal's sessions (`goal-<goalRunId>-s<n>`), and the workflow-shaped id its audit events are recorded under (`bureau-goal-audit:<goalRunId>`) are the goal's alone. Weft deletes every event carrying a workflow's id when it purges that workflow, so an ordinary run that merely shared an id with a goal's audit trail would erase the trail when it was purged, and checking ownership at the point of use cannot prevent that. Every id an ordinary caller chooses is therefore refused when it begins `goal:`, `goal-`, or `bureau-goal-audit:`: a child run's `childRunId` is rejected as `reserved-child-run-id`, and a `sessionId` given to `createRun`, to `bureau.run`, or to `createSchedule` throws `BureauError` `BAD_REQUEST` with a message starting `reserved-identifier:`. A `childRunId` is also refused when it begins `run:`, `session:`, or `schedule:`, the ids durable event history records those owners under, because a child's workflow id is its run id and purging the child would erase the owner's history. A goal's own starts build these ids themselves and never pass through that admission; the host-level operate-by-id APIs carry no principal by design and are host-trusted, so a host that forwards a user-supplied id to one of them is responsible for authorizing it. That covers the operators (`cancelDurableRun`, `abortRun`, `deleteRun`, `deleteSession`) and the readers (`getDurableRun`, `getRun`, `getRunReport`, `getReview`, `subscribeRunSnapshot`, and the run event feeds keyed by run id), and a goal's attempt run id (`goal-<goalRunId>-a<n>`) is guessable from the goal id where an ordinary run's is random; the ownership checks stay as defence in depth for a store something else wrote. A schedule persisted before this reservation existed whose session id begins with one of the three prefixes is not migrated: each of its fires is refused as `unavailable` and logs why, so such a schedule must be re-registered under another session id.

`create` writes the record before it starts the controller, and refuses before writing anything when the agent is unknown or cannot run durably, when the validator is not registered at that exact name and version (`validator-missing`, `validator-version-mismatch`), when the budget, retry policy, or objective breaks COR-638's rules, when the conversation policy is invalid or, for `fresh-from-artifact`, its handoff artifact fails COR-894's validation (`invalid-configuration`, which includes `resolveFreshAttemptSource` being unable to vouch for the artifact's source run), or when the goal id cannot name what a goal is made of (`invalid-goal-run-id`: a control character, a lone UTF-16 surrogate, or an id so long that a signal derived from it would pass Weft's 128-byte limit and never be delivered). A goal that requires deterministic validation but names a stochastic validator ends `failed` with `unsupported-validation` before any controller starts; that check also runs wherever a controller is about to be started for a goal nothing has run yet, so a process that died between recording the goal and ending it does not run attempts for it. Passing the same `goalRunId` with the same request answers `existing`, and for a goal that has not ended also makes sure its controller exists, which is how a `create` that died between recording the goal and starting the controller is healed by repeating it. A repeat of a `fresh-from-artifact` goal's request after its artifact's retention window has closed still answers `existing`: the artifact checks that depend on the time they run decide only a goal that is not already stored. A different request under the id answers `conflict`, and carries the stored goal only for a caller who may read it: another principal learns that the id is taken and nothing else.

`cancel` is an answer about durable state, not about a request having been sent. It writes a cancellation marker to the record first (after which the store accepts no transition but `canceled`), wakes the controller, cancels the controller's workflow, stops the attempt's run, commits `canceled` from the host, and then reads everything back once. Each outcome means exactly this:

- `canceled`: the fresh read found the goal record `canceled`, the controller's workflow terminal, its finalizer `succeeded` or not owed (a goal controller declares a finalizer that stops the attempt's run after a hard cancel, so a cancelled controller owes one unless it ended without ever reaching a decision point, or ended on its own as `completed` or `failed`), and the attempt's run terminal or absent. Nothing else is answered `canceled`.
- `cancellation-pending`: the marker is durable, so the goal will end `canceled` and nothing can overtake it, but the read found something unfinished, and `awaiting` names every such thing: `goal-record`, `controller`, `finalizer` (pending, running, or its status could not be read), `attempt-run`, `durable-engine`, or `finalizer-failed`. `durable-engine` is a bureau with no durable engine (`durableExecution: false` over a store that still holds goals): it can record the marker and the commit but can neither stop nor read the controller, its finalizer, or the attempt's run, so it never claims a workflow-level acknowledgement and stays pending until a bureau with an engine settles it. The first four are in progress, so call `cancel` or `recover` again: under the default `workflow-lease` ownership the engine runs a cancelled controller's finalizer in the background, so a `cancel` that has just hard-cancelled a running goal commonly answers `cancellation-pending` awaiting `finalizer`, and the next `cancel` answers `canceled` once it has run. `finalizer-failed` is different: the engine retried the finalizer, gave up, and recorded the failure, so asking again re-reads the same failure. It is written to the diagnostics with the engine's error, and the goal is never reported `canceled` while it stands, because whatever the finalizer was to stop may still be running. The failure is permanent: Weft retries a finalizer 8 times with backoff and then dead-letters it, so once that has happened `cancel` answers `finalizer-failed` every time, even when Bureau's own step (stopping the attempt's run) has already succeeded and nothing is running. Bureau has no way to re-drive a dead-lettered finalizer, so an operator does not wait or call `cancel` again. Read the engine's error in the diagnostics to learn why the abort kept failing, then check the attempt's run yourself with `bureau.cancelDurableRun('goal-<goalRunId>-a<n>')` (idempotent, and it answers `already-terminal` when the run has ended) and treat the goal as settled by hand once the run is terminal; the goal record is already `canceled`, so only the read-back answer stays `finalizer-failed`.
- `record-unreadable`: a record is stored under the id but cannot be decoded, which is a fault to repair and not absence (`close` and `create` answer the same way; `get` and `list` still treat the record as absent).
- `already-terminal`, `contended`, `not-found`: respectively, the goal ended for a reason other than cancellation and nothing was changed; the marker lost its compare-and-swap every time the store retried, so nothing was recorded and nothing will cancel the goal (call again); and there is no such goal, or one the principal does not own.

A goal whose record already says `canceled` is not finished by that alone: calling `cancel` again stops what is still running and reads back again, so a retry after `cancellation-pending` answers `canceled` once the world agrees, and `already-terminal` is only for a goal that ended for another reason. A start that is in flight when the cancellation lands cannot escape it: an attempt's start does not answer until its workflow exists, refuses to start for a goal whose marker is already there, and stops the run it just created if the marker appeared while it was starting. A validator that is executing when the goal is canceled is not told to stop (durable validation runs under a signal that never aborts, because shutdown is a crash for the next process to recover, not a verdict); it runs to completion and its verdict is discarded. Mailbox and Outbox settlement are not part of this: a goal is a workflow plus a child run, so the acknowledgement is the workflow's own, and remote-activity ledger cancellation is out of scope.

`recover` (also run once at boot, after Weft resumes workflows; with a `principal` and no id it sweeps only the goals that principal may see) makes the world agree with each unfinished goal's record. It starts a controller that was never started, restarts one that ended abnormally from the record (up to `MAXIMUM_CONTROLLER_RESTARTS`, counted in the record's `controllerRestarts` by a compare-and-swap on the count the recovery read, so of several recoveries that saw the same ended controller exactly one restarts it, after which the goal is reported `unrecoverable` and left as it is), completes a cancellation whose marker was written but never acted on (a suspended controller whose cancellation was marked is cancelled rather than resumed, since a resumed one would park again on a signal the marker never sends; reporting `cancellation-pending` rather than `canceled` when a run it could not stop still reads as running), and reconciles the attempt a running goal is waiting on: an attempt whose run already ended has its signal sent again under a stable id, one still running gets a forwarder, and one that never started is started. A goal interrupted by shutdown is deliberately left unfinished for the next process; its attempt's run is not aborted by `shutdown()`.

The boot sweep also runs on a bureau with no durable engine (`durableExecution: false` over a store that still holds goals): it can commit a recorded cancellation but can read nothing back, so that goal is reported `cancellation-pending` awaiting `durable-engine`, and every other unfinished goal is reported `unrecoverable` (there is no engine to run its controller), so an engine-less boot over a store that holds unfinished goals is `partial`. A controller that ended abnormally but whose restart cannot happen yet (its finalizer is still owed or could not be read, or its teardown is pending) is reported `restart-pending`: it has no controller and nothing retries it, so `recover` again does. Every entry of the sweep that is stuck rather than in progress is a per-run failure of `waitForRecovery()` (`outcome: 'partial'`), not a clean boot: `unrecoverable` (including a record that cannot be decoded, and a goal whose audit log has no room to record a restart), `restart-pending`, `cleanup-pending`, an `attempt` of `failed`, and a `cancellation-pending` awaiting `finalizer-failed` or `durable-engine`. A running or suspended controller under a recorded cancellation is always ended and its cancellation completed from the host, never signalled and waited for: a live controller may sit inside an activity (a validator, a start) that no signal reaches.

Recovery starts, resumes, and restarts nothing once the bureau is shutting down, and spends no restart on it. Such a goal is reported `shutting-down`, which is not a failure: nothing is wrong, the next boot recovers it. A closed goal that still owes its checkpoint cleanup is reported `shutting-down` too, not `already-terminal`, because its pruning was not started.

A goal that ended while an attempt's start could still be in flight may have a run its ending overtook: a start Weft timed out that keeps running in the background, the host's own recovery start, or a process that died after the engine started the run and before the start's own stand-down check stopped it. Those goals are `canceled`, `exhausted`, and `failed` because an attempt's start failed (`attempt-run-failed` with a start-failure detail), and they stay in the boot sweep until closed and cleaned up: the sweep and `recover(id)` stop the run they find, and `close` does it first, so a closed goal never strands one. A run that cannot be stopped, or cannot be looked for because the bureau has no durable engine, is reported `cleanup-pending`, which is a failure of `waitForRecovery()` (`partial`), and leaves the goal open. An engine-less bureau therefore never closes such a goal, as it never closes a `canceled` one: with no engine it cannot tell that no run was left, so the goal waits for a bureau that has one.

Stopping a run that exists cannot reach a start that has claimed its attempt's run but not yet created it, and no check from outside can: the engine's start takes no precondition on the claim, so there is no transaction across the two. So before it looks for a run, `cancel`, the sweep, `recover(id)`, and `close` tombstone the attempt's claim, by compare-and-swap from the claim's exact bytes or, where none exists, by creating a tombstoned one. A start that claims afterwards finds the tombstone and starts nothing. A run that was already past its claim carries a fence: before every step it reads the goal and its own claim, and it takes no step when the goal is over, the claim is tombstoned, or either cannot be read. The fence also enforces one invariant that closes the class of late starts, acknowledged-only runs: a goal attempt's run takes no agent step until the goal's record shows that attempt opened as running (the attempt at the run's index names the run's id, is `running`, is the last attempt, and is the goal's active work), which is the controller's open-attempt commit after the start settles. A start that Weft timed out, or that a crash or a failed controller stranded, can create its run long after anyone could adopt or stop it, and such a run is never acknowledged, so it never steps. In the ordinary window between the engine's start and that commit the run waits instead of stopping, polling the record with the fence's abortable backoff for at most the start activity's own bound (`START_ATTEMPT_MAXIMUM_TRIES` tries of `START_ATTEMPT_TIMEOUT_MS`, or what remains of the goal's aggregate duration if that is less); when the budget runs out, or the goal ends or is marked, or the claim is tombstoned, it takes zero steps. The wait does not hold the controller up, because the commit follows the start's return and waits on nothing the run does, and a controller that crashes after the start returned replays the recorded start and commits while the resumed run waits for it. A read that fails is tried five times, backing off on the runtime's clock for a few seconds, and a step is never taken on an unknown; the same verdict cancels the step's context compaction, which can reach a model before the step's own preparation reaches the fence. Recovery also tombstones these claims when it gives up on a goal's controller, and no tombstone is created for an attempt index at or past `maximumAttempts`, which no start can use. Such a run ends with the finish reason `tripwire` and zero agent steps, and no `onError` hook can retry or skip that. The most a start the goal's ending overtook can leave is a workflow that ended after zero steps under the attempt's deterministic id, which is pruned with the rest of the goal's history at `close`. A claim that cannot be tombstoned leaves the goal open: `cleanup-pending` for an ended goal, and `cancellation-pending` awaiting `attempt-run` for a canceled one.

Each attempt is its own durable run under its deterministic id; what carries a conversation from one attempt to the next is the goal's session in the bureau's `SessionStore`, so all three COR-638 conversation policies hold across a restart. The session ids are deterministic too (`goal-<goalRunId>-s<n>`), and every attempt's run is recorded in its session as one `RunRef` keyed by the attempt's run id. The turn an attempt receives is `goalAttemptInput` from operative, the same function the in-memory controller uses: attempt 0 runs the prompt as written, so the agent's own instructions frame it.

- `continue`: every attempt runs in one session, `goal-<goalRunId>-s0`. A retry is seeded with that session's history and its turn is the validator's feedback alone, appended as the next user message, so the transcript really carries over.
- `fork-from-baseline`: attempt 0 runs in `s0` and every retry runs in a new session `s<n>` forked from `s0` through the goal-declared `throughRun`, never from the last attempt. Its turn is the prompt followed by the feedback. A retry therefore sees the baseline transcript and nothing a later attempt added. A durable goal has no session before its first attempt, so the only run a retry can fork through is run 0 (the first attempt); `goals.create` rejects any other `throughRun` as `invalid-configuration` rather than let a goal spend an attempt before it could never retry.
- `fresh-from-artifact`: attempt 0 runs in `s0` and every retry starts a brand-new session `s<n>` from the goal's `instructions` and the validated handoff artifact (`createFreshAttemptSession`), then its turn is the prompt. It inherits no transcript. The artifact is validated at `create` and again before each retry that consumes it (so the retention window is measured when it is used). Because nothing in Bureau can vouch for an artifact's producing run, `BureauOptions.resolveFreshAttemptSource` supplies that, as `SessionHandleContext.resolveFreshAttemptSource` does; without it a `fresh-from-artifact` goal is refused at `create`.

A retry's seed is `{ conversation }` handed to the catalog agent, which snapshots it, and it is stored in the run's recovery record, so a recovered run resumes from the same seed. Starting an attempt is: adopt the run if its workflow exists; otherwise seat it (commit the previous attempt's transcript from the engine's checkpoint with operative's `reconcileTerminalRunRef`, which also writes the conversation boundary a fork reads; create the fork or fresh session if absent; build the seed), start it, and record its `RunRef`. Each step is safe to repeat. A crash between creating a fork or fresh session and starting the run finds that session on the next try instead of making a second; a crash between claiming the run and starting its workflow re-derives an equivalent seed and starts the claim once; a crash between the workflow's start and the session write is completed by the adopt path, which upserts the one `RunRef`. The user turn is not written to the session until the attempt's transcript is committed, and the forwarder commits that transcript before it tells the controller the attempt ended, so the next attempt always finds it. A transcript is not committed for an attempt that ends after its goal was canceled or ended. A goal's sessions record its `principal` as their authority, so another principal cannot read or continue the transcript through the session verbs. A durable goal does not accept a caller's existing session as its baseline. The validator is the same `Validator` interface as in memory and receives a `RunResult` rebuilt from the attempt's checkpoint. A validator can run twice if the process dies while it executes, and only the first committed decision counts, so a validator should be safe to run again. Validation evidence is stored inline, projected to JSON and capped at 64 KiB per attempt (an oversized outcome keeps its verdict and replaces each evidence detail with its size). The objective is capped at 64 KiB and refused above it.

A goal's audit events are recorded in the durable event history under a `goal` owner: `goal.started`, `goal.attempt.started`, `goal.attempt.validated`, the terminal `goal.succeeded`, `goal.exhausted`, `goal.failed`, and `goal.canceled`, and the durable-only `goal.recovered` for each controller restart. They are derived from the committed record and recorded idempotently under the key `<goalRunId>:<transitionSeq>`, so a replayed commit adds nothing. Events carry ids, names, statuses, reasons, and a digest of validator feedback; never evidence, raw feedback, the objective, or an error's `cause`. Reading them follows the goal: a `principal` that does not own the goal reads `not-found`, and omitting it is a trusted call. The owner is stored as `bureau-goal-audit:<goalRunId>` rather than `goal:<goalRunId>`, because `goal:<goalRunId>` is the controller's workflow id and Weft deletes every event carrying a workflow's id when it purges that workflow, which would erase the history when a restart replaces the controller. Every transition (and every counted controller restart) appends an entry to the goal record's append-only `auditLog` in the same compare-and-swap commit, holding the already-derived, JSON-safe events it implies. Boot replays the whole log idempotently, so a projection that failed is repaired whenever it was committed, even after later transitions: no audit event is permanently lost, and a repaired event is appended after the ones recorded since, carrying its own commit's timestamp. The log is bounded because attempts are: a durable goal's `maximumAttempts` is capped at 256 (`GOAL_MAXIMUM_ATTEMPTS`), and the log at `4 * 256 + 8` entries; the store refuses a write that would pass the cap rather than drop an entry. The record's `schemaVersion` is now 2 with no migration (the template is pre-release), so a version-1 record reads as corrupt.

`close` is for a goal that has ended. It sets `closedAt` once and answers with the truthful cleanup acknowledgement for the checkpoint history of the controller workflow and of every attempt's run under the bureau's `checkpointRetention`, the least favorable of them: `not-required` when the policy keeps everything or the goal never had a workflow, `completed` once pruned, `unresolved` or `failed` when any could not be. Attempt histories are pruned here, not as each attempt ends, because the goal reads an ended attempt's checkpoint until it is terminal. Calling it again retries the cleanup. A `canceled` goal is closed only once the same read-back `cancel` answers from finds its controller, finalizer, and attempt run ended: until then `close` answers `cancellation-pending` with `awaiting` and leaves `closedAt` unset, because a closed goal leaves the boot sweep and nothing would be left to finish it.

Not supported: `retry-now`, pause and resume, goals on an ephemeral bureau (`create` answers `durable-unavailable`), and the Bureau test harness's `startManagedGoal`.

### Media input (COR-716)

A run's input can be an ordered list of user-admissible text and media parts, not only a string: `bureau.run(name, parts)` (a non-empty list that passes the content schema, or a synchronous `BAD_REQUEST`), a child dispatched through `children.dispatch` (its grant binds the list by a digest over the parts as submitted, including each media part's source reference, with objective `content-parts`), a `submitSessionInput` payload, and the `input` of `createSchedule`. `createRun`'s `message` is still text.

- **Resolving assets.** When `assets` is configured, every run resolves a `managed-asset` part through `AssetService.resolve` as the run's owner of record (the request principal, the session's owner on a recovery, the schedule's owner on a fire). Bureau-held bytes reach the provider as inline base64, a provider-fetch declaration as its URL; the stored message keeps the asset id and revision. An asset the owner may not read, one that is not `available`, and a source kind Bureau holds no bytes for (`upload`, `local-file`, `mcp-resource`, `a2a-reference`) fail the step with a `MediaAdmissionError` before any provider call. `createAssetContentSourceResolver(assets, principalId)` builds the same resolver for a host that composes runs itself.
- **Recovery.** A durable catalog run's recovery record accepts a part-array input (it stays at `schemaVersion` 1: readers and writers ship together and the widening is additive), and a recovered run gets the same resolver and unverified-asset policy as a fresh one, resolving as its recorded principal. The asset service is built before the scheduler can fire, so a fire never finds it missing.
- **Safety.** The resolver reports `clean` when every safety gate cleared the asset, `flagged` when any did not, and `unknown` when none inspected it (always the case for a provider-fetch URL). A flagged asset is always refused. The input guardrail's `assetSafety: { unknown: 'block' }` (in `guardrails.input`) refuses unverified assets, including ones a `beforeGenerate` handler adds.
- **Selection.** A selection gate built by `createSelectionGateFor` receives the step's media at each `revalidate`, using the source form each part takes once resolved, so a run whose backend cannot accept it fails with a `SelectionRevalidationError` instead of a provider error. `PlanSelectionRequest.inputMedia` does the same for `planSelection`.
- **Caller-owned input.** `bureau.run`, a child dispatch, `submitSessionInput`, and `createSchedule` copy the parts they validated before their first await and persist the copy, so a caller editing its array after the call returns cannot change what was validated.
- **Persisted input.** A stored session input carries `schemaVersion` (`CURRENT_SCHEMA_VERSION` of `conversationalist`). The mailbox reader refuses any other value with `error:unsupported-schema-version`, and `submitSessionInput` refuses a payload that fails the content schema (or an empty list) with `BAD_REQUEST` instead of admitting input no run could read. A schedule's input is checked the same way when it is registered. An unpinned `managed-asset` in a schedule's input (no `revision`) resolves to the asset's latest revision at each fire, not the one current when the schedule was created; pin a `revision` to fix it.

### Session commit outbox (AB-389)

`SessionStore.save()`, `update()`, and `delete()` (`@lostgradient/operative`) no longer dispatch `SessionCreatedEvent`/`SessionSavedEvent`/`SessionDeletedEvent` directly—that fire-and-forget dispatch, immediately after each commit but not transactionally coupled to it, was a known limitation (AB-384, PR #592): a crash between a commit succeeding and its listener's write running lost the fact forever, and two `SessionStore` instances sharing one persistent backend could record events out of true commit order. Each commit now appends a `SessionOutboxEntry`—payload, incarnation, and the store's own monotonically increasing commit ordinal—to the SAME atomic batch as the write it describes, and dispatches only a best-effort `SessionOutboxAppendedEvent` drain trigger. `cleanup()` appends the same way (COR-718): one `session.deleted` entry per expired session, consecutive ordinals, one trigger naming the last.

`drainOutbox` (`create-bureau.ts`) is the ONE place those entries are replayed as the real events, in ordinal order: it reads `sessionStore.outbox.pending()` and, for each entry, first calls `sessionStore.outbox.claim(ordinal, { owner, until })` (AB-390)—a compare-and-swap on the entry's own `claim` field, keyed by this bureau instance's own drain-owner id (minted once via `RuntimeServices.identifiers.next()`) and `RuntimeServices.clock.now()`. Only a WON claim proceeds to dispatch the matching event onto the bureau-level emitter (isolated in its own try/catch—a throwing `bureau.toObservable()` subscriber is diagnosed and skipped, never allowed to leave the reserved lowest-ordinal entry permanently un-acknowledged and starve every later fact behind it); a claim that fails (a different, still-unexpired owner holds it) stops the WHOLE pass at that entry rather than skipping ahead to a later ordinal, preserving true commit order across drainers. After dispatch, it awaits `DurableEventProducer.waitForActiveWrites(owner)` for the durable write that dispatch triggers, then verifies the write actually SUCCEEDED—`waitForActiveWrites` resolving proves only that it settled—via `eventHistoryInstance.wasRecorded(owner, kind, dedupeKey)` (an O(1) storage read, skipped only when no durable event history is configured) and, for a `session.deleted` entry specifically, via a read-your-writes `auditTrail.query({ runId })` against the out-of-band audit record (skipped only when no KV persistence is configured)—and only once every configured verification passes does it call `sessionStore.outbox.acknowledge(ordinal, owner)`, which itself re-verifies this same owner still holds the claim before removing the entry. A failed verification, or a lost claim at acknowledge time, leaves the entry pending for a later drain to retry, rather than discarding it. Three drivers call this same function: the post-commit `SessionOutboxAppendedEvent` trigger (promptness only—tracked via `RuntimeServices.deferred`, so a test can `await runtime.deferred.drain()` for it deterministically), `runDurableMaintenance()` and the automatic run-ownership-pruning timer (both "on the runtime clock inside the durable maintenance pass"—the timer's own pending pass is awaited, and the pass's chained drain settles, BEFORE `shutdown()` aborts the durable event producer's signal, so a drain still in flight when disposal begins can still durably record what it dispatches), and `recoverDurableRuns()` (boot recovery, so a crash between a commit and its own drain is caught up before this bureau serves reads)—plus an authority-independent catch-up pass that runs unconditionally at the very start of boot, even when durable run reattachment itself is deferred pending a request-authority validator attachment. It is single-flighted per bureau instance—a caller invoking it while a drain is already running gets the SAME promise, and a join landing exactly as that drain is about to complete forces one more full pass before the promise resolves, so the post-commit trigger and an overlapping maintenance tick never both drain the same pending entry from within one process, and no join is ever silently dropped at the completion edge. A lost claim schedules its own retry (a single-slot timer, never more than one outstanding) armed at the CURRENT winning claim's own `until`—read directly off `outbox.claim()`'s own result, never off the pass's earlier `pending()` snapshot, which a peer's intervening `claim()` call could already have made stale—so a KV-only or manual-maintenance bureau still recovers an entry once the blocking lease expires, rather than waiting on an unrelated future trigger. Shutdown clears that retry timer and, because a timer whose callback already started running before the clear cannot be un-fired, also awaits any drain already in flight (whether from that retry or any other driver) before the durable event producer's signal is aborted.

`performDeleteSession` additionally calls `drainOutbox()` directly, right after `sessionStore.delete()` commits and gated on that call having actually removed a live record—"immediately after each commit" for the one call site that can know synchronously that its own commit just happened, so a caller awaiting `deleteSession()` observes the durable `session.deleted` record without needing to wait for the next trigger or maintenance tick.

**Claim lease across processes (AB-390):** the AB-389 residual—`pending()`/`acknowledge()` claiming nothing exclusively across bureau PROCESSES sharing one persistent backend—is closed by the claim described above. The maintenance-timer and boot-recovery drains no longer both dispatch the same still-unacknowledged entry: whichever process's `claim()` wins the compare-and-swap proceeds; the other's `claim()` fails and its pass stops there, picking the entry back up on a later tick once the current claim either acknowledges it or its lease lapses. A drainer that crashes between winning a claim and acknowledging leaves the entry claimed but undelivered only until its own lease's `until` passes—a later drain (this same process's next tick, or a peer's) reclaims and completes it exactly once, closing the AB-389 residual where `audit-trail.ts`'s `session.deleted` listener and a direct `bureau.addEventListener('session.deleted', ...)` consumer could each see a replay twice.

Two follow-on mechanisms close gaps a fixed lease alone would leave open (Codex P1 review findings, PR #599). First, a renewal timer runs for the ENTIRE stretch between winning a claim and acknowledging—the durable-write wait, `wasRecorded`, and the audit-trail read-your-writes query have no upper bound under real backpressure, so a claim taken once, before any of that, could otherwise lapse mid-wait and let a peer reclaim and dispatch the SAME entry again before this drainer ever discovers the loss. Second, when `claim()` loses to a still-live peer, this bureau arms a single-slot timer at that peer's own known `claim.until` (read directly off the `pending()` snapshot) rather than depending on whichever unrelated trigger happens to fire next—a KV-only or manual-maintenance bureau with no other commits arriving would otherwise have no way to notice the blocking claim expired. The drain-owner id itself is minted from `RuntimeServices.identifiers.next()` plus `crypto.randomUUID()`, not the runtime sequence alone—two independently constructed manual/deterministic runtimes with the same `identifierSeed` are documented to intentionally mint identical sequences (exact reproduction is the point of that seam), which would otherwise let two real bureau processes collide on the same drain-owner value and treat each other's claims as same-owner renewal.

### Review-transition audit records ride the outbox (AB-391)

`resolveReview`'s approve/deny/reject decisions, and the `reviewResolutionCleanupPending` retry path for a decision whose session-store commit previously failed, used to write their durable `review.<kind>.<approved|denied|rejected>` audit record via a SEPARATE, fire-and-forget `AuditTrail.record()` call AFTER the session-store commit (`persistReviewResolution`) that marks the review resolved. A crash between the two lost the audit record forever: the session commit already marks the review resolved, so nothing ever retries the write.

`SessionStore.update()` (`@lostgradient/operative`) now accepts an `options.outbox` list of `{ namespace, payload }` attachments, appended as `SessionOutboxEntry` values of kind `'session.attachment'` in the SAME `conditionalBatch` as the update's own body/summary/outbox-ordinal writes, at the ordinals immediately following the update's own `session.created`/`session.saved` entry. `persistReviewResolution` passes the pending decision's audit payload (`{ runId, type, detail, principal }`—exactly `AuditTrail.record()`'s own input shape) under the `'audit-record'` namespace. `drainOutbox` (generalized from `drainSessionOutbox`, which drained only session-lifecycle entries) replays a `session.attachment` entry into the real audit trail via `AuditTrail.record()`, stamped with the entry's own `committedAtMs` so a delayed replay never misdates the record, and verifies the write against the audit trail (by `runId`/`type`/`timestampMs`/`detail` identity) BEFORE acknowledging—the only idempotency guard here, since `record()` always mints a fresh key and a duplicate replay would otherwise produce a second, distinct record rather than a no-op. `resolveReview` calls `drainOutbox()` itself immediately after the resolution commit succeeds—the durable outbox entry (and the eventual audit record it names) is never lost regardless, but WHEN it becomes visible to an immediate `getReview(id)` depends on how many Bureau instances share this outbox (Codex P2 review finding, PR #601, "Ensure the new attachment is drained before returning"): `drainOutboxPass` stops the whole pass at the first still-claimed earlier ordinal rather than skipping ahead (see the claim-ordering doc comment above), so if a PEER instance currently holds the claim on an earlier entry, this call's own `drainOutbox()` can resolve normally without ever reaching THIS resolution's own attachment—`auditAlreadyAppended` is still correctly `true` (the coupled commit did land) and skipping the direct write is still correct, but the record is not yet audit-trail-visible. In that case (or in a single-instance deployment with nothing else contending for the outbox, where this is never observable) the record becomes visible on the peer's own drain, this bureau's next maintenance tick, or the claim's expiry-triggered retry—eventually consistent, not immediate. Verifying THIS SPECIFIC attachment synchronously would need `SessionStore.update()` to return the ordinal it assigned the attachment, which it does not today—tracked as a follow-up rather than solved in this pass.

This coupling covers exactly the transitions the fix targets—a review's terminal decision. `expired` (`sweepExpiredReviews`), `revoked`/`canceled` (`revokePendingApprovalsForRun`), and `superseded` (`resolveReview`'s tool-approval re-gate branch) have no preceding session-store commit to couple to (the first two never persist a session-store write on that path at all; `superseded`'s own preceding commit, `persistPendingApprovalOverrideWithRetry`, writes the REPLACEMENT approval, and bundling the superseded review's own audit payload—which embeds its now-revoked ORIGINAL approval token—into that same batch would put both tokens in one commit, a real behavioral difference, not just an implementation detail)—all three keep writing their audit record directly, exactly as before.

`SessionStore.update({ outbox })` is explicitly session-agnostic (any caller can append any `namespace`), so `drainOutboxPass` checks a `session.attachment` entry's namespace BEFORE claiming it: an unrecognized namespace is left pending and, critically, never claimed at all—claiming an entry this bureau will never acknowledge would only extend its lease on every maintenance tick (a same-owner `claim()` renews an existing lease), starving a different consumer that DOES recognize the namespace. `SessionStore.outbox`'s own contract requires replay exactly once, in ordinal order—a store-wide ordinal, never a per-session one—so an unrecognized namespace stops the WHOLE pass right there (Codex P1 review finding, PR #601, "Stop before later ordinals when an attachment is unknown") rather than draining a later, recognized ordinal first, which would reorder past a fact a different consumer has not replayed yet. A later trigger—this process's own next tick, or a peer's—gets a fresh look at it. A payload under this bureau's OWN `'audit-record'` namespace that fails shape validation is a different case—there is no future version of that namespace to defer to, so it is diagnosed and acknowledged without replay, same as always. The attachment replay's idempotency is `AuditTrail.record`'s own `dedupeKey` (Codex review finding, PR #601, "Make attachment replay deduplication atomic")—`session.attachment:<sessionId>:<ordinal>`—mirroring `durable-event-history.ts`'s own `dedupeKey` (see above): an atomic storage-level compare-and-swap, not a read-before-write existence query, so two Bureau processes both reclaiming this entry after a claim-lease renewal race can never both durably write it, and the write stays correct regardless of how much unrelated history shares the same `runId`/`type` (a read-scoped-by-`AuditTrail.query()`'s-default-`limit` check would not). `record()` rejects on a genuine storage failure when `dedupeKey` is supplied—unlike its default best-effort path—so `drainOutboxAttachmentEntry` leaves a failed write's entry claimed-but-unacknowledged for a later drain to retry rather than losing it. `resolveReview` and the cleanup-retry path both isolate this post-commit drain call in its own try/catch (Codex review finding, PR #601, "Isolate post-commit drain failures from review resolution"): a transient drain failure diagnoses and leaves the attachment pending, but never prevents the already-succeeded resolution from returning its result or dispatching its live event. `persistReviewResolution` reports whether its `sessionStore.update()` call actually committed (Codex review finding, PR #601, "Detect when the resolution update appends nothing")—`false` when the session vanished concurrently (the updater then returns `undefined`, appending neither the resolution nor the audit attachment)—so `recordReviewDecision` falls back to its own direct write instead of wrongly assuming the coupled write already covered it. Finally, `persistReviewResolution`'s own updater guards against an AMBIGUOUS commit failure (Codex P1 review finding, PR #601, "Avoid reattaching audits after an ambiguous commit")—the fault-engine's own `fail-after-commit` boundary names exactly this: `conditionalBatch` durably commits the resolution and its coupled attachment, but the call back still rejects (a lost acknowledgement). Retrying blindly (either `persistReviewResolutionWithRetry`'s own in-loop retry, or a wholly separate later call from the `reviewResolutionCleanupPending` path) would call `persistReviewResolution` again, which unconditionally appends ANOTHER `session.attachment` entry at a fresh ordinal—a distinct `dedupeKey` from the one the ambiguous attempt already committed, so the same decision would be recorded twice once both drained, even though the `dedupeKey` mechanism correctly prevents either individual entry from being replayed on its own. So the updater itself detects this on every attempt: if `reviewId` is already present in the CAS-fresh session's `resolvedReviewIds`, some earlier commit already durably landed this exact decision, and the updater returns `undefined`—`sessionStore.update()` never calls `commit()` at all, appending nothing more—while `persistReviewResolution` still reports success. Every write in this file—the action-stream listener, every out-of-band `record()` call (ordinary or `dedupeKey`-guarded), and the retention summary—now commits through the SAME `attemptKeyFencedWrite` helper (Codex P1 review finding, PR #601, "Fence ordinary writes against deduplicated audit keys"): a not-exists `conditionalBatch` precondition on the derived audit key itself, with a bounded fresh-sequence retry on collision, so a plain unconditional `kv.set` can never silently overwrite a record a DIFFERENT writer (dedupe-guarded or ordinary) already committed at the same key—which, for a `dedupeKey`-guarded record specifically, would otherwise be a PERMANENT, undetectable loss once the surviving marker makes a later replay treat it as already recorded. A best-effort caller degrades to diagnose-and-drop on retry exhaustion, never rejecting; a `strict`/`dedupeKey` caller still rejects. Separately, `resolveReview` fences a losing resolver BEFORE its irreversible action runs (Codex P1 review finding, PR #601, "Fence concurrent resolutions before performing the action"): before `resumeApproval`, `revokeApproval`, or the `signalSession` calls that deliver an approve/deny/reject decision, a plain `SessionStore.load` read checks whether a DIFFERENT resolver's decision is already durably recorded for this review id, throwing `CONFLICT` before any action rather than only after (`persistReviewResolution`'s own conflict detection, described above, still runs afterward as a second, DURABLE check). This is a plain read, not an atomic claim—a genuinely simultaneous pair, neither yet committed when the other reads, can still both pass it and both act; closing that residual window needs a two-phase durable resolution claim, tracked as a follow-up rather than shipped here.

That `resolvedReviewIds.includes(reviewId)` check alone cannot tell apart two situations that look identical from the id list alone (Codex P1 review finding, PR #601, "Distinguish concurrent resolvers from commit retries"): THIS call's own retry after an ambiguous commit (described above), versus a genuinely DIFFERENT resolver's decision having already won a race—two Bureau instances sharing a session store, both resolving the same still-pending review, is a scenario this codebase already documents and tests elsewhere (see "AB-390—outbox claim lease" tests). Conflating the two meant a losing resolver's call would report success and dispatch its own `ReviewApproved`/`ReviewDenied`/`ReviewRejectedEvent`, contradicting the sole durable audit record—which names the WINNING resolver's decision. Fixed by persisting the decision's own identity (`decision`, `principal`, `reason`) alongside `resolvedReviewIds`, in a sibling `resolvedReviewDecisions` metadata map. When `reviewId` is already resolved, the updater compares the persisted decision against this call's own: a match is the benign self-retry case (`alreadyLanded`, as before); a mismatch means a different resolver won, and `persistReviewResolution` throws `BureauError('...', 'CONFLICT')`—mirroring the existing `reviewResolutionCleanupPending` "already resolved" CONFLICT shape rather than inventing a new one. `persistReviewResolutionWithRetry` fails fast on this CONFLICT rather than retrying (it is not transient—retrying only re-throws the identical error), and `resolveReview`'s own catch skips registering `reviewResolutionCleanupPending` for it, since a losing resolver's call committed nothing and has nothing to clean up. A resolution recorded before this field existed (no persisted identity) is treated as the benign case, for backward compatibility with sessions resolved by an earlier version.

Two more fixes to the `dedupeKey` mechanism itself, both in `audit-trail.ts`. First, `writeOutOfBandRecord`'s `dedupeKey` branch now calls `trackWrite` (Codex P2 review finding, PR #601, "Track deduplicated audit writes before returning")—a non-rejecting derivative of the `conditionalBatch` promise, so `query()`, `runtime.deferred.drain()`, and `dispose()` all observe this write the same as every other path, while the REJECTING `conditionalBatch` promise itself is still what a `dedupeKey` caller awaits. Second, `prune()` now reconciles orphaned `audit-dedupe:v1:` markers (Codex P2 review finding, PR #601, "Prune dedupe markers with expired audit records")—every `record({ dedupeKey })` write leaves one of these permanently, and nothing previously deleted them, so retention bounded the audit records themselves but not this marker family. `runPrunePassLocked` lists every marker each pass (matching its own existing cost profile, which already lists every audit-record key each pass regardless of the retention floor) and deletes any whose named record no longer exists—a true RECONCILIATION rather than a filter over just this pass's own deleted candidates, so it also heals a marker orphaned by an EARLIER pass crashing between deleting a record and deleting its marker, which could never be re-discovered by matching against a fresh candidate list. Runs even on the "nothing qualified" early-return path, and is isolated in its own try/catch—a marker-cleanup failure never turns an otherwise-successful record prune into a rejected pass, and marker deletions are never counted in `prunedCount` or the `audit.pruned` summary, which describe audit records, not markers. `durable-event-history.ts`'s own `outbox-dedupe:` marker family has no equivalent cleanup—a separate, tracked gap (see `followUps`), since that file's pruning story is independent of this one.

Two more fixes, both Codex findings against the `dedupeKey` mechanism's own remaining edges. First (P1, "Guard the audit record key against cross-instance collisions"): the audit `key` a `dedupeKey` write commits under is derived from `sequence`, a LOCAL per-instance counter seeded from a boot-time scan—two `AuditTrail` instances booting from the same persisted floor, before either has written anything, can independently allocate the SAME `sequence` for the SAME `runId`/`timestampMs` (exactly the scenario `dedupeKey` exists to support: two Bureau processes racing over one still-pending review). The original single-attempt batch fenced only on the dedupe marker, so two DIFFERENT `dedupeKey`s colliding on the same derived `key` would both commit, the second silently overwriting the first's record. Fixed by fencing on the audit `key` too, as a second CAS precondition: when the batch fails, a direct read of the marker distinguishes a benign duplicate (marker present—this exact fact was already recorded) from a genuine key collision (marker absent—an unrelated record occupies this key), and a collision mints a fresh `sequence`/`key` and retries, bounded to 3 attempts before failing loudly. Second (P2, "Renew the prune lease during marker reconciliation"): `reconcileOrphanedDedupeMarkers`'s own scan can run long enough on a trail with many markers to outlast the prune lease's TTL, same as the record-delete loop it sits beside—now renews every 200 markers (sharing the delete loop's own `RENEW_EVERY_N_DELETES` cadence) and aborts the pass on a lost renewal, mirroring the delete loop's own partial-summary-then-throw contract exactly.

Finally, `@lostgradient/operative`'s `SessionStore.update()` now validates `options.outbox` entries synchronously, before `commit()`'s `conditionalBatch` ever runs (Codex P2 review finding, PR #601, "Validate attachments before committing malformed outbox entries")—an untyped caller (or a cast past `JSONValue`) passing `payload: undefined` would otherwise commit a `session.attachment` entry `JSON.stringify` silently strips that field from, and every LATER `outbox.pending()` call would then throw on it forever (`parseOutboxEntry` requires `payload`), permanently blocking delivery of that entry and everything queued behind it with no self-healing path. `update()` now throws `TypeError` for a non-string or empty `namespace`, or a `payload` that is `undefined` or not JSON-serializable, before anything commits.

`lastRunOwningPrincipals` is never pruned on a run's terminal transition, and never on a count (AB-363's coordinator ruling): pruning on either signal would reintroduce the exact denial AB-359 fixed for a run whose durable history is still pageable long after it completed. The only pruning is `pruneStaleRunOwnership`, which drops an entry once its run's ENTIRE durable event history has fallen below the fleet feed's retention floor, because a history that can no longer be paged needs no owner. It runs on every `bureau.runDurableMaintenance()` call (the manual/serverless host's own driver) AND, under the default `durableBackgroundTasks: 'automatic'` profile, on its own in-process interval—Weft's engine already runs its own `engine.runMaintenance()` automatically in that profile, but exposes no hook to run extra work after each cycle, so Bureau starts a second, `pruneStaleRunOwnership`-only interval (never re-invoking `engine.runMaintenance()` itself) rather than leaving pruning unreachable for the default profile (Codex review, PR #568, "Run ownership pruning in the automatic maintenance profile"). This timer is injectable-clock-aware (`RuntimeServices.timers`), and a failed pass is diagnosed rather than thrown. A tick that fires while the prior pass is still running skips starting a second one rather than overlapping them (Codex/Copilot review, PR #579, "Prevent overlapping automatic pruning passes"); `shutdown()`/`dispose()` both clear the interval AND await a pass still in flight before disposing the event history and storage it reads and writes (Codex review, PR #579, "Await running pruning passes before backend teardown"). The in-flight pass is tracked in a plain local variable, not `RuntimeServices.deferred`—nothing in production ever calls `deferred.drain()`, so tracking a recurring five-minute tick there would grow that ledger unboundedly for the life of the process (Codex review, PR #579, "Bound deferred tracking for recurring passes").

A candidate run is excluded from pruning—left for a later cycle—on any of four signals, none of them a read of run state through `engine.get` (an earlier revision used that and got the unknown-run case and the write-in-flight race wrong, Codex/Copilot review, PR #568): its `lastRequestAuthorities` entry still being present (still live, or terminal-but-awaiting-a-pending-approval-decision, which can still produce a future `review.*` durable event—a value present but NOT a plain record fails the WHOLE session closed rather than being read as "no live runs", Codex review, PR #568, "Preserve owners when the authority map is malformed"); `DurableEventProducer.hasActiveWrite({ kind: 'run', id })` reporting a `history.record()` write for it still in flight—closing the window between a run's terminal transition removing its authority entry and that SAME transition's own durable write actually committing (Codex/Copilot review, PR #568); or the run still being present in the in-memory run store (`store.getRun(runId) !== undefined`)—`deleteRun()` remains callable on any such run at any future point, and records a brand-new, retained `run.removed` durable event under this SAME owner (Codex review, PR #568, "Preserve ownership for a later run removal event"). That third signal is why pruning a still-live process's own runs is rarer in practice than the retention floor alone suggests: nothing in this codebase evicts a run from the store except `deleteRun()`, which an explicit call or `taskRetention` (30 days by default) makes, so a completed run stays protected until one of them deletes it, however far the floor advances past its history—pruning only reaches it after such a deletion (whose own `run.removed` then also ages past the floor) or on a later process's maintenance pass, since a terminal run is never reattached into the store at boot (only in-flight ones are), which is also why that later process needs no protection for a run it never held: `deleteRun()` throws `NOT_FOUND` for a run absent from its own store, so no future `run.removed` is possible for it there either. The fourth signal, under `durableOwnership: { ownership: 'workflow-lease' }` (the default), is `Engine.claimHolder(runId)` reporting the run's workflow claim held by any process (COR-204). It is checked last, only for a candidate the other three did not exclude, because it is one storage read per candidate per update attempt, and it is never called under `{ ownership: 'none' }`. It reads claim liveness, not run state, and it can only add an exclusion: no claim record or a stranded claim leaves the decision to the other three. Signals two and three are process-local, so this is what protects a run still executing on another instance whose `lastRequestAuthorities` entry is already gone from the shared session store (for example after a recovered run's invalid approval state is pruned); an ordinary live run is already protected everywhere by its authority entry. A claim a crashed instance never released reads as held until its grace-adjusted expiry, so pruning that run waits at most that long, and a rejected `claimHolder` read aborts the session's write and is diagnosed like any failed pass.

The retained-owner set itself is revalidated fresh immediately before each session's write (inside `SessionStore.update`'s callback, re-run on every conflict retry, and passed `{ refreshActivity: false }` so this maintenance write never itself reads as session activity—Codex review, PR #568, "Avoid refreshing session activity during retention pruning")—a run can dispatch, complete, and have its terminal event land in the feed entirely within the time this pass spends paging through other sessions, which would make a single up-front snapshot stale by the time that run's own session is reached (Codex review, PR #568, "Revalidate retained owners before pruning"). That revalidation is a cheap, cursor-resumed `DurableEventHistory.refreshRetainedRunOwnerIds()` call, not a second from-scratch `retainedRunOwnerIds()` full replay per candidate session—the latter would turn one maintenance pass into O(candidate sessions × retained events) storage reads (Codex review, PR #568, "Avoid replaying the full fleet feed per candidate session"); the initial snapshot (one full replay) is still taken once, up front, per pass. `refreshRetainedRunOwnerIds()` also mutates that ONE snapshot's owner set in place rather than cloning it on every call—a per-candidate, per-retry `Set` copy of every retained owner would have kept CPU/allocation cost at O(candidate sessions × retained owners) even after the storage-read cost above was fixed (Codex review, PR #579, "Stop copying the full owner set on every refresh"). Across instances sharing one backend, no primitive spans the fleet feed and the session store in one atomic operation, and `claimHolder`, like Weft's `holderStatus` beneath it, is a point-in-time read, not a lock. So an event for a pruned run can still land after the delete: a terminal run whose claim was already released can still be deleted (`run.removed`) or have a review resolved (`review.*`) by an instance that holds it in memory, and another instance's event can commit between a pass's fresh refresh and its session write. Both sides therefore verify after they write (COR-1380), and whichever read comes second restores the entry with an idempotent union write that preserves `updatedAt`. The pruner reads the feed again after each committed delete and puts back, with the principal it removed, every deleted run that is now retained, whatever kind of event made it so; a rejected restore write is diagnosed and the pass moves on to the next session. `deleteRun()` and every `review.*` transition (approve, deny, reject, expired, revoked, canceled, superseded) wait for their own durable write to settle, then read the run's entry and restore it with the run owner's principal, never the acting principal; a failed restore is diagnosed and never changes the call's own outcome. The guarantee: once a pass and a `deleteRun()` or `review.*` transition on the same run have both settled, the run's entry exists whenever a retained `run.removed` or `review.*` event for it exists, provided the recording instance holds the run's principal in memory. What remains: the entry is briefly absent between a prune commit and its restore; a pass that crashes, or whose post-delete refresh rejects, between its commit and its restore can leave the entry absent; an instance with no in-memory principal or session incarnation for the run (one rehydrated at boot after the entry was already pruned, or recovered without an incarnation), or a run recorded without a principal, gets no writer-side restore, and neither side ever restores into a session deleted and recreated under the same id since the entry was removed; and `run.completed`, `run.error`, `run.aborted`, `run.tripwire`, `schedule.completed`, and `schedule.failed` events under a run owner have no writer-side restore, so they are covered only by the exclusion signals and, when they land before the pruner's re-read, by the pruner-side restore. Under the opt-out `{ ownership: 'none' }` the claim signal is absent and every exclusion beyond the shared authority entry is process-local. Durable maintenance calls `FleetEventFeed.retain()` under `eventRetention` (7 days by default), so the floor advances and this pass has work whenever runs are older than the window.

```typescript
const subscription = bureau.subscribeEventHistory(
  { kind: 'run', id: runId },
  (event) => console.log(event.kind, event.payload),
  { since: lastKnownCursor },
);
// later
subscription.unsubscribe();
```

`subscribeEventHistory` replays every event after `since`, then transitions to live delivery with no gap and no duplicate at the handoff, built entirely on `FleetEventFeed.subscribe()`—Weft's own race-free replay-then-tail composition—so this module adds no sequencing of its own. Disposing one subscription (`unsubscribe()`, or aborting `options.signal`) stops delivery to that listener only; a second, independent subscription to the same owner is unaffected, and the underlying `FleetEventFeed` is released only when the whole store's `dispose()` runs (Gateway's paging/SSE/WebSocket projection—AB-91's `ab91-03`—remains a separate, not-yet-built slice).

`bureau.shutdown()`/`bureau.dispose()` dispose the producer, then this store (an `'event-history'` `BureauShutdownOwnerReport` row) in the same drain ordering as the audit trail, before the durable engine and raw storage are torn down.

### Governed memory (COR-41)

Pass a `GovernedMemory` as `BureauOptions.memory`, and every run Bureau composes recalls through mandatory recall admission and stores its final answer through write admission, both under an authority derived from the run's persisted request. The host builds the instance with `createGovernedMemory()` from `@lostgradient/memory`, so the host owns its storage, ledger, and policy. Bureau calls `memory.init()` while it composes and calls `memory.close()` without awaiting it when it shuts down. `bureau.memory` is the same instance, for the governance work the host does itself. The [memory README's governed memory section](../memory/README.md#governed-memory) is the API reference, and [Memory governance and lifecycle evaluation](../../documentation/memory-governance.md) covers the lifecycle across packages.

This example runs in [`src/memory-governance-guide.test.ts`](./src/memory-governance-guide.test.ts), which imports from `./index` instead of `@lostgradient/bureau` and asserts every commented result. It uses the deprecated `generate`, `stopWhen`, and `createRun` fields, because only the runs Bureau composes itself get memory hooks:

```typescript
import { createBureau } from '@lostgradient/bureau';
import {
  createGovernedMemory,
  createMemoryAuthority,
  createMemoryGovernanceLedger,
  createMemoryGovernancePolicy,
  createMockEmbedder,
  createWeftMemoryRecordStorage,
} from '@lostgradient/memory';
import { createMockGenerate, stopWhen, waitForRunState } from '@lostgradient/operative';
import { MemoryStorage } from '@lostgradient/weft';

const storage = new MemoryStorage();
const memory = createGovernedMemory({
  storage: createWeftMemoryRecordStorage(storage),
  ledger: createMemoryGovernanceLedger(storage),
  embedder: createMockEmbedder(64), // use a real embedder in production
  policy: createMemoryGovernancePolicy({ revision: 'governance:1' }),
});

const bureau = await createBureau({
  agents: {},
  generate: createMockGenerate([{ content: 'Booked seat 14C for Alice.', toolCalls: [] }]),
  stopWhen: stopWhen.noToolCalls(),
  memory,
  // A caller-supplied request authority is re-validated before every run.
  requestAuthorityValidator: () => true,
});

const run = await bureau.createRun({
  message: 'Book the 9:40 to Denver.',
  sessionId: 'session-42', // the memory collection this run recalls from and writes to
  requestContext: {
    authority: {
      principalId: 'user:alice',
      tenantId: 'acme',
      ownerId: 'alice',
      capabilities: ['tools:execute'],
      authorizationRevision: 'authorization:7',
    },
  },
});
await waitForRunState(bureau, run.id);

// The host reads memory with its own authority, never with the run's.
const auditor = createMemoryAuthority({
  principal: { kind: 'governance', id: 'governance:auditor' },
  tenantId: 'acme',
  ownerId: 'alice',
  purpose: 'audit',
  capabilities: ['memory:list', 'memory:inspect'],
  policyRevision: 'authorization:7',
  projection: 'audit',
});
const [stored] = await bureau.memory!.list(auditor, { collection: 'session-42' });
console.log(stored?.content); // 'Booked seat 14C for Alice.'
console.log(stored?.source); // 'conversation'
console.log(stored?.trust); // 'untrusted'
console.log(stored?.governance?.attribution.delegationChain.map((link) => link.principal.kind));
// ['service', 'user', 'run']

await bureau.dispose();
```

**Which runs get memory.** Bureau registers its two memory hooks in every run it composes itself: `createRun` runs, `submitSchedulerTask` tasks, durable schedule fires, and durable runs it recovers after a restart. A catalog run dispatched through `bureau.run(name, input)`, durable or not, gets neither hook, and neither does a `bureau.children` child, which is a catalog run too. Those hooks close over a Bureau session, and a catalog run has none (see `createRuntimeComposition`'s comment on Bureau invariants). A recovered run whose persisted request authority cannot be restored gets no memory hooks at all.

**How a run's authority is derived.** `createRunMemoryAuthority(requestContext, { runId }, options.memoryAuthority)` builds a three-link delegation chain: a `service` principal with id `bureau` holding `memoryAuthority.runCapabilities`, then the request principal (`requestPrincipal(principalId)`) holding the capabilities granted to it, then the run itself as a `run` principal whose id is the run id. A `submitSchedulerTask` task's run id is its task id, so the task id becomes the `run` principal's id. Tenant, owner, and authorization revision come from the request authority, the purpose from `memoryAuthority.purpose` (`'conversation-memory'` by default), and the projection is `bureau`. `runCapabilities` defaults to `DEFAULT_RUN_MEMORY_CAPABILITIES`, which is `memory:search` and `memory:write`. When the request authority names explicit `memory:*` capabilities, they can only narrow that grant. A request that names none receives it unchanged. An empty grant does not turn memory off. With `runCapabilities: []`, or with explicit request `memory:*` capabilities that share nothing with `runCapabilities`, both hooks stay attached, and every run's recall and write are refused as `missing-capability`. Each refusal is recorded in the governance ledger as a `memory.access.denied` event and passed to `onEvent`, so a sink that throws still fails the run. To attach no memory hooks at all, leave `BureauOptions.memory` unset.

The request authority is the run's `requestContext` when the caller supplies one. An authority whose `authorizationRevision` is not Bureau's own must pass `requestAuthorityValidator` before every run, or `createRun` throws `CONFLICT`. Without a `requestContext`, Bureau builds one: principal `request.principal`, or `run:<runId>` when there is none, tenant `bureau`, and owner the agent name (`bureau` by default). Every such run of one agent therefore shares one owner partition, separated only by session. Scheduled work, meaning schedule fires and `submitSchedulerTask` tasks, runs under a `service` request principal whose id is `system:scheduler`, in tenant `bureau`, owned by the agent name (for a task, its `metadata.agentName`, or `bureau`).

**What the hooks do.**

Both hook factories are exported from `@lostgradient/bureau`. Bureau builds its hooks once per run, from the run's memory authority and its session id, which is also the memory collection.

| Factory, registered as | When | What it does |
| --- | --- | --- |
| `createMemoryRecallHook(memory, authority, sessionId)`, registered as `bureau:memory-recall` (`prepareStep`) | Step 0 only, when the conversation has a user message with string content | Calls `recallForModel(authority, latestUserMessage, { collection: sessionId, limit: 5, contextId: authority.principal.id })`. The `contextId` is the run id, or the task id for a `submitSchedulerTask` task. When any evidence is admitted, it appends `bundle.rendered` as a system message whose metadata is `memoryEvidence: { sessionId, recordIds, withheld }`. |
| `createMemoryPersistHook(memory, authority, sessionId, runId?)`, registered as `bureau:memory-persist` (`onStep`) | The final step, when its content is not blank | Calls `write(authority, content, { collection: sessionId, source: 'conversation', memoryClass: 'episodic', metadata: { step, replay: 'effectful' }, dedupeKey })`. `dedupeKey` is `'<runId>:<step>'` when the hook was built with a `runId`. A replayed step's write then returns `duplicate` without storing anything, provided the governed memory's storage implements `getByDedupeKey()` and `putOnce()`, as both bundled backends do. On storage with neither method the key is ignored and the replayed write is stored again, and without `putOnce()` a replay racing the original write can store it twice. A hook built without a `runId` writes with no dedupe key. A rejected or quarantined write is recorded in the governance ledger and never reaches the run. A write that throws does reach it: see **What Bureau leaves to the host** below. |

Bureau passes a `runId` to the persistence hook for every run it composes. For `createRun` runs, durable schedule fires, and recovered runs, it is the run id. For a `submitSchedulerTask` task, it is the task id, which stays the same when the scheduler preempts and requeues the task, so the task's answer is written with the dedupe key `'<taskId>:<step>'`. The task id also stands in as the run principal, the recall `contextId`, and the session, so each task recalls from and writes to a collection named after its own task id.

Both hooks are classified `replay: 'effectful'`: recall writes ledger events and can quarantine a poisoned record, and persistence writes a record. When a recovered step runs again, recall is safe to repeat: the step's conversation is rebuilt, and a record quarantined the first time is simply absent. A step also runs again when the scheduler preempts a `submitSchedulerTask` task and requeues it: with a durable engine, the task resumes from its last completed step, and without one, it starts again from step 0. A repeated step has the same run id and step index as the first, so its write stores nothing, provided the governed memory's storage honors dedupe keys, as described above. A task that starts again without a durable engine repeats every step, and if its final answer lands on a different step than the first time, that answer has a new key and is stored as a second record.

**One predicate for every projection.** Bureau adds no memory check of its own and has no path around the governed memory: every hook call goes through `decideMemoryAccess()`, the same predicate every projection uses, with the same redaction decision. The memory package's `test/governance/predicate.test.ts` checks every projection against every operation and resource shape and expects identical decisions.

| Projection | What ships for it |
| --- | --- |
| `bureau` | The two hooks above, under `createRunMemoryAuthority()`. |
| `tool` | `createGovernedMemoryTools()`'s default authority. Bureau does not add these tools to runs. A host that adds them to a toolbox must give the request explicit `memory:*` capabilities, because the tools read the request authority, not `runCapabilities`. |
| `agent`, `child` | `attenuateMemoryAuthority()` for a host to derive a narrower authority. Bureau derives none for catalog agents or children. |
| `a2a`, `mcp` | Nothing: this repository has no A2A or MCP memory adapter. An adapter records the projection on the authority it builds and calls the governed memory like any other caller. |
| `audit`, `administrative` | The host's own reads, legal holds, retention sweeps, and deletions through `bureau.memory`, under the host's own authority. |

**What Bureau leaves to the host.** Governance events go to the governed memory's ledger and its `onEvent` sink. Bureau does not copy them into `bureau.auditTrail`, whose `AUDIT_EVENT_TYPES` has no memory entries. Read them with `bureau.memory.listEvents()`. Bureau does not catch what a memory hook throws, and governed memory awaits `onEvent` inside each call, so a sink that throws fails the run. Step 0's recall records an event, so the run ends with status `error` and an `AgentRunError` of kind `generate`, before any answer is written. A sink that throws only on the final answer's `memory.write.admitted` event ends the run with an `AgentRunError` of kind `policy`, after the answer is stored. Give governed memory an `onEvent` that never throws. Bureau never calls `processDeletionPropagation()`, `sweepRetention()`, or `expireWorkingMemory()`, and never deletes memory. Its hooks write only `episodic` records, so a working-memory record never comes from Bureau. Schedule those calls in the host, under a service or governance authority.

## `AgentDefinitions` and the Agent Catalog

`AgentDefinitions` (AB-15, AB-22) is a plain literal object—the `agents` map passed to `createBureau({ agents })`—of agent name to `RunnableAgent` (an `@lostgradient/operative` `createAgent()` or `createLazyAgent()` result). There is no register/unregister lifecycle: the map is fixed for the bureau's lifetime. `bureau.agents` exposes an immutable, read-only `BureauAgentCatalog` view over it (`get`/`find`/`has`/`names`/`entries`/`query`), and `bureau.run(name, input, options?)` dispatches to a named entry synchronously—like `RunnableAgent.run`, it returns the `AgentRun` handle immediately, never `Promise<AgentRun>`.

```typescript
import { createAgent } from '@lostgradient/operative';
import { createBureau } from '@lostgradient/bureau';

const bureau = await createBureau({
  agents: {
    researcher: createAgent({ generate, instructions: 'You are a research assistant.' }),
    writer: createAgent({ generate }),
  },
});

bureau.agents.has('researcher'); // narrows to a known agent name where TypeScript permits it
bureau.agents.names(); // ['researcher', 'writer']—definition order

const run = bureau.run('researcher', 'Summarize the Q3 report.');
for await (const event of run) {
  // ...
}
const result = await run.result();
```

`run`'s synchronous throws are limited to an unknown `name`, a disposed bureau, and malformed `input`/`options`; everything else (session, provider, tool, policy, or abort failures) settles through the returned `AgentRun` handle. `BureauRunOptions` (`sessionId?`, `signal?`, `traceContext?`, `withTraceContext?`, `principal?`) carries only call-scoped concerns—there is no per-call `systemPrompt`/`maximumSteps`/`maximumTokens` override; anything that shapes how an agent runs is fixed on its own definition (`createAgent({ instructions, maximumSteps, ... })`). `sessionId` correlates a durable dispatch to the engine's own session/recovery bookkeeping (a no-op when the run is dispatched in-memory); `principal` (AB-241) forwards into `AgentRunContext.principal` on both dispatch branches—the direct branch hands it straight to the agent's own `run()`, and the durable branch additionally records it exactly as `Bureau.createRun` does (`LivenessSnapshot.owner`, and the in-memory `runAttribution` map `eventHistory`'s principal gate consults)—so a caller sees the same attribution regardless of which branch a given agent takes. A non-string value throws synchronously (`BureauError` `BAD_REQUEST`).

`run` is independent of, and additive to, `createRun` below (`createRun` and the bureau-level `generate`/`provider`/`providers`/`routing`/`toolbox`/`guardrails`/`skills`/`stopWhen`/`maximumSteps`/`systemPrompt` fields it drives are all **deprecated**, not yet removed—see AB-242's decision record and the removal issue it names, AB-352): `run` dispatches to a catalog `RunnableAgent` (agent-owned generate/tools/durability by construction), while `createRun` keeps driving bureau-level `generate`/`provider` through the session/durable-execution machinery documented above. A bureau may use either, both, or neither—pass `agents: {}` for a bureau that only uses `createRun`. When a durable engine is composed (a persistent `storage` backend, or `durableExecution: true`) and the named agent supports AB-21's definition-resolution capability (every `createAgent`/`createLazyAgent` result does), `run` drives the dispatch through that same durable engine so it survives a crash and resumes; otherwise the agent's own in-memory `run()` is used directly.

### `createSupervisor` and `createAgentDiscoveryTool`

Both moved here from `operative` (AB-22), rebuilt against `BureauAgentCatalog<D>` in place of the deleted `AgentRegistry`.

```typescript
import {
  createAgentDiscoveryTool,
  createFanOutRouting,
  createSupervisor,
} from '@lostgradient/bureau';

const supervisor = createSupervisor({
  agents: bureau.agents,
  routing: createFanOutRouting(), // or a custom `RoutingStrategy<D>`
});

const { agentResults, synthesis } = await supervisor.delegate('Draft a Q3 summary.');

const discoveryTool = createAgentDiscoveryTool(bureau.agents);
```

`createSupervisor` delegates a task to one or more catalog agents chosen by a pluggable `RoutingStrategy<D>` (`(task, descriptors) => name | name[] | Promise<...>`; built-ins `createRoundRobinRouting`/`createFanOutRouting` only load the agents they actually select) and synthesizes their results—`delegate` (one task), `delegateAll` (many, sequential or parallel), and `pipeline` (chain each stage's output into the next stage's input). `createAgentDiscoveryTool` exposes a tool an orchestrating agent can call to search the catalog (case-insensitive substring match) across each agent's name, its `description`, and each `skillDescriptors` entry's name, description, and tags. Each match comes back as `{ name, description, skillDescriptors }`, the last two omitted for an agent that declares none. The search reads only metadata already on the catalog's agent objects, so it never loads a lazy agent; supply `description` and `skillDescriptors` to `createLazyAgent` for a lazy agent to be searchable by more than its name.

### `createBureauTestHarness(options)` (AB-261)

Composes a real `Bureau` over an injected `ManualRuntimeServices` (`options.runtime`, defaulting to a freshly constructed one) and an owned `BureauStorageFixture` (`options.storage`, required). The returned promise resolves only once `bureau.ready` is `true` and boot recovery has completed. ### Quiescence report and `close()` (AB-262)

```typescript
import { assertBureauQuiescent, BureauQuiescenceError } from '@lostgradient/bureau';
```

`harness.close(shutdownOptions?): Promise<BureauQuiescenceReport>` calls `bureau.shutdown(shutdownOptions)` (AB-207)—via `assertBureauQuiescent(harness, shutdownOptions)`—disposes `harness.storage`, then resolves with the report, or rejects with a `BureauQuiescenceError` (its `.report` carries the full structured detail) when anything Bureau owns was not quiescent. It never substitutes `bureau.dispose()` for `shutdown()`, and it is idempotent: a second call returns the exact same settled outcome without shutting down twice (a second call's own `shutdownOptions` are ignored, matching `bureau.shutdown()`'s own idempotency contract).

**The manual-runtime rule (AB-338):** `BureauOptions.shutdownTimeoutSleep`—the sleep `shutdown({ timeoutMilliseconds })`'s bounded wait races against—always stays driven by the bureau's own resolved `RuntimeServices.timers` (AB-260's deterministic contract); it never falls back to a real timer under a `ManualRuntimeServices`. That means nothing advances that sleep's timer on its own: under a plain `bureau.shutdown({ timeoutMilliseconds })` call against a manually-driven bureau, the caller owns advancing the clock (`runtime.advance(timeoutMilliseconds)`) far enough for the wait to elapse, exactly as it already owns advancing the clock for any other timer-driven behavior. `harness.close(shutdownOptions)` is the one exception: when `shutdownOptions.timeoutMilliseconds` is set, the harness itself advances its own `ManualRuntimeServices` by that many milliseconds once `bureau.shutdown()` has armed the timer—so a test calling `harness.close({ policy: 'drain', timeoutMilliseconds })` against a hung run never needs a real wall-clock wait or a manual `runtime.advance()` call of its own to observe a bounded drain resolve with the hung work reported under `incomplete`.

`BureauQuiescenceReport` extends `@lostgradient/operative`'s `QuiescenceReport` (`scope`, `quiescent`, `leaked`, `detached`) with ten Bureau-owned `readonly LeakedResource[]` rows: `activeRoots`/`activeDescendants` (from `harness.scope`/`harness.childRegistry`), `pendingWebhookDeliveries` (`webhookNotifier.listDeliveries()`, status `'pending'`), `durableAttempts` (`bureau.getDurableRun` for every id registered via `harness.registerDurableRun`, when non-terminal and not detached). `parkedWaits` and `pendingHookEffects` stay empty on this baseline—no public per-signal-wait listing or hook-effect tracking surface exists yet (AB-35, Backlog).

**`abortingRuns` (AB-369):** a `readonly { runId: string; since: number }[]` row, sourced from `bureau.listAbortingRuns()`—the public read over the same `abortingRunIds` bookkeeping `abortRun` maintains internally to guard against re-aborting a run it already requested cancellation for. `since` is the `RuntimeServices.clock.now()` timestamp `abortRun` recorded when cancellation was first requested. Unlike the ten rows above, a non-empty `abortingRuns` DOES fold into `quiescent` directly (`quiescent = leaked.length === 0 && abortingRuns.length === 0`) rather than through `leaked`: a run whose `ActiveRun.closed()` never settles after `abortRun` requested cancellation stays listed here for the life of the process, which is exactly the leak this row exists to surface. `BureauQuiescenceError`'s message names each entry under an `abortingRuns:` heading when the report is non-quiescent for this reason.

The other four—`runningScheduleFires`, `activeEvaluations`, `pendingAuditWrites`, `openStorageResources`—read empty on the common path (nothing genuinely survives an unbounded `bureau.shutdown()`, which awaits each owner's real drain) but populate for real once AB-265's fault engine forces a genuine leftover past a bounded `shutdown({ timeoutMilliseconds })` (AB-322): `runningScheduleFires` from `bureau.scheduler.getState().activeTask`, `activeEvaluations` from `bureau.onlineEvalSampler.activeEvaluationSnapshots()`, `pendingAuditWrites` from `harness.runtime.outstandingDeferred()` filtered to the `'audit-write'` label, and `openStorageResources` from the memory storage fixture's own public call accounting (`BureauStorageFixture.openHandles()`—sqlite/lmdb fixtures never open their own handle, so theirs always reads `[]`). The first three are read AFTER `bureau.shutdown()` returns but are deliberately never folded into `leaked`: the owner each names (`scheduler`/`online-evals`/`audit-trail`) is already reported under `incomplete` when a bounded `shutdown()` times out on it, and promoting the same fact into `leaked` too would double-report it. `openStorageResources` IS folded into `leaked`—nothing in `bureau.shutdown()`'s own owner accounting shadows a lingering low-level storage call, so this is the only place that leak is ever reported. `incomplete` carries any owner `bureau.shutdown({ timeoutMilliseconds })` itself classified `'unresolved'`—reported distinctly from `leaked`, never promoted into it.

```typescript
harness.registerDurableRun(summary.id, { detached: true });
const report = await harness.close();
report.detached; // [{ kind: 'durable-owner', id: summary.id }]—not a leak
```

A durable run registered with `detached: true` is recorded under `detached`, never under a leak row—a deliberate, recorded outcome (AB-34), not a way to hide a leak.

### `assembleReproductionArtifact(harness, recorder, options)` (AB-263)

Builds on a `harness` already constructed with `createBureauTestHarness` (see above):

```typescript
import { createEventRecorder } from '@lostgradient/operative';
import { assembleReproductionArtifact } from '@lostgradient/bureau';

const recorder = createEventRecorder(harness.runtime);
const run = harness.startRun('worker', 'hello');
recorder.attachIterable(run, { kind: 'run', id: 'worker-run' });

const terminalResult = await run.result();
const cleanupReport = await run.closed();
await harness.runtime.deferred.drain();

const artifact = await assembleReproductionArtifact(harness, recorder, {
  terminalResult,
  cleanupReport,
});
```

`ReproductionArtifact` here is `@lostgradient/operative`'s canonical declaration (AB-334), instantiated with Bureau's own `cleanupReport` union—`CleanupAcknowledgement | DeferredDrainReport | BureauShutdownReport`—since `bureau` can import that shared shape from `operative` but never the reverse. Assembles the normalized `ReproductionArtifact` AB-92's decision record fixes (AC8) from one harness run: `sourceRevision` (`git rev-parse HEAD`, read once), `packageVersions` (every workspace package's `name`/`version`, read from its `package.json`), `effectiveModel` (`harness.bureau.getConfiguration().provider`—requires `BureauOptions.provider` to be set alongside a scripted `generate`; throws rather than inventing a provider/model when it is not), `clockOrigin`/`identifierSeed`/`randomSeed` (`harness.runtime`'s own recorded seeds—present even for an unpinned, default-constructed runtime), `scriptedOutcomes`/`firedFaults` (always empty until AB-95's fault engine exists), `causalTrace` (`recorder.normalize()` and nothing else), `terminalResult`, and `cleanupReport`. `terminalResult` is redacted through `summarizeToolInput` before embedding—a privileged key (`password`, `secret`, `token`, `apiKey`, `authorization`, `credential`, `privateKey`) never appears in the serialized artifact. The returned object's keys are always written in AB-92's fixed field order, so `JSON.stringify` is byte-identical across two runs of the same scripted case with the same seeds.

`assembleReproductionArtifact` takes an optional fourth `environment` argument (AB-264): `{ sourceRevision?, packageVersions? }`. Supplying a field there replaces this function's own discovery for that field—`git rev-parse HEAD` and the `packages/*` manifest glob both assume a real repository checkout rooted at a `turbo.json`, neither of which exists inside a packed-and-path-installed tarball consumer (`scripts/verify-bureau-tarball-boundary.ts`'s probe passes both explicitly, since it already knows them from its own pack step). Omitted fields still discover normally, so every existing caller inside this repository is unaffected.

```typescript
const artifact = await assembleReproductionArtifact(
  harness,
  recorder,
  { terminalResult, cleanupReport },
  { sourceRevision, packageVersions },
);
```

### Bureau-scoped fault-plan vocabulary and selectors (AB-263)

```typescript
import {
  selectAuditWriteFaultTarget,
  selectSchedulerTaskFaultTarget,
  selectWebhookDeliveryFaultTarget,
  type BureauFaultPlan,
} from '@lostgradient/bureau';
```

`BureauFaultOperation` widens `@lostgradient/operative`'s `FaultOperation` with three Bureau-owned boundaries operative cannot see: `'webhook-delivery'`, `'audit-write'`, and `'scheduler-task'`. `BureauFaultPlanEntry`/`BureauFaultPlan` mirror operative's `FaultPlanEntry`/`FaultPlan` with that widened operation; every other fault type (`FaultBoundary`, `FaultOccurrence`, `FiredFault`, ...) is re-exported from operative verbatim—there is exactly one `FaultBoundary` union in the repository. No engine executes a `BureauFaultPlan` yet (AB-95); what ships here is the type vocabulary plus three selector functions that resolve a Bureau-scoped target to exactly one concrete resource, throwing `BureauFaultSelectorResolutionError` otherwise: `selectWebhookDeliveryFaultTarget(deliveries, deliveryId)` (by `WebhookDeliveryRecord.id`, from `WebhookNotifier.listDeliveries()`), `selectAuditWriteFaultTarget(records, auditEntryKey)` (by the audit entry key `encodeAuditEntryKey`—also exported from this package's root—produces from a queried `AuditRecord`'s `timestampMs`/`sequence`/`runId`), and `selectSchedulerTaskFaultTarget(tasks, taskId)` (by `SubmitSchedulerTaskResponse.taskId`).

### Storage fixtures

```typescript
import {
  createLmdbStorageFixture,
  createMemoryStorageFixture,
  createSqliteStorageFixture,
} from '@lostgradient/bureau';
```

Each factory returns a `BureauStorageFixture`: `{ configuration, path?, owned, dispose(), openHandles() }`. `configuration` passes straight to `BureauOptions.storage`. `createSqliteStorageFixture` takes `{ runtime, path? }`; `createLmdbStorageFixture` also accepts `durability?: 'full' | 'relaxed'` and defaults to production-equivalent `full` durability. Omit `path` for a fresh, unique path allocated from `runtime.identifiers.next('storage-fixture')` (`owned: true`, removed by `dispose()`), or supply your own `path` for a fixture that never allocates or deletes anything (`owned: false`). Their fixture itself never opens a live storage handle—the real backend connection is owned and closed by whatever composes `configuration` (typically `Bureau`)—so `dispose()` only ever governs the filesystem lifecycle of a path this fixture allocated, and `openHandles()` always returns `[]` (nothing of their own to account for).

`createMemoryStorageFixture(options?: { wrapStorage?: (storage: Storage) => Storage })` (AB-322) is the one exception: it constructs its own `MemoryStorage` instance directly—safe only for memory, since there is no real file handle or single-writer lock to race the way sqlite/lmdb would—and hands `Bureau` that INSTANCE as `configuration`, wrapped with public call accounting. `openHandles(): readonly string[]` names every call (`get`/`put`/`delete`/`scan`/`batch`/…) this fixture has seen START but not yet FINISH—empty on the happy path, and a real diagnostic once something (e.g. `createFaultEngine(...).wrapStorage`, passed through `options.wrapStorage` before this fixture's own accounting wraps the result) blocks a call deterministically. `dispose()` disposes that instance directly—`bureau.shutdown()` never closes a caller-supplied `Storage` instance, only one it resolved itself from a `StorageConfiguration`, so this fixture is the one thing that does.
