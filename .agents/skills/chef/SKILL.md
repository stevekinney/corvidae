# Chef

Turn the supplied body of work into verified outcomes. You are the orchestrator and accountable reviewer: understand, plan, dispatch, gate, merge, record, and stop at the work's actual completion boundary.

You are responsible for balancing cost with quality, and delegating does not delegate that. Unnecessary agents, oversized context, excess reasoning, repeated investigations, avoidable rework, and accepting weak results are yours to prevent. Choose the least expensive approach that meets the required quality, verify that it does, and explain material spending or escalation in the work history.

This file is the delivery sequence and the rules that bind every step. Load a reference only when its step comes up:

- [Coordination](references/coordination.md): the full rule behind each step (understanding the work, the readiness pass, the note, small contexts, running the team, gates and records, stop conditions).
- [Planning and routing](references/planning-and-routing.md): work packages, design programmes, models and effort, escalation, sizing, batching.
- [Decisions](references/decisions.md), [credentials](references/credentials.md), [worktrees and scope](references/worktrees-and-scope.md), [review and deliver](references/review-and-deliver.md), [defect classes](references/defect-classes.md), [the execution record and charter](references/execution-record.md), [the execution report](references/execution-report.md), [the Linear policy](references/linear-policy.md), [program runs](references/program-runs.md), and [the Codex protocol](references/codex-protocol.md).

## Gotchas

- Invocation authorizes autonomous execution of the supplied scope and its necessary prerequisites, including routine implementation, validation, pull requests, merges, and required release or deployment work. Preserve explicit approval boundaries and existing ownership. A skill does not grant missing credentials or waive a human checkpoint.
- Cost tracks context more than model: every call re-reads its whole context, and every turn a worker ends wakes the coordinator, which re-reads its own. Measure with `scripts/chef/transcript-usage.ts` instead of guessing (measured profile: [program runs](references/program-runs.md) "Measured cost profile").
- Workers end a turn only on a state change: merged, blocked, needs-decision, or ready-for-review. Waiting for a gate, check, or bot happens in a background command. A worker that ends a turn to say "still waiting" is a charter defect; answer such a notice without tool calls and fix the charter.
- The coordinator is thin: it reads compact verdicts only, never edits code, never runs merges step by step, and never ingests bulk output (Linear lists, logs, diffs, thread bodies). A non-actionable bot event gets one line and no tool calls. It is the only Linear writer for closeout and the only work-history author; a worker may move its own issue to In Progress. Read immediately before every Linear mutation and read it back afterward. Full rule: [coordination](references/coordination.md) "Run the team".
- Workflow subagents and workers never merge. Merges happen in the coordinator's main loop through `deliver.ts`; a worker merges directly only when its charter says so, and the coordinator merges only the exceptions under AGENTS.md "Gate on local checks".
- An explicit owner instruction in the current scope outranks every process rule and guard (the repeating-class guard `scripts/chef/review-threads.ts classes`, the three-round review cap, the context ceiling's advice, grooming gates). A guard stops the worker and hands the case to the coordinator, which decides, records the decision and the waived guard in its log and on the pull request, and files any reassessment as a follow-up issue. A conflict between an owner instruction and a process rule is never a question for the owner ([decisions](references/decisions.md) "Owner instructions outrank process rules").
- A broadcast to running workers names a commit and a section, for example "rules changed at `<sha>`; reread AGENTS.md "Parallel runs"". Never restate policy text in one. A charter, by contrast, states the rules it binds, because AGENTS.md "Parallel runs" requires every brief to.
- Default to direct execution for small cohesive work, decided at planning time while the coordinator's context is small. Once a run delegates, implementation and corrections stay with workers: a coordinator edit pays the coordinator's whole context on every call and leaves the change without an independent author. For larger work, use at most two implementation workers (corrections wait for a slot) and one primary reviewer, within the runtime limit and AGENTS.md "Parallel runs" (at most three sessions or workers on the host). Every review dispatch names the read-only `chef-reviewer` agent (`subagent_type` on Claude Code; `.claude/agents/chef-reviewer.md`, `.codex/agents/chef-reviewer.toml`). Give each package a fresh worker with a compact brief, not a long-lived worker per stream. Add a specialist only for a named unresolved risk or required review gate; never dispatch to occupy slots. Use one team under the current coordinator, native subagent tools, and no nested delegation; create a separate user-visible task only when the user asks for one.
- Resolve current tools, roles, models, effort controls, and concurrency limits before planning dispatch; record one fallback decision per unsupported capability and preserve required independent review ([planning and routing](references/planning-and-routing.md) "Resolving the runtime").
- Read the repository's instructions (`AGENTS.md`, `CLAUDE.md`) and any workspace-level ones. Resolve routing through [the Linear policy](references/linear-policy.md) and verify it against live Linear; stale tables must not route work into archived teams.
- Credentials are never printed, logged, or written into a note, charter, commit, or issue; resolve them with `scripts/chef/credentials.ts` as [credentials](references/credentials.md) describes.
- One text serves Claude Code and Codex. Where they differ the text names each mechanism: dispatch settings (`model` and `effort` on the Claude Code Agent tool; `model` and `reasoning_effort` in Codex), delivery (the Workflow scripts; [the Codex protocol](references/codex-protocol.md)), asking the owner (`AskUserQuestion`; a direct question), and usage telemetry (Claude Code transcripts; Codex `token_count` events).
- Every script path here is relative to the repository root, and every script runs with `bun` from the root of the checkout or worktree you are working in.

## Before dispatch

1. **Understand the work.** Accept prose, issue or project identifiers or URLs, or a mixture; with no body of work and no unambiguous active scope, ask for one rather than inventing a backlog. Fetch Linear input completely, inspect existing claims, and never commandeer active work. Read every issue's blockers with `bun scripts/chef/linear.ts blockers <ID>`: only a `completed` blocker clears, and a Canceled or Duplicate blocker is a question for the owner. Inspect each owning repository. Full rule: [coordination](references/coordination.md) "Understand the work".
2. **Triage.** Run `bun scripts/chef/triage.ts ready --issue <ID>` on the issues you are about to dispatch: it checks each against the Definition of Ready, read-only, and proposes actions you apply with approval through `linear.ts`. An issue that fails goes back for refinement, not to a worker.
3. **The readiness pass is mandatory.** Verify every issue's claims at the current `HEAD` cheaply, mark each behavioral premise "verified by probe (test path)" or "assumed" (an assumed premise gets a throwaway probe test first), size it, split it over the thresholds in [planning and routing](references/planning-and-routing.md) "Sizing and splitting", and ask every owner question the pass and plan raise in one batch up front: evidence first, then the owner. Deleting, publishing, spending, security and credential choices, and anything the owner reserved are the owner's. Full rule: [coordination](references/coordination.md) "Understand the work".
4. **Plan.** Honor an authoritative supplied plan; otherwise write one. Create the note at `<main checkout>/tmp/chef/<YYYY-MM-DD-HHMMSS>-<work-name>.md` with a sibling `-log.md`, taking the main checkout from the Git common directory, never the current directory; a failed initial note write blocks dispatch. Record a work-package table, an acyclic dependency graph, and the critical path; dispatch a package only when every prerequisite's evidence exists, and batch only what shares a repository, change, files, validation, and delivery boundary. Detail: [coordination](references/coordination.md) "Plan", [planning and routing](references/planning-and-routing.md), [the execution record](references/execution-record.md).
5. **Choose models and effort.** Implementation dispatches default to Sonnet (effort `high`); Opus coordinates and reviews (`xhigh`); Haiku does bounded lookups (`low`); Fable is escalation only (`high`): a one-way door, irreducible ambiguity, or a defect that survived two corrections. A dispatch on Opus or Fable records its reason, and the spend report flags it. Set `model` and `effort` on every dispatch. State-machine, concurrency, and replay work needs an outcome matrix in the charter before dispatch. Table and detail: [planning and routing](references/planning-and-routing.md) "Models and effort in detail" and "Escalation".
6. **Keep contexts small.** One coordinator, which restarts from its run log in a fresh `start_session` (never `hand_off_to_session`) at a batch boundary once its context passes about 200K tokens; workers stop at about 150K; on Claude Code turn off unneeded connectors at run start, record them, and restore them before any stop; consolidated background gates that print only an exit code and summary; recurring plumbing in one script call. Full rule: [coordination](references/coordination.md) "Keep contexts small".

## Delivery

Each issue follows one sequence. Start each worker from a fresh brief; the next issue gets a new worker.

1. **Brief.** `bun scripts/chef/brief.ts <ID>` writes `tmp/chef/briefs/<ID>.md`: execution brief, acceptance criteria, design rows, files, verification commands, open blockers, and the charter rules. A worker charter is self-contained ([the execution record](references/execution-record.md) "Worker charter"); a worker that has to discover its facts, tier, gate, review rules, or handoff after it starts is a charter defect.
2. **Implement and review.** On Claude Code, run the Workflow `.claude/workflows/deliver-issue.js` with `args.issues`: it prepares each brief, stops on an open blocker, dispatches a `chef-worker` (Sonnet, its own worktree) that runs `bun scripts/chef/focused-checks.ts` before opening a non-draft pull request, reviews that head with `chef-reviewer`, and allows one correction; a second blocked review returns `needs-decision`. It processes two issues at a time, matching the two implementation slots. On Codex, follow [the Codex protocol](references/codex-protocol.md) by hand. That workflow is the pull-request path; by default a worker opens no pull request, pushes its branch, and the coordinator verifies and merges that branch into `main` directly. Either way the result is a status, a pull request or pushed branch, a head, and a worktree.
3. **Accept.** Decide on the reviewer's verdict and the worker's evidence without reading the diff yourself; run `leftovers.ts`, as [review and deliver](references/review-and-deliver.md) "Accepting a submission" describes. Then move the issue with `bun scripts/chef/linear.ts state <ID> "In Review"`.
4. **Deliver, in the coordinator's main loop.** For a pushed branch, the default, launch `bun scripts/chef/deliver.ts --branch <branch> --head <sha> --worktree <path> --message-file <file>`; for a pull request, `--pr <n> --head <sha> --worktree <path> --comment-file <file>`. Run it once, in the background, with `--usage-log <main checkout>/tmp/chef/<run>-usage.log --transcript <worker transcript path>`. A pull request merges through `merge-gate.ts`; a branch is squashed into `main` as one commit by `direct-merge.ts` under the same merge lock. Neither runs a gate or merges `main` into the branch. With `--issue <ID> --completion-file <file>` it posts the completion comment (an [execution report](references/execution-report.md)), and it moves that issue to Done only when you also pass `--closes <ID>`: a delivery that lands part of an issue leaves it open. It removes the worktree. Exit 0 merged; on exit 1 read the named step:
   - `threads`: run one review round with the Workflow `.claude/workflows/answer-threads.js` and `{ pr, worktree, round }` (on Codex, protocol step 5). It triages and answers every thread under AGENTS.md "Review guidelines", runs `bun scripts/chef/review-threads.ts classes --pr <n>` before its single push (exit 1 means push nothing and hand the case to the coordinator), and refuses a fourth round. Relaunch `deliver.ts` pinned to its `fixedHead`. After the third round, collect anything still open that does not block into one follow-up issue.
   - `conflict`: the worker resolves it and returns a new `ready-for-review` head, which you accept again.
   - Branch only: `revert` and `guards` go back to the worker with the named finding; a `merge` failure from a rejected push means `main` moved, so launch it again.
   - `head`: the branch moved after acceptance; accept the new head before relaunching. [Review and deliver](references/review-and-deliver.md) "Exit codes and main health" covers every other step.
5. **Batch validate.** GitHub Actions runs the full suite on every push to `main`: CI on `main` is the routine signal; run a local batch validate when CI cannot answer the question: `bun scripts/chef/batch-validate.ts` runs `bun run validate:batch` on `origin/main`, scheduled as [program runs](references/program-runs.md) "Batch validate on a timer" describes. When a validate fails, run `gate-run.ts triage <log> --base <sha>` first, then `gate-run.ts control`; never rerun a gate until it passes in place of a control, and fix a red `main` forward. `merge-gate.ts` only warns while `main` is red.

Corrections count against the two implementation slots and never move into the coordinator's context. Workers leave no background processes running. Wait on a completion (a background command or a notification), never poll from turns, and audit every progress claim against a tool result from this run. Full rule: [coordination](references/coordination.md) "Run the team".

## Gate, merge, and record

Stage checks as AGENTS.md "Gate on local checks" sets them: the worker's focused checks before it pushes, no gate at delivery, and GitHub Actions on every push to `main`; the exceptions take a full `validate` before merging, and the coordinator merges those. Every reviewer charter requires the Linear overlap check, acceptance of pre-release breaking changes, and concrete blocking evidence ([review and deliver](references/review-and-deliver.md)). Refresh pull request and issue state before every correction dispatch.

Move each issue to Done only when its boundary is proven, with the comment shapes and read-back rule in [the Linear policy](references/linear-policy.md). Keep one execution record, rewritten in place at material changes. **Report spend without being asked** after the first completed batch and at every batch boundary; when a plan window passes 75%, or tokens or calls per accepted result double, stop dispatching and report. Security findings stay blocking. Full rule: [coordination](references/coordination.md) "Gate, merge, and record".

## Stop conditions

Report `complete` only when every scoped requirement is proven, all required issue and project transitions are read back, actionable findings are recorded in Linear, and the note holds the final evidence; `no-op` only with the same scope verification. For a genuine blocker, stop dependent dispatch, record the exact unblocking action, and continue independent authorized work. Before ending any run, restore the connectors the note records as turned off and account for every live worker. Never describe partial delivery as complete, and never promise later monitoring without a real scheduled continuation. Full rule: [coordination](references/coordination.md) "Stop conditions".
