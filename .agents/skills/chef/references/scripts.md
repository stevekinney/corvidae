# Plumbing scripts

Read this when a step calls for a chef script and you need what it does, its subcommands, or its exit codes. Each script's header holds its full usage.

Each lives in `scripts/chef/`, prints a few lines (or one JSON object with `--json`, on standard output whatever the exit code), and exits 0 on success, 1 when the checked condition fails, and 2 on invalid usage, as plain text on standard error; `credentials.ts` and `jev.ts` add 3 for an unavailable credential or model. Repository specifics come from `scripts/chef/repository.json`, the default `--config`: default branch, worktree roots per provider, manifest name, install, gate, and affected-check commands, the lock pattern, and the merge method. Here the worker runs focused checks on what it changed before opening a pull request (AGENTS.md "Gate on local checks"; not `bun run check`, and delivery runs no gate), and the batch gate is `repository.json`'s `batchCommand` (`bun run validate:batch`), which `batch-validate.ts` runs on `origin/main` through `gate-run.ts run`, under the `scripts/run-exclusively.ts` lock, its Bun test workers in the test slot pool. Use these instead of rebuilding them in a scratch directory the host may clear.

| Script | Use |
| --- | --- |
| `gate-run.ts` | `run` waits for the lock and records head, load, tree cleanliness, HEAD before and after, and the exit code; launch it in the background. `read` reports the result, treating a missing exit code, several `HEAD` lines, or a last line that is not the exit code as untrustworthy. `triage <log> --base <sha>` maps each failed task to the merged pull requests that touched its workspace, or says pre-existing. `control` alternates a test on candidate and base. |
| `merge-gate.ts` | Runs no test gate. Checks the pull request is open and its head matches the worktree (and `--head <sha>`, the head pinned at acceptance), GitHub reports no conflict with the base (it waits briefly while mergeability is `UNKNOWN`; a base that merely moved is not a refusal), and every thread is resolved; posts the comment, merges pinned to the head, and confirms the merged tree. A red `main` is a warning in the report. `--usage-log <file> --transcript <path>` appends tokens for the merged pull request. `--dry-run` only checks. |
| `review-threads.ts` | `list` pages every thread and fails when SEEN differs from TOTAL. `resolve` replies to and resolves threads from a TSV, then re-lists. `classes --pr <n>` exits 1 when one defect class appears in two or more review rounds. |
| `worktree.ts` | `create` runs the main-branch preflight, checks the manifest before installing, and can capture the scope baseline. `remove` refuses a dirty or busy worktree or an undelivered branch, then deletes the worktree and both branches; `--retired` skips the delivery check. |
| `worktree-scope.ts` | `capture` inventories every non-ignored path; `verify` fails on a change outside the allowed paths. |
| `review-boundary.ts` | `capture` and `verify` a directory boundary with deletion accounting, for the full mutation protocol. |
| `leftovers.ts` | Lock holder, processes inside each worktree, and recorded PIDs still alive; an unrunnable `lsof` reports unchecked, never empty. |
| `note.ts` | `state` rewrites a note section, `log` appends to the sibling log, `row` updates one batch-table cell and escapes the value; it is the only way to edit the batch table, never `sed`, `stats` reports sizes. |
| `linear.ts` | Issues: `read`, `state`, `comment` (`--update <comment-id>` replaces your own comment), `append`, `create` (refuses a duplicate title), `blockers`, and `block`. Projects: `project-read` (status, latest health, issue counts by state type), `project-state`, and `project-update` (refuses a body without the count lines). Each write is read back; it resolves `LINEAR_API_KEY` itself. |
| `drift.ts` | Read-only: lists COR issues whose Linear state disagrees with GitHub (`merged-open`, `review-without-pr`, `stale-in-progress`); exit 0 none, 1 findings. Run it on the batch-validate timer ([program runs](program-runs.md)). |
| `mutation-check.ts` | Applies a mutation, runs the test, restores and hash-checks the file, and fails when a mutation survives; `--spec` runs several. |
| `brief.ts` | `<ID>` turns a Linear issue into `tmp/chef/briefs/<ID>.md`: execution brief, acceptance criteria, design rows and board instructions when the issue names a design (flagging rows its criteria leave out), files, verification commands, and the charter rules. It only prepares the file; you start the session. |
| `design-ledger.ts` | `--index <file> --canvas <artifact id>` maps every row of a saved design-canvas index to the COR issues that carry it: criterion, deferred, context-only, unassigned, or rule. Exits 1 on any context-only or unassigned row. Run it before dispatching a design programme, after every readiness split, and before closing the programme ([planning and routing](planning-and-routing.md) "Design programmes"). |
| `packet.ts` | `new <area>` writes a repository-packet skeleton to `tmp/chef/packets/<area>.md`; `status <area>` prints its age and the commits on `origin/main` that touched its paths since it was written, exiting 1 when it is stale. |
| `main-health.ts` | Reports whether `main`'s last batch validate failed. `gate-run.ts run` writes the record for the batch command; `merge-gate.ts` reads it and warns in its report while `main` is red, and `--fixes-main` records a pull request as a repair. It never refuses a merge. |
| `batch-validate.ts` | Runs the batch validate on `origin/main` in a dedicated worktree when five merges or two hours have passed since the last one, and skips when the health record is already green at the current head. No load gate unless `--max-load <n>` is given; one host-wide owner through `<git common dir>/corvidae-batch-validate.lock`. Schedule it as [program runs](program-runs.md) "Batch validate on a timer" describes. |
| `deliver.ts` | `--pr <n> --worktree <wt> --comment-file <md> [--head <sha>] [--issue <ID> --completion-file <md>]... [--remove-worktree --provider claude\|codex --name <name>] [--usage-log <file> --transcript <path>] [--fixes-main] [--json]` merges through `merge-gate.ts`, closes each Linear issue with read-back, in order, one completion file per issue (each must be an [execution report](execution-report.md)), and removes the worktree, as one background command. It runs no gate and never merges `main` into the branch; it refuses only for a conflict with the base (step `conflict`), an unresolved review thread (step `threads`), or a head that is not the pinned one (step `head`). Exit 0 merged, 1 a failed step named, 2 usage. [Review and deliver](review-and-deliver.md) "Exit codes and main health" says what the coordinator does on each. |
| `transcript-usage.ts` | Token use, context size, and full-context cache rewrites per transcript, for Claude Code and Codex. |
| `credentials.ts` | `resolve` names a credential's source, never its value; `exec` runs a command with it set. |
| `focused-checks.ts` | `[--base <rev>] [--json] [--dry-run]` runs the per-pull-request gate as one command: format, the root lint and type-check, lint and type-check of the changed workspaces, the quick-tier tests the change reaches, and the isolated lane when it reaches one; warns on an oversized diff. Exit 0 passed, 1 a step failed, 2 usage. |
| `jev.ts` | `decide` asks Jev a yes/no, choice, or scale question against a threshold. |
| `jev-predicates.ts` | `list` names the predicates; `shadow <predicate> --evidence-file <json>` asks Jev and logs its answer to `<main checkout>/tmp/chef/jev-shadow.jsonl` without changing control flow (exit 0 even when Jev is unavailable); `outcome <id> --actual <value>` logs what actually happened; `report` measures agreement. The predicates are in [decisions](decisions.md) "Jev predicates". |
| `triage.ts` | Read-only Linear triage; it never writes Linear, and the coordinator applies its proposed actions through `linear.ts`. `ready` runs the mechanical Definition-of-Ready checks (default state Backlog), `stale` finds open issues whose files, symbols, or named issues have moved on or that a merged pull request already references, and `done` finds completed issues with no linking merged pull request and no execution report. `--jev shadow` adds advisory predicate answers. Exit 0 no findings, 1 findings, 2 usage, 3 Linear unavailable. |

## Workflows

On Claude Code two Workflow scripts run the agent steps of delivery; neither ever merges.

- `.claude/workflows/deliver-issue.js` takes `args.issues` (COR identifiers) and, two at a time, prepares each brief with `brief.ts`, stops on an open blocker, dispatches a `chef-worker` in its own worktree, reviews the head with `chef-reviewer`, and allows one correction; a second blocked review returns `needs-decision`. It returns each issue's status, pull request, head, worktree, review verdict, and shadow ids.
- `.claude/workflows/answer-threads.js` takes `{ pr, worktree, round }` and runs one review round: it triages every unresolved thread, fixes and answers them under AGENTS.md "Review guidelines", runs `review-threads.ts classes` before the single push, and refuses a round above three. It returns the answered and open thread ids and `fixedHead`.

On Codex, [the Codex protocol](codex-protocol.md) runs the same sequence by hand.
