# Review and deliver

Read this when reviewing a submission, choosing or reading a gate, triaging a failed batch gate, or closing out delivery. `SKILL.md` "Gate, merge, and record" keeps the sequence; this file holds the detail behind each step.

## Review

Keep one implementation owner and one primary reviewer through each correction cycle. Review actual diffs and acceptance evidence for correctness, scope, tests, failure handling, interfaces, and local conventions. Preserve independent review: the coordinator may review a worker's implementation; direct coordinator implementation needs an independent reviewer when review is required. Add specialists only for a named unresolved risk or required gate. Consolidate findings into one correction request to the owner. Re-review correction diffs and affected interfaces; widen review when changes invalidate earlier assumptions. Worker success is a submission, not delivery.

Apply AGENTS.md "Review guidelines" to every review, including specialist reviews, and include these rules in each reviewer charter:

- Before posting a finding or suggesting a correction, read linked COR issues and search the COR backlog across projects for the affected behavior, symbols, and proposed work. Read plausible matches for scope, status, acceptance criteria, and recorded decisions. Cite an existing ticket's identifier and link instead of duplicating work or expanding this pull request to implement it. A matching ticket does not excuse a concrete blocker introduced by this diff; explain why that failure must be fixed before merge. If Linear is unavailable, disclose the incomplete check without claiming no match exists or blocking solely on the lookup.
- Accept breaking changes in this pre-release workspace. Check affected in-repository callers and update them directly; do not demand compatibility wrappers, deprecation periods, or retention of obsolete APIs. Remove deprecated code in the replaced path. Continue scrutinizing persisted data, wire protocols, and published contracts for concrete defects.
- Report a blocker only with a supported input or reachable interleaving, the wrong result, and its concrete consequence. Review the changed behavior and honor recorded decisions. Omit naming, style, optional refactoring, speculative hardening, and unsupported edge cases. Touching a one-way door or deliberately breaking an old API is not itself a blocker.

A reviewer reviews by defect class, reading [the defect classes](defect-classes.md) first, and for any wrapper, adapter, or delegation change enumerates every property the wrapped object carries (approval policy, idempotency, gating, identity, context binding) and checks that each survives. The #595 approval bypass, which Codex found and the primary review missed, was such a change. Read the worker's defect-class report against [the defect classes](defect-classes.md) first: a class the worker marked as applying is where review starts. An omitted class is a prompt to inspect the changed behavior, not a finding by itself; report only a concrete defect that meets the policy above.

Keep review cheaper than the work it checks.

- **Verification passes:** brief a verifier with the open findings and the correction diff, under the same resume-or-fresh rule as any agent. Keep the primary-review tier for logic, concurrency, and security corrections. A mechanical correction (a rename, a test fix, a documentation change) can be verified at the economical coding tier.
- **One-way-door review:** it covers only the doors the change alters: a persisted format, a wire protocol, an authorization rule, or a published surface. Its brief names those files and the primary review's findings. Run it after the primary review settles, unless the door is the change's main risk, so it does not rediscover the same defects at the escalation tier's price.

Every review dispatch names the `chef-reviewer` agent (`.claude/agents/chef-reviewer.md` as the Claude Code `subagent_type`; `.codex/agents/chef-reviewer.toml` for Codex), which has no file-editing tools. Every review-only dispatch follows one blanket rule, whatever the reviewer's charter says. The reviewer invokes no skills, including harness skills such as Claude Code's built-in `code-review`, which are not files in this repository's skill directories yet still apply edits. The reviewer uses no file-editing tools. The reviewer records `git status --porcelain` and `git rev-parse HEAD` at the start and end of the review, and the review fails if either differs; test results gathered against a tree that changed mid-review are not evidence for the reviewed revision. This is a charter rule, not a permission restriction, so the coordinator still checks the tree before and after.

## Accepting a submission

A `ready-for-review` return is accepted only after the scope gate for its tier in [worktrees and scope](worktrees-and-scope.md) passes and the leftover check is clean. Before accepting any submission, run `leftovers.ts` and check for leftover processes this run created, attributing them by recorded PID or the session's shell-snapshot marker; kill only those, and never touch a process you cannot attribute to this run. A leaked busy loop silently degrades every later gate. Acceptance is the message that authorizes the worker to merge; a correction request is not acceptance, and the corrected head comes back as a new `ready-for-review`.

Reject a submission without a reviewable revision or artifact and request the missing evidence. On worker interruption, verify its live state and ownership before resuming or replacing it; persist the disposition and current artifacts first. If a worker crosses its authority boundary, stop it, inspect actual effects, and record the incident before recovery. Charters express constraints; they are not proof of runtime enforcement.

## Staging the gates

Run relevant formatting, lint, type checks, and causal regressions first, candidate review and corrections next, then expensive complete suites once the candidate stabilizes. In corvidae the tiers are AGENTS.md "Gate on local checks": focused `bunx turbo run <task> --filter=<workspace>` commands while working, `bun run check` at the head to merge, run shared outside the host lock, and one `bun run validate` on `main` per batch of merges, run by the coordinator in the background. Its exceptions (a one-way door, the lock or concurrency infrastructure, `turbo.json` and the root scripts) take a full `validate` before merging, and the coordinator merges those. Do not run a full `validate` per pull request: with parallel workers it queues behind the lock and never converges. A second `validate` queues behind the first under the `scripts/run-exclusively.ts` lock; launch the gate through `scripts/chef/gate-run.ts run`, which also waits for that lock, rather than starting a second copy.

A candidate is stable when its latest review or verification accepted it. Do not launch the repository-wide gate beside a review or verification that may still ask for changes; during correction loops, use the repository's affected-only check if it has one. Serialize other heavy host workloads, such as container or browser baseline runs, with the gates, under the repository's exclusive lock where one exists. A cheap known failure blocks an expensive launch. Explicit repository gates remain mandatory, including security checks; focused checks never replace them. Reuse evidence only when its revision or relevant content identity, command, environment assumptions, exit code, and evidence path remain valid. Code, dependencies, configuration, environment changes, or review findings invalidate affected evidence; another agent's repeated request does not.

Before a required full `bun run validate`, inspect the changed source files and the affected workspaces' `package.json` and `turbo.json` tasks. If a changed source file is subject to a per-file coverage floor, run that workspace's coverage-backed `test:gate` first (for example, `with-turborepo-cache bunx turbo run test:gate --filter=@lostgradient/weft`) on the stable candidate. This uses the same task key that `validate` will use, so a passing unchanged result can come from the shared cache. A failure returns to the owner before the expensive full gate. Record the command, head, and exit code; the focused result does not replace the required full `validate`. Do not run this preflight for an unchanged coverage-relevant tree whose passing coverage evidence remains valid.

Before starting a full gate, read `uptime` for the one-minute host load and `bun scripts/chef/leftovers.ts --json` for the active repository lock holder; check other known heavy repository processes too. In this repository, wait until load is below 8 and no other full gate is running; use a completion-driven background wait, and report prolonged contention rather than running competing suites. `gate-run.ts` records the starting load and lock waits, so report lock wait separately from test runtime. Schedule the batch command with `bun scripts/chef/batch-validate.ts --max-load 8`; the load check postpones work and never waives a test or raises a limit. Recheck the candidate head after waiting.

## Gaps and false witnesses

A workspace-filtered gate is a statement about the named workspaces only. Before acceptance, require passing evidence for the repository-level gates the change could affect, alongside the workspace-filtered gates named in the charter. Check repository instructions, scripts, and CI configuration for unfiltered gates and separately invoked suites, including downstream application tests; do not assume an aggregate validation command covers them. If no repository-level gates apply, the charter must explicitly state that and why. This holds equally for a check you run yourself between charters, where it is easiest to drop: short filtered commands are what keep cycles fast, and no template governs them. Name what a filtered command cannot reach before trusting it, and take a repository-level reading before reporting a tree's state to anyone.

Separate a gate that tells you nothing from one that tells you something false. A gate outside your filter is a gap: it reports on what it covers, and once you understand the task graph you can notice it is missing. A gate that returns green for the wrong reason is a false witness—it reads as evidence, and nothing in its output announces the problem. A cached result replayed for an unchanged input, an assertion whose subject can no longer render, and a pattern matched against output carrying ANSI escapes are all the second kind. Capture an exit status into a variable on its own line and assert on that; never grep output to decide pass or fail. A forcing flag is not a safe way to defeat a cache either: read what it changes beyond its name, because it reaches subprocesses and can turn a sound suite red. When a green could have come from either a fresh run or a replay, say which.

## Triaging a failed batch gate

Start with the script, not by hand: `bun scripts/chef/gate-run.ts triage <log> --base <sha>`, where `<sha>` is the `main` revision before the batch's merges. It maps each failed task to the merged pull requests that touched its workspace, or reports it as pre-existing. Route a mapped failure to that pull request's owner as a fix forward, and merge nothing else into a red `main` except that fix (AGENTS.md "Gate on local checks").

Use `gate-run.ts control` for anything the triage leaves ambiguous: a task that several merged pull requests touched, a failure in a file none of them changed, or a load-sensitive test. When the failing task or test lies outside the workspaces the candidate changed (including their dependents), or inside them but in a file the candidate did not touch, run a short alternating control of that test on the candidate and on the exact base revision under the same load. Candidate fails and base passes: the failure is candidate-caused and goes back to the package owner. Both fail the same way: it is pre-existing; record it, file or deliver the fix under its own issue, and do not route it to the package's corrector. Inconclusive: widen the control before deciding. Never rerun the gate until it passes as a substitute for the control.

## Merge integration

Other sessions keep landing code against the old surface while a pull request that removes or renames members is open, so the collision shows up at merge, not in the branch's own gate. For any such pull request the coordinator writes the removed and renamed identifiers, one per line, to a file and passes `--removed-names <file>` to `deliver.ts`. After it merges `main` in, `deliver.ts` fast-checks at step `integration`: the workspaces both the branch and the newly merged `main` touched, and the files that landed, for those names used as member accesses, quoted keys, or object keys, which is what finds the fixtures `tsc` cannot see (defect class 11). It fails in minutes with the failing files or `path:line (name)` hits, and puts the branch back to its previous head with nothing pushed. The worker fixes the hits, and the coordinator relaunches `deliver.ts`.

## Exit codes and main health

`deliver.ts` stops at step `threads` before it fetches, merges, or gates while a review thread is open, so answer and resolve them first. A gate failure is classified per failing test, by rerunning each failing file alone on the head and on `origin/main`, and never retried. Any test that fails alone on the branch and not on `main` makes the verdict `branch`, ahead of a `main`-reproduced failure in the same gate. Each class has an owner:

- **Exit 1** (a `branch` or `unclassified` failure, or any named step): the failure is the pull request's; it goes back to its worker.
- **Exit 3** (`main`): no test failed on the branch alone, and a failing file fails the same way on `main` too, so the failure is not this change's. The coordinator owns a fix-forward, or finds the pull request that owns the failing test and routes it there as under "Triaging a failed batch gate", and merges nothing else into the red `main`.
- **Exit 4** (`unreproduced`): every failing file passes alone on both trees, so load or a flake. The coordinator records the control and redelivers once; a second exit 4 goes to the owner as a load problem, not to a third blind run.
- `--waive-main-health --reason <owner quote>` merges past a red `main` and records an entry in the health file's `waivers` array (with no `controlHead`), never in `fixes`. It is allowed only on an explicit owner instruction in the current scope, quoted in the reason; it is exclusive with `--fixes-main`, and a worker never uses it.

Batch validate has one owner per host through `<git common dir>/corvidae-batch-validate.lock`, applies no load gate unless `--max-load <n>` is given, and skips when the health record is already green at the current head, so a second coordinator exits 0 instead of starting another.

## The review lifecycle

For every touched pull request, run the full repository review lifecycle: fresh fetch, all checks terminal and passing, all review bots terminal, paginated review threads resolved, and no conflicts with current `origin/main`. When the repository's own instructions (`AGENTS.md` or `CLAUDE.md`) document a merge gate that says merges do not wait for review bots, that relaxes only the wait (corvidae's "Gate on local checks" does, and merges are squash-only): still answer and resolve every review thread already opened, within the three-round cap in "Review guidelines", and treat one that names a serious defect as blocking. When the repository's instructions say nothing about review bots, every review bot must be terminal. Review comments belong on the relevant lines or files. Push once per correction round, not once per commit, because each push can start another bot review pass. After a brief pause, fetch and verify again before any merge. `merge-gate.ts` refuses a head that does not contain the current default branch, so concurrent worker merges serialize on it: a worker whose base moved merges `main` and gates again. Invalidate affected downstream validation when the base or interfaces move. Follow the repository's conflict policy; never disturb another owner's worktree.

## Delivery boundaries

Verify any required publication against the actual registry artifact and version, deployment against the expected revision and live behavior, and downstream adoption against the released dependency. Claim, checkpoint, record blockers, and move each issue to Done only when its boundary is proven, with the comment shapes and read-back rule in [the Linear policy](linear-policy.md). When the `linear-track-work` skill is installed, use it for those writes; otherwise `scripts/chef/linear.ts` does each one, with the steps spelled out there. Move a requested project to its terminal status only after every required child and project gate passes, through the `linear-update-project` skill when installed and otherwise by the Project Definition of Done in the same policy; do not close an entire project when only selected issues were requested.

An empty queue is a verified no-op only after checking requested acceptance criteria and live artifacts. Re-query the original issue/project scope before declaring completion. Preserve evidence for each requirement, including meaningful tests and external gate results.

## Delivery preflights and read-backs

Before every correction dispatch or `deliver.ts` launch, read `gh pr view <number> --json state,headRefOid,mergedAt,url`, `bun scripts/chef/linear.ts read <ID> --json`, and the assigned worktree's `git status --porcelain` and `git rev-parse HEAD`. Compare the pull request head and issue state with the run note. If the pull request merged, the issue closed, or the head changed elsewhere, stop the stale dispatch and reconcile the run note and delivery evidence. Check Linear's active ownership claim when it is disputed or has changed; the compact `linear.ts read` result does not include an assignee. A completed issue needs a read-back, not another correction. This checkpoint is cheap and applies even without a compaction or session resumption.

Use `bun scripts/chef/gate-run.ts read <log> --json` for a gate verdict, `bun scripts/chef/review-threads.ts list --pr <number>` for paginated threads, `gh pr view <number> --json state,headRefOid,mergeCommit,mergedAt` for merge state, and `bun scripts/chef/linear.ts read <ID> --json` for issue state. Run `git diff --name-only <base>..origin/main` against the pull request's changed-path list for an overlap check. Read only the fields needed for the decision and preserve the revision, exit code, and evidence path. These deterministic reads stay in the coordinator's context; dispatch an economical lookup agent only when the evidence requires interpretation, and a primary reviewer for correctness judgment.
