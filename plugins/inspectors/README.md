# @lostgradient/plugin-inspectors

An Interborough plugin that contributes six interface panels, MCP App pages the host builds at startup and serves as `ui://` resources.

| Panel | Resource | Linked tool | What it shows |
| --- | --- | --- | --- |
| `inspectors:run-inspector` | `ui://inspectors/run-inspector/v1` | `bureau.tasks.inspect` | One task's liveness, ownership tree, progress, result, and abort. It also reads `bureau.tasks.events` and aborts through `bureau.tasks.cancel`. |
| `inspectors:pending-review` | `ui://inspectors/pending-review/v1` | `bureau.reviews.list` | The caller's pending reviews: approve, deny, or reject with feedback. It also reads `bureau.reviews.get` and decides through `bureau.reviews.resolve`. |
| `inspectors:workflow-revision-review` | `ui://inspectors/workflow-revision-review/v1` | `bureau.workflows.update` | A proposed workflow revision, compared with the current one, which the caller can apply. It also reads `bureau.workflows.get`; applying goes through the host-only `bureau.workflows.update`. |
| `inspectors:schedule-editor` | `ui://inspectors/schedule-editor/v1` | none: a page and a run placement open it | The schedules the caller may change, and one schedule's form: when it runs, which agent or workflow it runs, and whether it is paused, or a new schedule with the same fields. It reads `bureau.schedules.list`, `bureau.schedules.get`, `bureau.agents.list`, `bureau.workflows.list` and, on a run's page, the run's task through `bureau.tasks.get`; saving goes through the host-only `bureau.schedules.create`, `bureau.schedules.update`, `bureau.schedules.pause` and `bureau.schedules.resume`. |
| `inspectors:run-timeline` | `ui://inspectors/run-timeline/v1` | `bureau.runs.timeline` | One run's steps as a waterfall: each step's status, duration and tries, with bars laid out by `stepWaterfall`, the function the run page uses. It reads `bureau.runs.timeline` and no other tool, and it changes nothing. In an external host (Claude Code, Claude Desktop) it is not yet recorded (COR-2220). |
| `inspectors:failure-explanation` | `ui://inspectors/failure-explanation/v1` | `bureau.tasks.explain` | Why one failed run failed, from what the Bureau stored about it and nothing else: the summary, the cause, the step, how often it was tried, the guardrails that fired and what to do next. It calls `bureau.tasks.explain`, a read, and no other tool. |

The failure explanation declares a `run` placement with `when: 'failed'`, so the page of a run that failed mounts it with the run's `taskId` (or, for a workflow instance, `runId`), which it reads through `bureau.tasks.explain`, and the page of any other run mounts nothing (Coordinator, 2026-11-22: shown only for failed runs). It declares a `chat-tool` placement for `bureau:tasks-explain`, so Chat opens it when an agent explains a run; that tool answers only for a run the calling run's owner owns, and in a workspace that owner must be a current member who is not a service, and any other run is `not-found`. The explain tool opens it with its result in any client that draws MCP Apps. Called directly for a run that did not fail, the panel says so in a sentence of its own ("This run didn’t fail, so there’s nothing to explain.", from the refusal's `run-not-failed` reason, with no run identifier and no quoted status) and shows the Bureau's remediation as what to do next. It draws the answer, and the refusal, with the one component the Run page draws the answer with (`@lostgradient/plugin-inspectors/failure-explanation.svelte`, the package's one extra export, which the application imports), so the two read alike. The words it draws are `@lostgradient/interborough-plugin/failure-explanation`, which imports no framework and reaches no Cinder, so Bureau, which depends on that package, does not either.

The run inspector and the run timeline declare a `run` placement, so a run's page mounts both, and the workflow revision review declares a `chat-tool` placement for `bureau:workflows-propose-update`, so Chat opens it when an agent proposes an update. The run timeline declares a `chat-tool` placement too, for `bureau:runs-timeline`, an agent tool that serves the same projection `bureau.runs.timeline` does for any run the calling run owns, so Chat opens the waterfall when an agent reads a run's timeline. The schedule editor declares a `page` placement (`/plugins/inspectors/schedules`, with no sidebar entry) and a `run` placement. A run's page passes it the run's `taskId`, and it opens the schedule whose fire started that run, or shows the list for a run nothing scheduled; a host that passes a `scheduleId` opens that schedule. The pending-review list declares none.

The schedule editor is the one panel that makes writes other than a workflow revision, so its four writes are reviewed as a security change. Each is in Bureau's `HOST_PANEL_OPERATIONS` and stays `mcpExposable: false`, so a model never sees them; a person is told apart from a model by the route, since only the host's panel routes reach `/jsonrpc` for a `hostOnlyTools` name. The host runs such a call inside Bureau's `runAsHostPanel`, an in-process scope no request can set, and the audit entry of each write (`schedule.created`, `schedule.updated`, `schedule.paused`, `schedule.resumed`) names the owner as its `principal` and the panel's URI as `detail.panelUri`. What the form sends, and which field a Bureau fault belongs to, is `@lostgradient/interborough-plugin/schedule-form`, which the application's own schedule page imports too, so no file of this plugin defines a schedule form of its own.

Each panel names a browser entry (`src/run-inspector/app.ts`, `src/pending-review/app.ts`, `src/workflow-revision/app.ts`, `src/schedule-editor/app.ts`, `src/run-timeline/app.ts`, `src/failure-explanation/app.ts`) rather than a built page. The host bundles the entry and the plugin's `styles` into one self-contained document with the script inline, and serves it under a content security policy that denies every origin and permission. The version is part of each URI: a changed contract is a new one. `opensFromTool` is the one tool a client runs to open a panel, and the host links only that tool to the page. `allowedTools` lists every tool the page calls, and a test scans each page's source so the list cannot drift.

Every panel is a Svelte component that renders Cinder through `@lostgradient/cinder/panel`, whose stylesheet reads the host's theme variables with Cinder's own values as the fallback, so the panels follow the owner's theme in light and dark. `src/host-theme.ts` applies the host's theme, style variables and fonts on connect and on every change, the same way for all five. Each panel's script (`app.ts`) holds the bridge and every `bureau.*` call; its component (`inspector.svelte`, `review-list.svelte`, `revision-review.svelte`, `timeline.svelte`) draws a view (`view.svelte.ts`) the script updates, in place, so a poll never moves the reader's focus. The page models (`model.ts`) are plain code with their own tests, and the components are tested against a DOM, so a panel's behavior is checked without a host. The Playwright specs that load the built pages in a sandboxed frame, in the host's light and dark themes, live in `applications/interborough/tests/panels`.

A panel is a document in a frame, so it cannot do what only the application's own interface can. What each of the six could not do inside it:

- The run inspector shows the run and aborts it through the bridge, but it cannot link to the run's page or to a child run, because the host's bridge refuses `ui/open-link`. The ownership tree is text.
- The pending-review list decides a review in the frame, but it cannot raise a notification or open the run a review belongs to. Its reject box is an inline form, not a dialog, because a dialog would stay inside the frame and could not cover the host.
- The workflow revision review compares and applies in the frame, but it cannot open the workflow's own page to edit it, and a long comparison scrolls inside the frame rather than in the host.
- The schedule editor takes the cadence as text, a cron expression or a duration, not through the application's cadence builder, so it shows no preview of the next runs; it cannot open a schedule's own page or its runs, and it cannot change a schedule's overlap policy, its recurring chat, or the text an agent already sends beyond replacing it. It leaves out canceled schedules, and a workflow file's own schedule, which only `bureau.workflows.*` changes, answers as not found when saved.
- The run timeline draws the steps in the frame, but it cannot open a step's detail, its input or its output, because `bureau.runs.timeline` serves names and timings only and the panel may call no other tool. It has no form and no control, so the frame's sandbox, which allows scripts and nothing else, costs it nothing. The read carries the run's status but not its start, so the bars are measured from the first step; a step the engine left `running` in a run that has `completed`, `failed`, `cancelled` or `timed-out` is drawn as ended, never as running, and the page says how the run stands.
- The failure explanation reads once and never polls, so a run that failed again after a retry is read by opening the panel again. It cannot retry the run or open its page, because the bridge refuses `ui/open-link` and the panel calls no tool but the explain read.

`src/plugin.test.ts` runs the plugin conformance suite. Refresh the committed identities after a schema change with `bun scripts/check-plugin-identities.ts --write plugins/inspectors`.
